## 1. Hosting Architecture: S3 + CloudFront + Route 53

For a client-side rendered (CSR) React app (such as Vite or Create React App), the standard AWS architecture utilizes **Amazon S3** for file storage and **Amazon CloudFront** as the Content Delivery Network (CDN).

```
                        ┌─────────────────────────────────────────────────────────┐
                        │                     AWS Cloud                           │
                        │                                                         │
 User ──► Route 53 ──► CloudFront (Edge CDN) ──(OAC)──► S3 Bucket (Private)       │
                        │   │                                                     │
                        │   └── SSL/TLS Cert (ACM)                                │
                        └─────────────────────────────────────────────────────────┘

```

### Setting Up S3 and CloudFront with Origin Access Control (OAC)

1. **Build the React Application:**

```bash
npm run build

```

This generates static production artifacts in the `dist/` or `build/` directory (`index.html`, JavaScript bundles, CSS files, and static assets).
2. **Upload Artifacts to S3:**

* Create an S3 bucket (e.g., `my-react-app-production`).
* Keep **Block All Public Access** turned **ON**. The S3 bucket itself should remain completely private.

1. **Configure CloudFront with OAC:**

* Create a CloudFront Distribution pointing to your S3 bucket as the **Origin Domain**.
* Select **Origin Access Control (OAC)** settings. CloudFront will prompt you to copy a generated bucket policy.
* Attach the generated policy to your S3 bucket policy editor. This grants read access *only* to CloudFront while blocking direct public internet access to S3.

#### Example S3 Bucket Policy for CloudFront OAC

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontServicePrincipal",
      "Effect": "Allow",
      "Principal": {
        "Service": "cloudfront.amazonaws.com"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-react-app-production/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::123456789012:distribution/E1A2B3C4D5E6F7"
        }
      }
    }
  ]
}

```

## 2. Client-Side Routing (Handling 403/404 Errors in React Router)

When a user visits `[https://yourdomain.com/](https://yourdomain.com/)`, CloudFront serves `index.html`. If the user then clicks a link inside your React app to navigate to `/dashboard`, **React Router** handles this in browser memory without sending a new request to the server.

However, if the user directly refreshes the page at `[https://yourdomain.com/dashboard](https://yourdomain.com/dashboard)` or enters that URL into their browser, the request goes directly to CloudFront. Because `/dashboard` does not exist as an actual file in the S3 bucket, S3 returns an `AccessDenied` (403) or `NoSuchKey` (404) error.

### The Fix: CloudFront Custom Error Pages

To support single-page application (SPA) client-side routing, configure custom error responses in CloudFront:

| HTTP Error Code    | Response Page Path | HTTP Response Code |
| ------------------ | ------------------ | ------------------ |
| **403: Forbidden** | `/index.html`      | **200: OK**        |
| **404: Not Found** | `/index.html`      | **200: OK**        |

When CloudFront encounters a 403 or 404 from S3, it responds by serving `index.html` with an HTTP status of `200 OK`. React Router then parses the browser URL `/dashboard` and renders the correct component view.

## 3. Cache Control & CloudFront Invalidations

To ensure fast load times without serving outdated code after deployments, use a split caching strategy based on asset types.

### Asset Cache Strategy

* **`index.html` (Must Never Cache):** Serves as the entry point pointing to hashed JavaScript/CSS bundles.
* **Header:** `Cache-Control: no-cache, no-store, must-revalidate`

* **Static Assets (`.js`, `.css`, images with content hashes):**
* **Header:** `Cache-Control: public, max-age=31536000, immutable`

### Executing Invalidation in CI/CD

When pushing a new React build to S3, existing users may continue to see old content due to CloudFront edge caching. Trigger an invalidation after uploading files:

```bash
# Sync local dist folder to S3
aws s3 sync ./dist s3://my-react-app-production --delete

# Invalidate index.html to force CloudFront to fetch fresh entrypoints
aws cloudfront create-invalidation \
  --distribution-id E1A2B3C4D5E6F7 \
  --paths "/index.html"

```

## 4. Automated CI/CD Pipeline (GitHub Actions Example)

To automate deployments on every `git push`, use GitHub Actions with AWS credentials provided via OpenID Connect (OIDC) or strict IAM deployment roles.

### Minimal IAM Deployment Policy

Create an IAM role for your deployment pipeline with minimal required permissions:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:PutObject",
        "s3:GetObject",
        "s3:ListBucket",
        "s3:DeleteObject"
      ],
      "Resource": [
        "arn:aws:s3:::my-react-app-production",
        "arn:aws:s3:::my-react-app-production/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": [
        "cloudfront:CreateInvalidation"
      ],
      "Resource": "arn:aws:cloudfront::123456789012:distribution/E1A2B3C4D5E6F7"
    }
  ]
}

```

### GitHub Actions Workflow (`.github/workflows/deploy.yml`)

```yaml
name: Deploy React App to AWS

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-style: '20'
          cache: 'npm'

      - name: Install Dependencies & Build
        run: |
          npm ci
          npm run build
        env:
          VITE_API_URL: https://api.yourdomain.com

      - name: Configure AWS Credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ap-south-1

      - name: Sync Artifacts to S3
        run: |
          aws s3 sync ./dist s3://my-react-app-production --delete

      - name: Invalidate CloudFront Cache
        run: |
          aws cloudfront create-invalidation --distribution-id ${{ secrets.CLOUDFRONT_DISTRIBUTION_ID }} --paths "/index.html"

```

## 5. Next.js & Server-Side Rendering (SSR) on AWS ECS vs. AWS Amplify

If your React application uses **Server-Side Rendering (SSR)** or **React Server Components (RSC)** (e.g., via Next.js or Remix), standard S3 static hosting is insufficient because a running Node.js server environment is required.

```text
               ┌─────────────────────────────────────────────────────────┐
               │                  SSR Deployment Options                 │
               └────────────────────────────┬────────────────────────────┘
                                            │
         ┌──────────────────────────────────┴──────────────────────────────────┐
         ▼                                                                     ▼
┌─────────────────────────────────┐                           ┌─────────────────────────────────┐
│       AWS ECS (Fargate)         │                           │           AWS Amplify           │
├─────────────────────────────────┤                           ├─────────────────────────────────┤
│ • Containerized Docker Service  │                           │ • Fully Managed Platform        │
│ • Full Auto-scaling control     │                           │ • Automatic SSR Handler infra   │
│ • Custom VPC networking & ALB   │                           │ • Zero infrastructure setup     │
└─────────────────────────────────┘                           └─────────────────────────────────┘

```

### Option A: AWS ECS (Elastic Container Service + Fargate)

Best for enterprise applications requiring precise network isolation, custom container configurations, or integration into an existing microservices architecture.

1. **Dockerize the Next.js/SSR App:**

```dockerfile
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV production
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build
EXPOSE 3000
CMD ["npm", "start"]

```

1. **Deploy to ECS Fargate behind an Application Load Balancer (ALB).**

### Option B: AWS Amplify (Managed Next.js Hosting)

Best for rapid development without managing Docker containers, load balancers, or auto-scaling groups.

* Connect your Git repository to AWS Amplify.
* Amplify automatically detects Next.js SSR build outputs and deploys the necessary Lambda@Edge/CloudFront infrastructure behind the scenes.
