### State Management: Single Record Principle

- **Single Source of Truth:** State must be declared as a single, normalized record or state machine using discriminated unions.
- **No Derived State in `useState`:** Never create secondary `useState` hooks for values that can be computed synchronously from existing props or state.
- **Discriminated Unions for Async UI:** Always represent asynchronous operations using explicit status states rather than multiple boolean flags (`isLoading`, `isError`, `isSuccess`).

const [data, setData] = useState<User null |>(null);

type AsyncState<T> =

  | { status: 'loading' }
  | { status: 'error'; error: Error }
  | { status: 'success'; data: T };

const [userState, setUserState] = useState<AsyncState<User>>({ status: 'idle' });

- **Exported Contracts:** Place shared models and API contracts in dedicated file modules (`*.types.ts` or `types/`).

- **Ban Pixel Units for Layouts:** NEVER use raw pixel values (`px`) for `margin`, `padding`, `font-size`, `width`, or `height`.

- Never animate layout properties like `width`, `height`, `top`, `left`, `margin`, or `padding`.

how to create a CLI verification loop script using TypeScript, Biome/ESLint, and Vitest for AI code.

Building an automated verification script creates a **closed loop** for your AI coding agent. When the AI outputs code, this script runs static compilation (`tsc`), linting/formatting (`biome` or `eslint`), and unit testing (`vitest`). If any phase fails, stdout/stderr is captured and injected back to the AI prompt context to trigger a self-correction loop.

---

## 1. The Script Architecture

The script uses Node.js `child_process` (specifically `execSync`) to run three verification stages sequentially:

1. **Type Checker:** `tsc --noEmit`
2. **Linter / Formatter:** `biome check` (or `eslint`)
3. **Unit Tests:** `vitest run`

```
                      [ AI Writes / Refactors Code ]
                                    │
                                    ▼
                     ┌──────────────────────────────┐
                     │   node scripts/verify-ai.js  │
                     └──────────────┬───────────────┘
                                    │
           ┌────────────────────────┼────────────────────────┐
           ▼                        ▼                        ▼
  ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────┐
  │ TypeScript Check│      │ Biome / ESLint  │      │  Vitest Runner  │
  └────────┬────────┘      └────────┬────────┘      └────────┬────────┘
           │ (Fail)                 │ (Fail)                 │ (Fail)
           └────────────────────────┼────────────────────────┘
                                    │
                                    ▼
                     ┌──────────────────────────────┐
                     │  Format Error Payload into   │
                     │   Markdown for AI Prompt     │
                     └──────────────────────────────┘

```

---

## 2. Verification Loop Script (`scripts/verify-ai.js`)

Save this file as `scripts/verify-ai.mjs` (or `.ts` if using `tsx` / `bun`).

````javascript
import { execSync } from "node:child_process";
import fs from "node:fs";

/**
 * Executes a terminal shell command and catches errors cleanly.
 */
function runCommand(name, command) {
  console.log(`\x1b[36m[VERIFY]\x1b[0m Running ${name}...`);
  try {
    const output = execSync(command, {
      encoding: "utf-8",
      stdio: ["pipe", "pipe", "pipe"], // Capture stdout and stderr
    });
    return { name, success: true, output };
  } catch (error) {
    const stdout = error.stdout ? error.stdout.toString() : "";
    const stderr = error.stderr ? error.stderr.toString() : "";
    return {
      name,
      success: false,
      output: `${stdout}\n${stderr}`.trim(),
    };
  }
}

function runVerificationLoop() {
  console.log("\n\x1b[33m=== STARTING AI CODE VERIFICATION LOOP ===\x1b[0m\n");

  // Define the stages
  const steps = [
    { name: "TypeScript Compiler", cmd: "npx tsc --noEmit" },
    {
      name: "Biome Linter & Formatter",
      cmd: "npx @biomejs/biome check --write .",
    },
    { name: "Vitest Unit Tests", cmd: "npx vitest run" },
  ];

  const failures = [];

  for (const step of steps) {
    const result = runCommand(step.name, step.cmd);

    if (result.success) {
      console.log(`\x1b[32m✔ ${step.name} passed!\x1b[0m\n`);
    } else {
      console.log(`\x1b[31m✖ ${step.name} failed!\x1b[0m\n`);
      failures.push(result);
      // Optional: Break on first failure to save AI context tokens
      break;
    }
  }

  if (failures.length === 0) {
    console.log(
      "\x1b[32m🚀 ALL VERIFICATIONS PASSED! Code is safe to commit.\x1b[0m\n",
    );
    // Remove stale error logs if present
    if (fs.existsSync("ai-errors.log")) fs.unlinkSync("ai-errors.log");
    process.exit(0);
  } else {
    // Format failure for AI Consumption
    const errorMarkdown = generateAiErrorPrompt(failures);
    fs.writeFileSync("ai-errors.log", errorMarkdown);

    console.error("\x1b[31m[FAILED] Verification loop caught issues.\x1b[0m");
    console.error(
      "Formatted error output dumped to \x1b[33mai-errors.log\x1b[0m\n",
    );
    process.exit(1);
  }
}

/**
 * Formats CLI outputs into a clean Markdown prompt ready for feed-back to the AI.
 */
function generateAiErrorPrompt(failures) {
  let markdown = `# ⚠️ VERIFICATION FAILURE REPORT\n\n`;
  markdown += `The code generated contains errors. Please fix the following failures:\n\n`;

  for (const failure of failures) {
    markdown += `## Failure Phase: ${failure.name}\n`;
    markdown += "```text\n";
    markdown += failure.output;
    markdown += "\n```\n\n";
  }

  markdown += `### Instructions for AI:\n`;
  markdown += `1. Review the error details and stack traces above.\n`;
  markdown += `2. Modify ONLY the files necessary to fix the reported issues.\n`;
  markdown += `3. Preserve existing architectural contracts (Single Record state, relative CSS units, typed interfaces).\n`;

  return markdown;
}

runVerificationLoop();
````

How do I hook this script into a Git pre-commit hook using Husky to prevent bad AI code from reaching main?

Setting up **Husky** with **lint-staged** creates an automated gatekeeper. Every time you (or an AI agent) run `git commit`, Husky intercepts the commit and executes your verification script. If TypeScript compiler checks, linters, or tests fail, the commit is aborted instantly.

Here is how to configure it step-by-step.

---

## Step 1: Install Husky and lint-staged

Run the following command in your terminal to install Husky and `lint-staged` as development dependencies:

```bash
npm install --save-dev husky lint-staged

```

---

## Step 2: Initialize Husky

Initialize Husky to automatically create the `.husky/` directory and configure your `package.json` setup script:

```bash
npx husky init

```

This will:

1. Create a `.husky/` folder in your project root.
2. Create a default pre-commit file inside `.husky/pre-commit`.
3. Add `"prepare": "husky"` to your `package.json` scripts so Husky installs automatically for anyone cloning the repository.

---

## Step 3: Configure `lint-staged` in `package.json`

Running tests and type-checks on the _entire_ codebase during every commit can slow down your workflow. Using `lint-staged` ensures the verification loop runs fast by targeting **only the files staged for commit**.

Add the `lint-staged` configuration to your `package.json`:

```json
{
  "name": "my-app",
  "scripts": {
    "prepare": "husky",
    "verify:ai": "node scripts/verify-ai.mjs"
  },
  "lint-staged": {
    "*.{ts,tsx,js,jsx}": [
      "biome check --write --no-errors-on-unmatched",
      "vitest related --run"
    ]
  }
}
```

---

## Step 4: Update `.husky/pre-commit` Hook

Open the `.husky/pre-commit` file and edit it to run your project checks. We will run **TypeScript type checking** across the project (since type errors can span across non-staged files) alongside **`lint-staged`** and your custom **verification script**.

Edit `.husky/pre-commit`:

```bash
#!/bin/sh
. "$(dirname "$0")/_/husky.sh"

echo "🔍 Running Pre-Commit Verification Gate..."

# 1. Run global TypeScript check
npx tsc --noEmit
if [ $? -ne 0 ]; then
  echo "❌ TypeScript type-check failed. Commit aborted."
  exit 1
fi

# 2. Run linting & tests on staged files
npx lint-staged
if [ $? -ne 0 ]; then
  echo "❌ Lint-staged checks failed. Commit aborted."
  exit 1
fi

# 3. Optional: Run full AI verification script
node scripts/verify-ai.mjs
if [ $? -ne 0 ]; then
  echo "❌ AI Verification script failed. Check ai-errors.log and fix errors before committing."
  exit 1
fi

echo "✅ All pre-commit checks passed! Commit accepted."

```

Make sure the hook file is executable (on macOS/Linux):

```bash
chmod +x .husky/pre-commit

```

how to configure ESLint or Biome rules to strictly catch hardcoded px values and non-GPU CSS animations.

You can enforce both rules—blocking raw `px` units and catching non-GPU CSS animations—using either **ESLint with Stylelint** (if you use CSS, Tailwind, or CSS-in-JS) or **Biome** with standard AST / CSS rules.

Here is how to set up both setups depending on your toolchain.

---

## Option A: Using Biome (Fastest & Modern)

Biome handles JavaScript/TypeScript and CSS natively in a single configuration file without needing extra plugins.

Add these rules to your `biome.json` at the root of your project:

```json
{
  "$schema": "https://biomejs.dev/schemas/1.8.3/schema.json",
  "css": {
    "linter": {
      "enabled": true
    }
  },
  "linter": {
    "enabled": true,
    "rules": {
      "css": {
        "nursery": {
          // Flags non-standard or banned units like px in CSS files
          "noUnknownUnit": "error"
        }
      },
      "style": {
        // Enforces strict TypeScript / JS idioms
        "useConst": "error",
        "noNonNullAssertion": "warn"
      }
    }
  }
}
```

> **Note on Biome CSS Support:** As of Biome 1.8+, CSS linting handles syntax checking and unknown units natively. For custom AST matching of specific values (like banning `px` completely except on `1px` borders), combining Biome with Stylelint yields the strictest guarantees.

---

## Option B: Using Stylelint + ESLint (Maximum Strictness)

Stylelint is the industry standard for enforcing specific CSS property constraints, unit bans, and animation restrictions across standard CSS, SCSS, CSS Modules, and Tailwind / CSS-in-JS.

### 1. Install Required Plugins

```bash
npm install --save-dev stylelint stylelint-config-standard stylelint-declaration-strict-value

```

### 2. Configure `.stylelintrc.json`

Create or update `.stylelintrc.json` to enforce **relative unit constraints** and **GPU-only transition properties**:

```json
{
  "extends": ["stylelint-config-standard"],
  "plugins": ["stylelint-declaration-strict-value"],
  "rules": {
    // 1. DISALLOW `px` UNITS (Except for 1px borders)
    "unit-disallowed-list": [
      ["px"],
      {
        "message": "Raw 'px' units are forbidden. Use relative units (rem, em, %, vh/vw) instead.",
        "ignoreProperties": {
          "px": [
            "border",
            "border-width",
            "box-shadow",
            "outline",
            "outline-width"
          ]
        }
      }
    ],

    // 2. RESTRICT CSS ANIMATIONS & TRANSITIONS TO GPU PROPERTIES ONLY
    // Banned: width, height, top, left, margin, padding, flex, etc.
    // Allowed: transform, opacity, filter, backdrop-filter, color
    "property-disallowed-list": [
      // Prevents animating properties that cause layout reflows
      ["transition-property"],
      {
        "message": "Only GPU-accelerated properties (transform, opacity, filter) may be animated."
      }
    ],

    "transition-property-no-property-exclusions": null,

    // Require explicit properties in transition declarations (prevents 'transition: all 0.3s')
    "plugin/declaration-strict-value": [
      ["/color$/", "fill", "stroke"],
      {
        "ignoreValues": ["transparent", "inherit", "currentColor"]
      }
    ]
  }
}
```

---

## Option C: Catching `px` in JSX / Inline Styles with ESLint

If your codebase or AI agent writes inline styles or CSS-in-JS (like `style={{ width: '300px', margin: 16 }}` or styled-components), standard CSS linters won't catch them.

Use **`eslint-plugin-no-restricted-syntax`** to intercept these via AST matching.

Add the following AST rule to your `.eslintrc.json` or `eslint.config.js`:

```javascript
// eslint.config.js (ESLint Flat Config)
import js from "@eslint/js";
import tseslint from "typescript-eslint";

export default tseslint.config({
  files: ["**/*.tsx", "**/*.jsx"],
  rules: {
    "no-restricted-syntax": [
      "error",
      // Rule 1: Catch hardcoded px strings in inline style objects
      {
        selector: "JSXAttribute[name.name='style'] Literal[value=/\\d+px/]",
        message:
          "Hardcoded 'px' strings in inline styles are forbidden. Use rem/em or relative design tokens.",
      },
      // Rule 2: Catch reflow animation properties in inline style definitions
      {
        selector:
          "Property[key.name=/(width|height|top|left|margin|padding)/][parent.parent.name.name='transition']",
        message:
          "Do not animate layout properties (width, height, top, left, margin, padding). Use transform or opacity instead.",
      },
      // Rule 3: Catch transition: 'all 0.3s' wildcard animations
      {
        selector: "Property[key.name='transition'][value.value=/all/]",
        message:
          "Wildcard 'transition: all' triggers full layout reflows. Explicitly target 'transform' or 'opacity'.",
      },
    ],
  },
});
```
