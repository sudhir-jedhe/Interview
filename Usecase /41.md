**Automatic Batching** is a performance optimization introduced in **React 18** where React groups multiple state updates into a single re-render—regardless of where the state updates originate.

By consolidating state updates, React avoids unnecessary intermediate renders and DOM repaints, keeping your application fast and smooth.

---

## What Changed in React 18?

### 1. Legacy Behavior (React 17 & Earlier: Partial Batching)

In React 17 and earlier, React **only batched state updates inside React event handlers** (like `onClick` or `onChange`).

If state updates happened inside **promises**, **asynchronous calls (`setTimeout`)**, or **native DOM event listeners**, React did **not** batch them. Each state update triggered its own immediate re-render.

```tsx
// ❌ React 17 Behavior
function handleClick() {
  fetch("/api/user").then(() => {
    // 2 separate state updates inside a Promise resolution:
    setIsLoading(false); // 🔴 Triggered Re-render #1
    setUser(data); // 🔴 Triggered Re-render #2
  });
}
```

### 2. Modern Behavior (React 18+: Automatic Batching)

With `createRoot()`, React 18 batches **all state updates automatically**, regardless of context or asynchronous boundaries.

```tsx
// ✅ React 18+ Behavior
function handleClick() {
  fetch("/api/user").then(() => {
    setIsLoading(false); // State updated
    setUser(data); // State updated
    // 🟢 React batches BOTH updates into a SINGLE Re-render!
  });
}
```

---

## Where Does Automatic Batching Work?

Automatic batching works everywhere out of the box when using `createRoot`:

1. **Native Promises / `async-await`:**

```tsx
await fetch("/api/data");
setCount((c) => c + 1);
setFlag((f) => !f); // 1 Re-render
```

2. **Timeouts & Intervals (`setTimeout`, `setInterval`):**

```tsx
setTimeout(() => {
  setCount((c) => c + 1);
  setFlag((f) => !f); // 1 Re-render
}, 1000);
```

3. **Native DOM Event Listeners:**

```tsx
element.addEventListener("click", () => {
  setCount((c) => c + 1);
  setFlag((f) => !f); // 1 Re-render
});
```

---

## How to Opt-Out of Automatic Batching (`flushSync`)

In rare edge cases, you may need React to immediately update the DOM synchronously before continuing code execution (e.g., measuring a DOM node's height right after changing state).

You can opt-out of automatic batching using `flushSync` from `react-dom`:

```tsx
import { useState } from "react";
import { flushSync } from "react-dom";

function handleClick() {
  // Force React to immediately flush state and update DOM synchronously
  flushSync(() => {
    setCount((c) => c + 1); // 🔴 Forces Re-render #1 immediately
  });

  // DOM is updated right here!
  console.log("Updated DOM element height:", divRef.current.offsetHeight);

  flushSync(() => {
    setFlag((f) => !f); // 🔴 Forces Re-render #2
  });
}
```

> **Warning:** `flushSync` breaks performance optimizations and can cause layout thrashing. Use it sparingly.

Explain React 18 Concurrent Rendering features like useTransition and useDeferredValue.

In standard React, rendering is **blocking and synchronous**. Once React starts rendering a component tree, nothing can stop it until it finishes—even if the user types into an input field or clicks a tab. On complex pages, this causes noticeable UI lag and frozen input boxes.

**Concurrent Rendering** in React 18 fixes this by allowing React to **interrupt, pause, resume, or abandon a re-render** to keep the main thread responsive for urgent user actions (like typing or clicking).

Two primary hooks unlock Concurrent Rendering in your components: **`useTransition`** and **`useDeferredValue`**.

---

## 1. `useTransition` — Marking State Updates as Non-Urgent

Use `useTransition` when **you control the state update** and want to tell React: _"Update this state in the background, but don't block typing or UI clicks while doing it."_

### How It Works:

- **Urgent Updates:** Direct state updates (e.g., updating an input box's text as the user types). React processes these immediately.
- **Non-Urgent Transitions:** Updates wrapped inside `startTransition(() => { ... })`. React computes these in the background and will interrupt them if a new urgent update arrives.

### Real-World Example: Fast Search Input with Heavy List Filtering

```tsx
import { useState, useTransition, ChangeEvent } from "react";

export function SearchPage() {
  const [text, setText] = useState("");
  const [query, setQuery] = useState("");

  // isPending is true while the background transition is rendering
  const [isPending, startTransition] = useTransition();

  const handleChange = (e: ChangeEvent<HTMLInputElement>) => {
    const value = e.target.value;

    // 1. URGENT UPDATE: Update input text immediately so typing feels instant
    setText(value);

    // 2. NON-URGENT TRANSITION: Defer the heavy list filtering in the background
    startTransition(() => {
      setQuery(value);
    });
  };

  return (
    <div>
      <input type="text" value={text} onChange={handleChange} />

      {/* Show a subtle loading indicator while transition finishes */}
      {isPending && <span className="spinner">Updating list...</span>}

      {/* Heavy component that takes 100ms+ to render */}
      <HeavySearchResults query={query} />
    </div>
  );
}
```

---

## 2. `useDeferredValue` — Deferring Received Props or Values

Use `useDeferredValue` when **you do not control the state setter directly** (e.g., receiving a prop from a parent component or a third-party library) and want a "debounced-like" non-blocking version of that value.

### How It Works:

- React renders the component with the _old_ deferred value first (keeping the screen immediately responsive).
- In the background, React tries to re-render with the _new_ deferred value. If a new update comes in while it's trying, React cancels the background work and restarts with the latest value.

### Real-World Example: Deferring a Prop Down to a Slow Component

```tsx
import { useState, useDeferredValue } from "react";

export function Dashboard({ rawSearchTerm }: { rawSearchTerm: string }) {
  // Create a deferred version of the prop
  const deferredSearchTerm = useDeferredValue(rawSearchTerm);

  // Check if the current rendered screen is showing stale data
  const isStale = rawSearchTerm !== deferredSearchTerm;

  return (
    <div style={{ opacity: isStale ? 0.6 : 1, transition: "opacity 0.2s" }}>
      {/* Heavy component re-renders with deferredSearchTerm in background */}
      <SlowDataGrid filter={deferredSearchTerm} />
    </div>
  );
}
```

---

## `useTransition` vs. `useDeferredValue` Comparison

| Feature               | `useTransition`                                          | `useDeferredValue`                                                         |
| --------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------- |
| **When to use?**      | You have access to the `setState` function.              | You don't have access to `setState` (e.g., working with incoming `props`). |
| **Primary Mechanism** | Wraps state updates: `startTransition(() => setVal(x))`. | Wraps values: `const deferred = useDeferredValue(val)`.                    |
| **Pending State**     | Provides an `isPending` boolean flag out of the box.     | No built-in flag (you compare `value !== deferredValue`).                  |
| **Analogy**           | _"Run this specific state update in the background."_    | _"Give me a lagged version of this value that updates in the background."_ |

---

## Key Takeaway: Concurrent Hooks vs. Traditional Debounce/Throttle

- **Debounce / Throttle:** Forces an arbitrary fixed delay (e.g., wait 300ms before doing anything). On fast machines, it introduces unnecessary lag. On slow machines, 300ms might still freeze the screen.
- **Concurrent Rendering (`useTransition` / `useDeferredValue`):** Has **zero artificial delay**. React starts rendering immediately in the background, yields to main-thread events if the user types, and completes as fast as the user's device allows.

In React, functional state updates—like `setCount(prev => prev + 1)`—allow you to update state based on the **previous state value**, guaranteeing that you are always working with the freshest data.

This is especially critical when dealing with **Automatic Batching**, **Asynchronous updates**, or **Closures**.

---

## 1. The Core Problem with Standard State Updates

React state updates are not applied immediately; they are scheduled. When you pass a direct value to a state setter, React uses the state value from the moment the component rendered (captured in a closure).

### ❌ The Bug: Direct Updates with Batching

```tsx
function handleMultipleClicks() {
  // Assume count is currently 0
  setCount(count + 1); // Reads count = 0 -> Schedules count = 1
  setCount(count + 1); // Reads count = 0 -> Schedules count = 1
  setCount(count + 1); // Reads count = 0 -> Schedules count = 1

  // Final count after re-render: 1 (NOT 3!)
}
```

Because all three calls read `count` as `0` from the current render's closure, React batches them and sets the new state to `0 + 1 = 1`.

---

## 2. How Functional Updates Fix It

When you pass a function to the state setter (`setCount(prev => prev + 1)`), React does not evaluate the state immediately.

Instead, React queues the updates in a **pending update queue** and passes the result of each step into the next function when processing the batch:

### ✅ The Fix: Functional Updates

```tsx
function handleMultipleClicks() {
  setCount((prev) => prev + 1); // Queue: [prev => prev + 1]
  setCount((prev) => prev + 1); // Queue: [prev => prev + 1, prev => prev + 1]
  setCount((prev) => prev + 1); // Queue: [prev => prev + 1, prev => prev + 1, prev => prev + 1]

  // React processes the queue during the batch update:
  // Initial count = 0
  // Step 1: 0 + 1 = 1
  // Step 2: 1 + 1 = 2
  // Step 3: 2 + 1 = 3
  // Final count after re-render: 3!
}
```

---

## 3. When SHOULD You Use Functional Updates?

You should always use the functional form in these three common scenarios:

### A. Updating State Multiple Times in One Event

As shown above, when chaining multiple updates within the same handler function.

### B. Inside Async Operations & Timers (`setTimeout`, Promises)

Asynchronous callbacks capture stale closures if they reference state directly.

```tsx
// ❌ Stale Closure Bug:
setTimeout(() => {
  setCount(count + 1); // Uses 'count' from 3 seconds ago!
}, 3000);

// ✅ Safe Functional Update:
setTimeout(() => {
  setCount((prev) => prev + 1); // Always receives current up-to-date state!
}, 3000);
```

### C. Inside `useEffect` or `useCallback` (Avoiding Dependency Loops)

Using functional updates allows you to remove state variables from the dependency array of `useEffect` or `useCallback`, preventing unnecessary effect re-runs.

```tsx
// ❌ Requires 'count' in dependencies -> Effect re-runs every time count changes
useEffect(() => {
  const interval = setInterval(() => {
    setCount(count + 1);
  }, 1000);
  return () => clearInterval(interval);
}, [count]);

// ✅ No 'count' dependency needed -> Interval runs smoothly without resetting
useEffect(() => {
  const interval = setInterval(() => {
    setCount((prev) => prev + 1);
  }, 1000);
  return () => clearInterval(interval);
}, []); // Empty dependency array!
```

---

## Summary Rule of Thumb

- Use **`setCount(count + 1)`** if the new state value is completely independent of the old state (e.g., setting state from an input field value: `setText(e.target.value)`).
- Use **`setCount(prev => prev + 1)`** whenever the new state relies on computing or modifying the **previous state value**.

**Request Batching** combines multiple individual API calls into a single HTTP payload or defers them briefly within a short time window (e.g., 10–50ms) to resolve them in bulk.

This technique dramatically accelerates data fetching by reducing network overhead, avoiding browser connection limits, and eliminating N+1 query problems.

---

## How Request Batching Works

Without batching, if 10 components on a page each request data for a specific user ID, the browser sends **10 separate HTTP requests**:

```text
Component A  ───► GET /api/user/1 ───► Server
Component B  ───► GET /api/user/2 ───► Server
Component C  ───► GET /api/user/3 ───► Server

```

With batching, a scheduler intercepts these calls, collects the IDs over a brief tick, and sends **1 single HTTP request**:

```text
Component A ─┐
Component B ─┼──► [ Batch Scheduler ] ───► POST /api/users (IDs: [1,2,3]) ───► Server
Component C ─┘

```

## Common Implementation Approaches

### 1. DataLoader Pattern (Client & Server)

Popularized by GraphQL, **DataLoader** queues requests during a single JavaScript Event Loop tick and batches them into a single call.

```typescript
import DataLoader from "dataloader";

// Batch function receives an array of keys (e.g., ['1', '2', '3'])
const userLoader = new DataLoader<string, User>(async (userIds) => {
  const response = await fetch("/api/users/batch", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ ids: userIds }),
  });
  const users: User[] = await response.json();

  // Return array of items matching the exact order of keys requested
  return userIds.map(
    (id) => users.find((user) => user.id === id) || new Error(`No user ${id}`),
  );
});

// Usage anywhere in your frontend app (all 3 calls combine into 1 network request):
const user1 = await userLoader.load("1");
const user2 = await userLoader.load("2");
const user3 = await userLoader.load("3");
```

---

### 2. GraphQL Request Batching

If using GraphQL (with clients like **Apollo Client**), batching multiple queries into a single HTTP POST request is enabled via `@apollo/client/link/batch-http`:

```typescript
import { ApolloClient, InMemoryCache } from "@apollo/client";
import { BatchHttpLink } from "@apollo/client/link/batch-http";

const batchLink = new BatchHttpLink({
  uri: "https://api.example.com/graphql",
  batchInterval: 20, // Wait 20ms to collect queries before firing HTTP request
  batchMax: 10, // Max queries per batch payload
});

const client = new ApolloClient({
  link: batchLink,
  cache: new InMemoryCache(),
});
```

### 3. Custom Batching Function (vanilla JS / React)

If your backend supports bulk endpoints (e.g., `/api/products?ids=1,2,3`), you can write a lightweight custom batcher:

```typescript
function createBatcher<TKey, TValue>(
  batchFetchFn: (keys: TKey[]) => Promise<Map<TKey, TValue>>,
  delayMs = 10,
) {
  let queue: {
    key: TKey;
    resolve: (val: TValue) => void;
    reject: (err: any) => void;
  }[] = [];
  let timer: NodeJS.Timeout | null = null;

  return function load(key: TKey): Promise<TValue> {
    return new Promise((resolve, reject) => {
      queue.push({ key, resolve, reject });

      if (!timer) {
        timer = setTimeout(async () => {
          const currentQueue = [...queue];
          queue = [];
          timer = null;

          try {
            const keys = currentQueue.map((item) => item.key);
            const resultMap = await batchFetchFn(keys);

            currentQueue.forEach((item) => {
              const val = resultMap.get(item.key);
              if (val !== undefined) item.resolve(val);
              else item.reject(new Error(`Missing key ${item.key}`));
            });
          } catch (err) {
            currentQueue.forEach((item) => item.reject(err));
          }
        }, delayMs);
      }
    });
  };
}
```

## Benefits & Trade-offs

| Pros                                                                                               | Cons / Trade-offs                                                                                                                                |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Bypasses HTTP/1.1 limits:** Bypasses browser limits (usually 6 parallel requests per domain).    | **Increased Latency:** Adds a slight artificial delay (10–50ms) to collect requests.                                                             |
| **Lower Server Overhead:** Reduces TLS handshakes, HTTP header parsing, and DB connection pooling. | **All-or-Nothing Failures:** If one request in a batch causes a $500$ server error, the entire batch might fail without granular error handling. |
| **Prevents N+1 Query Issues:** Solves waterfall request patterns in complex component trees.       | **Backend Requirement:** Requires backend API endpoints capable of processing batch requests.                                                    |
