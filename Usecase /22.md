Preventing **Cross-Site Scripting (XSS)** attacks requires ensuring that un-sanitized, malicious input provided by an attacker is never executed as active JavaScript or raw HTML in a victim's browser.

In modern React applications, while React's JSX syntax escapes variables by default, several vulnerabilities can still expose your app to XSS.

Here is a multi-layered defense strategy to completely secure your application against XSS.

---

## 1. Avoid `dangerouslySetInnerHTML` (or Sanitize Input)

React automatically escapes variables rendered inside JSX string interpolations (`<div>{userInput}</div>`), rendering raw text instead of HTML tags.

However, if you **must** render dynamic HTML (such as rich-text output from a CMS), React requires `dangerouslySetInnerHTML`. Passing unsanitized input here is the **#1 source of XSS in React applications**.

### ❌ Dangerous Code:

```jsx
// IF userInput contains <img src=x onerror=alert('XSS')>, it executes!
function Comment({ userInput }) {
  return <div dangerouslySetInnerHTML={{ __html: userInput }} />;
}
```

### ✅ Safe Code (Sanitize with DOMPurify):

Always sanitize dynamic HTML with a library like **DOMPurify** before passing it to `dangerouslySetInnerHTML`.

```jsx
import DOMPurify from "dompurify";

function Comment({ userInput }) {
  const cleanHtml = DOMPurify.sanitize(userInput);

  return <div dangerouslySetInnerHTML={{ __html: cleanHtml }} />;
}
```

---

## 2. Validate and Sanitize User-Provided URLs

An attacker can execute JavaScript without HTML tags by passing a `javascript:` pseudo-protocol URL into `href` or `src` attributes.

### ❌ Vulnerable Code:

```jsx
// If userUrl is "javascript:alert('Hacked')", clicking the link executes the script!
function UserLink({ userUrl }) {
  return <a href={userUrl}>Visit Profile</a>;
}
```

### ✅ Safe Code:

Validate that user-provided URLs start strictly with `http://` or `https://` before binding them to anchors, images, or iframes.

```jsx
function SafeUserLink({ userUrl }) {
  const isSafeUrl = (url) => {
    try {
      const parsed = new URL(url, window.location.origin);
      return parsed.protocol === "http:" || parsed.protocol === "https:";
    } catch {
      return false;
    }
  };

  const safeHref = isSafeUrl(userUrl) ? userUrl : "#";

  return (
    <a href={safeHref} rel="noopener noreferrer">
      Visit Profile
    </a>
  );
}
```

## 3. Implement a Strict Content Security Policy (CSP)

A **Content Security Policy (CSP)** is an HTTP response header sent by your web server that instructs the browser on which scripts, styles, and assets are allowed to run. It acts as a powerful safety net if XSS injection succeeds.

### Example CSP Header (Configured on Server / NGINX / Express):

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; object-src 'none';

```

### What this does:

- `default-src 'self'`: Only allows assets loaded from your own origin.
- `script-src 'self'`: Disallows execution of inline scripts (`<script>alert(1)</script>`) and restricts script execution solely to bundled domain files.
- `object-src 'none'`: Blocks legacy `<object>`, `<embed>`, and `<applet>` tags.

---

## 4. Secure Authentication Tokens (`HttpOnly` Cookies)

A common goal of XSS attacks is stealing authentication tokens to hijack user sessions.

- **Avoid `localStorage` or `sessionStorage`:** JavaScript can easily read `localStorage.getItem('token')`. If an XSS vulnerability exists anywhere on your domain, the attacker can exfiltrate your tokens.
- **Use `HttpOnly` Cookies:** Set authentication JWTs inside `HttpOnly`, `Secure`, `SameSite=Strict` HTTP cookies from your backend API. Client-side JavaScript **cannot** access `HttpOnly` cookies, shielding your tokens even if XSS occurs.

---

## 5. Encode/Sanitize Inputs on the Server Side

Front-end validation can be bypassed by hitting your backend APIs directly (e.g., using Postman or cURL).

- Always sanitize inputs on your backend API before storing them in your database.
- Use library utilities (like `express-validator` in Node.js or `bleach` in Python) to strip dangerous tags (`<script>`, `<iframe>`, `javascript:`) at the API ingestion level.

---

## 6. Prevent Reflected XSS with SSR (Server-Side Rendering)

If you use Next.js or Server-Side Rendering (SSR), beware of injecting unescaped backend state directly into initial HTML `<script>` tags.

### ❌ Vulnerable (Injecting raw JSON):

```html
<script>
  // If initialData contains "</script><script>alert('XSS')</script>", it executes!
  window.__INITIAL_DATA__ = ${JSON.stringify(initialData)};
</script>

```

### ✅ Safe:

Use a serialization helper like **`serialize-javascript`** to safely escape HTML tags and special characters in JSON objects before server-rendering:

```javascript
import serialize from "serialize-javascript";

const safeScript = `<script>window.__INITIAL_DATA__ = ${serialize(initialData, { isJSON: true })};</script>`;
```

---

## Summary Checklist for XSS Prevention

| Security Practice          | Target Vulnerability                                                  |
| -------------------------- | --------------------------------------------------------------------- |
| **Rely on JSX Escaping**   | Escapes standard string rendering (`<div>{text}</div>`).              |
| **Use DOMPurify**          | Prevents HTML/Script injection in `dangerouslySetInnerHTML`.          |
| **Validate Protocols**     | Prevents `javascript:` pseudo-protocol injection in `href` and `src`. |
| **Use `HttpOnly` Cookies** | Prevents token theft via `localStorage` if an XSS attack occurs.      |
| **Enforce Strict CSP**     | Prevents execution of inline scripts and untrusted external scripts.  |
