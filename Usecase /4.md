An application becomes slower after memoization is added. How can a performance optimisation increase CPU usage and memory consumption?

Memoization is not free—it trades **memory and compute overhead** upfront in exchange for skipping duplicate work. When applied incorrectly, that trade-off backfires completely, increasing both CPU load and memory usage.

---

### 1. The Cost of Cache Management (CPU Overhead)

Before a memoized function can execute its body, it must run lookup and comparison logic:

- **Arguments Equality Checks:** Every function call forces the memoization wrapper to compare incoming arguments against cached keys. Deep object comparisons (`JSON.stringify(args)` or recursive equality checks) consume far more CPU cycles than simple, cheap function bodies.
- **Cache Miss Overhead:** On every cache miss, your application incurs a **double penalty**: it pays the CPU overhead of key hashing and cache lookup, _plus_ the execution cost of running the actual function anyway.
- **Garbage Collection (GC) Pressure:** Frequently allocating small key objects or wrapper arrays for memoization lookups creates short-lived objects. This triggers frequent garbage collection pauses, spiking CPU usage.

```js
// WEAK PATTERN: The equality check is more CPU-intensive than the actual calculation
const cheapCalculation = (a, b) => a + b;

// Memoized version executes complex key serialization on EVERY call
const memoizedCheapCalc = memoize((a, b) => a + b, {
  serializer: (...args) => JSON.stringify(args), // JSON parsing consumes substantial CPU
});
```

---

### 2. Unbounded Caches and Memory Leaks (Memory Overhead)

By design, memoization retains references to function inputs and output results so they can be retrieved later:

- **Indefinite Cache Growth:** Standard JavaScript objects or `Map` instances used as caches never delete old entries automatically. If a function is called with high-cardinality arguments (e.g., unique user IDs, timestamps, or search queries), the cache grows endlessly.
- **Retaining Detached Objects:** If you pass objects or DOM nodes as arguments to a memoized function using a standard `Map` or object key, those objects cannot be garbage collected—even if the rest of your app no longer uses them.

```js
// MEMORY LEAK: Standard Map keeps every argument and return value in memory forever
const cache = new Map();

function memoizedCompute(userObject) {
  if (cache.has(userObject)) return cache.get(userObject);

  const result = heavyProcess(userObject);
  cache.set(userObject, result); // Holds strong reference to userObject
  return result;
}
```

---

### 3. Broken Equality in Frameworks like React (`useMemo` / `useCallback`)

In React, memoization hooks (`useMemo`, `useCallback`, `React.memo`) evaluate dependency arrays using `Object.is` (shallow comparison). Re-creating inline objects or function references breaks memoization entirely:

```jsx
function ParentComponent({ userId }) {
  // Creating an inline object on every render...
  const options = { priority: "high" };

  // ...causes options reference to change on every render!
  // useMemo re-executes 100% of the time (0% cache hits)
  const data = useMemo(() => {
    return calculateHeavyStats(userId, options);
  }, [userId, options]);

  return <ChildData data={data} />;
}
```

**Why this spikes CPU and Memory:**

1. **100% Cache Miss Rate:** The dependency check runs on every single render and always evaluates to `false`.
2. **Double Work:** You pay for the React hook dependency comparison overhead _and_ execute the underlying function every single time.
3. **Allocation Churn:** New instances of memoized functions and return values are continually instantiated and abandoned for GC.

---

### How to Fix Counterproductive Memoization

| Problem                 | Solution                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Cheap Functions**     | Do not memoize fast, primitive operations (simple math, basic string manipulation).                                 |
| **Unbounded Caches**    | Use a **Least Recently Used (LRU)** eviction policy to set a max cache size limit.                                  |
| **Object Key Leaks**    | Use **`WeakMap`** for caching object references so unreferenced keys can be garbage collected.                      |
| **Unstable React Deps** | Ensure values in dependency arrays are primitive values, or stabilized using `useMemo`/`useCallback` at the source. |
