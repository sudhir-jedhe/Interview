### 1. `process.nextTick()` vs `setImmediate()`

* **`process.nextTick()`**: Schedules a callback to execute on the **`nextTickQueue`**. This queue is processed **immediately after the current operation finishes**, before the JavaScript engine yields back to the Event Loop. It runs before any Event Loop phase transitions and before other microtasks.
* **`setImmediate()`**: Schedules a callback to run in the **Check phase** of the Event Loop (macrotask). It executes on the next full turn/phase of the loop.

```
Current Operation Completes
  │
  ├─► Drain nextTickQueue  (process.nextTick)
  ├─► Drain MicrotaskQueue (Promise.then / catch / finally)
  │
  ▼
Event Loop Phases (Timers ──► Pending ──► Poll ──► Check [setImmediate])

```

---

### 2. `process.nextTick()` vs Promise Microtasks

Both run outside the main Event Loop phases as microtasks, but they have distinct priority queues:

1. **`nextTickQueue`** (`process.nextTick`)
2. **`microtaskQueue`** (`Promise.then()`, `queueMicrotask()`)

Whenever Node.js transitions between operations, it **drains the entire `nextTickQueue` first**, and only then drains the `microtaskQueue`.

```javascript
Promise.resolve().then(() => console.log('Promise microtask'));
process.nextTick(() => console.log('nextTick microtask'));

// Output:
// nextTick microtask
// Promise microtask

```

---

### 3. Where Exactly Does `setTimeout()` Execute?

1. **Registration**: Calling `setTimeout(fn, ms)` creates a timer inside V8/Node.js managed by internal min-heaps/linked lists tracking deadlines.
2. **Execution**: The callback does **not** execute immediately when the timer expires. Instead, it waits for the Event Loop to enter the **Timers phase**.
3. In the Timers phase, Node.js checks if `now - startTime >= threshold`. If true, the callback is placed on the call stack and executed.

---

### 4. What Happens When `process.nextTick()` Keeps Scheduling Itself? Can It Starve the Event Loop?

**Yes, it completely starves the Event Loop.**

Because Node.js empties the `nextTickQueue` until it is completely dry before moving to the next Event Loop phase, recursive calls to `process.nextTick()` keep the thread trapped:

```javascript
function recursiveTick() {
  process.nextTick(recursiveTick);
}
recursiveTick();

setTimeout(() => {
  console.log('This will NEVER run');
}, 0);

```

* **Result**: The Timers, Poll, and Check phases never execute. I/O callbacks, network responses, and timer events are completely blocked.
* In older Node versions, this would hang indefinitely without an error; in modern Node versions, it can hit the `maxTickDepth` threshold or run until the process runs out of memory / locks the CPU at 100%.

---

### 5. Node.js Event Loop Phases

The libuv Event Loop cycles through six distinct phases:

```
   ┌───────────────────────────┐
┌─►│          Timers           │  ──► Executes setTimeout(), setInterval() callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     Pending Callbacks     │  ──► Executes deferred I/O callbacks (e.g., TCP errors)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │        Idle, Prepare      │  ──► Internal libuv housekeeping only
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           Poll            │  ──► Retrieves new I/O events; blocks/waits if idle
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           Check           │  ──► Executes setImmediate() callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
└──┤      Close Callbacks      │  ──► Executes socket.on('close'), handle cleanup
   └───────────────────────────┘
   
   ★ Between EVERY phase transition:
     1. Drain nextTickQueue
     2. Drain Promise microtaskQueue

```

---

### 6. Difference Between `setImmediate()` and `setTimeout(fn, 0)`

* `setTimeout(fn, 0)` is evaluated in the **Timers phase** (Node.js internally normalizes `0ms` to `1ms`).
* `setImmediate(fn)` is evaluated in the **Check phase**.

#### Context 1: In the Main/Global Module Scope (Non-Deterministic)

When executed at the top level, timing depends on process startup latency:

```javascript
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

```

* If the loop enters the Timers phase before 1ms elapses: `immediate` runs first.
* If process startup took $> 1\text{ms}$: `timeout` runs first.

#### Context 2: Inside an I/O Cycle (Deterministic)

Inside an I/O callback (Poll phase), `setImmediate()` **always runs first**.

```javascript
const fs = require('fs');

fs.readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});

// Guaranteed Output:
// immediate
// timeout

```

* **Reason**: An I/O callback executes in the **Poll phase**. Moving forward, the loop hits the **Check phase** (`setImmediate`) before circling back to the **Timers phase** (`setTimeout`).

### 7. Code Output Prediction: Nested `nextTick()`, Promises, and Timers

```javascript
console.log('1: Sync');

setTimeout(() => {
  console.log('2: Timeout 1');
  process.nextTick(() => console.log('3: Next Tick inside Timeout'));
  Promise.resolve().then(() => console.log('4: Promise inside Timeout'));
}, 0);

setImmediate(() => {
  console.log('5: Immediate 1');
  process.nextTick(() => console.log('6: Next Tick inside Immediate'));
});

Promise.resolve().then(() => {
  console.log('7: Promise 1');
  process.nextTick(() => console.log('8: Next Tick inside Promise'));
});

process.nextTick(() => {
  console.log('9: Next Tick 1');
  Promise.resolve().then(() => console.log('10: Promise inside Next Tick'));
});

console.log('11: Sync End');

```

#### Step-by-Step Resolution

1. **Synchronous Execution**: Prints `1: Sync`, then `11: Sync End`.
2. **Drain `nextTickQueue**`: Runs `9: Next Tick 1` (queues `10: Promise inside Next Tick` into microtask queue).
3. **Drain `microtaskQueue**`: Runs `7: Promise 1` (queues `8: Next Tick inside Promise` into nextTickQueue) and `10: Promise inside Next Tick`.
4. **Intermediate Drain**: Resolves newly added `8: Next Tick inside Promise`.
5. **Timers Phase**: Runs `2: Timeout 1` $\rightarrow$ drains its `nextTick` (`3`), then its `Promise` (`4`).
6. **Check Phase**: Runs `5: Immediate 1` $\rightarrow$ drains its `nextTick` (`6`).

#### Final Output

```text
1: Sync
11: Sync End
9: Next Tick 1
7: Promise 1
10: Promise inside Next Tick
8: Next Tick inside Promise
2: Timeout 1
3: Next Tick inside Timeout
4: Promise inside Timeout
5: Immediate 1
6: Next Tick inside Immediate

```

### 8. How Node.js Achieves Non-Blocking Asynchronous I/O

Node.js achieves non-blocking asynchronous execution through a split-tier architecture combining the **V8 Engine**, **libuv**, and **OS-level kernel notifications**.

```
┌─────────────────────────────────────────────────────────────┐
│                    V8 JavaScript Engine                     │
│                  (Single Call Stack Thread)                 │
└──────────────────────────────┬──────────────────────────────┘
                               │ (Native Bindings)
┌──────────────────────────────▼──────────────────────────────┐
│                            libuv                            │
│  ┌─────────────────────────┐   ┌─────────────────────────┐  │
│  │    Event Demultiplexer  │   │     libuv Threadpool    │  │
│  │ (epoll / kqueue / IOCP) │   │ (Default: 4 threads)    │  │
│  └────────────┬────────────┘   └────────────┬────────────┘  │
└───────────────┼─────────────────────────────┼───────────────┘
                │                             │
    ┌───────────▼───────────┐     ┌───────────▼───────────┐
    │  Network Sockets,     │     │  File System (fs),    │
    │  Pipes, DNS Resolve   │     │  Crypto, zlib, DNS    │
    └───────────────────────┘     └───────────────────────┘

```

#### 1. Network I/O (OS Kernel Demultiplexing)

Network operations (TCP/UDP, HTTP) do **not** use threads. They use non-blocking system calls handled by the OS kernel:

* **Linux**: `epoll`
* **macOS / BSD**: `kqueue`
* **Windows**: `IOCP`

The kernel tracks file descriptors and signals libuv when data is ready to be read or written.

#### 2. File & CPU-Heavy I/O (libuv Thread Pool)

Most operating systems do not provide universal asynchronous file system APIs. Libuv resolves this by using an internal **Thread Pool** (default: 4 threads, configurable via `UV_THREADPOOL_SIZE`). File I/O (`fs.readFile`), crypto functions (`crypto.pbkdf2`), and compression (`zlib`) are offloaded to these background worker threads.

---

### Detailed End-to-End Example: `fs.readFile()` vs `https.get()`

```javascript
const fs = require('fs');
const https = require('https');

console.log('Start');

// 1. Thread Pool Path (File System)
fs.readFile('data.txt', 'utf8', (err, data) => {
  if (err) throw err;
  console.log('File read completed');
});

// 2. Kernel Demultiplexing Path (Network)
https.get('https://nodejs.org', (res) => {
  console.log(`Network request completed with status: ${res.statusCode}`);
});

console.log('End');

```

#### Execution Lifecycle

```
1. Main Thread runs "console.log('Start')" ──► Prints 'Start'
   │
2. fs.readFile() invoked:
   └─► Offloaded to libuv Thread Pool worker.
   └─► Main thread DOES NOT WAIT; continues immediately.
   │
3. https.get() invoked:
   └─► OS socket opened with non-blocking flag (O_NONBLOCK).
   └─► Socket registered with epoll/kqueue.
   └─► Main thread DOES NOT WAIT; continues immediately.
   │
4. Main Thread runs "console.log('End')" ──► Prints 'End'
   │
5. Call Stack is now empty:
   └─► Event loop enters Poll Phase.
   │
6. Network / Disk events complete:
   ├─► epoll signals: socket data arrived ──► Network callback pushed to Poll queue.
   └─► Thread pool worker completes disk read ──► FS callback pushed to Poll queue.
   │
7. Event Loop pulls callbacks onto the V8 Call Stack and executes them.

```

#### Console Output

```text
Start
End
Network request completed with status: 200  (or File read completed, depending on latency)
File read completed

```

### Deep-Dive Additions & Edge Cases

#### 1️⃣ `process.nextTick()` vs Microtasks & Starvation Risk

* **Priority hierarchy:** `process.nextTick` executes **before** standard Promise microtasks (`Promise.then`, `queueMicrotask`).
* **Starvation warning:** Recursive calls to `process.nextTick()` will block all Event Loop phases, causing I/O starvation and unhandled timers.
* **Why use `nextTick`?** It is primarily designed to allow constructors/APIs to emit events or run callbacks *after* synchronous initialization but *before* returning control to the Event Loop:

```javascript
function StreamEmitter() {
  EventEmitter.call(this);
  // Emits after user attaches .on('data') handler in same tick
  process.nextTick(() => this.emit('ready'));
}

```

---

#### 2️⃣ Scaling Architecture: Cluster vs Worker Threads vs Containers

* **Memory & IPC Tradeoffs:**
* **Cluster:** Communicates via IPC (JSON serialization overhead); memory is completely isolated.
* **Worker Threads:** Supports zero-copy data transfer via `Transferable Objects` (`ArrayBuffer`) and shared mutable memory via `SharedArrayBuffer` + `Atomics`.

* **Containerized Workloads:** In modern Kubernetes/Docker environments, teams often run **1 single-core Node process per container** and let the orchestrator scale horizontally rather than managing in-app clustering.

---

#### 3️⃣ Module Caching & Cache Invalidation Nuances

* **Key Resolution:** The key in `require.cache` is the fully resolved, absolute filesystem path (`/app/dist/user.js`).
* **Bypassing Singleton / Cache Busting:**

```javascript
delete require.cache[require.resolve('./my-module')];
const freshInstance = require('./my-module');

```

* **ESM Comparison:** ES Modules (`import`) are also cached once resolved, but their module registry cannot be mutated or purged via a public API like `require.cache`.

---

#### 4️⃣ Asynchronous Error Handling & Process Safety

* **Fatal Unhandled Rejections:** In modern Node.js versions (v15+), an unhandled Promise rejection terminates the Node.js process by default with a non-zero exit code:

```javascript
process.on('unhandledRejection', (reason, promise) => {
  console.error('Unhandled Rejection at:', promise, 'reason:', reason);
  // Gracefully drain connections and exit
  process.exit(1);
});

```

* **Event Emitter Error Trap:** If an `EventEmitter` emits an `'error'` event and no listener is registered, Node.js throws an unhandled exception that crashes the process.

---

#### 5️⃣ Microtask Draining Between Event Loop Phases

* **Phase Transitions:** In modern Node.js, the microtask queues (`nextTickQueue` $\rightarrow$ `PromiseMicrotaskQueue`) are drained **immediately after every single callback executes**, not just at the end of each macro phase.

```
[ Callback in Timers / Poll / Check ]
                 │
                 ▼
       [ Drain nextTickQueue ]
                 │
                 ▼
     [ Drain Promise Microtasks ]
                 │
                 ▼
       [ Next Loop Phase ]

```

**11. What are Worker Threads?**
Worker threads (`worker_threads` module) allow Node.js to execute JavaScript code in parallel across multiple CPU threads within the same OS process.

* **How it works:** Each worker runs its own isolated V8 engine instance, event loop, and memory heap, but workers can share memory safely using `SharedArrayBuffer` or transfer data with `MessagePort` via structured cloning.
* **Why use them:** While Node.js excels at non-blocking I/O, heavy CPU-bound tasks (e.g., image/video processing, large file compression, cryptographic hashing, matrix calculations) block the main thread and event loop. Worker threads offload these CPU tasks without freezing incoming I/O.

---

**12. What is Middleware in Express.js?**
Middleware functions are pipeline functions that have access to the request object (`req`), response object (`res`), and the `next` middleware function in the application's request-response cycle.

* **Capabilities:** Execute code, modify `req` and `res`, terminate the request by sending a response, or call `next()` to pass control to the next handler.
* **Common Types:**
* *Application-level:* `app.use(express.json())`
* *Router-level:* `router.use('/admin', authGuard)`
* *Error-handling:* Defined with four parameters: `(err, req, res, next)`
* *Built-in / Third-party:* `cors`, `helmet`, `morgan`

---

**13. What is the Process Object in Node.js?**
The `process` object is a global instance of `EventEmitter` that provides information about, and control over, the current Node.js runtime process. It requires no `require()` or `import`.

* **Key capabilities:**
* *Environment variables:* `process.env` (e.g., `process.env.NODE_ENV`, `process.env.PORT`)
* *Process control:* `process.exit(code)`, `process.kill(pid)`
* *Event listening:* `process.on('uncaughtException', ...)`, `process.on('unhandledRejection', ...)`, `process.on('SIGTERM', ...)`
* *Resource monitoring:* `process.memoryUsage()`, `process.cpuUsage()`, `process.uptime()`
* *Asynchronous scheduling:* `process.nextTick()`

**14. How would you improve Node.js application security?**

* **Security Headers & CORS:** Use `helmet` to set secure HTTP headers (HSTS, CSP, X-Frame-Options) and configure strict CORS origin whitelisting.
* **Authentication & Cookies:** Use short-lived JWTs/sessions with `HttpOnly`, `Secure`, and `SameSite=Strict/Lax` cookies; enforce MFA/WebAuthn where appropriate.
* **Input Validation & Sanitization:** Validate schemas using libraries like Zod/Joi, prevent SQL injection with parameterized queries/ORMs, and prevent NoSQL injection by disallowing direct query operator injection (`$gt`, `$ne`).
* **Rate Limiting & DoS Protection:** Implement `express-rate-limit` or Redis token buckets to throttle brute-force/DDoS attempts, and set strict body parser limits (`express.json({ limit: '10kb' })`).
* **Dependency & Secret Management:** Audit packages with `npm audit` / Snyk, run on hardened least-privilege Docker containers, and keep secrets in encrypted vaults (e.g., AWS Secrets Manager, Vault) rather than `.env` files committed to source control.

---

**15. How would you optimize Node.js code and server performance?**

* **Never Block the Event Loop:** Offload heavy CPU work to Worker Threads or external background job queues (BullMQ/Redis), avoid synchronous operations (`fs.readFileSync`), and use streaming (`Stream.pipe()`) for large data payloads.
* **Scale Hardware Utilization:** Use process managers (PM2 / Kubernetes replicas) or the `cluster` module to spawn one Node.js process per CPU core.
* **Caching Layers:** Implement in-memory caches (Redis/Memcached) for hot database queries and cache static assets via CDNs.
* **Database & Network Optimization:** Maintain persistent database connection pools, eliminate N+1 queries using indexing/joins/DataLoaders, and enable HTTP/2 or Keep-Alive.
* **Profiling & APM:** Profile memory and event loop lag using clinic.js (`clinic doctor`, `clinic flame`) or Chrome DevTools profiler.
