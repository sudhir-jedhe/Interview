# Interview Q&A: Discriminated Unions and Literal Type Unions

**Q: Walk through how exhaustiveness checking with `never` works, end to end.**
A: After a `switch` (or `if`/`else if` chain) has explicitly handled every member of a discriminated union via checks on the discriminant, the value remaining in the `default` (or final `else`) branch is narrowed by TypeScript's control-flow analysis down to `never` — logically, "nothing is left, since every possibility was already handled." Assigning that narrowed value to a variable explicitly typed `never` compiles cleanly in that state. If a new member is later added to the union without a corresponding case being added anywhere the exhaustiveness pattern is used, the leftover branch is no longer actually empty — it narrows to the new, unhandled member instead of `never` — and the assignment to the `never`-typed variable now fails to compile, flagging exactly where a case is missing.

**Q: Why might you prefer a literal type union (`"pending" | "shipped"`) over a numeric `enum` for a status field?**
A: A literal union has zero runtime footprint — it's purely a compile-time construct erased after type checking, so the actual values are plain strings that serialize cleanly to JSON and match values coming directly from APIs. A numeric `enum` generates a real runtime object mapping names to numbers (and often numbers back to names), adding bundle size and requiring conversion/casting when the actual data source (an API response, a database column) sends plain strings rather than the enum's underlying numeric representation.

**Q: How do you get enum-like discoverability (autocomplete on named constants) without using TypeScript's `enum` keyword?**
A: Define a `const` object with `as const`, then derive a literal union type from its values using `typeof` and an indexed access type: `const Status = { Pending: "pending", Done: "done" } as const; type StatusValue = (typeof Status)[keyof typeof Status];`. This gives you `Status.Pending`-style named, autocomplete-friendly access to each value (reducing typo risk versus writing raw string literals everywhere), while `StatusValue` remains a plain literal union usable anywhere a union type is expected, with zero enum-specific runtime overhead.

**Q: Can a discriminant be something other than a string literal?**
A: Yes — any literal type works as a discriminant, including number literals, boolean literals, or even literal types from other primitives, as long as each union member has a distinct value for that property. String literals are by far the most common in practice (readable in logs, JSON-friendly, self-documenting), but a `kind: 0 | 1 | 2` numeric discriminant, for instance, narrows identically under a `switch` — the mechanism relies only on each member having a uniquely identifiable literal value for the shared property, not specifically on that value being a string.
