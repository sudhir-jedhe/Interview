# Interview Q&A: any, unknown, never, void

**Q: What's the difference between `any` and `unknown`?**
A: Both accept a value of any type. The difference is what you can do with the value afterward: `any` lets you call methods, access properties, and assign it anywhere with zero checks, effectively disabling type safety for anything it touches. `unknown` requires you to narrow the value (via `typeof`, `instanceof`, a type guard, etc.) before you can use it as anything more specific — you can't call a method or access a property on `unknown` directly. `unknown` is the type-safe counterpart to `any` and should be preferred at any boundary where data enters your program untyped (API responses, `JSON.parse`, `catch` blocks).

**Q: When would you legitimately use `any` instead of `unknown`?**
A: Rare, deliberate cases: incremental migration of a large JavaScript codebase where full typing isn't feasible yet, interfacing with a third-party library that ships bad or missing type definitions, or extremely dynamic metaprogramming code where narrowing would add friction without real benefit. Even then, it's best practice to isolate `any` usage behind a small, well-tested boundary function rather than letting it spread through a codebase — because `any` is contagious, any value derived from an `any` also becomes `any`.

**Q: What does a function returning `never` mean, and where have you used it?**
A: `never` means the function never successfully completes and returns a value to its caller — it always throws, always loops infinitely, or always calls `process.exit()`. The most common practical use is an `assertNever`/exhaustiveness-check helper: after a `switch` or `if`/`else if` chain has handled every member of a union, the remaining value in the `default`/`else` branch has type `never`. Passing it to a function typed to accept only `never` causes a compile error the moment a new union member is added anywhere without also adding a matching case — turning a "forgot to handle a new state" bug into a build failure instead of a silent runtime gap.

**Q: If a function is typed to return `void`, can it still `return` a value?**
A: Yes, syntactically and even at the type level in certain contexts — this is one of TypeScript's more surprising rules. A `void`-returning function is allowed to `return` an expression, and the returned value is simply ignored by the type system. This matters most for callback typing: if a callback parameter's type is `() => void`, you can pass in a function that returns something (like `(x) => array.push(x)`, which returns a number) without TypeScript complaining, because the contract only promises "the return value won't be used," not "there is no return value." Note this leniency is specific to `void`-typed function *types*, not to a variable explicitly declared to hold `undefined`.
