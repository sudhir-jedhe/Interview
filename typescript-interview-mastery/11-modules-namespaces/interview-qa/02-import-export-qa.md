# Interview Q&A: Import/Export Mechanics

**Q1: What's the actual difference between `import type { X } from "..."` and a regular `import { X } from "..."` where `X` happens to only be used as a type?**
A: Functionally, in a single-project TypeScript compile with full cross-file visibility, the compiler can often detect on its own that a regular import is type-only and erase it — the observable output can end up identical. The real difference shows up under **isolated/per-file transpilation** (esbuild, SWC, Babel's TS preset, or TypeScript's own `isolatedModules` mode): those tools transpile one file at a time without seeing what `X` actually is in its source file, so they can't safely tell whether a plain `import { X }` is type-only or not, and conservatively keep it as a runtime import. `import type` removes the ambiguity syntactically, guaranteeing erasure regardless of which tool or mode is compiling the file.

**Q2: Why might a regular `import` of a type-only name accidentally pull in unwanted runtime code?**
A: If the module being imported from has top-level side effects (e.g., it initializes a singleton, registers something globally, or has an expensive top-level computation) and a per-file transpiler can't prove the specific imported name is type-only, it keeps the whole import statement — which means the runtime bundle still executes that module's side effects, even though nothing at this call site actually needed the module to exist at runtime. This can also defeat tree-shaking: a bundler that sees a live import edge to a module may be conservative about eliminating code from it, even if every consumer only used it for types.

**Q3: What happens if two files both use `export default` and you accidentally import one's default as if it were the other's?**
A: Nothing catches this by name at the type level — default imports have no enforced name, so `import Foo from "./a"` and `import Foo from "./b"` are both syntactically valid regardless of what `a.ts` and `b.ts` actually export as default; you only get a type error if the imported value's *type* doesn't match how it's subsequently used. This is one of the concrete arguments for named exports: `import { UserCard } from "./UserCard"` fails to compile immediately if `UserCard` isn't actually exported from that path, giving you an error right at the import site rather than a possibly-confusing type mismatch further down.

**Q4: Can you re-export something you've imported, and why would you?**
A: Yes — `export { X } from "./module"` (or `export * from "./module"`) re-exports a name without needing a separate local `import` statement first. This is the standard pattern for building a "barrel" file (an `index.ts` that re-exports everything from a folder's submodules) so consumers can `import { A, B, C } from "./folder"` instead of reaching into individual files. The trade-off: barrel files can quietly hurt tree-shaking and increase the chance of circular-import issues in large codebases, so some teams deliberately avoid them for performance-sensitive packages.
