# Interview Q&A: Declaration Files and Module Augmentation

**Q1: When should you write your own `.d.ts` ambient declaration versus installing an `@types/*` package?**
A: Always check for an existing `@types/<package>` package first (or bundled types shipped by the library itself) — writing and maintaining your own ambient declarations is extra ongoing work and a source of drift if the library's real behavior changes. Reach for a hand-written `declare module` only when no types exist anywhere (no bundled types, no DefinitelyTyped package) and the library is small/stable enough that maintaining a minimal, accurate declaration by hand is worth it versus the cost of leaving it as `any`.

**Q2: Why does module augmentation only work with `interface`, not `type` aliases?**
A: Declaration merging — the mechanism augmentation relies on — is specifically a feature of `interface` declarations: TypeScript combines multiple `interface Foo { ... }` declarations sharing a name into one merged interface. `type` aliases are not mergeable in this way at all; declaring `type Foo = { a: string }` twice in a visible scope is a **compile error** (duplicate identifier), not a merge. This is one practical reason library authors sometimes prefer `interface` over `type` for their public config/options objects specifically to keep them augmentable by consumers.

**Q3: What's the purpose of the bare `import "some-module";` line before a `declare module "some-module" { ... }` augmentation block?**
A: It establishes that the `declare module` block is *augmenting* the real, already-existing module rather than potentially being interpreted as declaring a brand-new ambient module from scratch (which could shadow or conflict with the real one depending on module resolution and file inclusion order). The import itself is a side-effect-only import — its purpose isn't to actually use anything from the module in this file, it's to unambiguously tie the augmentation to the real module for the compiler.

**Q4: How would you write an ambient declaration for a library that attaches itself to the global `window` object rather than being imported?**
A: Use `declare global { interface Window { ... } }` inside a file that's a module (has at least one `import`/`export`, even a no-op `export {}` at the end) — `declare global` specifically requires being inside module scope to correctly target the global namespace rather than accidentally creating a new, separate global declaration. Without at least one `import`/`export` in the file, TypeScript treats the whole file as a global script, and a plain top-level `interface Window { ... }` (no `declare global` needed at all in that case) would already merge into the real `Window` interface directly — the `declare global` wrapper is specifically for when the surrounding file is otherwise a module.
