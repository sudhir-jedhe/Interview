Building a React Microfrontend (MFE) architecture from scratch is best achieved using **Webpack Module Federation**. This allows separate React applications to share components and dependencies at runtime.

Because configuration order is critical to ensuring dependencies and state load correctly, follow these exact steps.

1. **Scaffold the Applications:** Using the Module Federation CLI.
We will create two apps: a **Host** (the main shell) and a **Remote** (the microfrontend). Open your terminal and use `create-mf-app` to scaffold them quickly.

```bash
# Create the Host App
npx create-mf-app host-app
# (Select: Application, React, Webpack, JavaScript/TypeScript, CSS)

# Create the Remote App
npx create-mf-app remote-app
# (Select: Application, React, Webpack, JavaScript/TypeScript, CSS)

```

Install dependencies in both folders: `cd host-app && npm install`, then `cd ../remote-app && npm install`.

1. **Configure Module Federation:** Expose and Consume components.
Open the `webpack.config.js` file in **both** projects. We need to tell the Remote to expose its code, and the Host to consume it.

**In `remote-app/webpack.config.js`:**
Find the `ModuleFederationPlugin` and configure it to expose a `Widget` component:

```javascript
plugins: [
  new ModuleFederationPlugin({
    name: "remote",
    filename: "remoteEntry.js",
    exposes: {
      "./Widget": "./src/Widget", // We will create this file next
    },
    shared: {
      ...deps,
      react: { singleton: true, requiredVersion: deps.react },
      "react-dom": { singleton: true, requiredVersion: deps["react-dom"] },
      "react-redux": { singleton: true }, // Share Redux context
    },
  }),
]

```

**In `host-app/webpack.config.js`:**
Configure the Host to point to the Remote (assuming Remote runs on port 3001):

```javascript
plugins: [
  new ModuleFederationPlugin({
    name: "host",
    remotes: {
      remote: "remote@http://localhost:3001/remoteEntry.js",
    },
    shared: {
      ...deps,
      react: { singleton: true, requiredVersion: deps.react },
      "react-dom": { singleton: true, requiredVersion: deps["react-dom"] },
      "react-redux": { singleton: true },
    },
  }),
]

```

1. **Setup Global Redux Store:** In the Host Application.
The Host application should act as the single source of truth for global state. Install Redux in the host: `npm install @reduxjs/toolkit react-redux`.

**In `host-app/src/store.js`:**

```javascript
import { configureStore, createSlice } from '@reduxjs/toolkit';

const userSlice = createSlice({
  name: 'user',
  initialState: { name: 'Guest' },
  reducers: {
    setUser: (state, action) => { state.name = action.payload; }
  }
});

export const { setUser } = userSlice.actions;
export const store = configureStore({ reducer: { user: userSlice.reducer } });

```

1. **Build the Remote Component:** Using Redux and LocalStorage.
In the remote app, we will build the exposed component. It needs access to `react-redux` to read the shared state, and we will also demonstrate saving data to `localStorage`. Install Redux here as well: `npm install react-redux`.

**Create `remote-app/src/Widget.jsx`:**

```jsx
import React from 'react';
import { useSelector } from 'react-redux';

const Widget = () => {
  // 1. Read from shared Redux Store (provided by Host)
  const userName = useSelector((state) => state.user.name);

  // 2. Share data via LocalStorage
  const saveToStorage = () => {
    localStorage.setItem('mfe_shared_data', 'Hello from Remote!');
    window.dispatchEvent(new Event('storage')); // Notify other MFEs
  };

  return (
    <div style={{ border: '2px solid blue', padding: '1rem' }}>
      <h2>Remote Widget</h2>
      <p>Redux State (User): {userName}</p>
      <button onClick={saveToStorage}>Save to LocalStorage</button>
    </div>
  );
};

export default Widget;

```

1. **Integrate and Render in the Host:**
Finally, bring it all together in the Host application. We will wrap the application in the Redux `<Provider>` so the remote component can inherit the context.

**In `host-app/src/App.jsx`:**

```jsx
import React, { Suspense, useEffect, useState } from 'react';
import { Provider, useDispatch } from 'react-redux';
import { store, setUser } from './store';

// Dynamically import the Remote component
const RemoteWidget = React.lazy(() => import('remote/Widget'));

const AppContent = () => {
  const dispatch = useDispatch();
  const [storageData, setStorageData] = useState('');

  useEffect(() => {
    // Listen for LocalStorage changes triggered by the Remote
    const handleStorage = () => {
      setStorageData(localStorage.getItem('mfe_shared_data'));
    };
    window.addEventListener('storage', handleStorage);
    return () => window.removeEventListener('storage', handleStorage);
  }, []);

  return (
    <div style={{ border: '2px solid green', padding: '2rem' }}>
      <h1>Host Application</h1>
      <button onClick={() => dispatch(setUser('Admin User'))}>
        Update Redux State
      </button>
      <p>LocalStorage Data: {storageData}</p>
      
      <Suspense fallback={<div>Loading Remote...</div>}>
        <RemoteWidget />
      </Suspense>
    </div>
  );
};

const App = () => (
  <Provider store={store}>
    <AppContent />
  </Provider>
);

export default App;

```

To run the project, start both development servers by running `npm run start` in both the `host-app` and `remote-app` directories. When you load the Host app on `localhost:3000`, it will fetch the Remote component, share the Redux context natively, and allow seamless communication via `localStorage`.

How do I scope CSS in Webpack Module Federation so styles from the host and remote don't conflict?

Because microfrontends share the same browser window and DOM, global CSS will inevitably collide (e.g., if both the Host and Remote define a `.btn` class, whichever loads last wins).

To prevent this, you must scope your CSS to the specific application. In a Webpack/React Module Federation setup, there are three primary strategies. As a React developer, you will likely find **CSS Modules** or **CSS-in-JS** to be the most robust solutions.

Here is how to implement each.

---

### Strategy 1: CSS Modules (Recommended Webpack Native)

CSS Modules automatically hash your class names during the Webpack build process (e.g., `.btn` becomes `.btn_xyz123`), guaranteeing zero collisions across microfrontends.

**1. Update `webpack.config.js`:**
Modify the CSS rule in both your Host and Remote Webpack configs to enable modules.

```javascript
module: {
  rules: [
    {
      test: /\.module\.css$/, // Target only .module.css files
      use: [
        "style-loader",
        {
          loader: "css-loader",
          options: {
            modules: {
              // Generates unique class names like: remoteApp__button__2Kj3a
              localIdentName: "[name]__[local]__[hash:base64:5]", 
            },
          },
        },
      ],
    },
    // Keep a standard CSS rule for global styles (like resets)
    {
      test: /(?<!\.module)\.css$/,
      use: ["style-loader", "css-loader"],
    },
  ],
}

```

**2. Use in your React Component:**
Rename your stylesheet to `Widget.module.css` and import it as an object.

```jsx
import React from 'react';
import styles from './Widget.module.css';

const Widget = () => (
  <div className={styles.container}>
    <button className={styles.primaryButton}>Scoped Button</button>
  </div>
);

```

---

### Strategy 2: CSS-in-JS (Styled-Components or Emotion)

Libraries like `styled-components` generate unique class names at runtime. This works beautifully for microfrontends, but **requires a strict Webpack configuration** to prevent runtime crashes.

**The MFE Gotcha:** You cannot have multiple versions of `styled-components` running on the same page, or the styling engine will break. It must be declared as a singleton.

**1. Update `webpack.config.js` (Host and Remote):**

```javascript
const deps = require("./package.json").dependencies;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      // ...name, remotes, exposes
      shared: {
        ...deps,
        react: { singleton: true, requiredVersion: deps.react },
        "react-dom": { singleton: true, requiredVersion: deps["react-dom"] },
        // YOU MUST ADD THIS:
        "styled-components": { 
          singleton: true, 
          requiredVersion: deps["styled-components"] 
        },
      },
    }),
  ],
};

```

**2. Use normally in your code:**
The hashing is handled automatically by the library, isolating the styles to that specific component regardless of which MFE loaded it.

---

### Strategy 3: Prefixing via PostCSS (Best for Legacy CSS)

If you have an existing application with hundreds of global CSS files and migrating to CSS Modules is too much work, you can use PostCSS to automatically prepend a unique wrapper class (e.g., `.remote-app`) to every CSS rule during the build.

**1. Install dependencies:**
`npm install postcss postcss-loader postcss-prefix-selector --save-dev`

**2. Create `postcss.config.js` in your Remote app:**

```javascript
const prefixer = require('postcss-prefix-selector');

module.exports = {
  plugins: [
    prefixer({
      prefix: '.remote-app-wrapper',
      // Optional: ignore specific global classes like 'body' or 'html'
      exclude: ['body', 'html'], 
    }),
  ],
};

```

**3. Update Webpack:**
Add `postcss-loader` to your CSS rules.

```javascript
{
  test: /\.css$/,
  use: ["style-loader", "css-loader", "postcss-loader"],
}

```

**4. Wrap your MFE entry point:**
When exposing your remote component, wrap it in a `div` containing that prefix.

```jsx
const Widget = () => {
  return (
    <div className="remote-app-wrapper">
      {/* All global CSS inside here is safely scoped */}
      <h1 className="title">Remote Title</h1> 
    </div>
  );
};

```

How do I configure React Router v6 to work seamlessly across a host application and multiple microfrontends?

The biggest trap when adding React Router to a microfrontend architecture is accidentally rendering multiple `<BrowserRouter>` instances. If the Host and the Remote both try to control the browser's history API simultaneously, your navigation will break and routes will desync.

The golden rule is: **The Host application owns the `BrowserRouter`, and the Remote applications inherit it.**

Here is the step-by-step configuration to make React Router v6 work seamlessly across your architecture.

1. **Share React Router as a Singleton:** Host and Remote Webpack Configs.
Just like Redux and React, `react-router-dom` relies on React Context. If the Host and Remote load different instances of the router, the Remote won't be able to read the routing context. You must declare it as a singleton in **both** `webpack.config.js` files.

```javascript
const deps = require("./package.json").dependencies;

// Add this to the 'shared' object in BOTH Webpack configs
shared: {
  ...deps,
  react: { singleton: true, requiredVersion: deps.react },
  "react-dom": { singleton: true, requiredVersion: deps["react-dom"] },
  "react-router-dom": { 
    singleton: true, 
    requiredVersion: deps["react-router-dom"] 
  },
}

```

1. **Configure the Host Application:** host-app/src/App.jsx.
The Host acts as the shell. It initializes the `<BrowserRouter>` and defines the base route for the Remote. **Crucially, you must append `/*` to the Remote's route** so React Router knows to pass control down to the Remote for nested URLs.

```jsx
import React, { Suspense } from 'react';
import { BrowserRouter, Routes, Route, Link } from 'react-router-dom';

const RemoteApp = React.lazy(() => import('remote/App'));

const Host = () => (
  <BrowserRouter>
    <nav style={{ padding: '1rem', background: '#eee' }}>
      <Link to="/" style={{ marginRight: '1rem' }}>Home</Link>
      <Link to="/remote">Go to Remote</Link>
    </nav>

    <Suspense fallback={<div>Loading Remote...</div>}>
      <Routes>
        <Route path="/" element={<h2>Host Home Page</h2>} />
        {/* The /* is mandatory for nested routing inside the Remote */}
        <Route path="/remote/*" element={<RemoteApp />} />
      </Routes>
    </Suspense>
  </BrowserRouter>
);

export default Host;

```

1. **Configure the Remote Application:** remote-app/src/App.jsx.
The Remote exposes a component that contains `<Routes>`, but **it does not include a `<BrowserRouter>**`. Because it shares the `react-router-dom` singleton from Webpack, it automatically hooks into the Host's history.

Use relative links inside the Remote. Since the Host mounted it at `/remote`, a relative link to `details` will automatically resolve to `/remote/details`.

```jsx
import React from 'react';
import { Routes, Route, Link } from 'react-router-dom';

// These components are internal to the remote
const RemoteHome = () => (
  <div>
    <h3>Remote Home</h3>
    {/* Relative link: resolves to /remote/details */}
    <Link to="details">View Details</Link> 
  </div>
);

const RemoteDetails = () => <h3>Remote Details Page</h3>;

// This is the component exposed via Webpack
const RemoteApp = () => {
  return (
    <div style={{ border: '2px solid blue', padding: '1rem' }}>
      <h2>Remote Microfrontend</h2>
      <Routes>
        {/* Matches /remote */}
        <Route path="/" element={<RemoteHome />} /> 
        {/* Matches /remote/details */}
        <Route path="details" element={<RemoteDetails />} /> 
      </Routes>
    </div>
  );
};

export default RemoteApp;

```

### Running the Remote Standalone (Optional but Recommended)

During development, your team might want to run the Remote app on its own (e.g., on `localhost:3001`), outside of the Host. If they do, the app will crash because it lacks a `BrowserRouter`.

You can solve this by keeping `remote-app/src/App.jsx` router-agnostic (as written above), but wrapping it in a `<BrowserRouter>` solely inside its local `bootstrap.js` or `index.js` file:

```jsx
// remote-app/src/bootstrap.js
import React from 'react';
import { createRoot } from 'react-dom/client';
import { BrowserRouter } from 'react-router-dom';
import App from './App';

const root = createRoot(document.getElementById('root'));
root.render(
  <BrowserRouter>
    <App />
  </BrowserRouter>
);

```

This guarantees the Remote gets a `BrowserRouter` when developed locally, but safely inherits the Host's router when consumed via Module Federation.

How do I implement Error Boundaries to prevent my host application from crashing if a microfrontend fails to load or goes offline?

When you dynamically import a microfrontend using `React.lazy(() => import('remote/App'))`, React relies on the network to fetch the `remoteEntry.js` file. If the remote server is down, the network drops, or the file is blocked, the `import()` promise rejects.

If this rejection is not caught, React's default behavior is to unmount the entire component tree—crashing your entire Host application to a white screen.

To prevent this, you must wrap the remote component in an **Error Boundary**. Here is how to build and implement one specifically for microfrontends.

1. **Create the Error Boundary:** Standard React Class Component.
Currently, React requires a Class Component to catch rendering and lazy-loading errors (there is no native Hook for this yet).

Create a new file in your Host application called `ErrorBoundary.jsx`. We will design it to render a safe fallback UI instead of crashing, and provide a button to let the user try again.

```jsx
import React from 'react';

class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  // Update state so the next render shows the fallback UI
  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  // Log the error to an error reporting service
  componentDidCatch(error, errorInfo) {
    console.error("Microfrontend failed to load:", error, errorInfo);
  }

  render() {
    if (this.state.hasError) {
      // You can render any custom fallback UI
      return (
        <div style={{ padding: '1rem', border: '1px solid red', background: '#ffebee', color: '#c62828' }}>
          <h3>Service Temporarily Unavailable</h3>
          <p>We could not load this section of the application.</p>
          <button 
            onClick={() => this.setState({ hasError: false })}
            style={{ padding: '0.5rem 1rem', cursor: 'pointer' }}
          >
            Try Again
          </button>
        </div>
      );
    }

    return this.props.children; 
  }
}

export default ErrorBoundary;

```

1. **Wrap the Remote Component:** In host-app/src/App.jsx.
Now, wrap the lazy-loaded Remote component with both `ErrorBoundary` and `Suspense`.

**Important ordering:** The `<ErrorBoundary>` must sit *outside* of the lazy component. It can wrap the `<Suspense>` boundary, or sit just inside it, but placing it outside `Suspense` ensures it catches both loading errors and rendering errors within the fallback.

```jsx
import React, { Suspense } from 'react';
import { BrowserRouter, Routes, Route, Link } from 'react-router-dom';
import ErrorBoundary from './ErrorBoundary';

const RemoteApp = React.lazy(() => import('remote/App'));

const Host = () => (
  <BrowserRouter>
    <nav style={{ padding: '1rem', background: '#eee' }}>
      <Link to="/">Home</Link> | <Link to="/remote">Remote Feature</Link>
    </nav>

    {/* The rest of the host app continues working even if RemoteApp fails */}
    <Routes>
      <Route path="/" element={<h2>Host Home Page</h2>} />
      
      <Route path="/remote/*" element={
        <ErrorBoundary>
          <Suspense fallback={<div>Loading remote feature...</div>}>
            <RemoteApp />
          </Suspense>
        </ErrorBoundary>
      } />
    </Routes>
  </BrowserRouter>
);

export default Host;

```

### Advanced Strategy: Third-Party Libraries

If you prefer not to write class components, you can install `react-error-boundary` (`npm install react-error-boundary`). It provides a modern, functional approach with hooks.

```jsx
import { ErrorBoundary } from 'react-error-boundary';

function Fallback({ error, resetErrorBoundary }) {
  return (
    <div role="alert">
      <p>Microfrontend failed to load:</p>
      <pre style={{ color: 'red' }}>{error.message}</pre>
      <button onClick={resetErrorBoundary}>Try again</button>
    </div>
  );
}

// In your router:
<ErrorBoundary FallbackComponent={Fallback}>
  <Suspense fallback={<div>Loading...</div>}>
    <RemoteApp />
  </Suspense>
</ErrorBoundary>

```

How do I handle user authentication and share JWT tokens across a React microfrontend architecture?

The golden rule of microfrontend authentication is: **The Host application is the gatekeeper.**

Microfrontends should never implement their own login screens or manage authentication flows. They should assume the user is authenticated and simply consume the state and tokens provided by the Host.

Here are the three standard patterns for managing and sharing JWTs across a Webpack Module Federation architecture, ordered from the most practical for your current setup to the most secure for production.

---

### Pattern 1: In-Memory State (via Shared Redux/Context)

Because you have already configured a singleton Redux store in your Webpack configuration, you can use it to hold the JWT. Storing the token in memory (Redux) is significantly safer than `localStorage` because it is wiped clean if an attacker tries to execute a Cross-Site Scripting (XSS) attack that refreshes the page.

**1. Host Application (The Gatekeeper):**
The Host handles the login API call, receives the JWT, and dispatches it to the shared Redux store.

```javascript
// host-app/src/store.js
import { configureStore, createSlice } from '@reduxjs/toolkit';

const authSlice = createSlice({
  name: 'auth',
  initialState: { token: null, isAuthenticated: false },
  reducers: {
    setToken: (state, action) => {
      state.token = action.payload;
      state.isAuthenticated = !!action.payload;
    },
    logout: (state) => {
      state.token = null;
      state.isAuthenticated = false;
    }
  }
});

export const { setToken, logout } = authSlice.actions;
export const store = configureStore({ reducer: { auth: authSlice.reducer } });

```

**2. Remote Application (The Consumer):**
The Remote simply uses `useSelector` to grab the token right before making its own API calls.

```jsx
// remote-app/src/Widget.jsx
import React, { useEffect } from 'react';
import { useSelector } from 'react-redux';

const Widget = () => {
  // Grab the token from the Host's Redux store
  const token = useSelector((state) => state.auth.token);

  useEffect(() => {
    if (token) {
      // Use the token for the Remote's specific API calls
      fetch('https://api.example.com/remote-data', {
        headers: { Authorization: `Bearer ${token}` }
      });
    }
  }, [token]);

  if (!token) return <div>Please log in via the main application.</div>;

  return <div>Remote Data Loaded securely!</div>;
};

```

---

### Pattern 2: The Shared Auth Utility

If you don't want to use Redux, you can have the Host expose a vanilla JavaScript singleton that manages the token. Both the Host and the Remote import this exact same file.

**1. Create `host-app/src/authService.js`:**

```javascript
let jwtToken = null;
const listeners = new Set();

export const authService = {
  getToken: () => jwtToken,
  setToken: (newToken) => {
    jwtToken = newToken;
    listeners.forEach(listener => listener(jwtToken));
  },
  subscribe: (listener) => {
    listeners.add(listener);
    return () => listeners.delete(listener); // Unsubscribe
  }
};

```

**2. Expose it via Webpack (Host):**

```javascript
new ModuleFederationPlugin({
  name: "host",
  exposes: {
    "./authService": "./src/authService",
  },
  // ...
})

```

**3. Consume it in the Remote:**

```jsx
import { authService } from 'host/authService';

// Now the remote can call authService.getToken() whenever it needs to fetch data

```

---

### Pattern 3: HTTP-Only Cookies (The Enterprise Standard)

If you are building a highly secure application, **do not share JWTs via JavaScript at all.**

Instead, bypass the frontend completely. Have your backend issue the JWT inside an `HttpOnly` cookie. This prevents any JavaScript (including malicious third-party scripts) from accessing the token, effectively eliminating XSS token theft.

**How it works in an MFE:**

1. The user logs in via the Host app.
2. The backend responds with a `Set-Cookie: token=eyJhb...; HttpOnly; Secure; SameSite=Strict`.
3. When the Remote app needs to make an API call, it doesn't need to look for a token. It just makes a standard request, and the browser automatically attaches the cookie.

**The Code (Host & Remote):**
You don't need Redux or exposed services. You just need to tell `fetch` or `axios` to include credentials in every request.

```javascript
// Using Fetch
fetch('https://api.example.com/data', {
  credentials: 'include' // This forces the browser to send the HttpOnly cookie
});

// Using Axios
axios.get('https://api.example.com/data', {
  withCredentials: true 
});

```

*Note: This pattern requires your Host, Remotes, and API to share the same root domain or be carefully configured for Cross-Origin Resource Sharing (CORS).*

How do I deploy microfrontends using CI/CD so I can update a remote application without rebuilding the host?

The entire premise of Webpack Module Federation is **runtime integration**. Because the Host fetches the Remote over the network when the user opens the browser, the Host does not care when the Remote was built—it only cares about the URL where `remoteEntry.js` lives.

To update a Remote without rebuilding the Host, you simply deploy the Remote's compiled files to a static server or CDN and overwrite the old `remoteEntry.js` file.

Here is the exact setup required to make this work in production.

1. **Configure Production URLs in Webpack:** Host and Remote Setup.
Locally, you used `localhost:3001`. In production, you must hardcode the public CDN or server URL so the Host knows exactly where to look, and the Remote knows where to load its own split chunks from.

**In `remote-app/webpack.config.js`:**
Set the `publicPath` so the Remote's internal imports resolve to its own CDN folder, not the Host's domain.

```javascript
module.exports = {
  // ...
  output: {
    // Must end with a trailing slash!
    publicPath: "https://cdn.example.com/remote-app/", 
    filename: "[name].[contenthash].js",
  },
  plugins: [
    new ModuleFederationPlugin({
      name: "remote",
      filename: "remoteEntry.js", // Do NOT hash this filename
      exposes: { "./Widget": "./src/Widget" },
      // ...shared deps
    })
  ]
};

```

**In `host-app/webpack.config.js`:**
Point the Host to the production URL of the Remote.

```javascript
module.exports = {
  // ...
  plugins: [
    new ModuleFederationPlugin({
      name: "host",
      remotes: {
        // Points directly to the static file on the CDN
        remote: "remote@https://cdn.example.com/remote-app/remoteEntry.js",
      },
    })
  ]
};

```

1. **Configure Cache Invalidation Strategy:** The most common MFE failure point.
If the browser caches `remoteEntry.js`, your users will never see the updated Remote application, and the Host might try to fetch older JavaScript chunks that you have already deleted from the server.

You must configure your hosting provider (AWS S3/CloudFront, Nginx, Vercel, Netlify) with these exact caching rules:

* **Rule 1:** `remoteEntry.js` and `index.html` MUST have `Cache-Control: no-cache, no-store, must-revalidate`. The browser must download this file fresh every single time.
* **Rule 2:** All other files (e.g., `main.123456.chunk.js`, images, CSS) should be cached forever: `Cache-Control: max-age=31536000, immutable`. Because Webpack hashes these filenames, they will never collide.

1. **Build the CI/CD Pipeline:** Example: GitHub Actions to AWS.
The CI/CD pipeline for the Remote application is completely independent. It builds the code, uploads the new chunks, and explicitly invalidates the CDN cache for the entry file.

When this pipeline finishes, the Host application instantly gets the new UI the next time a user refreshes the page—zero Host deployments required.

```yaml
name: Deploy Remote Application
on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v3

      - name: Install and Build
        run: |
          npm ci
          npm run build
          
      - name: Sync to Cloud Storage (e.g., AWS S3)
        # Uploads all hashed chunks and the new remoteEntry.js
        run: aws s3 sync dist/ s3://my-mfe-bucket/remote-app/ --delete
        
      - name: Invalidate CDN Cache
        # Forces the CDN to drop the old remoteEntry.js immediately
        run: aws cloudfront create-invalidation --distribution-id MY_ID --paths "/remote-app/remoteEntry.js"

```

### Handling Version Mismatches

Because you are deploying independently, you run a small risk of the Host and Remote falling out of sync if they expect different props or global states.

To mitigate this, treat the exposed components of your Remote like a public API. If you need to make a breaking change to `<Widget/>` (e.g., requiring a fundamentally new prop), **do not overwrite it**. Instead, expose a new file (`exposes: { "./WidgetV2": "./src/WidgetV2" }`), deploy the Remote, and then safely update the Host to consume `./WidgetV2` when the Host is ready.

The React code for sharing React Router across microfrontends remains **exactly the same** whether you use Webpack or Vite. The Host still owns the `<BrowserRouter>`, and the Remote still uses relative `<Routes>`.

The only difference is how you configure the build tool to share `react-router-dom` as a singleton. In Vite, this is handled using the `@originjs/vite-plugin-federation` plugin.

Here is the step-by-step Vite configuration.

1. **Install the Federation Plugin:** Host and Remote.
First, ensure you have the Vite federation plugin installed in both your Host and Remote projects.

```bash
npm install @originjs/vite-plugin-federation --save-dev

```

1. **Configure the Remote Application:** remote-app/vite.config.js.
You must expose your Remote's App component and declare `react-router-dom` in the `shared` array. This tells Vite not to bundle a duplicate version of the router.

```javascript
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import federation from '@originjs/vite-plugin-federation';

export default defineConfig({
  plugins: [
    react(),
    federation({
      name: 'remote_app',
      filename: 'remoteEntry.js',
      exposes: {
        './App': './src/App.jsx', // The component containing your <Routes>
      },
      shared: ['react', 'react-dom', 'react-router-dom']
    })
  ],
  build: {
    target: 'esnext' // Required for top-level await used by federation
  }
});

```

1. **Configure the Host Application:** host-app/vite.config.js.
The Host consumes the remote entry and also declares `react-router-dom` as a shared dependency.

```javascript
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import federation from '@originjs/vite-plugin-federation';

export default defineConfig({
  plugins: [
    react(),
    federation({
      name: 'host_app',
      remotes: {
        // In dev, this points to the built remote preview server
        remote: 'http://localhost:5001/assets/remoteEntry.js', 
      },
      shared: ['react', 'react-dom', 'react-router-dom']
    })
  ],
  build: {
    target: 'esnext'
  }
});

```

1. **Implement the Components:** The React Code.
The actual React code is identical to the Webpack implementation.

**In the Host App (`src/App.jsx`):**

```jsx
import React, { Suspense } from 'react';
import { BrowserRouter, Routes, Route, Link } from 'react-router-dom';

// Import the remote just like in Webpack
const RemoteApp = React.lazy(() => import('remote/App'));

const Host = () => (
  <BrowserRouter>
    <nav><Link to="/remote">Go to Remote</Link></nav>
    <Suspense fallback={<div>Loading...</div>}>
      <Routes>
        <Route path="/" element={<h2>Host Home</h2>} />
        {/* The /* is still required */}
        <Route path="/remote/*" element={<RemoteApp />} />
      </Routes>
    </Suspense>
  </BrowserRouter>
);

export default Host;

```

**In the Remote App (`src/App.jsx`):**

```jsx
import React from 'react';
import { Routes, Route, Link } from 'react-router-dom';

const RemoteApp = () => (
  <Routes>
    {/* Do not include a BrowserRouter here */}
    <Route path="/" element={<h2>Remote Home</h2>} /> 
    <Route path="details" element={<h2>Remote Details</h2>} /> 
  </Routes>
);

export default RemoteApp;

```

> **Crucial Vite Dev Server Gotcha:** Unlike Webpack, the `@originjs/vite-plugin-federation` plugin often struggles to serve dynamically exposed modules via the standard `vite` dev command. To test this locally, you usually need to **build and serve** the remote application:
>
> 1. In the remote app: run `npx vite build && npx vite preview --port 5001`
> 2. In the host app: run `npx vite dev`
