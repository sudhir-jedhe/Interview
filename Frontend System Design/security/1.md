Securing a modern front-end application requires a **defense-in-depth architecture**—implementing controls at the network, browser, code, and header levels.

---

## 1. Cross-Site Scripting (XSS) Protection

XSS occurs when an attacker injects malicious JavaScript into your application that executes in user browsers.

* **Input Sanitization & Output Encoding:** Never render untrusted user input directly into HTML. Use context-aware encoding (HTML, attribute, JavaScript, or URL context).
* **Safe Framework Rendering:** Modern frameworks (React, Angular, Vue) automatically encode strings rendered via templates (`{variable}`). Avoid dangerous escape hatches like React's `dangerouslySetInnerHTML`, Vue's `v-html`, or element `.innerHTML`.
* **Content Security Policy (CSP):** Set a strict `Content-Security-Policy` header to restrict where scripts can load from and disable inline script execution unless nonced:

```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://trustedscripts.com;

```

* **HttpOnly Cookies:** Store sensitive authentication tokens (like JWTs or Session IDs) in `HttpOnly` cookies rather than `localStorage` or `sessionStorage` so JavaScript cannot access them.

---

## 2. iFrame Protection & Clickjacking

Clickjacking tricks users into clicking transparent iframe layers over legitimate elements.

* **`X-Frame-Options` Header:** Instructs browsers whether the page can be rendered inside an `<iframe>`:

```http
X-Frame-Options: DENY

```

*(Use `SAMEORIGIN` if you need internal framing).*

* **CSP `frame-ancestors`:** Modern replacement for `X-Frame-Options`:

```http
Content-Security-Policy: frame-ancestors 'none';

```

---

## 3. Security Headers & Client-Side Hardening

Essential HTTP security headers sent by your web server/CDN to instruct browser behavior:

| Security Header                       | Recommended Value                              | Purpose                                                                         |
| ------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------- |
| **Strict-Transport-Security**         | `max-age=31536000; includeSubDomains; preload` | Enforces HTTPS strictly (HSTS).                                                 |
| **X-Content-Type-Options**            | `nosniff`                                      | Prevents MIME-type sniffing (forcing browser to respect declared content-type). |
| **Referrer-Policy**                   | `strict-origin-when-cross-origin`              | Limits sensitive information leaked in referrer headers.                        |
| **Cross-Origin-Opener-Policy (COOP)** | `same-origin`                                  | Isolates your window context from cross-origin popups.                          |

---

## 4. Permissions Policy (formerly Feature Policy)

Restricts which browser APIs and hardware features (camera, microphone, geolocation, payment APIs) your application or embedded iframes can access.

```http
Permissions-Policy: camera=(), microphone=(), geolocation=(self "https://maps.example.com")

```

---

## 5. Subresource Integrity (SRI)

Ensures third-party scripts or CDNs (e.g., Google Fonts, Analytics, Bootstrap) haven't been tampered with or compromised.

Include cryptographic hashes in script tags:

```html
<script 
  src="https://cdn.example.com/library.js" 
  integrity="sha384-oqVuAfXRKap7fdgcCY5uykM6+R9GqQ8K/uxy9rx7HNQlGYb15M8w=" 
  crossorigin="anonymous">
</script>

```

---

## 6. Cross-Origin Resource Sharing (CORS)

CORS is a browser enforcement mechanism that prevents unauthorized domains from reading your server's responses.

* **Backend Enforced:** Configure CORS on your backend server, not the front end.
* **Avoid Wildcards with Credentials:** Never use `Access-Control-Allow-Origin: *` alongside `Access-Control-Allow-Credentials: true`.
* **Explicit Allowlist:** Restrict `Access-Control-Allow-Origin` strictly to your trusted client domains (e.g., `[https://app.yourdomain.com](https://app.yourdomain.com)`).

---

## 7. Cross-Site Request Forgery (CSRF)

CSRF forces an authenticated user to execute unwanted actions on a web application in which they are currently authenticated.

* **SameSite Cookie Attribute:** Set cookie flags to `SameSite=Strict` or `SameSite=Lax`:

```http
Set-Cookie: session_id=xyz; Secure; HttpOnly; SameSite=Strict

```

* **Anti-CSRF Tokens:** Pass a unique, cryptographically secure CSRF token in custom request headers (`X-CSRF-Token`) for modifying state requests (POST, PUT, DELETE).

---

## 8. Input Validation & Sanitization

* **Client-Side Validation:** Enhances UX by checking input formats before sending network requests, but **never relied upon for security** since client state can be bypassed.
* **Sanitization Libraries:** If user-generated rich text HTML must be rendered, run it through proven libraries like **DOMPurify** before insertion:

```javascript
import DOMPurify from 'dompurify';
const cleanHTML = DOMPurify.sanitize(dirtyUserInput);

```

---

## 9. Secure Communication & Protocols

* **Enforce HTTPS (TLS 1.3):** Ensure all communication occurs over encrypted channels.
* **Secure Cookies:** Always apply the `Secure` flag so cookies travel exclusively over HTTPS.
* **WebSocket Security:** Use `wss://` instead of `ws://` for WebSocket endpoints, and validate token payloads on connection handshakes.

---

## 10. Dependency Security & Supply Chain Defense

Modern front-end applications rely heavily on third-party `npm` dependencies, creating supply chain attack risks.

* **Automated Audits:** Integrate tools like `npm audit`, `Snyk`, or `Dependabot` into your CI/CD pipeline to catch vulnerable packages.
* **Lockfiles:** Commit `package-lock.json` or `yarn.lock` to guarantee deterministic builds.
* **Pin Dependencies:** Avoid aggressive wildcard versions (`^` or `*`) for critical security packages.

---

## 11. Backend-Adjacent Risks (SSRF & SSJI Context)

While Server-Side Request Forgery (SSRF) and Server-Side JavaScript Injection (SSJI) operate on servers, front-end architecture must prevent triggering them:

* **SSRF Mitigation:** Front-end forms that accept arbitrary URLs (e.g., image webhooks or URL previewers) should pass URLs to a backend that strictly validates destination IP addresses (disallowing internal IPs like `127.0.0.1` or `169.254.169.254`).
* **SSJI Mitigation (Node.js/SSR):** When using Next.js, Nuxt, or Node-based Server-Side Rendering (SSR), never execute user inputs via dynamic code evaluation like `eval()`, `new Function()`, or `vm.runInContext()`.

---

## 12. Compliance & Regulatory Controls

* **GDPR / CCPA / Local Regulations:** Implement Cookie Consent Banners and Data Minimization techniques. Do not store PII (Personally Identifiable Information) unnecessarily in browser storage.
* **PCI-DSS:** If handling payments, delegate sensitive card processing directly to compliant iframe components (e.g., Stripe Elements) so card data never touches your client bundle directly.
