In **Front-End System Design**, **Logging and Monitoring** is the practice of capturing, collecting, analyzing, and visualizing client-side errors, application performance metrics, network failures, and user interactions in real time.

Because front-end applications run across thousands of untrusted user devices (varying operating systems, browser engines, network conditions, and screen sizes), client-side logging and monitoring act as the **flight data recorder** for your application. Without it, developers are completely blind to production bugs, slow page loads, memory leaks, and broken user flows.

## 1. Error Tracking & Exception Logging

Client-side errors occur in user browsers that developers cannot access directly. Error tracking automatically captures these exceptions alongside contextual metadata (browser version, OS, URL, user ID, release version, and stack traces).

### A. React Error Boundaries

React applications crash silently or display a white screen when an unhandled rendering error occurs. Use **Error Boundaries** to catch component render failures, log them to telemetry services (e.g., Sentry, Datadog, LogRocket), and render a graceful fallback UI.

```tsx
// src/components/ErrorBoundary.tsx
import React, { Component, ErrorInfo, ReactNode } from 'react';

interface Props {
  children: ReactNode;
  fallback?: ReactNode;
}

interface State {
  hasError: boolean;
}

export class ErrorBoundary extends Component<Props, State> {
  public state: State = { hasError: false };

  public static getDerivedStateFromError(_: Error): State {
    return { hasError: true };
  }

  public componentDidCatch(error: Error, errorInfo: ErrorInfo) {
    // Send error stack trace and component stack tree to logging telemetry
    console.error('Unhandled UI Error:', error, errorInfo);
    
    // Example: Dispatch to external logging service
    if (window.telemetry) {
      window.telemetry.logError(error, {
        extra: { componentStack: errorInfo.componentStack },
      });
    }
  }

  public render() {
    if (this.state.hasError) {
      return this.props.fallback || (
        <div role="alert" className="error-fallback">
          <h2>Something went wrong.</h2>
          <button onClick={() => window.location.reload()}>Reload Page</button>
        </div>
      );
    }

    return this.props.children;
  }
}

```

### B. Global Unhandled Rejection & Error Listeners

Capture errors occurring outside the React render tree (such as unhandled Promise rejections or asynchronous network script failures):

```typescript
// src/logging/globalErrorHandler.ts
export function initializeGlobalLogging() {
  // Capture unhandled JavaScript exceptions
  window.addEventListener('error', (event) => {
    reportToTelemetry({
      type: 'UNHANDLED_EXCEPTION',
      message: event.message,
      filename: event.filename,
      lineno: event.lineno,
      colno: event.colno,
      stack: event.error?.stack,
    });
  });

  // Capture rejected promises (e.g., failed async/await calls without try/catch)
  window.addEventListener('unhandledrejection', (event) => {
    reportToTelemetry({
      type: 'UNHANDLED_PROMISE_REJECTION',
      reason: event.reason?.message || event.reason,
      stack: event.reason?.stack,
    });
  });
}

```

## 2. Real User Monitoring (RUM) & Core Web Vitals

**Real User Monitoring (RUM)** continuously captures performance metrics from actual users interacting with your production application.

Monitoring focuses heavily on Google's **Core Web Vitals**:

* **LCP (Largest Contentful Paint):** Measures loading performance (Target: $\le 2.5\text{s}$).
* **INP (Interaction to Next Paint):** Measures interactivity and main-thread responsiveness (Target: $\le 200\text{ms}$).
* **CLS (Cumulative Layout Shift):** Measures visual stability (Target: $\le 0.1$).

### Measuring Core Web Vitals Programmatically

Using the official `web-vitals` library, you can log real user performance directly to your analytics pipeline:

```typescript
// src/logging/vitals.ts
import { onLCP, onINP, onCLS } from 'web-vitals';

function sendToAnalytics(metric: any) {
  const body = JSON.stringify({
    name: metric.name,
    value: metric.value,
    rating: metric.rating, // 'good' | 'needs-improvement' | 'poor'
    id: metric.id,
    navigationType: metric.navigationType,
  });

  // Use sendBeacon to ensure data is transmitted even if the page unloads
  if (navigator.sendBeacon) {
    navigator.sendBeacon('/api/v1/telemetry/vitals', body);
  } else {
    fetch('/api/v1/telemetry/vitals', {
      body,
      method: 'POST',
      keepalive: true,
      headers: { 'Content-Type': 'application/json' },
    });
  }
}

export function reportWebVitals() {
  onLCP(sendToAnalytics);
  onINP(sendToAnalytics);
  onCLS(sendToAnalytics);
}

```

## 3. Contextual Breadcrumbs & Session Replays

When an error occurs, knowing *only* the error message is often insufficient to reproduce the bug. Modern front-end monitoring tools capture **Breadcrumbs**—a chronological timeline of events leading up to the error:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         CHRONOLOGICAL BREADCRUMB TIMELINE                   │
│                                                                             │
│  [10:00:01 AM] User navigated to '/checkout'                                │
│  [10:00:03 AM] User clicked button 'Apply Promo Code'                       │
│  [10:00:04 AM] HTTP POST '/api/promo' responded with 500 Internal Error     │
│  [10:00:05 AM] ❌ Uncaught TypeError: Cannot read property 'discount'      │
└─────────────────────────────────────────────────────────────────────────────┘

```

* **Session Replay (LogRocket, Sentry Replay, FullStory):** Reconstructs a DOM-level video playback of the user's session preceding a crash, showing exact mouse movements, scroll behavior, and UI interactions without recording sensitive personal input fields.

## 4. Privacy & Performance Considerations in Front-End Logging

Client-side monitoring runs inside the user's browser, introducing two critical responsibilities:

1. **PII Scrubbing & Sanitization (Privacy):**

* **Never log sensitive data:** Passwords, credit card numbers, JWT auth tokens, or Personally Identifiable Information (PII) must be masked or scrubbed on the client *before* being sent to logging servers.
* Configure loggers to sanitize input values and Authorization headers automatically.

1. **Performance Overhead & Batching:**

* Sending an HTTP request for every single console log or click event overburdens network resources and drains mobile device battery power.
* **Batching Strategy:** Queue logs locally in memory or `IndexedDB` and send them periodically in batches using **`navigator.sendBeacon()`** (which runs asynchronously without blocking page unloads or main-thread rendering).
