**JavaScript Modules** allow you to break code into reusable, isolated files with explicit imports and exports. This prevents global scope pollution, enforces clean boundaries, and improves maintainability.

Modern JavaScript uses **ES Modules (ESM)**, introduced in ECMAScript 2015 (ES6), which is natively supported across all modern browsers and Node.js.

---

## 1. Core Concepts: `export` and `import`

Modules use `export` to expose values (functions, objects, primitives, classes) and `import` to consume them in another file.

### A. Named Exports vs. Default Exports

| Feature              | Named Exports                        | Default Exports                 |
| -------------------- | ------------------------------------ | ------------------------------- |
| **Exports per file** | Multiple per file                    | Maximum **1** per file          |
| **Import Syntax**    | Requires curly braces `{ name }`     | No curly braces `name`          |
| **Naming on Import** | Must match export name (or use `as`) | Can be renamed freely on import |

---

### B. Named Exports Example

```javascript
// mathUtils.js - Exposing multiple named utilities
export const PI = 3.14159;

export function add(a, b) {
  return a + b;
}

export function multiply(a, b) {
  return a * b;
}

```

```javascript
// app.js - Importing specific named utilities
import { PI, add, multiply } from './mathUtils.js';

console.log(add(5, 10)); // 15
console.log(multiply(2, PI)); // 6.28318

```

---

### C. Default Exports Example

```javascript
// Logger.js - Single primary export
export default class Logger {
  log(message) {
    console.log(`[LOG]: ${message}`);
  }
}

```

```javascript
// app.js - Import default export (no curly braces, can rename freely)
import CustomLogger from './Logger.js';

const logger = new CustomLogger();
logger.log("App initialized");

```

---

### D. Combining Named and Default Exports

```javascript
// User.js
export default class User {
  constructor(name) {
    this.name = name;
  }
}

export const USER_ROLE_ADMIN = 'ADMIN';
export const USER_ROLE_GUEST = 'GUEST';

```

```javascript
// app.js
import User, { USER_ROLE_ADMIN, USER_ROLE_GUEST } from './User.js';

```

## 2. Advanced Import Techniques

### Renaming Imports (`as`)

```javascript
import { add as sum, multiply as product } from './mathUtils.js';

console.log(sum(10, 20)); // 30

```

### Importing Everything as a Namespace Object

```javascript
import * as MathUtils from './mathUtils.js';

console.log(MathUtils.PI);
console.log(MathUtils.add(3, 4));

```

### Re-exporting (Barrel Pattern)

Consolidate exports from multiple sub-modules into a single entry point:

```javascript
// utils/index.js
export { add, multiply } from './mathUtils.js';
export { default as Logger } from './Logger.js';

```

```javascript
// app.js
import { add, Logger } from './utils/index.js';

```

## 3. Dynamic Imports (`import()`)

Static imports (`import ... from ...`) are loaded at boot time. **Dynamic imports** load modules asynchronously on demand, returning a Promise. This enables **code splitting** and faster initial page load times.

```javascript
// app.js
const button = document.getElementById("analytics-btn");

button.addEventListener("click", async () => {
  try {
    // Module is downloaded ONLY when the button is clicked
    const { trackEvent } = await import("./analytics.js");
    trackEvent("Button Clicked");
  } catch (error) {
    console.error("Failed to load analytics module:", error);
  }
});

```

## 4. Running Modules in Browsers & Node.js

### A. In HTML (Browser)

Include `type="module"` in your `<script>` tag. Browser modules are automatically executed in **strict mode** (`"use strict"`) and deferred until HTML parsing completes.

```html
<script type="module" src="app.js"></script>

```

### B. In Node.js

To use ES Modules in Node.js (v12+):

1. Add `"type": "module"` to your project's `package.json`.
2. Or use the `.mjs` file extension (e.g., `app.mjs`).

## 5. ES Modules (ESM) vs CommonJS (CJS)

| Feature                  | ES Modules (ESM)                 | CommonJS (CJS)                 |
| ------------------------ | -------------------------------- | ------------------------------ |
| **Syntax**               | `import` / `export`              | `require()` / `module.exports` |
| **Environment**          | Native Browsers & Modern Node.js | Legacy Node.js                 |
| **Module Resolution**    | Asynchronous / Static analysis   | Synchronous / Dynamic runtime  |
| **Tree Shaking Support** | ✅ Excellent (Dead code removal)  | ❌ Poor                         |
| **Top-Level `await**`    | ✅ Supported                      | ❌ Not Supported                |

Explain Top-Level await in ES Modules with code examples

**Top-Level `await**` allows developers to use the `await` keyword directly at the top level of an **ES Module** without wrapping it inside an `async` function or an Immediately Invoked Function Expression (IIFE).

It enables modules to act like big async functions: an ES Module that uses top-level `await` will pause its execution—and delay the execution of any parent modules importing it—until the awaited Promise resolves.

---

## 1. Why Top-Level `await` Was Introduced

Prior to Top-Level `await`, JavaScript required all asynchronous operations to be enclosed within `async` functions:

```javascript
// ❌ Old Way (Required IIFE wrapper to use await)
import { connectDB } from './db.js';

(async () => {
  const db = await connectDB();
  db.query('SELECT * FROM users');
})();

```

If another module imported this file, it had no native way of knowing when the database connection finished initializing, leading to race conditions. Top-Level `await` solves this by orchestrating module loading dependency trees asynchronously.

---

## 2. Practical Use Cases & Code Examples

### A. Dynamic Resource Initialization (e.g., Database / WebSockets)

A module can pause its export execution until a remote resource or connection is fully initialized.

```javascript
// dbConnection.js
import { createConnection } from 'database-driver';

console.log('1. Initiating DB connection...');

// Pauses execution of dbConnection.js until connected
export const db = await createConnection({
  host: 'localhost',
  port: 5432,
});

console.log('2. DB connection established successfully!');

```

```javascript
// app.js
import { db } from './dbConnection.js';

// Guaranteed to run ONLY AFTER db connection is ready
const users = await db.query('SELECT * FROM users');
console.log('3. Fetched users:', users);

```

---

### B. Dynamic Module Fallbacks / Conditional Loading

Load dependencies conditionally based on runtime environments or network availability:

```javascript
// i18n.js
let messages;

try {
  // Attempt to fetch dynamic translation file over network
  const response = await fetch('/api/translations/es');
  messages = await response.json();
} catch (error) {
  console.warn('Network failed. Falling back to local default translations.');
  // Dynamic import fallback
  const fallback = await import('./locales/en.js');
  messages = fallback.default;
}

export { messages };

```

---

### C. Environment Initialization & Feature Detection

Prepare configuration objects asynchronously before export:

```javascript
// config.js
const processEnv = typeof process !== 'undefined' ? process.env : {};

// Fetch remote configuration flags before exporting
const configResponse = await fetch('/api/config');
const remoteConfig = await configResponse.json();

export const CONFIG = {
  apiUrl: remoteConfig.API_URL || processEnv.API_URL || 'https://fallback.example.com',
  enableFeatureX: remoteConfig.FLAGS?.FEATURE_X ?? false,
};

```

## 3. How Top-Level `await` Affects Module Loading Order

Top-level `await` blocks the execution of dependent child and parent modules, but **it does not block sibling module downloads**.

When module `A` imports module `B` (which uses top-level `await`) and module `C`:

1. `B` and `C` are fetched and evaluated in parallel.
2. `B` pauses its own execution at the `await` statement.
3. `A` waits for `B`'s promise to resolve before executing `A`'s main code body.

```text
       ┌───────────┐
       │   app.js  │  (Waits for db.js to resolve)
       └─────┬─────┘
             │
   ┌─────────┴─────────┐
   ▼                   ▼
┌────────┐        ┌────────┐
│  db.js │        │ util.js│
└────────┘        └────────┘
(Top-Level
 Await)

```

## 4. Error Handling with `try...catch`

If a top-level `await` promise rejects, the entire module fails to evaluate, throwing an error up the module dependency tree. Wrap top-level `await` calls in `try...catch` blocks to handle rejections gracefully:

```javascript
// dataService.js
export let data;

try {
  const response = await fetch('https://api.example.com/data');
  if (!response.ok) throw new Error(`HTTP Error ${response.status}`);
  data = await response.json();
} catch (error) {
  console.error('Failed to load initial data:', error.message);
  data = []; // Fallback value
}

```

## 5. Environment & Compatibility Requirements

Top-Level `await` is supported out of the box in:

* **Browsers:** All modern evergreen browsers (Chrome 89+, Safari 15+, Firefox 89+, Edge 89+).
* **Node.js:** Node.js v14.8+ (when using ES Modules via `"type": "module"` in `package.json` or `.mjs` files).
* **Bundlers:** Vite, Webpack 5+, Rollup, and Esbuild natively support top-level `await`.

Explain Dynamic Imports and Code Splitting in JavaScript with code examples

**Dynamic Imports** and **Code Splitting** are performance optimization techniques in JavaScript. They allow you to split your application's bundle into smaller chunks and load them on demand (lazily) rather than sending one massive JavaScript file to the user up front.

This reduces the initial page bundle size, speeds up **Initial Page Load** and **Time to Interactive (TTI)**, and saves user bandwidth.

---

## 1. Static vs. Dynamic Imports

* **Static Import (`import x from 'y'`):** Loaded synchronously at the top of a file during initial module evaluation. All code imported statically is bundled together into the main JavaScript entry file.
* **Dynamic Import (`import('y')`):** A function-like expression that loads an ES Module asynchronously. It returns a **Promise** that resolves to the module object, triggering code bundlers (like Vite, Webpack, or Rollup) to split that file into a separate "chunk".

---

## 2. Basic Dynamic Import Syntax

```javascript
// math.js - A separate utility module
export function calculateHeavyData(data) {
  return data.map(x => x * 42);
}

export function unusedHelper() {
  console.log("This won't be loaded until requested!");
}

```

```javascript
// app.js - Main Application Entry
const button = document.getElementById("process-btn");

button.addEventListener("click", async () => {
  try {
    // 1. Module is downloaded over the network ONLY when the user clicks the button
    const mathModule = await import("./math.js");

    // 2. Call the exported functions on the returned module object
    const result = mathModule.calculateHeavyData([1, 2, 3]);
    console.log("Calculation Result:", result);

  } catch (error) {
    console.error("Failed to dynamically load module:", error);
  }
});

```

## 3. Common Use Cases for Code Splitting

### A. Route-Based Code Splitting

In Single Page Applications (SPAs), users don't need the code for the `/admin` dashboard or `/settings` page when visiting the home page (`/`).

```javascript
// router.js
const routes = {
  "/": () => import("./pages/Home.js"),
  "/dashboard": () => import("./pages/Dashboard.js"),
  "/settings": () => import("./pages/Settings.js"),
};

async function navigate(path) {
  const loadPage = routes[path];

  if (loadPage) {
    // Show a loading spinner UI
    showSpinner();

    // Dynamically fetch and execute only the route component needed
    const pageModule = await loadPage();
    pageModule.render();

    hideSpinner();
  }
}

// User navigates to dashboard
navigate("/dashboard");

```

---

### B. Heavy Third-Party Library Lazy Loading

If your application uses heavy libraries (like Chart.js, PDF generators, or rich text editors), defer downloading them until the user explicitly triggers that feature.

```javascript
// pdfExporter.js
document.getElementById("export-pdf-btn").addEventListener("click", async () => {
  // Download pdfmake library (~500KB) only when user clicks "Export PDF"
  const { default: pdfMake } = await import("pdfmake/build/pdfmake");
  const { default: pdfFonts } = await import("pdfmake/build/vfs_fonts");

  pdfMake.vfs = pdfFonts.pdfMake.vfs;

  const docDefinition = { content: 'Dynamic PDF Document Generation' };
  pdfMake.createPdf(docDefinition).download("export.pdf");
});

```

---

### C. Conditional Feature Loading (e.g., Mobile vs. Desktop)

```javascript
async function loadDeviceSpecificUI() {
  if (window.innerWidth < 768) {
    // Load lightweight mobile navigation drawer
    const { initMobileNav } = await import("./mobileNav.js");
    initMobileNav();
  } else {
    // Load full desktop sidebar widget
    const { initDesktopSidebar } = await import("./desktopSidebar.js");
    initDesktopSidebar();
  }
}

loadDeviceSpecificUI();

```

## 4. Code Splitting in Modern Frameworks

### React (`React.lazy` & `Suspense`)

```jsx
import React, { Suspense, lazy } from 'react';

// Lazy load the heavy chart component
const HeavyAnalyticsChart = lazy(() => import('./HeavyAnalyticsChart'));

function Dashboard() {
  return (
    <div>
      <h1>User Dashboard</h1>

      {/* Render fallback loader while HeavyAnalyticsChart chunk downloads */}
      <Suspense fallback={<div>Loading Chart...</div>}>
        <HeavyAnalyticsChart />
      </Suspense>
    </div>
  );
}

```

## 5. Preloading and Prefetching Chunks

You can give hints to the browser to download dynamic chunks during idle time before the user actually clicks a button:

### Webpack Magic Comments

```javascript
// Prefetch: Downloads in the background during browser idle time
const ChartModule = await import(
  /* webpackPrefetch: true */ 
  './HeavyChart.js'
);

// Preload: Downloads in parallel with the parent chunk
const CriticalModule = await import(
  /* webpackPreload: true */ 
  './CriticalModal.js'
);

```

## Summary Comparison

| Metric                 | Static Imports                                    | Dynamic Imports                                  |
| ---------------------- | ------------------------------------------------- | ------------------------------------------------ |
| **Loading Mechanism**  | Synchronous at startup.                           | Asynchronous on-demand.                          |
| **Bundle Impact**      | All code merged into 1 bundle.                    | Code split into multiple `.js` chunks.           |
| **Initial Load Speed** | Slower (larger file download).                    | Faster (minimal core bundle).                    |
| **Best Used For**      | Core app shell, shared utilities, framework code. | Modals, heavy charts, route pages, export tools. |
