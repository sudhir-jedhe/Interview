## Part 1: Beginner Functions

### 1. What are Functions?

A function is a reusable block of code designed to perform a specific task. They prevent code duplication and help organize logic. Functions execute only when they are **invoked** (called).

```javascript
// Function Declaration
function greet() {
  console.log("Hello, welcome to JavaScript!");
}

```

### 2. Calling (Invoking) Functions

You execute a function by appending parentheses `()` to its name.

```javascript
greet(); // Executes the function and logs: "Hello, welcome to JavaScript!"

```

### 3. Function Parameters

Parameters act as named placeholders defined in the function signature to receive input data.

```javascript
function greetUser(userName) { // 'userName' is a parameter
  console.log(`Hello, ${userName}!`);
}

```

### 4. Function Return Values

Functions use the `return` statement to send a calculated value back to the caller and halt execution within the function body.

```javascript
function add(a, b) {
  return a + b; // Returns the sum and exits the function
}

const sum = add(5, 10); // sum holds the value 15

```

---

## Part 2: Intermediate Functions

### 5. Function Parameters vs. Arguments

* **Parameters:** The variable names listed in the function definition signature (`a`, `b`).
* **Arguments:** The actual values passed into the function when invoking it (`5`, `10`).

```javascript
function multiply(x, y) { // x, y are Parameters
  return x * y;
}

multiply(4, 3); // 4, 3 are Arguments

```

### 6. Function Expressions

A function can be defined and assigned to a variable. Unlike function declarations, function expressions are **not hoisted** (cannot be called before their definition line).

```javascript
const calculateArea = function(width, height) {
  return width * height;
};

console.log(calculateArea(5, 4)); // 20

```

### 7. Arrow Functions

Introduced in ES6, arrow functions provide a concise syntax for function expressions.

```javascript
// 1. Standard Arrow Function
const double = (num) => {
  return num * 2;
};

// 2. Concise Syntax (Omitting curly braces & implicit return for single expressions)
const doubleConcise = num => num * 2;

console.log(doubleConcise(5)); // 10

```

### Step 2: JavaScript Callbacks

A **callback** is a function passed as an argument to another function, intended to be executed later.

```javascript
function fetchData(callback) {
  setTimeout(() => {
    const data = { id: 1, name: "Alice" };
    callback(data); // Executing the callback function
  }, 1000);
}

// Passing an inline function as a callback
fetchData((user) => {
  console.log("Data received for:", user.name);
});

```

### Step 3: The `this` Keyword

The value of `this` inside a standard function is determined by **how the function is invoked**:

1. **In an Object Method:** `this` refers to the owner object.
2. **Standalone Function:** `this` refers to the global object (`window` in browsers, `global` in Node.js) or `undefined` in strict mode (`"use strict"`).
3. **In Arrow Functions:** Arrow functions **do not have their own `this**`. They inherit `this` lexically from the surrounding scope.

```javascript
const user = {
  name: "Bob",
  // Standard method: 'this' refers to user object
  greetStandard() {
    console.log(`Hi, I'm ${this.name}`);
  },
  // Arrow method: 'this' inherits from outer scope (Window/Global)
  greetArrow: () => {
    console.log(`Hi, I'm ${this.name}`);
  }
};

user.greetStandard(); // "Hi, I'm Bob"
user.greetArrow();    // "Hi, I'm undefined"

```

---

### Steps 4, 5 & 6: Explicit Binding (`call`, `apply`, `bind`)

These built-in methods allow you to explicitly set the context of `this` when invoking a function.

```javascript
function introduce(greeting, punctuation) {
  console.log(`${greeting}, I'm ${this.name}${punctuation}`);
}

const person = { name: "Charlie" };

// 1. call(): Invokes function immediately with arguments passed INDIVIDUALLY
introduce.call(person, "Hello", "!"); 
// Output: "Hello, I'm Charlie!"

// 2. apply(): Invokes function immediately with arguments passed as an ARRAY
introduce.apply(person, ["Hey", "."]); 
// Output: "Hey, I'm Charlie."

// 3. bind(): Returns a NEW function with 'this' permanently bound for LATER invocation
const boundIntroduce = introduce.bind(person, "Welcome");
boundIntroduce("!!!"); 
// Output: "Welcome, I'm Charlie!!!"

```

---

### Step 7: Self-Invoking Functions (IIFE)

An **Immediately Invoked Function Expression (IIFE)** executes as soon as it is defined. It creates a private lexical scope, avoiding global namespace pollution.

```javascript
(function() {
  const privateSecret = "12345";
  console.log("IIFE executed immediately!");
})();

// console.log(privateSecret); // ReferenceError: privateSecret is not defined

```

---

### Step 8: JavaScript Closures

A **closure** is a function that retains access to variables from its outer (enclosing) scope even after the outer function has finished executing.

```javascript
function createCounter() {
  let count = 0; // Private outer variable

  return function() {
    count++; // Accesses 'count' from outer lexical scope
    return count;
  };
}

const counter = createCounter();

console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3

```

---

### Step 9: Function Reference, Methods & Properties

In JavaScript, **functions are First-Class Objects**. They can be assigned to variables, passed as arguments, returned from other functions, and possess built-in properties and methods.

```javascript
function sampleFunction(a, b, c) {}

// Properties
console.log(sampleFunction.name);   // "sampleFunction" (Function name string)
console.log(sampleFunction.length); // 3 (Number of expected parameters)

// Methods inherited from Function.prototype
console.log(typeof sampleFunction.toString); // "function"
console.log(sampleFunction.toString());     // "function sampleFunction(a, b, c) {}"

```

## 3 Important Function Behavior Details

### 1. Function Call vs. Function Reference

Passing parentheses executes the function. Omitting parentheses passes the function as a value (a reference), which is how callbacks work:

```javascript
function getGreeting() {
  return "Hello!";
}

let result = getGreeting(); // Executed! 'result' stores the string "Hello!"
let reference = getGreeting; // NOT executed! 'reference' stores the getGreeting function object

```

### 2. Default Return Value (`undefined`)

If a function does not contain an explicit `return` statement (or uses a bare `return;`), it automatically returns `undefined`:

```javascript
function logMessage(msg) {
  console.log(msg);
  // No return statement here
}

let output = logMessage("Test"); // Logs "Test"
console.log(output);            // Output: undefined

```

### 3. Missing Arguments vs. Extra Arguments

JavaScript does not throw an error if you pass fewer or more arguments than defined parameters:

* **Fewer arguments:** Unsupplied parameters default to `undefined`.
* **Extra arguments:** Additional inputs are accepted without error and can be accessed via the `arguments` object or rest parameters (`...args`).

```javascript
function add(a, b) {
  return a + b;
}

console.log(add(5));       // NaN (because 5 + undefined = NaN)
console.log(add(5, 5, 20)); // 10 (ignores 20)

```

What is the difference between Function Declarations and Function Expressions in JavaScript, especially regarding hoisting?

The core difference between **Function Declarations** and **Function Expressions** in JavaScript lies in **syntax**, **when they are created**, and **how the JavaScript engine handles Hoisting**.

---

## 1. Syntax Comparison

### Function Declaration

A Function Declaration is a standalone statement that uses the `function` keyword, followed by a mandatory function name.

```javascript
function greet() {
  return "Hello!";
}

```

### Function Expression

A Function Expression creates a function inside an expression (typically by assigning an anonymous or named function to a variable).

```javascript
const greet = function() {
  return "Hello!";
};

```

---

## 2. Hoisting Behavior (The Key Difference)

**Hoisting** is JavaScript's default behavior of moving declarations to the top of their containing scope during the compilation phase before code execution.

### Function Declarations are Fully Hoisted

Both the **function name and the entire function implementation** are hoisted to the top of the scope. This means you can invoke a Function Declaration **before** it appears in your source code.

```javascript
// ✅ Works perfectly!
console.log(sayHello()); // Output: "Hello World"

function sayHello() {
  return "Hello World";
}

```

**How JS interprets it:**

```javascript
// During compilation phase:
function sayHello() {
  return "Hello World";
}

// During execution phase:
console.log(sayHello());

```

---

### Function Expressions are NOT Hoisted (Variable Hoisting Rules Apply)

When you assign a function to a variable (`const`, `let`, or `var`), **only the variable declaration is hoisted, not the function assignment itself**.

#### With `const` or `let`

Variables declared with `const` or `let` stay in the **Temporal Dead Zone (TDZ)** from the start of the block until the execution reaches the definition line. Calling them early throws a `ReferenceError`.

```javascript
// ❌ ReferenceError: Cannot access 'sayHello' before initialization
console.log(sayHello()); 

const sayHello = function() {
  return "Hello World";
};

```

#### With `var`

Variables declared with `var` are hoisted with an initial value of `undefined`. Calling them before initialization throws a `TypeError` because `undefined` is not a function.

```javascript
// ❌ TypeError: sayHello is not a function
console.log(sayHello()); 

var sayHello = function() {
  return "Hello World";
};

```

---

## 3. Scope & Block-Level Behavior

In modern JavaScript (ES6+), Function Declarations inside code blocks (`if`, `for`, `{}`) are **block-scoped**.

```javascript
if (true) {
  function doSomething() {
    return "Inside block";
  }
}

// In strict mode / ES6 environment, block-scoped declarations aren't accessible outside
console.log(doSomething()); // Works in some legacy non-strict browsers, but throws ReferenceError in strict mode

```

Function Expressions assigned to `let` or `const` strictly adhere to block scoping rules without ambiguity:

```javascript
if (true) {
  const doSomething = function() {
    return "Inside block";
  };
}

// ❌ ReferenceError: doSomething is not defined
console.log(doSomething()); 

```

---

## Comparison Matrix

| Feature              | Function Declaration                           | Function Expression                                      |
| -------------------- | ---------------------------------------------- | -------------------------------------------------------- |
| **Syntax**           | `function foo() {}`                            | `const foo = function() {};`                             |
| **Hoisting**         | **Fully hoisted** (can call before definition) | **Not hoisted** (throws `ReferenceError` or `TypeError`) |
| **Name Requirement** | Mandatory                                      | Optional (anonymous) or Named                            |
| **When Created**     | During script/scope compilation                | When execution reaches the code line                     |
| **Use Cases**        | Top-level utility functions, main API helpers  | Callbacks, conditionally defined functions, closures     |

---

## Which Should You Use?

* **Use Function Declarations** when writing primary, top-level utility functions or helper functions that you want available throughout your module or script regardless of declaration order.
* **Use Function Expressions (or Arrow Functions)** when assigning callbacks, passing functions as arguments to higher-order functions (`map`, `filter`), or enforcing strict top-to-bottom variable initialization order.

What are the key differences between standard Function Expressions and Arrow Functions in JavaScript?

The primary difference between standard function expressions and arrow functions in JavaScript boils down to syntax, `this` binding, and how they behave as constructors or arguments.

| Feature                  | Function Expression                                  | Arrow Function                                                   |
| ------------------------ | ---------------------------------------------------- | ---------------------------------------------------------------- |
| **Syntax**               | Verbose (`function() {}`)                            | Concisions (`() => {}`), implicit returns for single expressions |
| **`this` Binding**       | **Dynamic**: Defined by *how* the function is called | **Lexical**: Inherits `this` from surrounding scope              |
| **`arguments` Object**   | Available natively inside function                   | Not available (use rest parameters `...args` instead)            |
| **Constructor Usage**    | Can be used with `new`                               | Cannot be used with `new` (throws `TypeError`)                   |
| **`prototype` Property** | Has a `prototype` property                           | Does not have a `prototype` property                             |
| **Duplicate Parameters** | Allowed in non-strict mode                           | Syntax error always                                              |

---

### Key Technical Breakdown

#### 1. `this` Binding (The Most Critical Difference)

Standard function expressions create their own `this` context depending on execution context (e.g., global object, method owner, or `undefined` in strict mode). Arrow functions do **not** have their own `this`; they bind `this` lexically from the enclosing execution context.

```javascript
// Standard Function: 'this' changes based on caller
const obj = {
  count: 10,
  incrementLater: function() {
    setTimeout(function() {
      // 'this' refers to Timeout/Window, not 'obj'
      console.log(this.count); // undefined
    }, 100);
  }
};

// Arrow Function: Lexical 'this' captured from surrounding scope
const objArrow = {
  count: 10,
  incrementLater: function() {
    setTimeout(() => {
      // 'this' inherits directly from objArrow
      console.log(this.count); // 10
    }, 100);
  }
};

```

#### 2. Constructor & Prototype Behavior

Function expressions can act as constructors using the `new` keyword. Arrow functions cannot be instantiated and lack a `prototype` property.

```javascript
const Standard = function() {};
const instance = new Standard(); // Works

const Arrow = () => {};
const failedInstance = new Arrow(); // TypeError: Arrow is not a constructor

```

#### 3. Arguments Object

Standard functions expose a local `arguments` array-like object containing passed parameters. Arrow functions lack this object; accessing it will look up the scope chain or throw an error. Use ES6 rest parameters instead.

```javascript
// Standard Function
function showArgs() {
  console.log(arguments[0]); // 1
}
showArgs(1, 2);

// Arrow Function
const showArgsArrow = (...args) => {
  console.log(args[0]); // 1
};
showArgsArrow(1, 2);

```

#### 4. Implicit Returns

Arrow functions allow concise single-expression returns without using the `return` keyword or curly braces `{}`.

```javascript
// Standard
const add = function(a, b) {
  return a + b;
};

// Arrow (Implicit return)
const addArrow = (a, b) => a + b;

// Arrow returning an object implicitly requires parentheses
const makeObj = (key, val) => ({ [key]: val });

```

---

### When to Use Which?

* **Use Arrow Functions for:** Callbacks (`map`, `filter`, `reduce`), inline event handlers where you want lexical `this`, array methods, and short utility functions.
* **Use Function Expressions for:** Object methods requiring dynamic `this`, constructor functions/classes, dynamic function scoping, and functions requiring standard `arguments` access.

Are there performance differences between standard function expressions and arrow functions in V8?

In modern V8 engines (Chrome, Node.js), **there is no meaningful performance difference** between standard function expressions and arrow functions for typical execution and run-time speed.

V8 compiles both syntax constructs into the same underlying bytecode representation, so once optimized by TurboFan (V8's optimizing compiler), the engine executes both at virtually identical speeds.

---

### Key Technical Breakdown

#### 1. Execution Speed & Micro-benchmarks

* **In-line execution:** Simple function calls perform identically whether written as `function() {}` or `() => {}`.
* **Method invocation:** A method called on an object executes at the same speed regardless of how it was declared.

#### 2. Creation / Allocation Overhead

* **Creation cost:** Instantiating an arrow function vs. a standard function expression in a tight loop takes virtually the same amount of CPU time and memory allocation.
* **Prototype allocation:** Standard function expressions automatically allocate a `prototype` object property upon creation, whereas arrow functions do not. While this makes arrow functions *negligibly* smaller in object allocation footprint, TurboFan and V8's memory allocators make this difference completely unnoticeable in practice.

```javascript
// Creates a function + prototype object
const fn = function() {}; 
console.log(fn.prototype); // { constructor: f }

// Creates ONLY a function (no prototype property)
const arrow = () => {}; 
console.log(arrow.prototype); // undefined

```

#### 3. Scope & `this` Overhead

* **Lexical Scope Resolution:** An arrow function closes over `this` lexically. In V8, accessing a closed-over `this` inside an arrow function uses standard context lookup—the same mechanism as closing over any regular variable (`const self = this`).
* **Explicit Binding:** Standard function expressions bound via `.bind(this)` are actually **slower** than equivalent arrow functions because `.bind()` creates a bound function exotic object and adds an extra layer of invocation overhead in V8.

```javascript
// SLOWER: .bind() creates extra wrapper object & function overhead
element.addEventListener('click', this.handleClick.bind(this));

// FASTER / PREFERRED: Lexical arrow function is lighter than .bind()
element.addEventListener('click', (e) => this.handleClick(e));

```

---

### Real-World Guidance

| Scenario                               | Performance Impact                                                                                                                                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Inline Callbacks (`map`, `filter`)** | Identical performance. Use arrow functions for clean syntax.                                                                                                                             |
| **Arrow vs `.bind(this)**`             | **Arrow functions are faster.** Avoid using `.bind()` in hot code paths.                                                                                                                 |
| **Class Properties vs Methods**        | Class methods (`handleClick() {}`) share prototype functions and save memory compared to class fields (`handleClick = () => {}`), which re-create function instances per class instance. |

Explain self-invoked functions (IIFEs) in JavaScript with examples.
An **IIFE** (Immediately Invoked Function Expression) — often referred to as a self-invoked function — is a JavaScript function that runs automatically as soon as it is defined.

---

### Anatomy of an IIFE

To make a function run immediately upon definition, wrap the function inside grouping parentheses `()` to convert it into an expression, then append invocation parentheses `()` to call it instantly:

```javascript
(function() {
  console.log("I run immediately!");
})();

```

#### Why the grouping parentheses `()` are required

In JavaScript, starting a line with the keyword `function` forces the engine to parse it as a **Function Declaration**, which requires a name and cannot be invoked on the spot. Wrapping it in `()` tells the JavaScript parser to evaluate it as a **Function Expression**, which can be invoked right away.

---

### Key Variations & Examples

#### 1. Arrow Function IIFE

Modern JavaScript lets you write concise IIFEs using ES6 arrow functions:

```javascript
(() => {
  console.log("Arrow function IIFE executed!");
})();

```

#### 2. Passing Arguments to an IIFE

You can pass values into an IIFE via the trailing invocation parentheses:

```javascript
(function(appName, version) {
  console.log(`Initializing ${appName} v${version}`);
})("MyDashboard", "2.1.0");
// Output: Initializing MyDashboard v2.1.0

```

#### 3. Assigning the Return Value

An IIFE can return a value directly to a variable:

```javascript
const result = (() => {
  const a = 10;
  const b = 20;
  return a + b; // Complex setup logic stays encapsulated
})();

console.log(result); // 30

```

---

### Primary Use Cases

#### 1. Avoiding Global Scope Pollution (Data Privacy)

Variables declared inside an IIFE exist only within its inner execution scope and cannot leak into the global scope:

```javascript
(() => {
  // Temporary setup variable
  let counter = 0;
  console.log("Setup completed.");
})();

// Attempting to access 'counter' outside throws an error:
// console.log(counter); // ReferenceError: counter is not defined

```

#### 2. The Module Pattern (Private Variables & Public API)

Before ES6 modules (`import`/`export`) became native, IIFEs were the standard way to create private scope with exposed methods:

```javascript
const CounterModule = (() => {
  let count = 0; // Private state

  return {
    increment: () => ++count,
    decrement: () => --count,
    getCount: () => count
  };
})();

console.log(CounterModule.getCount()); // 0
CounterModule.increment();
console.log(CounterModule.getCount()); // 1
// CounterModule.count is undefined (protected from outside modification)

```

#### 3. Top-Level `async` Setup

Before top-level `await` was supported across environments, IIFEs were standard for executing `async/await` code at script startup:

```javascript
(async () => {
  const response = await fetch("https://api.github.com/users/octocat");
  const data = await response.json();
  console.log(data.name);
})();

```

>
> ```javascript

Both **ES6 Modules (ESM)** and **Immediately Invoked Function Expressions (IIFEs)** are techniques used in JavaScript to encapsulate scope and manage state, but they belong to different eras of JavaScript development and operate at different structural levels.

Here is a side-by-side comparison of how they handle scoping, state management, and modern relevance.

---

### Key Comparisons

| Feature                   | ES6 Modules (ESM)                                               | IIFEs (Pattern)                                                                  |
| ------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Primary Level**         | **File / Module Level** (Native runtime construct)              | **Function / Execution Level** (Pattern using standard functions)                |
| **Scope Creation**        | Automatically top-level module scope (implicit strict mode)     | Function scope created upon immediate execution                                  |
| **State Encapsulation**   | Top-level variables remain private unless explicitly `export`ed | Variables inside the outer function remain private via closure                   |
| **Public API**            | Explicitly defined via `export` / `import`                      | Explicitly returned as an object or attached to a global scope                   |
| **Execution**             | Executed once when imported; singletons by default              | Executed immediately where defined                                               |
| **Dependency Management** | Built-in module graph resolution (`import`/`export`)            | Manual order of script tags or explicit parameters passed in                     |
| **Modern Usage**          | **Standard** for code organization, libraries, and applications | Niche use cases (e.g., inline scripts, isolated quick blocks, dynamic execution) |

---

### Scope & State Encapsulation

#### IIFE (Immediately Invoked Function Expression)

An IIFE leverages JavaScript’s function scope to create a private boundary, preventing variable leakage into the global scope. State is preserved using **closures**.

```javascript
const CounterModule = (function () {
  // Private state
  let count = 0;

  // Public API exposed via closure
  return {
    increment() {
      count++;
      return count;
    },
    getCount() {
      return count;
    }
  };
})();

CounterModule.increment(); // 1
console.log(CounterModule.count); // undefined (private)

```

* **Pros:** Works in every JavaScript engine ever created; doesn't require build tools or specific script attributes.
* **Cons:** Managing dependencies between multiple IIFEs requires careful order of `<script>` tags, making large-scale state architecture prone to `ReferenceError`s and global namespace pollution (e.g., hanging `CounterModule` on `window`).

---

#### ES6 Modules (ESM)

ES6 Modules introduce official, language-level module scope. Every ESM file operates in its own strict-mode scope by default.

```javascript
// counter.js
// Private state (scoped to this file)
let count = 0;

// Public exports
export function increment() {
  count++;
  return count;
}

export function getCount() {
  return count;
}

```

```javascript
// main.js
import { increment, getCount } from './counter.js';

increment(); // 1
console.log(count); // ReferenceError: count is not defined

```

* **Live Bindings:** Unlike IIFE object returns (which return copies of primitive values), ESM exports **live bindings**. If internal state changes inside `counter.js`, importing modules see the updated value in real-time.
* **Singleton State:** A module is loaded and executed only **once**. Multiple imports across an application share the same underlying state within that module file.

---

### Modern Context & Verdict

1. **Architecture & Bundling:** Modern Web development (Node.js, React, Vite, Webpack) relies entirely on **ES6 Modules**. Tree-shaking, code-splitting, and static dependency analysis are only possible with ESM's static `import`/`export` syntax.
2. **Where IIFEs Still Exist:**

* **Bundler Output Target:** Tools like Rollup or Esbuild often compile ESM source code down to IIFEs when generating a single, standalone `<script>` file for browsers that need zero external dependency lookups.
* **Bookmarklets & Injected Scripts:** When executing isolated code snippets (e.g., via browser extensions or browser console scripts) without polluting the host page's global namespace.
* **Top-Level `async` Workarounds:** Before top-level `await` was natively supported in ESM, developers wrapped asynchronous setup logic inside `(async () => { ... })()`.

**Summary:** Use **ES6 Modules** as your default approach for organizing applications, sharing state across files, and writing maintainable code. Reserve **IIFEs** for specific runtime utility scripts, legacy browser targets, or isolated inline execution blocks.

### Parameters vs. Arguments

---

### JavaScript's Parameter Rules

1. **No Data Types:** JavaScript does not enforce parameter types (e.g., you cannot strictly declare that a parameter must be a `number` or `string` natively).
2. **No Type Checking:** Passing a string where a number is expected will not throw a type error automatically; it may result in string concatenation or `NaN`.
3. **No Count Checking:** JavaScript does not throw an error if you pass fewer or more arguments than the function declared parameters for.

---

### What Happens with Missing or Incorrect Arguments?

If a parameter is omitted during invocation, its value inside the function defaults to `undefined`. Operations on `undefined` often yield unexpected results like `NaN`.

```javascript
function toCelsius(fahrenheit) {
  return (5/9) * (fahrenheit - 32);
}

// Missing argument -> fahrenheit is undefined
// (undefined - 32) evaluates to NaN
let result = toCelsius(); // returns NaN

```

---

### Default Parameter Values (ES6+)

Introduced in ECMAScript 2015, default parameters allow you to set fallback values if an argument is `undefined` or omitted when calling the function:

```javascript
// Set a default value of 32 for fahrenheit
function toCelsius(fahrenheit = 32) {
  return (5/9) * (fahrenheit - 32);
}

console.log(toCelsius());   // 0 (uses default 32)
console.log(toCelsius(77)); // 25 (uses provided argument 77)

```

#### Handling Multiple Default Parameters

function greet(name = "Guest", greeting = "Hello") {

}

### Core Principles of `return`

#### 1. Sends Data Back to the Caller

The `return` keyword passes a calculated value, object, string, array, or primitive out of the function so it can be assigned to a variable, used in expressions, or passed to other functions.

```javascript
function fullName(firstName, lastName) {
  return firstName + " " + lastName;
}

// Stored in a variable

// Used directly in an expression
let total = multiply(2, 3) * 10; // 6 * 10 = 60

```

---

#### 2. Immediate Execution Halt

As soon as JavaScript encounters a `return` statement, **execution stops immediately**. Any code written below it in the same block is completely ignored (unreachable code).

```javascript
function multiply(a, b) {
  return "Done";
  
  // Unreachable code (never runs)
  return a * b; 
}

console.log(multiply(4, 3)); // "Done"

```

---

#### 3. Early Returns (Guard Clauses)

You can use `return` to exit a function early based on conditions, which prevents deep `if/else` nesting.

```javascript
function checkAge(age) {
  if (age < 18) {
    return "Too young"; // Exits here if under 18
  }
  
  return "Access granted"; // Only reached if 18 or older
}

```

A **pure function** is a deterministic function that always produces the exact same output for the same input arguments and produces zero side effects outside its scope.

An **impure function** relies on or modifies state outside its local scope, or performs observable side effects (like mutating variables, making API requests, or modifying DOM elements).

---

### Key Requirements of Pure Functions

1. **Deterministic:** Given the inputs `(a, b)`, the output will *always* be identical regardless of how many times or when it is called.
2. **No Side Effects:** It does not alter external variables, mutate input parameters, log to the console, write to a database, or modify the DOM.

---

### Pure Function Examples

#### Example 1: Pure Calculation

```javascript
// Pure: Output depends solely on parameters 'a' and 'b'
function add(a, b) {
  return a + b;
}

add(2, 3); // Always returns 5
add(2, 3); // Always returns 5

```

#### Example 2: Non-mutating Array Transformation

```javascript
// Pure: Returns a new array without modifying the original input array
function addElementPure(arr, newElement) {
  return [...arr, newElement]; // Uses spread operator to keep input pristine
}

const originalList = [1, 2, 3];
const updatedList = addElementPure(originalList, 4);

console.log(originalList); // [1, 2, 3] (unmodified)
console.log(updatedList);  // [1, 2, 3, 4]

```

---

### Impure Function Examples

#### Example 1: Depending on External State

```javascript
let taxRate = 0.08; // External variable

// Impure: Result changes if external 'taxRate' is modified elsewhere
function calculateTotal(subtotal) {
  return subtotal + (subtotal * taxRate);
}

calculateTotal(100); // Returns 108

taxRate = 0.10; // State change elsewhere in the app
calculateTotal(100); // Returns 110 (Same input '100', different output)

```

#### Example 2: Mutating External State or Parameters

```javascript
const cart = ["Apple", "Banana"];

// Impure: Mutates the global 'cart' array directly
function addToCart(item) {
  cart.push(item); // Side effect: mutates external data
  return cart;
}

addToCart("Orange");

```

#### Example 3: Non-deterministic Built-in API Dependencies

Functions using `Math.random()`, `Date.now()`, or UUID generators are inherently impure because they return different values on every execution.

```javascript
// Impure: Output changes every time it runs
function generateUser(name) {
  return {
    id: Math.random(), // Non-deterministic
    createdAt: new Date(), // Depends on external system clock
    name: name
  };
}

```

#### Example 4: Performing I/O Side Effects

Modifying DOM elements, logging to the console, writing files, or making HTTP API requests are all considered side effects.

```javascript
// Impure: Modifies external DOM state directly
function updateGreeting(name) {
  document.getElementById("heading").textContent = `Hello, ${name}`;
}

```

### Feature Comparison

| Feature                         | Pure Function                                   | Impure Function                                            |
| ------------------------------- | ----------------------------------------------- | ---------------------------------------------------------- |
| **Output Determinism**          | 100% predictable based on inputs                | Can change based on time, global state, or environment     |
| **External State Dependencies** | Reads **only** from parameter inputs            | May read from global variables, DOM, or external APIs      |
| **Mutation / Side Effects**     | None                                            | May mutate inputs, update outer scope variables, or do I/O |
| **Testability**                 | Easy to unit test (no mocks or setups required) | Requires mocking external dependencies, state, or DOM      |
| **Caching / Memoization**       | Can be safely cached based on arguments         | Cannot be cached safely                                    |

### Why Pure Functions Matter in Web Development

* **Predictable State Management:** Modern UI frameworks like React, Redux, and Vue rely heavily on pure functions (e.g., Redux reducers, React functional components) to reliably detect state changes via immutable updates.
* **Refactoring & Debugging:** Pure functions are isolated units of code; you can move or debug them without worrying about hidden system dependencies.
* **Optimization (Memoization):** Because pure functions always produce the same output for a given input, expensive calculations can be cached (memoized) automatically.

Show how to implement a memoization wrapper function in JavaScript for pure functions.

Here is a generic memoization wrapper function designed for pure functions in JavaScript.

### Implementation

```javascript
/**
 * Wraps a pure function with a memoization layer to cache computed results.
 * 
 * @param {Function} fn - The pure function to memoize.
 * @param {Function} [keyGenerator] - Optional custom strategy to compute cache keys.
 * @returns {Function} Memoized version of the function.
 */
function memoize(fn, keyGenerator) {
  const cache = new Map();

  return function (...args) {
    // Determine key: use custom generator or default to JSON stringifying args
    const key = keyGenerator ? keyGenerator(...args) : JSON.stringify(args);

    if (cache.has(key)) {
      return cache.get(key);
    }

    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

```

---

### Basic Usage Example

```javascript
// A costly pure function
function fibonacci(n) {
  if (n <= 1) return n;
  return memoizedFib(n - 1) + memoizedFib(n - 2);
}

// Memoize the function
const memoizedFib = memoize(fibonacci);

console.time("First Execution");
console.log(memoizedFib(40)); // Computes value
console.timeEnd("First Execution"); // ~100-200ms

console.time("Cached Execution");
console.log(memoizedFib(40)); // Fetches directly from cache
console.timeEnd("Cached Execution"); // ~0.01ms

```

---

### Handling Complex Arguments & Objects

By default, `JSON.stringify(args)` handles basic primitives and arrays well. However, for functions accepting complex objects, DOM nodes, or functions as parameters, pass a custom key generator:

```javascript
const getUserFullName = memoize(
  (user) => `${user.firstName} ${user.lastName}`,
  (user) => user.id // Custom key based on unique ID instead of full object serialization
);

const user = { id: 101, firstName: "Ada", lastName: "Lovelace" };
console.log(getUserFullName(user)); // Computes
console.log(getUserFullName(user)); // Cache hit

```

---

### Key Features of this Pattern

1. **Closure Scoped Cache:** The `cache` variable (a native `Map`) remains isolated inside the closure created by `memoize`, preventing global pollution.
2. **Context Preservation:** Uses `fn.apply(this, args)` so `this` references are maintained correctly if the function is a method on an object or class instance.
3. **Pure Function Requirement:** This works exclusively for **pure functions**—functions that produce the exact same return value given the same arguments and have zero side effects.

## Key Modern JS Additions

### 1. Modern Alternative: `arguments` vs. Rest Parameters (`...args`)

While the built-in `arguments` object is essential legacy knowledge, modern JavaScript (ES6+) heavily favors **Rest Parameters** (`...args`):

* **`arguments`** is an *array-like object* (it lacks standard array methods like `.map()`, `.filter()`, or `.reduce()`) and is **not available inside arrow functions**.
* **Rest parameters** (`...args`) create a **real Array**, allowing you to use array methods directly:

```javascript
// Modern way using Rest Parameters & reduce
function sumAll(...numbers) {
  return numbers.reduce((total, num) => total + num, 0);
}

sumAll(1, 123, 500, 115, 44, 88); // 871

```

---

### 2. Pass-by-Value Nuance for Objects

JavaScript is **always pass-by-value**. When passing an object, the "value" being passed is the **copy of the memory reference**.

* **Mutating a property** alters the original object:

```javascript
function updateName(obj) {
  obj.name = "Alice"; // Modifies original object
}

```

* **Reassigning the object parameter** severs the link and does **not** change the outer variable:

```javascript
function replaceObject(obj) {
  obj = { name: "Bob" }; // Does NOT change the original variable outside
}

```

---

### 3. Named Arguments Pattern (Object Destructuring)

Because JavaScript assigns arguments sequentially by position, managing many arguments can be error-prone. The standard JavaScript pattern for "named parameters" uses **object destructuring**:

```javascript
// Order no longer matters, and default values still work
function createUser({ name, role = "User", age }) {
  return `${name} (${role}) is ${age} years old.`;
}

createUser({ age: 28, name: "Sarah" }); 
// Output: "Sarah (User) is 28 years old."

```
