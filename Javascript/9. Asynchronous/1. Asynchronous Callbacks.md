An **asynchronous callback** is a function passed as an argument to another function that is executed **after** an asynchronous task completes (such as reading a file, fetching data from an API, or waiting for a timer).

Instead of blocking the execution thread while waiting for a slow task to finish, JavaScript delegates the operation to the browser or Node.js runtime and continues running the rest of your code. Once the operation finishes, the callback function is pushed to the **Callback Queue** and executed via the **Event Loop**.

---

## 1. Synchronous vs. Asynchronous Callbacks

### Synchronous Callback (Blocking)

Executed immediately during the execution of the higher-order function:

```javascript
const numbers = [1, 2, 3];

// Array methods like map or forEach execute their callbacks synchronously
numbers.forEach((num) => {
  console.log(num);
});

console.log("Finished loop"); 
// Output order: 1, 2, 3, "Finished loop"

```

### Asynchronous Callback (Non-Blocking)

Deferred until an asynchronous operation completes:

```javascript
console.log("Start");

// setTimeout delegates timer execution to the browser Web API
setTimeout(() => {
  console.log("Callback executed after 2 seconds");
}, 2000);

console.log("End");

/* 
Output order:
1. Start
2. End
3. Callback executed after 2 seconds (Outputted last!)
*/

```

---

## 2. Real-World Patterns: Node.js "Error-First" Callbacks

In traditional Node.js and legacy asynchronous APIs, the standard pattern for callbacks is the **Error-First Callback**. The first argument is reserved for an error object (`err`), and the second argument holds the successful data (`data`).

```javascript
const fs = require("fs");

// Asynchronous file read using error-first callback
fs.readFile("example.txt", "utf8", (err, data) => {
  if (err) {
    console.error("Failed to read file:", err);
    return;
  }
  console.log("File content:", data);
});

console.log("Reading file in background...");

```

---

## 3. The Problem: "Callback Hell" (Pyramid of Doom)

When multiple asynchronous tasks depend on each other sequentially, nesting callbacks inside callbacks leads to unreadable, hard-to-maintain code known as **Callback Hell**.

```javascript
// Example of Callback Hell
getUserData(userId, (err, user) => {
  if (err) return handleError(err);

  getOrders(user.id, (err, orders) => {
    if (err) return handleError(err);

    getOrderDetails(orders[0].id, (err, details) => {
      if (err) return handleError(err);

      getPaymentInfo(details.paymentId, (err, payment) => {
        if (err) return handleError(err);
        console.log("Payment details:", payment);
      });
    });
  });
});

```

---

## 4. Modern Solution: Refactoring to Promises & Async/Await

To fix Callback Hell, modern JavaScript wraps asynchronous operations in **Promises**, allowing flat chaining or `async/await` syntax.

### A. Wrapping a Callback in a Promise

```javascript
// Promisify a callback function
function getUserDataPromise(userId) {
  return new Promise((resolve, reject) => {
    getUserData(userId, (err, user) => {
      if (err) reject(err);
      else resolve(user);
    });
  });
}

```

### B. Clean Async/Await Syntax

```javascript
// Resolving the pyramid of doom using modern async/await
async function loadPaymentDetails(userId) {
  try {
    const user = await getUserDataPromise(userId);
    const orders = await getOrdersPromise(user.id);
    const details = await getOrderDetailsPromise(orders[0].id);
    const payment = await getPaymentInfoPromise(details.paymentId);

    console.log("Payment details:", payment);
  } catch (error) {
    console.error("Error loading payment details:", error);
  }
}

```

Explain how the JavaScript Event Loop works including Microtask Queue and Callback Queue with code examples

The **JavaScript Event Loop** is the mechanism that allows JavaScript—a single-threaded language—to execute non-blocking asynchronous operations. It coordinates execution between the **Call Stack**, **Web APIs**, the **Microtask Queue**, and the **Callback (Macrotask) Queue**.

---

## 1. Core Architecture Components

1. **Call Stack:** Executes single-threaded JavaScript code line-by-line using a LIFO (Last In, First Out) stack.
2. **Web APIs / Node APIs:** Offloads asynchronous tasks (timers, fetch requests, DOM events) to browser or system background threads.
3. **Microtask Queue:** Holds high-priority callbacks generated by **Promises**, `queueMicrotask()`, `MutationObserver`, and Node.js `process.nextTick()`.
4. **Callback (Macrotask) Queue:** Holds standard asynchronous callbacks from `setTimeout()`, `setInterval()`, `setImmediate()`, and event listeners.
5. **Event Loop:** A continuous process that monitors the Call Stack. When the Call Stack is empty, it processes tasks in this order:

* **Flush ALL microtasks** in the Microtask Queue until empty.
* **Execute ONE macrotask** from the Callback Queue.
* Repeat cycle.

---

## 2. Priority Rule: Microtasks vs. Macrotasks

> **Golden Rule of the Event Loop:**
> Before the Event Loop picks **one** item from the Callback (Macrotask) Queue, it **MUST drain every single task** currently waiting in the Microtask Queue.

```text
       ┌──────────────────────────────┐
       │   1. Execute Call Stack      │
       └──────────────┬───────────────┘
                      │
                      ▼
       ┌──────────────────────────────┐
       │ 2. Drain ALL Microtasks      │◄─── (Promises, queueMicrotask)
       └──────────────┬───────────────┘
                      │
                      ▼
       ┌──────────────────────────────┐
       │ 3. Execute ONE Macrotask     │◄─── (setTimeout, setInterval)
       └──────────────┬───────────────┘
                      │
                      └─────────────────────┐
                                            │
                                            ▼ (Loop Repeats)

```

---

## 3. Step-by-Step Execution Code Example

Analyze the code snippet below to see how synchronous code, microtasks, and macrotasks execute in order:

```javascript
console.log("1. Synchronous Start");

// Macrotask (Callback Queue)
setTimeout(() => {
  console.log("2. setTimeout (Macrotask)");
}, 0);

// Microtask (Microtask Queue)
Promise.resolve().then(() => {
  console.log("3. Promise 1 (Microtask)");
});

// Microtask nesting another Microtask
queueMicrotask(() => {
  console.log("4. queueMicrotask 1 (Microtask)");
  
  Promise.resolve().then(() => {
    console.log("5. Nested Promise (Microtask)");
  });
});

console.log("6. Synchronous End");

```

### Execution Step-by-Step

1. **Synchronous Phase:**

* Line 1 logs `"1. Synchronous Start"`.
* Line 4: `setTimeout` callback is registered via Web API timer and pushed to the **Macrotask Queue**.
* Line 9: `.then()` callback is pushed to the **Microtask Queue**.
* Line 14: `queueMicrotask` callback is pushed to the **Microtask Queue**.
* Line 22 logs `"6. Synchronous End"`.
* **Call Stack is now EMPTY.**

1. **Microtask Phase (Draining Queue):**

* Event Loop checks Microtask Queue.
* Executes Promise 1: logs `"3. Promise 1 (Microtask)"`.
* Executes queueMicrotask 1: logs `"4. queueMicrotask 1 (Microtask)"` and enqueues *Nested Promise*.
* Drains the newly added Nested Promise: logs `"5. Nested Promise (Microtask)"`.
* **Microtask Queue is now EMPTY.**

1. **Macrotask Phase:**

* Event Loop picks 1 item from Callback (Macrotask) Queue.
* Executes `setTimeout` callback: logs `"2. setTimeout (Macrotask)"`.

### Console Output Order

```text
1. Synchronous Start
6. Synchronous End
3. Promise 1 (Microtask)
4. queueMicrotask 1 (Microtask)
5. Nested Promise (Microtask)
2. setTimeout (Macrotask)

```

## 4. Starving the Macrotask Queue (Microtask Loops)

Because the Event Loop completely empties the Microtask Queue before moving to the Macrotask Queue, continuously adding microtasks inside a microtask callback will **starve the Event Loop**, freezing UI rendering and preventing timers or click events from running:

```javascript
// WARNING: Infinite Microtask Loop - Freezes the Browser tab!
function infiniteMicrotask() {
  Promise.resolve().then(() => {
    infiniteMicrotask(); // Enqueues another microtask continuously
  });
}

// setTimeout will NEVER execute because the Microtask Queue is never empty!
setTimeout(() => {
  console.log("This line will never run!");
}, 0);

infiniteMicrotask();

```

Explain how process.nextTick works in Node.js Event Loop compared to standard microtasks with code examples

In Node.js, **`process.nextTick()`** is an asynchronous mechanism that bypasses standard Event Loop phases to execute a callback immediately after the current synchronous code finishes executing.

Crucially, Node.js maintains **two separate queues** for microtasks:

1. **The Next Tick Queue:** Exclusively for callbacks registered via `process.nextTick()`.
2. **The Microtask Queue:** For standard Promises (`.then()`, `.catch()`) and `queueMicrotask()`.

Node.js always empties the **Next Tick Queue first**, before it even looks at the standard Microtask Queue.

---

## 1. Execution Order: `nextTick` vs Promises vs Timers

Because `process.nextTick()` has the absolute highest priority of any asynchronous operation in Node.js, it will always "cut in line" ahead of Promises.

### Code Example

```javascript
console.log("1. Synchronous Start");

// 1. Standard Macrotask
setTimeout(() => {
  console.log("6. setTimeout (Macrotask)");
}, 0);

// 2. Standard Microtask
Promise.resolve().then(() => {
  console.log("4. Promise 1 (Standard Microtask)");
});

// 3. Node.js Next Tick
process.nextTick(() => {
  console.log("3. process.nextTick (Highest Priority)");
});

// 4. Another Standard Microtask
Promise.resolve().then(() => {
  console.log("5. Promise 2 (Standard Microtask)");
});

console.log("2. Synchronous End");

```

### Console Output Order

```text
1. Synchronous Start
2. Synchronous End
3. process.nextTick (Highest Priority)
4. Promise 1 (Standard Microtask)
5. Promise 2 (Standard Microtask)
6. setTimeout (Macrotask)

```

**Why this happens:**

1. The Call Stack runs the synchronous code (`1` and `2`).
2. The V8 engine checks the **Next Tick Queue** and executes it (`3`).
3. Only after the Next Tick Queue is completely empty does V8 check the **Microtask Queue** and execute the Promises (`4` and `5`).
4. Finally, the Event Loop moves to the Timer phase to execute the Macrotask (`6`).

---

## 2. The Starvation Risk (Blocking Promises)

Because Node.js processes all `nextTick` callbacks before moving to Promises, a recursive `process.nextTick` loop will completely starve standard microtasks (Promises) and the rest of the Event Loop.

```javascript
// A standard Promise
Promise.resolve().then(() => {
  console.log("This Promise will NEVER execute!");
});

// Recursive nextTick
function loopNextTick() {
  process.nextTick(() => {
    loopNextTick(); // Queues another nextTick indefinitely
  });
}

loopNextTick();

console.log("Synchronous code finishes, then nextTick blocks forever.");

```

If you run this code, the `Promise.then()` will never fire, and the Node.js process will hang endlessly because the Next Tick Queue never empties. *(Note: Standard `queueMicrotask` also starves the Event Loop, but `nextTick` starves `queueMicrotask` itself).*

---

## 3. When Should You Use `process.nextTick()`?

Despite the risks, `process.nextTick()` is heavily used within Node.js core libraries (like `fs` and `http`) for two specific architectural patterns:

### Pattern A: Emitting Events Asynchronously

When creating a custom `EventEmitter`, you must ensure the user has time to attach `.on()` listeners *before* you emit an event. `process.nextTick` defers the emission just long enough for the synchronous attachment to finish.

```javascript
const EventEmitter = require('events');

class MyEmitter extends EventEmitter {
  constructor() {
    super();
    
    // BAD: Emitting synchronously. Listeners aren't attached yet!
    // this.emit('start'); 

    // GOOD: Defer execution until the current script finishes evaluating
    process.nextTick(() => {
      this.emit('start');
    });
  }
}

const myObj = new MyEmitter();

// Because we used nextTick, this listener catches the event
myObj.on('start', () => {
  console.log('Started successfully!');
});

```

### Pattern B: Making APIs 100% Asynchronous

If an API is usually asynchronous but sometimes returns cached data synchronously, returning data synchronously can cause race conditions. `process.nextTick` forces the function to behave asynchronously in all scenarios.

```javascript
const cache = { user: "Alice" };

function fetchUser(callback) {
  if (cache.user) {
    // Force the cached response to still be asynchronous
    process.nextTick(() => callback(null, cache.user));
  } else {
    // Standard async database call
    database.fetch((err, user) => callback(err, user));
  }
}

```
