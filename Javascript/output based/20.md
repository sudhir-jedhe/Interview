Memory leaks and performance bottlenecks are some of the most insidious bugs in JavaScript. Because JavaScript is a garbage-collected language, developers often assume they don't need to manage memory. However, if you accidentally keep a reference to an object, the garbage collector will never free it—eventually crashing your app.

Here is a masterclass batch of real-world bugs focused on **Memory Leaks, Event Listeners, and Performance Thrashing**, and how to fix them.

---

### 1. The Uncleared Event Listener (The SPA Ghost)

❌ **The Bug:**
In Single Page Applications (SPAs) like React, Vue, or even Vanilla JS routers, components are constantly created and destroyed. If you attach an event listener to the `window` or `document` and forget to remove it, the listener lives forever. Every time the user visits the page, a *new* listener is added, duplicating the executions and keeping the component's memory alive.

```javascript
function attachScroll() {
  const massiveDataBox = new Array(1000000).fill("Data");
  
  window.addEventListener('scroll', () => {
    // This closure captures massiveDataBox forever!
    console.log("Scrolled!", massiveDataBox.length);
  });
}

```

✅ **The Fix:**
Always store a reference to the exact same function signature, and explicitly remove it when the component unmounts or the task is done.

```javascript
let massiveDataBox = [];

function handleScroll() {
  console.log("Scrolled!", massiveDataBox.length);
}

function attachScroll() {
  massiveDataBox = new Array(1000000).fill("Data");
  window.addEventListener('scroll', handleScroll);
}

function detachScroll() {
  window.removeEventListener('scroll', handleScroll);
  massiveDataBox = null; // Free the memory!
}

```

* **Why it works:** `removeEventListener` requires the exact same function reference that was passed to `addEventListener`. Using an anonymous arrow function makes removal impossible.

### 2. The Dangling Interval

❌ **The Bug:**
You start a polling mechanism to fetch data, but the user navigates away or closes the UI component. The interval keeps running in the background indefinitely, eating CPU cycles and holding onto closed network connections.

```javascript
function startPolling() {
  setInterval(() => {
    fetch('/api/updates').then(res => console.log("Fetching..."));
  }, 5000);
}

```

✅ **The Fix:**
Always capture the interval ID and provide a teardown mechanism.

```javascript
let pollTimer;

function startPolling() {
  pollTimer = setInterval(() => {
    fetch('/api/updates').then(res => console.log("Fetching..."));
  }, 5000);
}

function stopPolling() {
  clearInterval(pollTimer);
}

```

### 3. Layout Thrashing (Forced Synchronous Layout)

❌ **The Bug:**
You want to resize a list of DOM elements based on their current height. You read the height, then immediately update it inside a loop. This forces the browser to recalculate the page layout (Reflow) on every single iteration, destroying your frame rate.

```javascript
const boxes = document.querySelectorAll('.box');

for (let i = 0; i < boxes.length; i++) {
  // READ (forces layout calculation)
  const currentHeight = boxes[i].offsetHeight; 
  
  // WRITE (invalidates layout)
  boxes[i].style.height = (currentHeight + 10) + 'px'; 
}

```

✅ **The Fix:**
Batch your DOM reads together, and then batch your DOM writes together.

```javascript
const boxes = document.querySelectorAll('.box');
const heights = [];

// Phase 1: Batch all READS
for (let i = 0; i < boxes.length; i++) {
  heights.push(boxes[i].offsetHeight);
}

// Phase 2: Batch all WRITES
for (let i = 0; i < boxes.length; i++) {
  boxes[i].style.height = (heights[i] + 10) + 'px';
}

```

* **Why it works:** The browser is smart. If you only do writes, it waits until the script finishes to paint. But if you ask for a layout metric (`offsetHeight`) immediately after a write, the browser panics and halts execution to calculate the exact pixels instantly. Separating reads and writes lets the browser optimize the rendering pipeline.

### 4. Closures Holding Onto DOM Elements

❌ **The Bug:**
You remove an element from the DOM using `.remove()`, but it doesn't get garbage collected because a JavaScript variable or closure is still holding a reference to it. This creates a "detached DOM node" memory leak.

```javascript
let detachedNodes = [];

function removeElement() {
  const myDiv = document.getElementById("target");
  document.body.removeChild(myDiv);
  
  // BUG: We saved a reference to the removed DOM node!
  detachedNodes.push(myDiv); 
}

```

✅ **The Fix:**
Nullify references to DOM nodes once they are removed from the document.

```javascript
function removeElement() {
  let myDiv = document.getElementById("target");
  document.body.removeChild(myDiv);
  
  // Explicitly clear the reference so the Garbage Collector can clean it up
  myDiv = null; 
}

```

### 5. Accidental Global Variables

❌ **The Bug:**
In non-strict mode, assigning a value to a variable you never declared automatically attaches it to the global `window` object. It will never be garbage collected for the entire lifespan of the application.

```javascript
function processData(data) {
  // Forgot 'const' or 'let'!
  tempCache = data.map(item => item.value); 
  return tempCache.join(",");
}

```

✅ **The Fix:**
Always use `strict mode` (which modern bundlers do by default) and properly declare your variables.

```javascript
'use strict';

function processData(data) {
  // Properly scoped. Will be garbage collected when function ends.
  const tempCache = data.map(item => item.value); 
  return tempCache.join(",");
}

```

### 6. The `console.log` Memory Leak

❌ **The Bug:**
You leave a `console.log` containing massive data objects in your production code.

```javascript
function fetchMassivePayload() {
  const payload = getGiganticData();
  // The browser dev tools must keep this object in memory just in case 
  // you decide to open the console and inspect it later!
  console.log("Payload loaded:", payload); 
}

```

✅ **The Fix:**
Strip `console.log` statements in production environments using your bundler (like Webpack's Terser plugin or Vite's esbuild config). If you must log, log primitive values (like IDs or lengths) rather than the entire object reference.

```javascript
function fetchMassivePayload() {
  const payload = getGiganticData();
  console.log("Payload loaded, total items:", payload.length); 
}

```
