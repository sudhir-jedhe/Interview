Asynchronous JavaScript is notoriously tricky. Promises and `async/await` were introduced to make our lives easier, but they brought along a whole new class of invisible bugs—silent failures, race conditions, and performance bottlenecks.

Here is a masterclass batch of the most common **Async/Await, Promise, and Race Condition bugs**, and exactly how to fix them.

---

### 1. The `try/catch` Return Trap

❌ **The Bug:**
You wrap an asynchronous function call in a `try/catch` block to handle network errors, but when the API fails, the application crashes anyway because the `catch` block is completely ignored.

```javascript
async function fetchUserData() {
  try {
    // BUG: Returning an un-awaited Promise escapes the try/catch!
    return fetch('/api/user/123'); 
  } catch (error) {
    console.error("Failed to fetch user:", error);
    return null;
  }
}

```

✅ **The Fix:**
You must `await` the Promise *before* returning it if you want the local `catch` block to handle its rejection.

```javascript
async function fetchUserData() {
  try {
    // FIX: Await the promise so the function pauses here
    return await fetch('/api/user/123'); 
  } catch (error) {
    console.error("Failed to fetch user:", error);
    return null;
  }
}

```

* **Why it works:** When you `return fetch(...)` without `await`, you are synchronously returning a pending Promise object to the caller. The `try` block succeeds immediately. When the network request eventually fails a second later, it throws an Unhandled Promise Rejection in the caller's scope, bypassing your `catch` entirely.

### 2. The Sequential Bottleneck (Fake Parallelism)

❌ **The Bug:**
You need to fetch a user's profile and their posts. You use `await` sequentially. The page takes 6 seconds to load, even though each request only takes 3 seconds.

```javascript
async function getDashboardData() {
  // BUG: Starts fetching profile. Waits 3 seconds...
  const profile = await fetch('/api/profile').then(r => r.json());
  
  // Starts fetching posts ONLY after profile finishes. Waits 3 seconds...
  const posts = await fetch('/api/posts').then(r => r.json()); 
  
  return { profile, posts }; // Total time: 6 seconds
}

```

✅ **The Fix:**
Trigger both network requests simultaneously, then `await` their collective resolution using `Promise.all`.

```javascript
async function getDashboardData() {
  // FIX: Fire both requests at the same time
  const profilePromise = fetch('/api/profile').then(r => r.json());
  const postsPromise = fetch('/api/posts').then(r => r.json());
  
  // Await them together
  const [profile, posts] = await Promise.all([profilePromise, postsPromise]);
  
  return { profile, posts }; // Total time: 3 seconds
}

```

* **Why it works:** Promises begin executing the exact moment they are created. By creating both promises before using `await`, they run in parallel. `Promise.all` waits for the slowest one to finish.

### 3. The Broken Promise Chain (Missing Returns)

❌ **The Bug:**
You chain multiple `.then()` blocks together. The first block modifies the data, but the second block receives `undefined` and crashes.

```javascript
fetch('/api/user')
  .then(res => res.json())
  .then(user => {
    // BUG: Forgot to return the result!
    formatUserData(user); 
  })
  .then(formattedUser => {
    console.log(formattedUser.name); // Crashes: Cannot read properties of undefined
  });

```

✅ **The Fix:**
Always explicitly `return` data if you want the next `.then()` in the chain to receive it.

```javascript
fetch('/api/user')
  .then(res => res.json())
  .then(user => {
    // FIX: Return the manipulated data
    return formatUserData(user); 
  })
  .then(formattedUser => {
    console.log(formattedUser.name); // Works perfectly
  });

```

### 4. The Autocomplete Race Condition (Overlapping Requests)

❌ **The Bug:**
You build an autocomplete search bar. The user types "A", which triggers a slow API call (takes 2s). The user immediately types "B" ("AB"), which triggers a fast API call (takes 0.5s). The UI displays the results for "AB", but 1.5 seconds later, the slow request for "A" finishes and overwrites the UI with outdated results.

```javascript
let searchResults = [];

async function handleSearch(query) {
  // BUG: If multiple searches are fired, the slowest one always wins, 
  // regardless of which one was requested last.
  const response = await fetch(`/api/search?q=${query}`);
  searchResults = await response.json();
  render(searchResults);
}

```

✅ **The Fix:**
Use an `AbortController` to cancel any pending requests the moment a new one is fired.

```javascript
let searchResults = [];
let abortController = null;

async function handleSearch(query) {
  // Cancel the previous request if it's still running
  if (abortController) {
    abortController.abort();
  }
  
  // Create a new controller for the current request
  abortController = new AbortController();
  
  try {
    const response = await fetch(`/api/search?q=${query}`, { 
      signal: abortController.signal 
    });
    searchResults = await response.json();
    render(searchResults);
  } catch (error) {
    if (error.name === 'AbortError') {
      console.log('Stale search request cancelled');
    } else {
      console.error('Search failed', error);
    }
  }
}

```

### 5. The `forEach` Async Mirage

❌ **The Bug:**
You need to process a list of files sequentially. You map over them with `forEach`, expecting the code to wait for all files to process before logging "All done!". Instead, "All done!" prints immediately, and the files process in random order.

```javascript
async function processFiles(files) {
  // BUG: forEach is synchronous. It fires these off and moves on instantly.
  files.forEach(async (file) => {
    await upload(file);
  });
  
  console.log("All done!"); // Prints immediately before uploads finish
}

```

✅ **The Fix:**
Use a `for...of` loop for strict sequential execution, or `Promise.all` + `.map()` for parallel execution.

```javascript
// FIX A: Sequential execution (Wait for file 1 before starting file 2)
async function processFilesSequentially(files) {
  for (const file of files) {
    await upload(file);
  }
  console.log("All done!");
}

// FIX B: Parallel execution (Upload all at once, wait for all to finish)
async function processFilesInParallel(files) {
  await Promise.all(files.map(file => upload(file)));
  console.log("All done!");
}

```

The DOM has decades of legacy quirks baked into it. If you don't know the exact differences between how certain events propagate, or how the browser renders strings into nodes, you will run into these bizarre, silent failures.

Here is a fresh batch of **Advanced DOM Quirks and Layout Bugs**.

---

### 1. The `innerHTML +=` Listener Wipeout

❌ **The Bug:**
You have a list of items with click listeners. When the user clicks "Add Item", you append a new item using `innerHTML +=`. Suddenly, all the old items stop responding to clicks.

```javascript
const list = document.getElementById('my-list');

// BUG: This reads the HTML string, destroys ALL existing DOM nodes inside the list, 
// and recreates them from scratch. All attached event listeners are destroyed!
function addItem() {
  list.innerHTML += `<li class="item">New Item</li>`;
}

```

✅ **The Fix:**
Use `insertAdjacentHTML`. It parses the new string and injects the resulting nodes into the DOM *without* touching or destroying the existing elements.

```javascript
function addItem() {
  // FIX: Injects safely at the end without destroying existing nodes
  list.insertAdjacentHTML('beforeend', `<li class="item">New Item</li>`);
}

```

### 2. The Non-Bubbling `focus` Trap

❌ **The Bug:**
You want to implement event delegation to track whenever *any* input field on your form receives focus. You attach a `focus` listener to the form, but it never fires.

```javascript
const form = document.getElementById('checkout-form');

// BUG: The 'focus' and 'blur' events DO NOT BUBBLE. 
// When an input gets focus, the event stops right there.
form.addEventListener('focus', (e) => {
  console.log("Input focused:", e.target.name);
});

```

✅ **The Fix:**
Use `focusin` and `focusout`. These are exact duplicates of `focus` and `blur`, but they were specifically designed by browsers to bubble up the DOM tree.

```javascript
// FIX: focusin bubbles perfectly for event delegation
form.addEventListener('focusin', (e) => {
  if (e.target.tagName === 'INPUT') {
    console.log("Input focused:", e.target.name);
  }
});

```

### 3. The Shrinking `HTMLCollection` Trap

❌ **The Bug:**
You want to find all elements with the class "error-message" and remove them. You loop through them, but only *half* of the messages disappear.

```javascript
// getElementsByClassName returns a LIVE HTMLCollection
const errors = document.getElementsByClassName('error-message');

// BUG: As you remove elements, the list dynamically shrinks.
// When i=0, you remove the 1st item. The 2nd item slides into index 0.
// Then i becomes 1, and you skip the new 0th item entirely!
for (let i = 0; i < errors.length; i++) {
  errors[i].remove(); 
}

```

✅ **The Fix:**
Either iterate backward, use a `while` loop, or convert the live collection to a static array before iterating.

```javascript
// FIX A: Convert to a static array using Array.from() or spread operator
const errorsArray = Array.from(document.getElementsByClassName('error-message'));
errorsArray.forEach(err => err.remove());

// FIX B: Use querySelectorAll (which returns a STATIC NodeList)
const staticErrors = document.querySelectorAll('.error-message');
staticErrors.forEach(err => err.remove());

// FIX C: Iterate backward
const errors = document.getElementsByClassName('error-message');
for (let i = errors.length - 1; i >= 0; i--) {
  errors[i].remove();
}

```

### 4. The Passive Listener Scroll Jank

❌ **The Bug:**
You attach a `touchstart` or `wheel` event listener to track user interactions. The browser's scrolling performance suddenly drops to 15 frames per second, and Lighthouse flags your site for "blocking scrolling."

```javascript
// BUG: The browser doesn't know if your function will call e.preventDefault() 
// to stop the scroll. So it waits for your JavaScript to finish executing 
// before it actually moves the pixels on the screen, causing massive lag.
window.addEventListener('touchstart', (e) => {
  trackUserInteraction(e);
});

```

✅ **The Fix:**
Pass `{ passive: true }` as the third argument to the event listener. This is a promise to the browser that you will *never* call `e.preventDefault()`, allowing the browser to scroll the page instantly on a separate thread.

```javascript
window.addEventListener('touchstart', (e) => {
  trackUserInteraction(e);
}, { passive: true }); // FIX: Unblocks the scrolling thread

```

### 5. The Stacking Context Trap (Z-Index Failure)

❌ **The Bug:**
You use JavaScript to inject a modal dialog into a widget on your page. You give the modal `z-index: 999999`. However, it still appears hidden behind the site's sticky header (which only has `z-index: 10`).

```javascript
const widget = document.getElementById('sidebar-widget');
const modal = document.createElement('div');

modal.style.position = 'absolute';
modal.style.zIndex = '999999'; // BUG: Irrelevant if the parent has a stacking context!

widget.appendChild(modal); 

```

✅ **The Fix:**
`z-index` is not global; it is scoped to its parent's **Stacking Context**. If your `#sidebar-widget` has `position: relative` and `z-index: 1`, nothing inside it can ever float above an element with `z-index: 2`, even if you give the child a z-index of a billion.

To fix this, JavaScript-driven modals should *always* be injected at the very root of the DOM (often called a React Portal).

```javascript
const modal = document.createElement('div');

modal.style.position = 'fixed';
modal.style.zIndex = '999999';

// FIX: Append directly to the body, escaping all parent stacking contexts
document.body.appendChild(modal); 

```
