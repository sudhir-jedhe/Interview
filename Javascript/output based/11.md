Here is a batch of advanced output-based questions focusing on **JavaScript Design Patterns**. These test your understanding of how to structure code for reusability, encapsulation, and state management.

### **1. The Singleton Pattern (State Sharing)**

**Question:**
What will be logged to the console?

```javascript
class ConfigManager {
  constructor() {
    if (ConfigManager.instance) {
      return ConfigManager.instance;
    }
    this.settings = { theme: "light" };
    ConfigManager.instance = this;
  }
}

const config1 = new ConfigManager();
const config2 = new ConfigManager();

config1.settings.theme = "dark";

console.log(config2.settings.theme);
console.log(config1 === config2);

```

**Output:**

```text
dark
true

```

* **Explanation:** The Singleton pattern ensures that a class has only one instance and provides a global point of access to it. By returning the cached `ConfigManager.instance`, both `config1` and `config2` point to the exact same object in memory. Modifying the settings via `config1` instantly reflects in `config2`.

### **2. The Module Pattern (Encapsulation via Closures)**

**Question:**
What is the output of the following code?

```javascript
const BankAccount = (function() {
  let balance = 1000; // Private variable

  return {
    deposit: function(amount) {
      balance += amount;
    },
    getBalance: function() {
      return balance;
    }
  };
})();

BankAccount.deposit(500);
BankAccount.balance = 1000000;

console.log(BankAccount.getBalance());
console.log(BankAccount.balance);

```

**Output:**

```text
1500
1000000

```

* **Explanation:** The Module pattern uses an IIFE (Immediately Invoked Function Expression) to create private scope. The internal `balance` variable is completely inaccessible from the outside. Setting `BankAccount.balance = 1000000` merely creates a new, public property on the returned object, which does absolutely nothing to the private `balance` hidden inside the closure.

### **3. The Observer Pattern (Pub/Sub)**

**Question:**
What will be logged when `newsletter.publish()` is called?

```javascript
class Subject {
  constructor() {
    this.observers = [];
  }
  subscribe(fn) {
    this.observers.push(fn);
  }
  unsubscribe(fn) {
    this.observers = this.observers.filter(observer => observer !== fn);
  }
  publish(data) {
    this.observers.forEach(observer => observer(data));
  }
}

const newsletter = new Subject();

const reader1 = (article) => console.log("Reader 1 got: " + article);
const reader2 = (article) => console.log("Reader 2 got: " + article);

newsletter.subscribe(reader1);
newsletter.subscribe(reader2);
newsletter.unsubscribe(reader1);

newsletter.publish("Design Patterns");

```

**Output:**

```text
Reader 2 got: Design Patterns

```

* **Explanation:** The Observer pattern defines a one-to-many dependency so that when one object changes state, all its dependents are notified. `reader1` is subscribed and then immediately unsubscribed by filtering it out of the array. When `publish` is called, only `reader2` remains in the observers list to receive the broadcast.

### **4. The Factory Pattern (Dynamic Object Creation)**

**Question:**
What gets logged to the console?

```javascript
class Developer {
  constructor(name) {
    this.name = name;
    this.type = "Developer";
  }
}

class Designer {
  constructor(name) {
    this.name = name;
    this.type = "Designer";
  }
}

class EmployeeFactory {
  create(name, type) {
    switch(type) {
      case 1: return new Developer(name);
      case 2: return new Designer(name);
    }
  }
}

const factory = new EmployeeFactory();
const emp = factory.create("Alice", 1);

console.log(emp.type);
console.log(emp instanceof Developer);
console.log(emp instanceof EmployeeFactory);

```

**Output:**

```text
Developer
true
false

```

* **Explanation:** The Factory pattern abstracts the creation logic of objects. The factory itself (`EmployeeFactory`) does not become the prototype of the created objects. Instead, it dynamically instantiates and returns instances of other classes (`Developer`). Therefore, `emp` is an instance of `Developer`, not the factory.

### **5. The Prototype Pattern (Cloning via `Object.create`)**

**Question:**
What is the output of this pattern implementation?

```javascript
const carPrototype = {
  wheels: 4,
  clone() {
    return Object.create(this);
  }
};

const myCar = carPrototype.clone();
myCar.color = "Red";

console.log(myCar.wheels);
console.log(myCar.hasOwnProperty('wheels'));
console.log(myCar.hasOwnProperty('color'));

```

**Output:**

```text
4
false
true

```

* **Explanation:** The Prototype pattern creates new objects by cloning an existing prototype rather than instantiating a class. `Object.create(this)` creates a new empty object whose `__proto__` points to `carPrototype`. Because `wheels` is inherited from the prototype, `hasOwnProperty('wheels')` is false, while `color` was directly added to the instance, making it true.

### **6. The Proxy Pattern (Modern Meta-Programming)**

**Question:**
What gets logged when interacting with this proxied object?

```javascript
const user = { name: "Raj" };

const userProxy = new Proxy(user, {
  get(target, prop) {
    if (prop === "age") {
      return 25;
    }
    return prop in target ? target[prop] : "Not Found";
  }
});

console.log(userProxy.name);
console.log(userProxy.age);
console.log(userProxy.email);
console.log(user.age);

```

**Output:**

```text
Raj
25
Not Found
undefined

```

* **Explanation:** The Proxy pattern (natively supported in modern JS) wraps an object to intercept and redefine fundamental operations (like property lookup).
* `name` exists on the target.
* `age` is synthetically generated by the Proxy's `get` trap, but it is **never** added to the underlying `user` object (which is why `user.age` is `undefined`).
* `email` does not exist, triggering the fallback `"Not Found"`.
