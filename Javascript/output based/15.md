Here is a masterclass batch of **output-based questions specifically focused on React Rendering, Hooks, and State Mechanics**. These questions test your knowledge of how and when React decides to re-render, stale closures, batching, and strict mode.

---

### **1. The State Snapshot (Closure Trap)**

**Question:**
Assume the user clicks the "Click Me" button exactly once. What will be logged to the console?

```jsx
import { useState } from "react";

function Counter() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    setCount(count + 1);
    setTimeout(() => {
      console.log("Count is:", count);
    }, 2000);
  };

  return <button onClick={handleClick}>Click Me</button>;
}

```

**Output:**

```text
Count is: 0

```

* **Explanation:** State variables in React behave like constant snapshots for any given render. When `handleClick` is invoked, `count` is `0` in that render's closure. `setCount` queues an update for the *next* render, but the `setTimeout` callback forms a closure over the *current* render's variables. Therefore, it logs `0`, even though the UI will have updated to `1`.

### **2. State Mutation and Object References**

**Question:**
What gets logged to the console when the button is clicked, and does the UI update?

```jsx
import { useState } from "react";

function Profile() {
  console.log("Profile Rendered");
  const [user, setUser] = useState({ name: "Alice", age: 25 });

  const updateAge = () => {
    user.age = 26; 
    setUser(user); 
  };

  return <button onClick={updateAge}>Update Age</button>;
}

```

**Output:**

```text
Profile Rendered (Logged on initial mount only)

```

* **Explanation:** When the button is clicked, nothing is logged, and the UI does **not** update. React uses `Object.is()` to compare the old state and the new state to determine if a re-render is needed. Because we mutated the `user` object directly and passed the exact same memory reference back to `setUser`, React evaluates `user === user` as `true` and bails out of the render entirely. *(Fix: `setUser({ ...user, age: 26 })`)*.

### **3. React 18 Batching (Synchronous vs Asynchronous)**

**Question:**
Assume React 18. How many times will "App Rendered" be logged when the button is clicked?

```jsx
import { useState } from "react";

function App() {
  console.log("App Rendered");
  const [a, setA] = useState(0);
  const [b, setB] = useState(0);

  const handleClick = () => {
    setTimeout(() => {
      setA(a + 1);
      setB(b + 1);
    }, 100);
  };

  return <button onClick={handleClick}>Batch Update</button>;
}

```

**Output:**

```text
App Rendered (Once on mount)
App Rendered (Once after click)

```

* **Explanation:** In React 17, `setTimeout` or Promises broke state batching, resulting in two separate re-renders. However, **React 18 introduced Automatic Batching**. No matter where state updates happen (inside native DOM events, timeouts, or promises), React will batch them together. It updates both `a` and `b` and triggers only a single re-render.

### **4. Strict Mode Double Rendering**

**Question:**
If this app is wrapped in `<React.StrictMode>`, what is logged when the component mounts?

```jsx
import { useState } from "react";

let renderCount = 0;

function Tracker() {
  renderCount++;
  console.log("Rendered:", renderCount);
  
  const [state, setState] = useState(0);
  
  return <div>{state}</div>;
}

```

**Output:**

```text
Rendered: 1
Rendered: 2

```

* **Explanation:** In development mode, React's Strict Mode intentionally double-invokes function component bodies, state updaters, and render phases. This is designed to expose side effects hidden in the render phase. Because `renderCount` is an external variable mutated during rendering (which is a bad practice / impure function), Strict Mode successfully exposes it by incrementing it twice. (In production, it only logs once).

### **5. Eager vs. Lazy Initialization**

**Question:**
If the user clicks the button, how many times will "Heavy Calculation" be logged?

```jsx
import { useState } from "react";

function calculateInitial() {
  console.log("Heavy Calculation");
  return 100;
}

function App() {
  const [value, setValue] = useState(calculateInitial());
  const [count, setCount] = useState(0);

  return <button onClick={() => setCount(c => c + 1)}>Update</button>;
}

```

**Output:**

```text
Heavy Calculation (On Mount)
Heavy Calculation (On Click)

```

* **Explanation:** `useState(calculateInitial())` is an eager initialization. The JavaScript engine executes `calculateInitial()` on **every single render** to evaluate the argument passed to `useState`, even though React ignores the result after the initial mount.
*(Fix: Pass a function reference instead: `useState(calculateInitial)` or `useState(() => calculateInitial())`. This is called Lazy Initialization, and it only runs on mount).*

### **6. `useEffect` Cleanup Timeline**

**Question:**
What is the exact sequence of console logs when the component mounts, and then the user clicks the button once?

```jsx
import { useState, useEffect } from "react";

function Lifecycle() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    console.log("Effect run:", count);
    return () => {
      console.log("Cleanup:", count);
    };
  }, [count]);

  console.log("Render phase:", count);

  return <button onClick={() => setCount(1)}>Update</button>;
}

```

**Output:**

```text
Render phase: 0
Effect run: 0
// --- User clicks the button ---
Render phase: 1
Cleanup: 0
Effect run: 1

```

* **Explanation:**

1. Component renders with `count=0`, then the effect runs.
2. State changes to `1`. The component re-renders with `count=1`.
3. **Crucial rule:** Before applying the *new* effect, React runs the *cleanup* function from the previous render. Because it's a closure, the cleanup function remembers `count=0`.
4. Finally, the new effect runs with `count=1`.

### **7. `useRef` and Re-rendering**

**Question:**
When the user clicks the button, what happens to the console logs and the UI?

```jsx
import { useRef } from "react";

function Counter() {
  console.log("Component Rendered");
  const countRef = useRef(0);

  const handleClick = () => {
    countRef.current += 1;
    console.log("Ref value:", countRef.current);
  };

  return (
    <div>
      <p>UI Count: {countRef.current}</p>
      <button onClick={handleClick}>Increment</button>
    </div>
  );
}

```

**Output:**

```text
Ref value: 1

```

* **Explanation:** The console correctly logs the incremented value (`1`), but the UI will remain stuck at `UI Count: 0`. "Component Rendered" will **not** log again. Mutating a `useRef`'s `.current` property changes the value in memory synchronously, but it does **not** trigger a React re-render.

### **8. Consecutive State Updates**

**Question:**
What will the final `score` displayed on the UI be after the user clicks the button once?

```jsx
import { useState } from "react";

function Game() {
  const [score, setScore] = useState(0);

  const handleScore = () => {
    setScore(score + 1);
    setScore(score + 2);
    setScore(score + 3);
  };

  return <button onClick={handleScore}>Score: {score}</button>;
}

```

**Output:**

```text
Score: 3

```

* **Explanation:** In the closure of the `handleScore` function, `score` is strictly `0`. The code translates to:

1. `setScore(0 + 1)`
2. `setScore(0 + 2)`
3. `setScore(0 + 3)`
React batches these updates and applies the last one, effectively overwriting the previous setter calls. *(Fix: If you need them to stack, use the updater function: `setScore(prev => prev + 3)`).*
