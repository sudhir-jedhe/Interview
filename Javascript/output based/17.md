Here is a masterclass batch of output-based questions focusing on **React Context, `React.memo`, and Re-render Optimization**. These questions test your understanding of referential equality, component composition, and how Context interacts with memoized components.

---

### **1. The Inline Context Value Trap**

**Question:**
Assume the user clicks the "Increment" button. What gets logged to the console?

```jsx
import { useState, createContext, useContext, memo } from "react";

const ThemeContext = createContext();

const ThemedButton = memo(() => {
  console.log("Button Rendered");
  const theme = useContext(ThemeContext);
  return <button style={{ background: theme }}>Action</button>;
});

function App() {
  console.log("App Rendered");
  const [count, setCount] = useState(0);

  return (
    <ThemeContext.Provider value={{ theme: "dark" }}>
      <p>Count: {count}</p>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
      <ThemedButton />
    </ThemeContext.Provider>
  );
}

```

**Output:**

```text
App Rendered
Button Rendered

```

* **Explanation:** Even though `ThemedButton` is wrapped in `React.memo` and the theme string `"dark"` never actually changes, the button still re-renders. Why? Because the `value` prop is passed an inline object literal: `value={{ theme: "dark" }}`. Every time `App` re-renders (due to `count` changing), a brand-new object is created in memory. The Context detects a new reference, bypassing `React.memo`, and forces all consumers to re-render. *(Fix: `const themeValue = useMemo(() => ({ theme: "dark" }), [])`)*.

### **2. `useContext` Bypassing `React.memo**`

**Question:**
Assume the `ThemeContext` updates from "dark" to "light" due to a parent state change. Does `<Header/>` re-render?

```jsx
import { memo, useContext } from "react";

const Header = memo((props) => {
  console.log("Header Rendered");
  const theme = useContext(ThemeContext);
  
  return <h1 className={theme}>{props.title}</h1>;
});

// Used elsewhere as: <Header title="Dashboard" />

```

**Output:**

```text
Header Rendered

```

* **Explanation:** Yes, it re-renders. `React.memo` *only* evaluates the props passed directly to the component (in this case, `title`). However, calling `useContext` establishes a direct subscription to the context. When the context value changes, React guarantees that the consuming component will re-render, completely ignoring the `React.memo` bailout.

### **3. The Unused Context Property Problem**

**Question:**
The user clicks a button to update `user.name`. Does the `<Settings/>` component re-render?

```jsx
import { createContext, useContext, useState } from "react";

const AppContext = createContext();

function Settings() {
  console.log("Settings Rendered");
  const { theme } = useContext(AppContext);
  return <div>Theme is {theme}</div>;
}

function App() {
  const [user, setUser] = useState({ name: "Alice" });
  const [theme, setTheme] = useState("dark");

  return (
    <AppContext.Provider value={{ user, theme }}>
      <Settings />
      <button onClick={() => setUser({ name: "Bob" })}>Change User</button>
    </AppContext.Provider>
  );
}

```

**Output:**

```text
Settings Rendered

```

* **Explanation:** Yes, `<Settings/>` re-renders. React Context does not support "selectors" out of the box. Even though `<Settings/>` destructures `{ theme }` and completely ignores `user`, it is subscribed to the *entire* `value` object. When `user` changes, the `value` object reference changes, forcing every single consumer of `AppContext` to re-render, regardless of which properties they actually use. *(Fix: Split into two contexts: `UserContext` and `ThemeContext`).*

### **4. `React.memo` Failing on the `children` Prop**

**Question:**
If the parent component re-renders for an unrelated reason, does `<Card/>` re-render?

```jsx
import { memo } from "react";

const Card = memo(({ children }) => {
  console.log("Card Rendered");
  return <div className="card">{children}</div>;
});

function App() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
      <Card>
        <p>Hello World</p>
      </Card>
    </div>
  );
}

```

**Output:**

```text
Card Rendered (Every time the button is clicked)

```

* **Explanation:** `React.memo` does a shallow comparison of props. Passing elements between the opening and closing tags implicitly passes them as the `children` prop. Under the hood, JSX `<p>Hello World</p>` transpiles to `React.createElement('p', null, 'Hello World')`. This function returns a *brand-new object* on every single render of `App`. Because `oldProps.children !== newProps.children`, `React.memo` sees a prop change and allows the re-render.

### **5. The Component Composition Bailout (No `memo` needed)**

**Question:**
When the user clicks the button, does the `<Child/>` component re-render?

```jsx
import { useState } from "react";

function ParentWrapper({ children }) {
  console.log("Parent Rendered");
  const [color, setColor] = useState("red");

  return (
    <div style={{ background: color }}>
      <button onClick={() => setColor("blue")}>Change Color</button>
      {children}
    </div>
  );
}

function Child() {
  console.log("Child Rendered");
  return <h1>I am a child</h1>;
}

function App() {
  console.log("App Rendered");
  return (
    <ParentWrapper>
      <Child />
    </ParentWrapper>
  );
}

```

**Output:**

```text
Parent Rendered

```

*(The Child is NOT rendered again)*

* **Explanation:** This is one of the most powerful and misunderstood performance optimizations in React. When `ParentWrapper` updates its own state (`color`), it re-renders. However, it does not re-render `Child`. Why? Because `Child` was instantiated and passed in by `App`. `App` did not re-render, so the `children` prop passed to `ParentWrapper` is the exact same object reference as before. React recognizes that `children` hasn't changed and skips evaluating the `<Child/>` component entirely—all without needing `React.memo`.
