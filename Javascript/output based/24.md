TypeScript is supposed to be your safety net, but if you abuse `any`, fail to narrow types properly, or misunderstand generics, that net turns into a straightjacket. You end up fighting the compiler instead of writing features.

Here is a masterclass batch of the most common **TypeScript anti-patterns, typing failures, and generic mistakes**, and exactly how to fix them.

---

### 1. The `Array.filter` Narrowing Failure (The `is` Keyword)

❌ **The Bug:**
You have an array with some `null` or `undefined` values. You use `.filter()` to remove them, but TypeScript still complains that the values might be null when you try to map over them.

```typescript
const rawData: (string | null)[] = ["apple", null, "banana"];

// BUG: TypeScript's type checker isn't smart enough to look inside 
// the callback and realize the resulting array only contains strings.
const cleanData = rawData.filter(item => item !== null);

// TS Error: Object is possibly 'null'.
cleanData.map(item => item.toUpperCase()); 

```

✅ **The Fix:**
Use a **Type Predicate** (`item is type`) in the filter callback to explicitly tell the compiler how to narrow the type.

```typescript
// FIX: The return type `item is string` tells TS that if this function 
// returns true, the item is guaranteed to be a string.
const cleanData = rawData.filter((item): item is string => item !== null);

// Works perfectly! TS knows cleanData is string[]
cleanData.map(item => item.toUpperCase()); 

```

### 2. The `JSON.parse` Any Leak

❌ **The Bug:**
`JSON.parse()` returns `any` by default. If you don't type it immediately, that `any` silently leaks into your entire codebase, disabling type-checking for every variable it touches and leading to runtime crashes.

```typescript
const jsonString = '{"user": {"name": "Alice"}}';

// BUG: parsedData is 'any'. TypeScript has gone blind.
const parsedData = JSON.parse(jsonString);

// TS allows this, but it will crash at runtime because 'profile' doesn't exist!
console.log(parsedData.profile.age); 

```

✅ **The Fix:**
Force `JSON.parse` to return `unknown`, and then validate the data before casting it to an interface. `unknown` is the safe version of `any`—it forces you to check the type before accessing properties.

```typescript
interface UserData {
  user: { name: string };
}

// FIX: Cast to unknown first to block blind property access
const parsedData = JSON.parse(jsonString) as unknown;

// Now, manually validate it (or better, use a library like Zod)
if (
  parsedData !== null && 
  typeof parsedData === 'object' && 
  'user' in parsedData
) {
  // Safe to cast now
  const safeData = parsedData as UserData;
  console.log(safeData.user.name);
}

```

### 3. The Missing Generic Constraint

❌ **The Bug:**
You write a reusable generic function to extract the `id` from any object. But TypeScript throws an error because it doesn't know if the generic type `T` actually has an `id` property.

```typescript
// BUG: T could literally be anything (a string, a number, an empty object).
function extractId<T>(item: T) {
  // TS Error: Property 'id' does not exist on type 'T'.
  return item.id; 
}

```

✅ **The Fix:**
Use the `extends` keyword to constrain the generic. This tells TypeScript: *"T can be any type, **as long as** it has an id property."*

```typescript
// FIX: Constrain T to objects containing an id of type string or number
function extractId<T extends { id: string | number }>(item: T) {
  return item.id; // Works perfectly
}

extractId({ id: 1, name: "Alice" }); // Valid
extractId({ name: "Bob" }); // TS Error: Object literal may only specify known properties

```

### 4. The Discriminated Union Failure

❌ **The Bug:**
You have a union type representing different shapes. You try to write a function that calculates the area, but TypeScript yells at you when you try to access shape-specific properties.

```typescript
interface Circle { radius: number; }
interface Square { sideLength: number; }

type Shape = Circle | Square;

function getArea(shape: Shape) {
  // BUG: TypeScript doesn't know which shape it is.
  // TS Error: Property 'radius' does not exist on type 'Shape'.
  if (shape.radius) {
    return Math.PI * shape.radius ** 2;
  }
}

```

✅ **The Fix:**
Add a literal string property (a **discriminator**) to all interfaces in the union. This allows TypeScript to seamlessly narrow the type using a `switch` or `if` statement.

```typescript
// FIX: Add a distinct literal 'kind' or 'type' property
interface Circle { kind: 'circle'; radius: number; }
interface Square { kind: 'square'; sideLength: number; }

type Shape = Circle | Square;

function getArea(shape: Shape) {
  switch (shape.kind) {
    case 'circle':
      // TS knows 100% this is a Circle. It auto-completes 'radius'.
      return Math.PI * shape.radius ** 2; 
    case 'square':
      // TS knows 100% this is a Square.
      return shape.sideLength ** 2;
  }
}

```

### 5. Overly Permissive Callbacks (Destroying Inference)

❌ **The Bug:**
You write a higher-order function that takes a callback. To satisfy TypeScript, you quickly type the callback's argument as `any`. This completely destroys TypeScript's ability to infer types for the developer using your function.

```typescript
// BUG: Using 'any' for the callback argument destroys type inference.
function processArray(items: string[], callback: (item: any) => void) {
  for (const item of items) {
    callback(item);
  }
}

processArray(["apple", "banana"], (fruit) => {
  // TS doesn't know 'fruit' is a string. It thinks it's 'any'.
  // Auto-complete won't work, and typos won't be caught.
  console.log(fruit.toUppercase()); // No TS error for the typo!
});

```

✅ **The Fix:**
Use a Generic `<T>` to link the type of the array to the type of the callback argument. This preserves inference all the way through the chain.

```typescript
// FIX: Link the array type (T[]) to the callback type (T)
function processArray<T>(items: T[], callback: (item: T) => void) {
  for (const item of items) {
    callback(item);
  }
}

processArray(["apple", "banana"], (fruit) => {
  // TS knows 'fruit' is a string!
  // TS Error: Property 'toUppercase' does not exist on type 'string'. Did you mean 'toUpperCase'?
  console.log(fruit.toUppercase()); 
});

```
