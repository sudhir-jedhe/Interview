### **1. The `useEffect` Fetching Race Condition**

**Question:**
Assume fetching User 1 takes **3 seconds** and fetching User 2 takes **1 second**. The user clicks the "Load User 1" button, and then a half-second later, clicks "Load User 2". What is the final data displayed on the screen?

```jsx
import { useState, useEffect } from "react";

function UserProfile({ userId }) {
  const [data, setData] = useState(null);

  useEffect(() => {
    let isMounted = true;
    
    fetch(`https://api.example.com/users/${userId}`)
      .then(res => res.json())
      .then(userData => {
        setData(userData);
      });
      
  }, [userId]);

  return <div>{data ? data.name : "Loading..."}</div>;
}

```

**Output:**

```text
User 1's Name

```

* **Explanation:** This is a classic data-fetching race condition.

1. `userId` 1 triggers a fetch (takes 3s).
2. `userId` 2 triggers a fetch (takes 1s).
3. The fetch for User 2 resolves first (after 1s). The state updates, and the UI displays User 2.
4. Two seconds later, the fetch for User 1 finally resolves. It calls `setData` with User 1's data, overwriting the correct state with stale data.
*(Fix: Implement an `AbortController` or a boolean cleanup flag in the `useEffect` return statement to ignore the first request).*

### **2. The Suspense Contract (Throwing Promises)**

**Question:**
When this component renders, what does React do? Does it crash with an error?

```jsx
let cache = null;

function fetchData() {
  if (cache) return cache;
  
  const promise = new Promise(resolve => {
    setTimeout(() => {
      cache = "Hello World";
      resolve();
    }, 1000);
  });
  
  throw promise; 
}

function AsyncGreeting() {
  const data = fetchData();
  return <h1>{data}</h1>;
}

// Rendered inside:
// <Suspense fallback={<h2>Loading...</h2>}>
//   <AsyncGreeting />
// </Suspense>

```

**Output:**
*The UI displays `<h2>Loading...</h2>` for 1 second, then updates to `<h1>Hello World</h1>`.*

* **Explanation:** This is exactly how React Suspense works under the hood. If a component (or a hook it calls) **throws a Promise** during the render phase, React catches that Promise. It suspends the rendering of that component tree, finds the nearest `<Suspense>` boundary above it, and displays the `fallback`. Once the thrown Promise resolves, React attempts to re-render the component from scratch.

### **3. `startTransition` vs Standard State Updates**

**Question:**
Assume the user clicks the "Switch to Profile" button. `<ProfileTab/>` is a heavy component wrapped in Suspense that takes 2 seconds to load its data. What does the user see visually during those 2 seconds?

```jsx
import { useState, useTransition, Suspense } from "react";

function App() {
  const [tab, setTab] = useState("home");
  const [isPending, startTransition] = useTransition();

  const handleTabSwitch = () => {
    startTransition(() => {
      setTab("profile");
    });
  };

  return (
    <div>
      <button onClick={handleTabSwitch}>Switch to Profile</button>
      <Suspense fallback={<p>Loading Tab...</p>}>
        {tab === "home" ? <HomeTab /> : <ProfileTab />}
      </Suspense>
    </div>
  );
}

```

**Output:**
*The user continues to see the `<HomeTab/>` (the old UI) for 2 seconds. The `Loading Tab...` fallback is completely bypassed.*

* **Explanation:** `startTransition` tells React that the state update is a non-urgent "transition." When a transition triggers a component that suspends, React deliberately **avoids hiding the current UI**. Instead of aggressively tearing down the `<HomeTab/>` to show a loading spinner, it keeps the app interactive on the old screen while rendering the new screen in the background. (You can use `isPending` to show a subtle loading indicator on the button itself).

### **4. The Data Fetching Waterfall**

**Question:**
Assume `fetchUser` takes 2 seconds, and `fetchPosts` takes 2 seconds. How long does it take from the initial mount for the user's posts to appear on the screen?

```jsx
function App() {
  const user = useUserFetch(); // Suspends for 2 seconds
  
  return (
    <Suspense fallback={<p>Loading User...</p>}>
      <UserHeader user={user} />
      <Suspense fallback={<p>Loading Posts...</p>}>
        <UserPosts userId={user.id} /> 
      </Suspense>
    </Suspense>
  );
}

function UserPosts({ userId }) {
  const posts = usePostsFetch(userId); // Suspends for 2 seconds
  return <ul>{/* ...render posts */}</ul>;
}

```

**Output:**

```text
4 seconds

```

* **Explanation:** This is a "waterfall." Because `App` suspends on `useUserFetch`, the rendering of the `App` component is halted. The `<UserPosts/>` component does not even mount, and therefore its fetch request does not even begin, until the user data fully resolves. The requests happen sequentially (2s + 2s = 4s).
*(Fix: Hoist the fetch for both user and posts to the top level, or use a router/framework loader that fetches them in parallel before rendering).*

### **5. React 18 Strict Mode & Missing Cleanups**

**Question:**
This app is wrapped in `<React.StrictMode>` and running in React 18 development mode. When it mounts, what gets logged to the Network tab/console?

```jsx
import { useEffect } from "react";

function AnalyticsTracker() {
  useEffect(() => {
    console.log("Sending page view event to API...");
    fetch("https://api.example.com/track", { method: "POST" });
  }, []); // Empty dependency array

  return <div>Welcome to the page</div>;
}

```

**Output:**

```text
Sending page view event to API...
Sending page view event to API...

```

*(Two identical network requests are fired).*

* **Explanation:** In React 18, Strict Mode intentionally simulates a component unmounting and remounting immediately (`Mount -> Unmount -> Remount`). Because the developer did not provide a cleanup function to cancel the fetch (via `AbortController`), the `useEffect` runs twice, sending duplicate analytics events. This behavior ensures developers catch missing cleanup logic for asynchronous operations.
