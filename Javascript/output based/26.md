When should you avoid using async/await and prefer Promise chaining?

Real-world scenario only.

Here is the breakdown of these classic JavaScript quirks and architecture decisions.

### 1. The `NaN` Paradox

**Output:**

```javascript
"number"
false

```

**Why it happens:**

* `typeof NaN === "number"`: In JavaScript (and the IEEE 754 floating-point standard it relies on), `NaN` stands for "Not-a-Number," but it is technically categorized as a numeric data type representing an undefined or unrepresentable mathematical result (like `0 / 0`).
* `NaN === NaN`: By the same IEEE 754 standard, `NaN` is designed to be unequal to everything, including itself. To safely check if a value is `NaN`, you must use `Number.isNaN(value)`.

---

### 2. The Temporal Dead Zone (TDZ)

**Output:**

```javascript
ReferenceError: Cannot access 'x' before initialization

```

**Why it happens:**
This is the **Temporal Dead Zone (TDZ)** in action. When the engine executes `test()`, it hoists the `let x = 20;` declaration to the top of the function's block scope. It knows a local `x` exists, but unlike `var` (which initializes as `undefined`), `let` and `const` remain entirely uninitialized until execution reaches their exact line.

Calling `console.log(x)` before the initialization line catches the variable in the TDZ, crashing the script. It does *not* fall back to the outer `let x = 10` because the inner block has already reserved `x`.

---

### 3. Mutating Array Length

**Output:**

```javascript
[]

```

**Why it happens:**
In JavaScript, an array's `.length` property is explicitly writable. Setting it to `0` acts as an in-place truncation, instantly deleting all elements.

**Is it safe in production?**
Yes, it is standard and highly performant for emptying an array.

**When is it dangerous?**
It becomes dangerous when **multiple variables reference the same array**.

* If you clear it via `arr = []`, you only reassign *that specific variable*. Other references keep the original data.
* If you clear it via `arr.length = 0`, you mutate the array in memory. *All* references to that array will instantly see an empty array, which can introduce catastrophic side effects if another part of your application still expects the data.

---

### 4. Object Keys and Coercion

**Result:**

```javascript
456

```

**Why it happens:**
JavaScript object keys can only be Strings or Symbols. If you try to use an object (like `b` or `c`) as a key, JavaScript implicitly coerces it to a string by calling its `.toString()` method.

For plain objects, `.toString()` returns the string `"[object Object]"`.

1. `a[b] = 123` evaluates to `a["[object Object]"] = 123`.
2. `a[c] = 456` evaluates to `a["[object Object]"] = 456`, overwriting the first assignment.
3. `a[b]` retrieves the value at `a["[object Object]"]`, which is now `456`.

---

### 5. Architecture: `async/await` vs. Promise Chaining

**When to prefer Promise chaining (`.then().catch()`):**
You should prefer Promise chaining for **"fire-and-forget" background operations** where you explicitly *do not* want to block the execution thread, but you still need error handling.

**Real-World Scenario:**
You are writing an API route for user registration. After successfully inserting the user into your database, you want to send a welcome email and log an analytics event, then return a success response to the client immediately.

If you use `await`, the client waits needlessly for the email and logging to finish:

```javascript
// BAD: Blocks the user from getting their response quickly
await database.insert(user);
await sendWelcomeEmail(user); 
await logAnalytics("signup");
res.status(200).send("Created");

```

By chaining, you kick off the background tasks and handle their potential failures cleanly without a messy `try/catch` block, while immediately freeing the main thread to respond to the client:

```javascript
// GOOD: Client gets immediate response; background tasks run concurrently
await database.insert(user);

sendWelcomeEmail(user).catch(err => logger.error("Email failed", err));
logAnalytics("signup").catch(err => logger.error("Analytics failed", err));

res.status(200).send("Created");

```
