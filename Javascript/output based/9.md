Here is a masterclass batch of **advanced output-based questions** focusing exclusively on the darkest corners of **Asynchronous JavaScript**—including Promise state-machine quirks, `async/await` execution order, and microtask/macrotask event loop traps.

---

### **1. The `forEach` Async Trap**

**Question:**
What will be the output, and how long will it take for the final `console.log` to execute?

```javascript
const delay = (ms) => new Promise(res => setTimeout(res, ms));

async function processArray(arr) {
  arr.forEach(async (num) => {
    await delay(1000);
    console.log(num);
  });
  console.log("Done");
}

processArray([1, 2, 3]);

```

**Output:**

```text
Done
// ... (1 second later) ...
1
2
3

```

* **Explanation:** The `Array.prototype.forEach` method is completely synchronous and does not wait for Promises to resolve. It fires off all three `async` callbacks concurrently and immediately moves to the next line, logging `"Done"`. Because they run concurrently, `1`, `2`, and `3` all print at roughly the exact same time after 1 second, not 3 seconds. *(Fix: Use a `for...of` loop if you need sequential execution).*

### **2. `return` vs `return await` inside `try/catch**`

**Question:**
What gets logged to the console?

```javascript
async function fetchSafe() {
  try {
    return Promise.reject("Network Error");
  } catch (error) {
    return "Recovered";
  }
}

fetchSafe()
  .then(res => console.log("Success:", res))
  .catch(err => console.log("Caught:", err));

```

**Output:**

```text
Caught: Network Error

```

* **Explanation:** When you `return Promise.reject(...)`, the function completes and hands that rejected promise *back to the caller*. The rejection happens asynchronously *outside* of the `fetchSafe` function's execution context. Therefore, the internal `try/catch` block never catches it.
* **The Fix:** If you change it to `return await Promise.reject(...)`, the function unwraps the promise locally, triggering the internal `catch` block, which would output `Success: Recovered`.

### **3. The Promise Fall-Through (Passing Non-Functions)**

**Question:**

```javascript
Promise.resolve("A")
  .then("B")
  .then(console.log)
  .catch("C");

```

**Output:**

```text
A

```

* **Explanation:** The `.then()` and `.catch()` methods expect a **function** as an argument. If you pass a non-function (like the string `"B"`), JavaScript silently ignores it and passes the resolved value from the previous promise (`"A"`) straight through to the next `.then()` in the chain.

### **4. Resolving a Promise with a Promise**

**Question:**

```javascript
const innerPromise = Promise.reject("Failure");

const outerPromise = new Promise((resolve, reject) => {
  resolve(innerPromise);
});

outerPromise
  .then(() => console.log("Outer Resolved"))
  .catch(err => console.log("Outer Rejected:", err));

```

**Output:**

```text
Outer Rejected: Failure

```

* **Explanation:** The `resolve` function of a Promise has a special behavior. If you resolve a promise with *another* promise, the outer promise "locks in" to the state of the inner promise. Because `innerPromise` is rejected, `outerPromise` adopts that rejection, skipping the `.then()` and going straight to the `.catch()`.

### **5. The Empty Array Race**

**Question:**

```javascript
console.log("Start");

Promise.race([])
  .then(() => console.log("Race Won"))
  .catch(() => console.log("Race Lost"));

Promise.any([])
  .then(() => console.log("Any Won"))
  .catch(err => console.log(err.name));

console.log("End");

```

**Output:**

```text
Start
End
AggregateError

```

* **Explanation:**
* `Promise.race([])` with an empty array **hangs forever**. It never resolves and never rejects because there is no promise to win the race.
* `Promise.any([])` waits for the first successful promise. Since the array is empty, it realizes success is impossible and immediately rejects with an `AggregateError`.

### **6. The Unhandled Synchronous Throw**

**Question:**

```javascript
console.log("1");

const p = new Promise((resolve, reject) => {
  console.log("2");
  throw new Error("Oops");
  console.log("3");
});

p.catch(() => console.log("4"));

console.log("5");

```

**Output:**

```text
1
2
5
4

```

* **Explanation:** The executor function passed to `new Promise` runs **synchronously**. It logs `1` and `2`. When it hits the `throw`, it doesn't crash the program; instead, the Promise constructor catches the error implicitly and turns it into a **Promise Rejection**. It skips `3`, logs `5` synchronously, and then handles the rejection asynchronously in the microtask queue, logging `4`.

### **7. Microtask Queue Starvation**

**Question:**
If you run this code, will `"Timeout"` ever be logged?

```javascript
setTimeout(() => console.log("Timeout"), 0);

function infiniteMicrotasks() {
  Promise.resolve().then(infiniteMicrotasks);
}

infiniteMicrotasks();

```

**Output:**
*No output / The browser tab freezes*

* **Explanation:** The Event Loop must completely empty the Microtask Queue before it is allowed to process the next item in the Macrotask Queue (like `setTimeout`). Because `infiniteMicrotasks` constantly pushes a new microtask onto the queue, the Microtask Queue never empties. The Event Loop gets trapped forever, starving the Macrotask queue and preventing the UI from rendering.

### **8. Multiple `await`s on the Same Promise**

**Question:**

```javascript
const sharedPromise = new Promise(resolve => {
  console.log("Initializing...");
  setTimeout(() => resolve("Data"), 100);
});

async function a() {
  console.log("A: ", await sharedPromise);
}

async function b() {
  console.log("B: ", await sharedPromise);
}

a();
b();

```

**Output:**

```text
Initializing...
A: Data
B: Data

```

* **Explanation:** A Promise executes its internal logic exactly **once**, the moment it is created (which is why "Initializing..." logs immediately and only once). Once it resolves, it caches its result. Multiple async functions can `await` the exact same promise object. When the 100ms timer finishes, both functions receive the cached `"Data"` value and execute their continuations in the order they were queued.

### **9. `finally` Return Values**

**Question:**

```javascript
Promise.resolve("Apple")
  .finally(() => "Banana")
  .then(res => console.log(res))
  .catch(err => console.log(err));

Promise.reject("Apple")
  .finally(() => { throw "Orange"; })
  .catch(err => console.log(err));

```

**Output:**

```text
Apple
Orange

```

* **Explanation:**

1. `.finally()` **does not modify** the resolved value of a promise chain. Returning `"Banana"` does nothing; the original `"Apple"` passes through to `.then()`.
2. However, if a `.finally()` block **throws an error** (or returns a rejected promise), that new error supersedes the previous state and becomes the new rejection reason, passing `"Orange"` to `.catch()`.

### **10. Async Method Context Loss**

**Question:**

```javascript
const api = {
  data: "Secret",
  async fetchData() {
    return Promise.resolve(this.data);
  }
};

const fetch = api.fetchData;

fetch().then(console.log);

```

**Output:**

```text
undefined

```

* **Explanation:** Even though `fetchData` is an `async` function and returns a Promise, it is still subject to standard JavaScript `this` binding rules. By stripping the method off the object (`const fetch = api.fetchData`) and calling it as a standalone function (`fetch()`), the `this` context defaults to the global window object (or `undefined` in strict mode), losing access to `this.data`.
