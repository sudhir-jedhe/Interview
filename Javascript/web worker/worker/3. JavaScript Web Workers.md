**Web Workers** allow you to run JavaScript in background threads, completely separate from the main execution thread.

By default, browser JavaScript runs on a **single main thread**. If a heavy computation (like processing large datasets, image manipulation, or complex parsing) runs on the main thread, the page freezes, animations stutter, and user interactions (clicks, typing, scrolling) become unresponsive. Web Workers solve this by offloading heavy tasks to a true CPU-level background thread.

---

## 1. Core Architecture & Constraints

```text
┌─────────────────────────┐                        ┌─────────────────────────┐
│ Main Thread (DOM / UI)  │                        │ Worker Thread           │
│                         │  worker.postMessage()  │                         │
│ - Handles user events   │ ─────────────────────► │ - Runs heavy CPU code   │
│ - Manipulates DOM       │                        │ - Isolated execution    │
│ - Renders UI            │ ◄───────────────────── │ - No DOM access         │
└─────────────────────────┘   self.postMessage()   └─────────────────────────┘

```

### What Web Workers CAN and CANNOT Do

| Feature                                          | Main Thread | Worker Thread |
| ------------------------------------------------ | ----------- | ------------- |
| **DOM Access (`document`, `window`)**            | ✅ Yes       | ❌ No          |
| **Network Requests (`fetch`, `XMLHttpRequest`)** | ✅ Yes       | ✅ Yes         |
| **Timers (`setTimeout`, `setInterval`)**         | ✅ Yes       | ✅ Yes         |
| **Client-Side Storage (`IndexedDB`)**            | ✅ Yes       | ✅ Yes         |
| **UI Event Listeners (`click`, `scroll`)**       | ✅ Yes       | ❌ No          |
| **`WebAssembly` Support**                        | ✅ Yes       | ✅ Yes         |

## 2. Basic Dedicated Web Worker Example

A **Dedicated Worker** is linked to the single script/tab that spawned it.

### Step 1: The Worker Script (`worker.js`)

Inside the worker, `self` represents the worker scope.

```javascript
// worker.js
self.onmessage = function (event) {
  console.log('[Worker] Received task data:', event.data);

  const { number } = event.data;

  // Perform CPU-intensive calculation (e.g., Fibonacci)
  const result = fibonacci(number);

  // Send calculated result back to main thread
  self.postMessage({ number, result });
};

function fibonacci(n) {
  if (n <= 1) return n;
  return fibonacci(n - 1) + fibonacci(n - 2);
}

```

---

### Step 2: The Main Script (`main.js`)

Spawn the worker, send messages via `.postMessage()`, and listen for responses via `.onmessage`.

```javascript
// main.js

// 1. Instantiate the background worker
const worker = new Worker('worker.js');

// 2. Listen for messages returned from the worker
worker.onmessage = function (event) {
  const { number, result } = event.data;
  console.log(`[Main] Worker computed Fibonacci(${number}) = ${result}`);

  // Optional: Terminate worker when finished to free CPU memory
  // worker.terminate();
};

// 3. Listen for worker execution errors
worker.onerror = function (error) {
  console.error('[Main] Worker Error:', error.message);
};

// 4. Trigger heavy computation in background
console.log('[Main] Sending task to worker...');
worker.postMessage({ number: 42 }); // UI remains completely smooth and responsive!

```

## 3. High-Performance Zero-Copy Data Transfers (`TransferableObjects`)

When passing standard JavaScript objects via `postMessage()`, the browser uses the **Structured Clone algorithm** (copying the data in memory). Passing massive array buffers (like raw video/image pixels) can introduce cloning latency.

To pass data with zero copying cost, use **Transferable Objects** (such as `ArrayBuffer`, `MessagePort`, or `ImageBitmap`). Transferring ownership instantly hands memory off to the target thread and makes the buffer inaccessible on the sender thread.

```javascript
// main.js
const worker = new Worker('worker.js');

// Create a 50MB raw buffer
const largeBuffer = new ArrayBuffer(50 * 1024 * 1024);

console.log('Buffer size in main thread before transfer:', largeBuffer.byteLength); // 52428800

// Pass the buffer as a Transferable Object in the 2nd argument array
worker.postMessage({ buffer: largeBuffer }, [largeBuffer]);

// Memory was transferred instantly: byteLength is now 0 on main thread!
console.log('Buffer size in main thread after transfer:', largeBuffer.byteLength); // 0

```

## 4. Inline Web Workers (Without External Files)

If you need a worker inside a single JavaScript file (or single-page applications) without creating a physical `/worker.js` file on disk, use `URL.createObjectURL()` and a `Blob`:

```javascript
function createInlineWorker(workerFunc) {
  const code = `(${workerFunc.toString()})();`;
  const blob = new Blob([code], { type: 'application/javascript' });
  return new Worker(URL.createObjectURL(blob));
}

// Inline worker implementation
const myWorker = createInlineWorker(() => {
  self.onmessage = (e) => {
    const double = e.data * 2;
    self.postMessage(double);
  };
});

myWorker.onmessage = (e) => {
  console.log('Inline worker result:', e.data); // 84
};

myWorker.postMessage(42);

```

## 5. Types of Web Workers Compared

| Worker Type          | Lifetime / Scope                                             | Common Use Case                                                           |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| **Dedicated Worker** | Tied to a single tab/script session.                         | Data parsing, image/video filtering, heavy math calculations.             |
| **SharedWorker**     | Shared across multiple open tabs/windows of the same origin. | Centralizing state, single WebSocket connection, shared IndexedDB access. |
| **Service Worker**   | Event-driven background proxy independent of tabs.           | Offline caching, background sync, Web Push notifications.                 |

---

## Summary Best Practices

1. **Keep UI Thread Clean:** If a task takes longer than $16\text{ms}$ (1 frame at 60 FPS), offload it to a Dedicated Web Worker.
2. **Terminate Unused Workers:** Call `worker.terminate()` from the main thread or `self.close()` inside the worker to release browser thread pools when processing is complete.
3. **Use Bundlers / ES Modules:** Modern bundlers like Vite and Webpack support native worker syntax: `new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })`.

Explain how to manage IndexedDB inside a SharedWorker with code examples

Managing IndexedDB inside a **SharedWorker** centralizes all client-side database reads, writes, and schema migrations into a single multi-tab thread.

Instead of having multiple browser tabs opening separate IndexedDB connections—which leads to `versionchange` locks, schema upgrade blocks, and race conditions—all open tabs delegate database interactions to the SharedWorker through a unified `MessagePort` architecture.

## 2. Step 1: The SharedWorker Script (`db-worker.js`)

The SharedWorker opens a **single** persistent connection to IndexedDB, listens for incoming messages from connected tabs, executes database operations safely, and broadcasts mutations back to all open tabs.

```javascript
// db-worker.js

// Track all active tab ports for broadcasting
const connectedPorts = new Set();
let db = null;

// Initialize IndexedDB connection inside the SharedWorker
function initDB() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open("AppSharedDB", 1);

    request.onupgradeneeded = (event) => {
      const db = event.target.result;
      if (!db.objectStoreNames.contains("users")) {
        db.createObjectStore("users", { keyPath: "id" });
      }
    };

    request.onsuccess = (event) => {
      db = event.target.result;
      console.log("[SharedWorker] IndexedDB connected successfully.");
      resolve(db);
    };

    request.onerror = (event) => {
      console.error("[SharedWorker] IndexedDB error:", event.target.error);
      reject(event.target.error);
    };
  });
}

// Start database connection
const dbPromise = initDB();

// Handle tab connections
self.onconnect = (event) => {
  const port = event.ports[0];
  connectedPorts.add(port);
  port.start();

  port.onmessage = async (event) => {
    const { id, action, payload } = event.data;

    // Ensure DB is initialized before processing requests
    await dbPromise;

    try {
      let result;

      switch (action) {
        case "GET_ALL_USERS":
          result = await getAllUsers();
          port.postMessage({ id, success: true, result });
          break;

        case "ADD_USER":
          result = await addUser(payload);
          port.postMessage({ id, success: true, result });

          // Broadcast change to ALL other open tabs
          broadcastEvent("USER_ADDED", result, port);
          break;

        default:
          port.postMessage({ id, success: false, error: "Unknown action" });
      }
    } catch (error) {
      port.postMessage({ id, success: false, error: error.message });
    }
  };

  // Clean up disconnected ports
  port.onmessageerror = () => connectedPorts.delete(port);
};

// ====================================================
// IndexedDB Helper Operations
// ====================================================

function getAllUsers() {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("users", "readonly");
    const store = tx.objectStore("users");
    const request = store.getAll();

    request.onsuccess = () => resolve(request.result);
    request.onerror = () => reject(request.error);
  });
}

function addUser(user) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("users", "readwrite");
    const store = tx.objectStore("users");
    const request = store.put(user);

    request.onsuccess = () => resolve(user);
    request.onerror = () => reject(request.error);
  });
}

// Broadcast updates to all connected tabs except sender (optional)
function broadcastEvent(type, payload, senderPort) {
  const message = { type, payload, isBroadcast: true };
  connectedPorts.forEach((p) => {
    if (p !== senderPort) {
      p.postMessage(message);
    }
  });
}

```

## 3. Step 2: The Main Thread Client (`db-client.js`)

Tabs interact with the SharedWorker using a Promise-based RPC (Remote Procedure Call) wrapper. Each request attaches a unique request ID so responses can be matched cleanly.

```javascript
// db-client.js
class SharedDBClient {
  constructor() {
    this.worker = new SharedWorker("db-worker.js");
    this.port = this.worker.port;
    this.pendingRequests = new Map();
    this.requestId = 0;

    this.init();
  }

  init() {
    this.port.start();

    // Listen for responses and broadcast events from SharedWorker
    this.port.onmessage = (event) => {
      const { id, success, result, error, isBroadcast, type, payload } = event.data;

      // Handle real-time broadcast updates from other tabs
      if (isBroadcast) {
        console.log(`[Tab UI Sync] Received broadcast event "${type}":`, payload);
        this.onBroadcastReceived(type, payload);
        return;
      }

      // Resolve pending RPC request Promise
      if (this.pendingRequests.has(id)) {
        const { resolve, reject } = this.pendingRequests.get(id);
        this.pendingRequests.delete(id);

        if (success) {
          resolve(result);
        } else {
          reject(new Error(error));
        }
      }
    };
  }

  // Generic request dispatcher returning a Promise
  sendRequest(action, payload = null) {
    return new Promise((resolve, reject) => {
      const id = ++this.requestId;
      this.pendingRequests.set(id, { resolve, reject });

      this.port.postMessage({ id, action, payload });
    });
  }

  // API Methods
  getAllUsers() {
    return this.sendRequest("GET_ALL_USERS");
  }

  addUser(user) {
    return this.sendRequest("ADD_USER", user);
  }

  // Hook for UI updates when another tab modifies the DB
  onBroadcastReceived(type, payload) {
    if (type === "USER_ADDED") {
      const userList = document.querySelector("#user-list");
      if (userList) {
        const li = document.createElement("li");
        li.textContent = `${payload.name} (ID: ${payload.id})`;
        userList.appendChild(li);
      }
    }
  }
}

// ====================================================
// Usage inside Web Page
// ====================================================
const dbClient = new SharedDBClient();

// Add user on button click
document.querySelector("#addBtn").addEventListener("click", async () => {
  const newUser = { id: Date.now(), name: "Alice" };
  await dbClient.addUser(newUser);
  console.log("User saved via SharedWorker!");
});

// Fetch all users on load
window.addEventListener("DOMContentLoaded", async () => {
  const users = await dbClient.getAllUsers();
  console.log("Loaded users:", users);
});

```

## 4. Key Advantages of This Pattern

1. **Eliminates `versionchange` Lock Conflicts:** Because only one thread holds a database connection, opening 50 tabs won't trigger database lock contention or `onblocked` errors during schema migrations.
2. **Built-in Cross-Tab Broadcasting:** When Tab 1 writes data, the SharedWorker automatically pushes the change notification to Tabs 2, 3, and 4 over open `MessagePort` channels.
3. **Connection Pooling:** Cuts down memory and CPU overhead by maintaining a single database instance instead of spawning multiple connections across tabs.

| **Locking Overhead** | Multi-tab transaction & schema locks      | Serialized inside a single thread                |

Explain how to manage a single WebSocket connection and IndexedDB inside a SharedWorker with code examples

Combining a **SharedWorker**, a **single WebSocket connection**, and **IndexedDB** establishes a centralized background hub for multi-tab web applications.

Instead of every open tab establishing its own WebSocket connection and running separate database reads/writes, the SharedWorker centralizes these responsibilities:

1. **Single WebSocket Management:** Maintains one persistent real-time socket connection regardless of how many tabs the user opens.
2. **Centralized Data Storage:** Persists incoming real-time socket payloads directly into **IndexedDB** without multi-tab locking conflicts or race conditions.
3. **Cross-Tab State Broadcasting:** Distributes live socket events and database updates to all connected tabs over `MessagePort` instances.

## 1. Step 1: The SharedWorker Script (`shared-hub.js`)

The SharedWorker opens a single connection to IndexedDB, initializes a WebSocket instance, handles reconnects automatically, and routes incoming/outgoing messages across active tab ports.

```javascript
// shared-hub.js (SharedWorker)

const connectedPorts = new Set();
let db = null;
let socket = null;
let reconnectTimer = null;

// ====================================================
// 1. INDEXEDDB INITIALIZATION & HELPERS
// ====================================================
function initDB() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open("AppHubDB", 1);

    request.onupgradeneeded = (e) => {
      const database = e.target.result;
      if (!database.objectStoreNames.contains("messages")) {
        database.createObjectStore("messages", { keyPath: "id" });
      }
    };

    request.onsuccess = (e) => {
      db = e.target.result;
      console.log("[SharedWorker] IndexedDB initialized.");
      resolve(db);
    };

    request.onerror = (e) => reject(e.target.error);
  });
}

function saveMessageToDB(message) {
  return new Promise((resolve, reject) => {
    if (!db) return reject(new Error("Database not ready"));
    const tx = db.transaction("messages", "readwrite");
    const store = tx.objectStore("messages");
    const req = store.put(message);

    req.onsuccess = () => resolve(message);
    req.onerror = () => reject(req.error);
  });
}

function getAllMessagesFromDB() {
  return new Promise((resolve, reject) => {
    if (!db) return reject(new Error("Database not ready"));
    const tx = db.transaction("messages", "readonly");
    const store = tx.objectStore("messages");
    const req = store.getAll();

    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}

// ====================================================
// 2. WEBSOCKET MANAGEMENT
// ====================================================
function initWebSocket() {
  if (socket && (socket.readyState === WebSocket.OPEN || socket.readyState === WebSocket.CONNECTING)) {
    return;
  }

  console.log("[SharedWorker] Connecting to WebSocket...");
  socket = new WebSocket("wss://echo.websocket.events"); // Public echo socket for testing

  socket.onopen = () => {
    console.log("[SharedWorker] WebSocket connection established.");
    broadcastToAllTabs({ type: "SOCKET_STATUS", status: "CONNECTED" });
  };

  socket.onmessage = async (event) => {
    console.log("[SharedWorker] Received WebSocket message:", event.data);

    const messageData = {
      id: Date.now() + Math.random().toString(36).substr(2, 4),
      text: event.data,
      timestamp: Date.now(),
    };

    try {
      // Step A: Persist payload directly into IndexedDB
      await saveMessageToDB(messageData);

      // Step B: Broadcast payload and update notification to all tabs
      broadcastToAllTabs({
        type: "NEW_MESSAGE",
        payload: messageData,
      });
    } catch (err) {
      console.error("[SharedWorker] Failed to persist socket message:", err);
    }
  };

  socket.onclose = () => {
    console.warn("[SharedWorker] WebSocket disconnected. Retrying in 3 seconds...");
    broadcastToAllTabs({ type: "SOCKET_STATUS", status: "DISCONNECTED" });

    // Auto-reconnect after delay
    clearTimeout(reconnectTimer);
    reconnectTimer = setTimeout(initWebSocket, 3000);
  };

  socket.onerror = (err) => {
    console.error("[SharedWorker] WebSocket error:", err);
  };
}

function broadcastToAllTabs(message) {
  connectedPorts.forEach((port) => port.postMessage(message));
}

// ====================================================
// 3. TAB PORT COMMUNICATION & RPC HANDLER
// ====================================================
const dbPromise = initDB();

self.onconnect = (event) => {
  const port = event.ports[0];
  connectedPorts.add(port);
  port.start();

  // Initialize socket when at least one tab opens
  initWebSocket();

  port.onmessage = async (event) => {
    const { id, action, payload } = event.data;
    await dbPromise;

    try {
      switch (action) {
        case "GET_HISTORY": {
          const messages = await getAllMessagesFromDB();
          port.postMessage({ id, success: true, result: messages });
          break;
        }

        case "SEND_WEBSOCKET_MESSAGE": {
          if (socket && socket.readyState === WebSocket.OPEN) {
            socket.send(payload.text);
            port.postMessage({ id, success: true });
          } else {
            port.postMessage({ id, success: false, error: "WebSocket is not connected" });
          }
          break;
        }

        default:
          port.postMessage({ id, success: false, error: "Unknown action" });
      }
    } catch (error) {
      port.postMessage({ id, success: false, error: error.message });
    }
  };

  // Clean up port reference when tab closes
  port.onmessageerror = () => connectedPorts.delete(port);
};

```

## 2. Step 2: Main Thread Tab Client (`hub-client.js`)

Each open tab connects to `shared-hub.js`. It exposes a Promise-based request-response pattern for querying IndexedDB or sending socket messages, and registers a listener for live broadcast updates pushed from the SharedWorker.

```javascript
// hub-client.js
class SharedHubClient {
  constructor() {
    this.worker = new SharedWorker("shared-hub.js");
    this.port = this.worker.port;
    this.pendingRequests = new Map();
    this.requestId = 0;
    this.listeners = new Map();

    this.init();
  }

  init() {
    this.port.start();

    this.port.onmessage = (event) => {
      const data = event.data;

      // Check if message is a broadcast from the worker
      if (data.type) {
        this.emit(data.type, data.payload || data.status);
        return;
      }

      // Handle RPC Request/Response promises
      const { id, success, result, error } = data;
      if (this.pendingRequests.has(id)) {
        const { resolve, reject } = this.pendingRequests.get(id);
        this.pendingRequests.delete(id);

        if (success) {
          resolve(result);
        } else {
          reject(new Error(error));
        }
      }
    };
  }

  // Event Emitter for broadcasts
  on(event, callback) {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, []);
    }
    this.listeners.get(event).push(callback);
  }

  emit(event, payload) {
    if (this.listeners.has(event)) {
      this.listeners.get(event).forEach((cb) => cb(payload));
    }
  }

  // Dispatch message to SharedWorker
  sendRequest(action, payload = null) {
    return new Promise((resolve, reject) => {
      const id = ++this.requestId;
      this.pendingRequests.set(id, { resolve, reject });
      this.port.postMessage({ id, action, payload });
    });
  }

  // API Methods
  getHistory() {
    return this.sendRequest("GET_HISTORY");
  }

  sendMessageOverSocket(text) {
    return this.sendRequest("SEND_WEBSOCKET_MESSAGE", { text });
  }
}

```

Explain Service Worker caching strategies with code examples

Service Worker caching strategies dictate how an application serves resources when a user visits a page. Depending on the resource type—such as static assets, dynamic API data, or user avatars—choosing the right strategy determines whether your app prioritizes **speed**, **freshness**, or **offline availability**.

---

## 1. Summary Matrix

| Strategy                   | Speed     | Freshness                                      | Offline Support | Best Used For                                             |
| -------------------------- | --------- | ---------------------------------------------- | --------------- | --------------------------------------------------------- |
| **Cache First**            | ⚡ Fastest | 🐢 Slow (stale until cache update)              | ✅ Excellent     | Static assets (CSS, JS, fonts, images).                   |
| **Network First**          | 🐢 Slower  | ⚡ Always fresh (if online)                     | ✅ Fallback      | Frequently updating content (user feeds, dashboards).     |
| **Stale-While-Revalidate** | ⚡ Fastest | ⚡ Medium (serves stale, updates in background) | ✅ Excellent     | Avatar images, news feeds, non-critical APIs.             |
| **Network Only**           | 🐢 Slower  | ⚡ Always fresh                                 | ❌ None          | Non-cacheable transactions (checkout API, POST requests). |
| **Cache Only**             | ⚡ Fastest | ❌ Never updates                                | ✅ Excellent     | Pre-cached core app shell assets (e.g. `offline.html`).   |

## 2. The 5 Core Strategies with Code Examples

All examples below belong inside a Service Worker file (`sw.js`) listening to the `fetch` event.

### 1. Cache First (Falling Back to Network)

Looks for a match in the cache first. If found, returns it immediately. If not found, fetches it from the network, caches it for future requests, and returns it.

```javascript
// sw.js
const CACHE_NAME = "static-assets-v1";

self.addEventListener("fetch", (event) => {
  // Apply Cache-First to images, fonts, and static bundles
  if (event.request.destination === "style" || event.request.destination === "image") {
    event.respondWith(
      caches.match(event.request).then((cachedResponse) => {
        if (cachedResponse) {
          return cachedResponse; // Return cached asset immediately
        }

        // Fetch from network if missing in cache
        return fetch(event.request).then((networkResponse) => {
          // Open cache and save the new asset
          return caches.open(CACHE_NAME).then((cache) => {
            cache.put(event.request, networkResponse.clone());
            return networkResponse;
          });
        });
      })
    );
  }
});

```

---

### 2. Network First (Falling Back to Cache)

Attempts to fetch the freshest version over the network. If the request fails (e.g., user is offline or connection is poor), it falls back to serving the cached version.

```javascript
// sw.js
const DYNAMIC_CACHE = "dynamic-data-v1";

self.addEventListener("fetch", (event) => {
  // Apply Network-First to API data or main page documents
  if (event.request.mode === "navigate" || event.request.url.includes("/api/")) {
    event.respondWith(
      fetch(event.request)
        .then((networkResponse) => {
          // Update cache with the latest response from network
          return caches.open(DYNAMIC_CACHE).then((cache) => {
            cache.put(event.request, networkResponse.clone());
            return networkResponse;
          });
        })
        .catch(() => {
          // Offline fallback: serve cached version if network fails
          return caches.match(event.request);
        })
    );
  }
});

```

---

### 3. Stale-While-Revalidate (Fastest + Auto-Updating)

Instantly serves the cached version to keep the UI feeling instant, while asynchronously sending a network request in the background to update the cache for the *next* page load.

```javascript
// sw.js
const SWR_CACHE = "swr-cache-v1";

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.open(SWR_CACHE).then((cache) => {
      return cache.match(event.request).then((cachedResponse) => {
        // Trigger background revalidation request
        const fetchPromise = fetch(event.request).then((networkResponse) => {
          // Update cache in the background
          cache.put(event.request, networkResponse.clone());
          return networkResponse;
        });

        // Return cached version immediately if available, else wait for network
        return cachedResponse || fetchPromise;
      });
    })
  );
});

```

---

### 4. Network Only

Bypasses the Service Worker cache completely and sends the request directly to the network. If offline, the request fails.

```javascript
// sw.js
self.addEventListener("fetch", (event) => {
  // Never cache POST requests or payments
  if (event.request.method === "POST" || event.request.url.includes("/api/checkout")) {
    event.respondWith(fetch(event.request));
  }
});

```

---

### 5. Cache Only

Serves requests strictly from the cache. If the asset does not exist in the cache, the request fails. Useful for static offline fallbacks pre-cached during Service Worker installation.

```javascript
// sw.js
self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open("offline-v1").then((cache) => {
      // Pre-cache offline page during installation
      return cache.add("/offline.html");
    })
  );
});

self.addEventListener("fetch", (event) => {
  // Serve offline page if user is completely disconnected
  if (event.request.mode === "navigate") {
    event.respondWith(
      fetch(event.request).catch(() => caches.match("/offline.html"))
    );
  }
});

```

## 3. Declarative Routing with Workbox

Writing manual `caches.match()` and `fetch()` handlers for every route can become tedious. Google's **Workbox** library simplifies routing strategies using a declarative syntax:

```javascript
import { registerRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';

// 1. Cache-First for Images with expiration rule
registerRoute(
  ({ request }) => request.destination === 'image',
  new CacheFirst({
    cacheName: 'images-cache',
    plugins: [
      new ExpirationPlugin({
        maxEntries: 60,
        maxAgeSeconds: 30 * 24 * 60 * 60, // 30 Days
      }),
    ],
  })
);

// 2. Network-First for API calls
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/'),
  new NetworkFirst({
    cacheName: 'api-cache',
  })
);

// 3. Stale-While-Revalidate for CSS/JS assets
registerRoute(
  ({ request }) => request.destination === 'script' || request.destination === 'style',
  new StaleWhileRevalidate({
    cacheName: 'static-resources',
  })
);

```
