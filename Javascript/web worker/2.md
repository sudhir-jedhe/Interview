Explain Service Worker caching strategies with code examples

Service Worker caching strategies dictate how an application serves resources when a user visits a page. Depending on the resource type—such as static assets, dynamic API data, or user avatars—choosing the right strategy determines whether your app prioritizes **speed**, **freshness**, or **offline availability**.

---

## 1. Summary Matrix

| Strategy                   | Speed     | Freshness                                      | Offline Support | Best Used For                                             |
| -------------------------- | --------- | ---------------------------------------------- | --------------- | --------------------------------------------------------- |
| **Cache First**            | ⚡ Fastest | 🐢 Slow (stale until cache update)              | ✅ Excellent     | Static assets (CSS, JS, fonts, images).                   |
| **Network First**          | 🐢 Slower  | ⚡ Always fresh (if online)                     | ✅ Fallback      | Frequently updating content (user feeds, dashboards).     |
| **Stale-While-Revalidate** | ⚡ Fastest | ⚡ Medium (serves stale, updates in background) | ✅ Excellent     | Avatar images, news feeds, non-critical APIs.             |
| **Network Only**           | 🐢 Slower  | ⚡ Always fresh                                 | ❌ None          | Non-cacheable transactions (checkout API, POST requests). |
| **Cache Only**             | ⚡ Fastest | ❌ Never updates                                | ✅ Excellent     | Pre-cached core app shell assets (e.g. offline.html).     |

---

## 2. The 5 Core Strategies with Code Examples

All examples below belong inside a Service Worker file (`sw.js`) listening to the `fetch` event.

### 1. Cache First (Falling Back to Network)

Looks for a match in the cache first. If found, returns it immediately. If not found, fetches it from the network, caches it for future requests, and returns it.

```javascript
// sw.js
const CACHE_NAME = "static-assets-v1";

self.addEventListener("fetch", (event) => {
  // Apply Cache-First to images, fonts, and static bundles
  if (event.request.destination === "style" || event.request.destination === "image") {
    event.respondWith(
      caches.match(event.request).then((cachedResponse) => {
        if (cachedResponse) {
          return cachedResponse; // Return cached asset immediately
        }

        // Fetch from network if missing in cache
        return fetch(event.request).then((networkResponse) => {
          // Open cache and save the new asset
          return caches.open(CACHE_NAME).then((cache) => {
            cache.put(event.request, networkResponse.clone());
            return networkResponse;
          });
        });
      })
    );
  }
});

```

---

### 2. Network First (Falling Back to Cache)

Attempts to fetch the freshest version over the network. If the request fails (e.g., user is offline or connection is poor), it falls back to serving the cached version.

```javascript
// sw.js
const DYNAMIC_CACHE = "dynamic-data-v1";

self.addEventListener("fetch", (event) => {
  // Apply Network-First to API data or main page documents
  if (event.request.mode === "navigate" || event.request.url.includes("/api/")) {
    event.respondWith(
      fetch(event.request)
        .then((networkResponse) => {
          // Update cache with the latest response from network
          return caches.open(DYNAMIC_CACHE).then((cache) => {
            cache.put(event.request, networkResponse.clone());
            return networkResponse;
          });
        })
        .catch(() => {
          // Offline fallback: serve cached version if network fails
          return caches.match(event.request);
        })
    );
  }
});

```

---

### 3. Stale-While-Revalidate (Fastest + Auto-Updating)

Instantly serves the cached version to keep the UI feeling instant, while asynchronously sending a network request in the background to update the cache for the *next* page load.

```javascript
// sw.js
const SWR_CACHE = "swr-cache-v1";

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.open(SWR_CACHE).then((cache) => {
      return cache.match(event.request).then((cachedResponse) => {
        // Trigger background revalidation request
        const fetchPromise = fetch(event.request).then((networkResponse) => {
          // Update cache in the background
          cache.put(event.request, networkResponse.clone());
          return networkResponse;
        });

        // Return cached version immediately if available, else wait for network
        return cachedResponse || fetchPromise;
      });
    })
  );
});

```

---

### 4. Network Only

Bypasses the Service Worker cache completely and sends the request directly to the network. If offline, the request fails.

```javascript
// sw.js
self.addEventListener("fetch", (event) => {
  // Never cache POST requests or payments
  if (event.request.method === "POST" || event.request.url.includes("/api/checkout")) {
    event.respondWith(fetch(event.request));
  }
});

```

---

### 5. Cache Only

Serves requests strictly from the cache. If the asset does not exist in the cache, the request fails. Useful for static offline fallbacks pre-cached during Service Worker installation.

```javascript
// sw.js
self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open("offline-v1").then((cache) => {
      // Pre-cache offline page during installation
      return cache.add("/offline.html");
    })
  );
});

self.addEventListener("fetch", (event) => {
  // Serve offline page if user is completely disconnected
  if (event.request.mode === "navigate") {
    event.respondWith(
      fetch(event.request).catch(() => caches.match("/offline.html"))
    );
  }
});

```

---

## 3. High-Level Management with Workbox

Writing manual `caches.match()` and `fetch()` handlers for every route can become tedious. Google's **Workbox** library simplifies routing strategies using a declarative syntax:

```javascript
import { registerRoute } from 'workbox-routing';
import { CacheFirst, NetworkFirst, StaleWhileRevalidate } from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';

// 1. Cache-First for Images with expiration rule
registerRoute(
  ({ request }) => request.destination === 'image',
  new CacheFirst({
    cacheName: 'images-cache',
    plugins: [
      new ExpirationPlugin({
        maxEntries: 60,
        maxAgeSeconds: 30 * 24 * 60 * 60, // 30 Days
      }),
    ],
  })
);

// 2. Network-First for API calls
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/'),
  new NetworkFirst({
    cacheName: 'api-cache',
  })
);

// 3. Stale-While-Revalidate for CSS/JS assets
registerRoute(
  ({ request }) => request.destination === 'script' || request.destination === 'style',
  new StaleWhileRevalidate({
    cacheName: 'static-resources',
  })
);

```

Explain Service Worker cache versioning and update activation lifecycle with code examples

When updating a Service Worker, managing **cache versioning** and understanding the **Service Worker lifecycle** is critical.

Without proper versioning and activation management, users can get stuck on old cached JavaScript/CSS assets indefinitely, or the application might crash due to mismatched cache assets between old and new versions.

---

## 1. The Service Worker Lifecycle

A Service Worker goes through three distinct phases:

```text
 ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
 │  Installing  │ ──► │   Waiting    │ ──► │  Activated   │
 │ (Pre-caches) │     │ (Skip-Waiting│     │(Cleans old   │
 └──────────────┘     │   required)  │     │  caches)     │
                      └──────────────┘     └──────────────┘

```

1. **Install (`install` event):** The browser detects byte changes in `sw.js`. It downloads the new file and triggers the `install` event to pre-cache static assets for the **new version**.
2. **Waiting / Installed:** The new Service Worker is ready, but it enters a **waiting state** so it does not interrupt open browser tabs running the old version.
3. **Activate (`activate` event):** Once all open tabs running the old version are closed (or skipped via `skipWaiting()`), the new Service Worker activates and cleans up **outdated cache versions**.

---

## 2. Complete Production Implementation (`sw.js`)

Here is a full Service Worker implementation demonstrating cache versioning, immediate activation (`skipWaiting`), and automatic cleanup of legacy caches (`caches.delete`).

```javascript
// Change version string whenever updating assets/code
const CACHE_VERSION = "v2";
const STATIC_CACHE = `static-assets-${CACHE_VERSION}`;
const DYNAMIC_CACHE = `dynamic-data-${CACHE_VERSION}`;

// Pre-cached assets for the App Shell
const PRECACHE_ASSETS = [
  "/",
  "/index.html",
  "/styles.css",
  "/app.js",
  "/offline.html"
];

// ====================================================
// 1. INSTALL EVENT: Pre-cache new version assets
// ====================================================
self.addEventListener("install", (event) => {
  console.log(`[Service Worker ${CACHE_VERSION}] Installing...`);

  event.waitUntil(
    caches.open(STATIC_CACHE).then((cache) => {
      console.log(`[Service Worker ${CACHE_VERSION}] Pre-caching app shell...`);
      return cache.addAll(PRECACHE_ASSETS);
    })
  );

  // Force the waiting Service Worker to become the active Service Worker immediately
  self.skipWaiting();
});

// ====================================================
// 2. ACTIVATE EVENT: Delete obsolete caches
// ====================================================
self.addEventListener("activate", (event) => {
  console.log(`[Service Worker ${CACHE_VERSION}] Activating...`);

  event.waitUntil(
    caches.keys().then((cacheNames) => {
      return Promise.all(
        cacheNames.map((cacheName) => {
          // Delete any cache that belongs to an older version
          if (cacheName !== STATIC_CACHE && cacheName !== DYNAMIC_CACHE) {
            console.log(`[Service Worker ${CACHE_VERSION}] Deleting old cache: ${cacheName}`);
            return caches.delete(cacheName);
          }
        })
      );
    }).then(() => {
      // Take control of all unlocked open clients/tabs immediately
      return self.clients.claim();
    })
  );
});

// ====================================================
// 3. FETCH EVENT: Serve active version assets
// ====================================================
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cachedResponse) => {
      if (cachedResponse) {
        return cachedResponse;
      }
      return fetch(event.request).then((networkResponse) => {
        return caches.open(DYNAMIC_CACHE).then((cache) => {
          cache.put(event.request, networkResponse.clone());
          return networkResponse;
        });
      });
    }).catch(() => caches.match("/offline.html"))
  );
});

```

## 3. Client-Side Lifecycle Management (`app.js`)

To notify users in real-time when an update is available (and allow them to refresh to load the latest app version), listen to lifecycle events on the main thread:

```javascript
// app.js (Main Thread)
if ("serviceWorker" in navigator) {
  window.addEventListener("load", async () => {
    try {
      const registration = await navigator.serviceWorker.register("/sw.js");

      // 1. Check if an update is already waiting
      if (registration.waiting) {
        promptUserForUpdate(registration.waiting);
      }

      // 2. Listen for new updates detected in the background
      registration.addEventListener("updatefound", () => {
        const newWorker = registration.installing;

        newWorker.addEventListener("statechange", () => {
          if (newWorker.state === "installed" && navigator.serviceWorker.controller) {
            // New version installed, waiting for user activation
            promptUserForUpdate(newWorker);
          }
        });
      });

    } catch (error) {
      console.error("Service Worker registration failed:", error);
    }
  });

  // Reload page automatically when the new Service Worker takes control
  let refreshing = false;
  navigator.serviceWorker.addEventListener("controllerchange", () => {
    if (!refreshing) {
      refreshing = true;
      window.location.reload();
    }
  });
}

function promptUserForUpdate(worker) {
  // Show a UI toast notification to the user
  const userConfirmed = confirm("A new version of the app is available! Reload now?");
  if (userConfirmed) {
    // Send message to Service Worker to trigger skipWaiting()
    worker.postMessage({ action: "skipWaiting" });
  }
}

```

---

## 4. Key Activation Directives Explained

### `self.skipWaiting()`

* **Default behavior:** When a new `sw.js` installs, it sits in the `waiting` state until **all** open tabs running the old Service Worker are closed by the user.
* **With `skipWaiting()`:** The installing worker skips the waiting state and moves directly to the `activate` phase.

### `self.clients.claim()`

* **Default behavior:** An activated Service Worker does not control existing open tabs until those tabs are reloaded.
* **With `clients.claim()`:** The newly activated Service Worker takes immediate control of all open pages/tabs in the scope without requiring a page reload.

---

## Summary Lifecycle Flow

| Phase        | Event              | Action Taken                                           | Key Method                 |
| ------------ | ------------------ | ------------------------------------------------------ | -------------------------- |
| **Install**  | `install`          | Pre-caches static assets under `v2` cache names.       | `self.skipWaiting()`       |
| **Activate** | `activate`         | Compares cache names and deletes outdated `v1` caches. | `self.clients.claim()`     |
| **Update**   | `controllerchange` | Main thread detects controller swap and reloads UI.    | `window.location.reload()` |

Explain Background Sync API in Service Workers with code examples

The **Background Sync API** is a Web API that allows web applications to defer server requests to a background Service Worker until a user has a stable internet connection.

If a user performs an action while offline (e.g., sending a message, posting a comment, or submitting a form), standard `fetch()` calls fail immediately. Background Sync queues these requests in persistent storage (like `IndexedDB`) and registers a **sync event**. The browser then executes the request automatically in the background as soon as connectivity is restored—even if the user has closed the tab or navigated away.

---

## How Background Sync Works

```text
┌─────────────────┐       1. Offline Form Submit       ┌──────────────────┐
│ Main Thread Page│ ─────────────────────────────────► │ IndexedDB Queue  │
└────────┬────────┘                                    └────────┬─────────┘
         │                                                      │
         │ 2. Register Sync ('sync-messages')                   │
         ▼                                                      │
┌─────────────────┐       3. Connection Restored        ┌───────┴──────────┐
│ Service Worker  │ ◄────────────────────────────────── │  Sync Event      │
└────────┬────────┘                                     └───────┬──────────┘
         │                                                      │
         │ 4. Read Queue & Send Fetch                           │
         ▼                                                      │
┌─────────────────┐ ◄───────────────────────────────────────────┘
│ Server / API    │
└─────────────────┘

```

---

## 1. Step 1: Registering a Sync Task on the Main Thread (`app.js`)

When a user submits a form or performs an offline action:

1. Save the payload to **IndexedDB** so it survives browser restarts.
2. Register a sync task tag (e.g., `'sync-pending-messages'`) using `navigator.serviceWorker.ready`.

```javascript
// app.js (Main Thread)
import { saveToIndexedDB } from './db-utils.js'; // Helper function to save to IndexedDB

async function handleSendMessage(messageData) {
  try {
    // Attempt standard network request first
    const response = await fetch('/api/messages', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(messageData)
    });

    if (response.ok) {
      console.log('Message sent successfully online!');
      return;
    }
  } catch (error) {
    console.warn('Network offline or failed. Registering Background Sync...');
  }

  // Fallback: If offline or request failed
  if ('serviceWorker' in navigator && 'SyncManager' in window) {
    // 1. Save data to IndexedDB
    await saveToIndexedDB('pending_messages', messageData);

    // 2. Register sync tag with the Service Worker
    const registration = await navigator.serviceWorker.ready;
    await registration.sync.register('sync-pending-messages');

    console.log('Background Sync registered! Will send when online.');
  } else {
    console.error('Background Sync not supported in this browser.');
  }
}

```

---

## 2. Step 2: Listening for the Sync Event in the Service Worker (`sw.js`)

In the Service Worker, listen for the `'sync'` event. Check the event tag, retrieve queued items from IndexedDB, and send them to the server.

```javascript
// sw.js (Service Worker)
import { getFromIndexedDB, deleteFromIndexedDB } from './db-utils.js';

self.addEventListener('sync', (event) => {
  // Check for the specific sync tag
  if (event.tag === 'sync-pending-messages') {
    console.log('[Service Worker] Sync event triggered for: sync-pending-messages');

    // waitUntil keeps the Service Worker alive until the promise resolves
    event.waitUntil(processPendingMessages());
  }
});

async function processPendingMessages() {
  // 1. Read all pending items from IndexedDB
  const pendingMessages = await getFromIndexedDB('pending_messages');

  for (const message of pendingMessages) {
    try {
      // 2. Attempt to POST data to the server
      const response = await fetch('/api/messages', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(message)
      });

      if (response.ok) {
        console.log(`[Service Worker] Successfully synced message #${message.id}`);
        // 3. Remove successfully sent item from IndexedDB
        await deleteFromIndexedDB('pending_messages', message.id);
      } else {
        throw new Error(`Server status HTTP ${response.status}`);
      }
    } catch (error) {
      console.error(`[Service Worker] Sync failed for message #${message.id}:`, error.message);
      
      // Re-throwing the error causes the browser to retry the sync event later with exponential backoff
      throw error;
    }
  }
}

```

---

## 3. Retries and Exponential Backoff

If `event.waitUntil()` receives a rejected Promise (for example, if the server returns a $503$ error or the connection drops mid-sync):

* The browser automatically re-schedules the `sync` event.
* Retries occur using a browser-managed **exponential backoff** strategy.
* The Service Worker will retry periodically until the operation succeeds or max retries are reached.

---

## 4. Browser Compatibility & Limits

| Feature                   | Support             | Notes                                                                                         |
| ------------------------- | ------------------- | --------------------------------------------------------------------------------------------- |
| **Chrome / Edge / Opera** | ✅ Full Support      | Supported in all Chromium desktop and Android browsers.                                       |
| **Firefox**               | ⚠️ Partial / Flagged | In active development; requires experimental flags in some builds.                            |
| **Safari (iOS / macOS)**  | ❌ Not Supported     | Safari does not support the One-Shot Background Sync API (uses Background Fetch API instead). |

### Graceful Fallback Strategy

Because Safari lacks support for Background Sync, always implement a fallback checking `navigator.onLine` or listening to the `'online'` window event:

```javascript
// Fallback for browsers lacking SyncManager support
if (!('SyncManager' in window)) {
  window.addEventListener('online', () => {
    console.log('Online event detected. Triggering manual queue processing...');
    processPendingMessagesManually();
  });
}

```

Explain Periodic Background Sync API in Service Workers with code examples

While standard **Background Sync** triggers a task once when the user recovers network connection, the **Periodic Background Sync API** allows web applications to schedule background updates at periodic intervals (e.g., daily, hourly, or every few hours).

This enables Progressive Web Apps (PWAs) to fetch fresh content—like news articles, weather updates, or social feeds—in the background so that the latest content is instantly available the next time the user opens the app, even if they are offline.

---

## 1. How Periodic Sync Works & Key Requirements

Because periodic execution drains battery and uses background data, browsers enforce strict permissions and requirements:

1. **PWA Requirement:** The site must be installed as a Progressive Web App (PWA).
2. **Site Engagement Score:** The browser allocates sync frequency based on how often the user visits the site. High engagement = more frequent background updates.
3. **Permission Check:** Requires the `'periodic-background-sync'` permission (granted automatically on installed PWAs in Chromium browsers).

```text
┌─────────────────┐       1. Register Periodic Sync    ┌──────────────────┐
│ Main Thread Page│ ─────────────────────────────────► │ Browser Scheduler│
└─────────────────┘                                    └────────┬─────────┘
                                                                │
                                                                │ 2. Interval Elapsed &
                                                                │    Conditions Met
                                                                ▼
┌─────────────────┐       3. Fetch & Update Cache      ┌──────────────────┐
│ Server / API    │ ◄───────────────────────────────── │ Service Worker   │
└─────────────────┘                                    └──────────────────┘

```

---

## 2. Step 1: Requesting Permission and Registering (`app.js`)

Registration happens on the main thread. You verify browser support, check or request the permission state, and register a tag with a `minInterval`.

```javascript
// app.js (Main Thread)
async function registerPeriodicSync() {
  if (!('serviceWorker' in navigator)) return;

  const registration = await navigator.serviceWorker.ready;

  // 1. Check if Periodic Background Sync is supported by the browser
  if ('periodicSync' in registration) {
    try {
      // 2. Check permission status
      const status = await navigator.permissions.query({
        name: 'periodic-background-sync',
      });

      if (status.state === 'granted') {
        // 3. Register the periodic sync tag
        // minInterval is a hint in milliseconds (e.g., 24 hours)
        await registration.periodicSync.register('update-latest-news', {
          minInterval: 24 * 60 * 60 * 1000, // Request update once per day
        });

        console.log('Periodic Background Sync registered successfully!');
      } else {
        console.warn('Periodic Background Sync permission denied.');
      }
    } catch (error) {
      console.error('Periodic Sync registration failed:', error);
    }
  } else {
    console.log('Periodic Background Sync is not supported by this browser.');
  }
}

registerPeriodicSync();

```

---

## 3. Step 2: Handling the Event in the Service Worker (`sw.js`)

In the Service Worker, listen for the **`periodicsync`** event, match the registered tag, and fetch fresh data to update the Cache Storage.

```javascript
// sw.js (Service Worker)
const NEWS_CACHE_NAME = 'latest-news-v1';

self.addEventListener('periodicsync', (event) => {
  if (event.tag === 'update-latest-news') {
    console.log('[Service Worker] Running periodic sync: update-latest-news');

    // Keep the Service Worker alive until the background fetch/cache completes
    event.waitUntil(fetchAndCacheLatestNews());
  }
});

async function fetchAndCacheLatestNews() {
  try {
    const response = await fetch('/api/news/latest');
    
    if (response.ok) {
      const cache = await caches.open(NEWS_CACHE_NAME);
      // Cache the response so it is immediately ready when the user opens the app
      await cache.put('/api/news/latest', response);
      console.log('[Service Worker] Background content refresh complete!');
    }
  } catch (error) {
    console.error('[Service Worker] Periodic fetch failed:', error);
  }
}

```

You can query currently registered periodic sync tags or remove them if the user disables background updates in your app settings.

```javascript
async function listPeriodicSyncTags() {

  }
```

Explain Background Fetch API in Service Workers with code examples

The **Background Fetch API** allows web applications to handle large downloads or uploads (such as movies, podcasts, audio tracks, or large game assets) reliably in the background.

Unlike standard `fetch()` calls or standard Background Sync—which time out if the user closes the tab or if a download takes too long—Background Fetch delegates the network transfer to the browser's native download manager.

This means the transfer **continues running even if the user closes all browser tabs**, provides a native OS progress notification bar, and allows users to pause or cancel the download.

---

## How Background Fetch Works

```text
┌─────────────────┐      1. Request Large Download     ┌────────────────────┐
│ Main Thread Page│ ─────────────────────────────────► │ Background Fetch   │
└─────────────────┘                                    │     Manager        │
                                                       └─────────┬──────────┘
                                                                 │
                                                                 │ 2. Transfers Data in Background
                                                                 │    (User can close tab)
                                                                 ▼
┌─────────────────┐      3. Store Downloaded Assets    ┌────────────────────┐
│ Cache Storage   │ ◄───────────────────────────────── │  Service Worker    │
└─────────────────┘                                    └────────────────────┘

```

---

## 1. Step 1: Initiating a Background Fetch (`app.js`)

You trigger a background fetch using `registration.backgroundFetch.fetch()`, providing a unique ID, an array of URLs to download, and UI metadata (title, icons, download size hints).

```javascript
// app.js (Main Thread)
async function downloadMovieAssets(movieId, videoUrls) {
  if (!('serviceWorker' in navigator)) return;

  const registration = await navigator.serviceWorker.ready;

  // 1. Check if Background Fetch is supported
  if ('backgroundFetch' in registration) {
    try {
      // 2. Start the background fetch job
      const bgFetch = await registration.backgroundFetch.fetch(
        `download-movie-${movieId}`, // Unique ID for this fetch task
        videoUrls,                   // Array of URLs to download
        {
          title: 'Downloading Sci-Fi Movie (1080p)',
          icons: [{
            sizes: '192x192',
            src: '/images/movie-icon.png',
            type: 'image/png',
          }],
          downloadTotal: 450 * 1024 * 1024 // Estimated total size in bytes (450MB)
        }
      );

      console.log('Background fetch started successfully!');

      // 3. Listen for progress events on the main thread (if tab is open)
      bgFetch.addEventListener('progress', () => {
        const percent = Math.round((bgFetch.downloaded / bgFetch.downloadTotal) * 100);
        console.log(`Download progress: ${percent}% (${bgFetch.downloaded} bytes downloaded)`);
      });

    } catch (error) {
      console.error('Background Fetch failed to start:', error);
    }
  } else {
    console.warn('Background Fetch API is not supported in this browser.');
  }
}

// Example: Trigger download for multiple video chunks
downloadMovieAssets('101', [
  '/media/movie-part1.mp4',
  '/media/movie-part2.mp4',
  '/media/movie-cover.jpg'
]);

```

## 2. Step 2: Handling Completion in the Service Worker (`sw.js`)

## 1. Step 1: Requesting Permission & Subscribing (`app.js`)

Before receiving push notifications, you must request permission from the user and generate a **PushSubscription** object containing a unique endpoint URL and encryption keys.

```javascript
// app.js (Main Thread)

async function subscribeToWebPush() {
  if (!('serviceWorker' in navigator) || !('PushManager' in window)) {
    console.warn('Push Messaging is not supported in this browser.');
    return;
  }

  try {
    // 1. Request Notification Permission
    const permission = await Notification.requestPermission();
    if (permission !== 'granted') {
      throw new Error('Notification permission was denied by the user.');
    }

    // 2. Wait for Service Worker registration
    const registration = await navigator.serviceWorker.ready;

    // 3. Subscribe to the Push Service using VAPID key
    const subscription = await registration.pushManager.subscribe({
      userVisibleOnly: true, // Guarantees every push shows a visible notification
      applicationServerKey: urlBase64ToUint8Array(VAPID_PUBLIC_KEY)
    });

    console.log('User Push Subscription:', JSON.stringify(subscription));

    // 4. Send subscription keys to your backend server to save in DB
    await fetch('/api/save-subscription', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(subscription)
    });

    console.log('Push Subscription saved to server successfully!');

  } catch (error) {
    console.error('Failed to subscribe user to push notifications:', error);
  }
}

// Utility function: Convert VAPID base64 string to Uint8Array
function urlBase64ToUint8Array(base64String) {
  const padding = '='.repeat((4 - (base64String.length % 4)) % 4);
  const base64 = (base64String + padding).replace(/-/g, '+').replace(/_/g, '/');
  const rawData = window.atob(base64);
  const outputArray = new Uint8Array(rawData.length);
  for (let i = 0; i < rawData.length; ++i) {
    outputArray[i] = rawData.charCodeAt(i);
  }
  return outputArray;
}
```

Explain BroadcastChannel API in JavaScript with code examples

The **`BroadcastChannel` API** provides a simple, high-performance way for different browser contexts—such as multiple open **tabs, windows, frames/iframes, or Web Workers** from the *same origin*—to communicate directly with one another.

Unlike `postMessage` (which requires maintaining explicit references to specific `window` objects or `Worker` instances), `BroadcastChannel` uses a **publish-subscribe model**. Any context that joins a channel by name automatically receives all messages published to that channel.

---

The **Web Locks API** (`navigator.locks`) allows web applications running across multiple browser contexts (**tabs, windows, Workers, or Service Workers**) from the same origin to coordinate access to shared resources using asynchronous locks.

When multiple open tabs attempt to access, mutate, or process the same underlying resource simultaneously—such as writing to an **IndexedDB** database, sending requests over a **Single-Connection WebSocket**, or processing an **offline sync queue**—concurrent access can cause race conditions or data corruption. The Web Locks API prevents these issues by ensuring that **only one tab at a time** can acquire a lock and execute a designated task.

---

## 1. Core Mechanics: `navigator.locks.request()`

To request a lock, call `navigator.locks.request(name, callback)`.

* The browser holds the lock for the duration of your async `callback` function.
* Once the returned Promise resolves (or rejects), the lock is **automatically released** for the next waiting tab.
* If a tab or worker crashes or is closed, the browser **automatically cleans up and releases** all held locks.

```text
┌─────────────────┐       Request Lock ('my_resource')       ┌──────────────────┐
│ Tab A           │ ───────────────────────────────────────► │ Web Locks Manager│
└─────────────────┘                                          └────────┬─────────┘
                                                                      │
                                   Grants Lock to Tab A               │
                                ◄─────────────────────────────────────┘
                                                                      │
┌─────────────────┐       Request Lock ('my_resource')                │ (Enqueues Tab B)
│ Tab B           │ ──────────────────────────────────────────────────┤
└─────────────────┘                                                   │
                                                                      ▼
                                   Waits until Tab A finishes/releases

```

---

## 2. Basic Code Example: Exclusive Lock

By default, locks are **exclusive** (`mode: 'exclusive'`). Only one callback across all tabs can execute at any given moment.

```javascript
// Function to safely update a shared IndexedDB or LocalStorage database
async function safeDatabaseWrite(updateData) {
  if (!('locks' in navigator)) {
    console.warn('Web Locks API not supported in this environment.');
    return;
  }

  // Request an exclusive lock named 'db_write_lock'
  await navigator.locks.request('db_write_lock', async (lock) => {
    console.log(`[${lock.name}] Lock acquired! Reading and updating database...`);

    // Perform critical section tasks without interference from other tabs
    const currentData = await readDataFromDB();
    const updatedData = { ...currentData, ...updateData };
    await writeDataToDB(updatedData);

    console.log(`[${lock.name}] Database updated successfully.`);
    // The lock is automatically released when this async function returns
  });

  console.log('Lock released. Proceeding with UI updates...');
}

```

---

## 3. Shared Locks (`mode: 'shared'`)

The Web Locks API supports a **Read/Write Lock Pattern**:

* **Shared Mode (`shared`):** Multiple tabs can acquire a shared lock simultaneously (ideal for multiple concurrent *read* operations).
* **Exclusive Mode (`exclusive`):** Blocks all other readers and writers (ideal for single *write* or mutation operations).

```javascript
// Tab A, B, C: Can all run concurrent reads simultaneously
async function performConcurrentRead() {
  await navigator.locks.request('my_resource', { mode: 'shared' }, async (lock) => {
    console.log('Shared read lock acquired. Multiple tabs can execute this concurrently.');
    await readData();
  });
}

// Tab D: Will wait until ALL shared reads complete before executing
async function performExclusiveWrite() {
  await navigator.locks.request('my_resource', { mode: 'exclusive' }, async (lock) => {
    console.log('Exclusive write lock acquired. Blocks all readers and writers.');
    await writeData();
  });
}

```

Explain leader election algorithms in browser multi-tab JavaScript with code examples

In multi-tab web applications, **Leader Election** ensures that only **one single tab** acts as the "Leader" responsible for executing shared tasks (such as maintaining a WebSocket connection, running periodic polling API calls, or performing background data syncs), while all other open tabs act as "Followers".

If the leader tab is closed or crashes, one of the follower tabs immediately takes over leadership.

---

## Why Use Leader Election?

* **Resource Optimization:** Prevents opening 10 separate WebSocket or SSE connections if a user opens 10 tabs of your web app.
* **Avoid Network Rate Limits:** Prevents duplicated API polling requests that trigger HTTP `429 Too Many Requests`.
* **Database State Integrity:** Eliminates race conditions when multiple tabs write to IndexedDB simultaneously.

---

## Approach 1: Web Locks API (Modern Native Standard)

The **Web Locks API** (`navigator.locks`) is the cleanest, most reliable approach.

When a tab requests a lock with a callback that **never resolves** (a promise that stays pending), that tab holds leadership. If the leader tab closes or crashes, the browser automatically releases the lock, and the next waiting tab acquires it instantly.

```javascript
// leader-election-weblocks.js
class WebLockLeaderElector {
  constructor(lockName = 'app_leader_lock') {
    this.lockName = lockName;
    this.isLeader = false;
    this.onLeaderCallback = null;
  }

  /**
   * Start participating in the leader election.
   * @param {Function} onBecomeLeader - Function triggered when THIS tab becomes leader.
   */
  async start(onBecomeLeader) {
    if (!('locks' in navigator)) {
      console.warn('Web Locks API not supported. Falling back...');
      return;
    }

    this.onLeaderCallback = onBecomeLeader;

    // Request an exclusive lock. If another tab holds it, this promise waits in queue.
    navigator.locks.request(this.lockName, async (lock) => {
      // 1. This block runs ONLY when this tab gets the lock
      this.isLeader = true;
      console.log('👑 This tab has been elected as LEADER!');

      if (this.onLeaderCallback) {
        this.onLeaderCallback();
      }

      // 2. Keep the promise pending indefinitely so the browser holds the lock.
      // If the user closes this tab, the browser automatically releases the lock.
      await new Promise(() => {}); 
    });
  }
}

// ====================================================
// Usage Example
// ====================================================
const elector = new WebLockLeaderElector();

elector.start(() => {
  // Execute tasks reserved strictly for the Leader tab
  console.log('Starting single WebSocket connection...');
  connectWebSocket();
});

function connectWebSocket() {
  // Only the Leader tab opens a live WebSocket
  const socket = new WebSocket('wss://example.com/live-feed');
  
  // Optional: Use BroadcastChannel to stream received messages to follower tabs
  const channel = new BroadcastChannel('socket_data');
  socket.onmessage = (event) => {
    channel.postMessage(event.data);
  };
}

```

## Approach 2: BroadcastChannel + Heartbeat (Fallback / Legacy)

If you need compatibility with environments where the Web Locks API is unavailable, you can build a **Heartbeat-based Election** using `BroadcastChannel` and `localStorage`.

### Algorithm Flow

1. **Heartbeat:** The current leader broadcasts a `HEARTBEAT` message every 1,000ms.
2. **Timeout:** Followers listen for heartbeats. If no heartbeat arrives for 2,500ms, followers assume the leader died and start an election.
3. **Claim:** The first tab to claim leadership writes its ID to `localStorage` and broadcasts `CLAIM_LEADER`.

```javascript
// leader-election-broadcast.js
class HeartbeatLeaderElector {
  constructor(channelName = 'leader_election') {
    this.id = `tab_${Math.random().toString(36).substring(2, 9)}`;
    this.channel = new BroadcastChannel(channelName);
    this.isLeader = false;
    this.heartbeatTimer = null;
    this.checkTimer = null;
    this.lastHeartbeat = Date.now();
    this.onBecomeLeader = null;
  }

  start(onBecomeLeader) {
    this.onBecomeLeader = onBecomeLeader;

    // Listen for messages from other tabs
    this.channel.onmessage = (event) => this.handleMessage(event.data);

    // Periodically monitor if the leader is alive
    this.checkTimer = setInterval(() => this.checkLeaderHealth(), 1000);

    // Announce presence and check if a leader exists
    this.claimLeadership();
  }

  handleMessage(data) {
    if (data.type === 'HEARTBEAT') {
      if (data.leaderId !== this.id) {
        this.lastHeartbeat = Date.now();
        if (this.isLeader) {
          // Conflict resolution: Step down if another tab claims leadership
          this.stepDown();
        }
      }
    } else if (data.type === 'CLAIM_LEADER') {
      this.lastHeartbeat = Date.now();
    }
  }

  checkLeaderHealth() {
    if (this.isLeader) return;

    // If no heartbeat received in 2.5 seconds, trigger election
    if (Date.now() - this.lastHeartbeat > 2500) {
      console.log('Leader timed out! Attempting to claim leadership...');
      this.claimLeadership();
    }
  }

  claimLeadership() {
    this.isLeader = true;
    this.lastHeartbeat = Date.now();

    // Broadcast claim
    this.channel.postMessage({ type: 'CLAIM_LEADER', leaderId: this.id });

    // Start sending heartbeats every 1 second
    if (this.heartbeatTimer) clearInterval(this.heartbeatTimer);
    this.heartbeatTimer = setInterval(() => {
      this.channel.postMessage({ type: 'HEARTBEAT', leaderId: this.id });
    }, 1000);

    console.log(`👑 Tab ${this.id} claimed leadership!`);

    if (this.onBecomeLeader) {
      this.onBecomeLeader();
    }
  }

  stepDown() {
    this.isLeader = false;
    if (this.heartbeatTimer) clearInterval(this.heartbeatTimer);
    console.log('Stepped down from leadership.');
  }
}

// Usage Example
const elector = new HeartbeatLeaderElector();
elector.start(() => {
  console.log('I am now the active leader tab!');
});

```

Explain how Service Workers intercept network requests for offline caching with code examples

Service Workers act as a **programmable network proxy** sitting between your web application, the browser's cache, and the network. By intercepting outgoing `fetch` events, a Service Worker can inspect HTTP requests and decide whether to serve content directly from **Cache Storage**, fetch it from the network, or combine both strategies.

---

## 1. How Network Interception Works

When a page under a registered Service Worker's scope makes any HTTP request (e.g., HTML page loads, CSS, JS, images, or API `fetch()` calls):

1. The browser fires a **`fetch` event** inside the Service Worker thread.
2. The Service Worker intercepts the request via `event.respondWith()`.
3. Inside `event.respondWith()`, you pass a `Promise` that resolves to a `Response` object—whether sourced from the cache, network, or dynamically generated.

```text
┌──────────────┐         1. Request          ┌─────────────────┐
│ Web Page /   │ ──────────────────────────► │ Service Worker  │
│ Main Thread  │                             │ (sw.js)         │
└──────▲───────┘                             └────────┬────────┘
       │                                              │
       │ 4. Response                                  │ 2. Check Cache
       │    (from Cache or Network)                   ▼
       │                                     ┌─────────────────┐
       └──────────────────────────────────── │ Cache Storage / │
                                             │ Remote Network  │
                                             └─────────────────┘

```

---

## 2. Step 1: Pre-caching Core Offline Assets (`install` event)

Before intercepting requests, pre-cache your essential offline assets (HTML, CSS, JS) during the Service Worker's `install` lifecycle event.

## 3. Step 2: Intercepting Requests (`fetch` event)

Listen for the `fetch` event and customize how different types of requests are served.

### Strategy A: Cache First (Falling back to Network)

Ideal for static, immutable assets like images, fonts, and stylesheets.

```javascript
// sw.js
self.addEventListener('fetch', (event) => {
  const request = event.request;

  // Intercept image and style requests using Cache-First
  if (request.destination === 'image' || request.destination === 'style') {
    event.respondWith(
      caches.match(request).then((cachedResponse) => {
        // Return cached version if found
        if (cachedResponse) {
          return cachedResponse;
        }

        // Otherwise fetch from network, add to cache, and return response
        return fetch(request).then((networkResponse) => {
          // Response streams can only be consumed once, so clone it
          const responseToCache = networkResponse.clone();

          caches.open(CACHE_NAME).then((cache) => {
            cache.put(request, responseToCache);
          });

          return networkResponse;
        });
      })
    );
  }
});

```

### Strategy B: Network First (Falling back to Offline Page)

Ideal for HTML page navigation and dynamic API requests that need fresh data when online, but require an offline fallback when disconnected.

```javascript
// sw.js
self.addEventListener('fetch', (event) => {
  const request = event.request;

  // Intercept main page navigation requests
  if (request.mode === 'navigate') {
    event.respondWith(
      fetch(request)
        .then((networkResponse) => {
          // Update cached version of the page when online
          return caches.open(CACHE_NAME).then((cache) => {
            cache.put(request, networkResponse.clone());
            return networkResponse;
          });
        })
        .catch(() => {
          // If network fails (offline), serve cached page or offline fallback page
          return caches.match(request).then((cachedResponse) => {
            return cachedResponse || caches.match('/offline.html');
          });
        })
    );
  }
});

```

## 4. Complete Unified Example

Here is a full production-ready `sw.js` script combining pre-caching, dynamic asset caching, and offline page fallback:

```javascript
// sw.js
const CACHE_NAME = 'app-cache-v1';
const OFFLINE_URL = '/offline.html';

const STATIC_ASSETS = [
  '/',
  '/index.html',
  '/styles.css',
  '/app.js',
  OFFLINE_URL
];

// Install: Pre-cache core shell
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(STATIC_ASSETS))
  );
  self.skipWaiting();
});

// Activate: Clean up old caches
self.addEventListener('activate', (event) => {
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(
        keys.map((key) => {
          if (key !== CACHE_NAME) return caches.delete(key);
        })
      )
    )
  );
  self.clients.claim();
});

// Intercept Network Requests
self.addEventListener('fetch', (event) => {
  // Ignore non-GET requests (e.g. POST, PUT, DELETE)
  if (event.request.method !== 'GET') return;

  event.respondWith(
    caches.match(event.request).then((cachedResponse) => {
      // 1. Serve from cache if available
      if (cachedResponse) {
        return cachedResponse;
      }

      // 2. Otherwise fetch from network
      return fetch(event.request)
        .then((networkResponse) => {
          // Don't cache invalid responses or third-party opaque scripts
          if (!networkResponse || networkResponse.status !== 200) {
            return networkResponse;
          }

          // Cache fresh copy dynamically
          const responseClone = networkResponse.clone();
          caches.open(CACHE_NAME).then((cache) => {
            cache.put(event.request, responseClone);
          });

          return networkResponse;
        })
        .catch(() => {
          // 3. Network failed & no cache match: handle navigation offline fallback
          if (event.request.mode === 'navigate') {
            return caches.match(OFFLINE_URL);
          }
        });
    })
  );
});

```

## Important Rules for Intercepting Fetch Events

1. **HTTPS Required:** Service Workers require a secure origin (HTTPS or `localhost`) due to the sensitive nature of network request manipulation.
2. **Cloning Responses:** A `Response` body can only be read once. Always call `.clone()` before saving a network response to Cache Storage while returning the original to the browser.
3. **HTTP Scope:** A Service Worker located at `/sw.js` can only intercept requests within its directory scope and subdirectories (e.g., `/` or `/app/`).

Explain Service Worker caching strategies with code examples

Service Worker caching strategies dictate how an application serves resources when a user visits a page. Depending on the resource type—such as static assets, dynamic API data, or user avatars—choosing the right strategy determines whether your app prioritizes **speed**, **freshness**, or **offline availability**.

---

## 1. Summary Matrix

| Strategy                   | Speed     | Freshness                                      | Offline Support | Best Used For                                             |
| -------------------------- | --------- | ---------------------------------------------- | --------------- | --------------------------------------------------------- |
| **Cache First**            | ⚡ Fastest | 🐢 Slow (stale until cache update)              | ✅ Excellent     | Static assets (CSS, JS, fonts, images).                   |
| **Network First**          | 🐢 Slower  | ⚡ Always fresh (if online)                     | ✅ Fallback      | Frequently updating content (user feeds, dashboards).     |
| **Stale-While-Revalidate** | ⚡ Fastest | ⚡ Medium (serves stale, updates in background) | ✅ Excellent     | Avatar images, news feeds, non-critical APIs.             |
| **Network Only**           | 🐢 Slower  | ⚡ Always fresh                                 | ❌ None          | Non-cacheable transactions (checkout API, POST requests). |
| **Cache Only**             | ⚡ Fastest | ❌ Never updates                                | ✅ Excellent     | Pre-cached core app shell assets (e.g. `offline.html`).   |

## 2. The 5 Core Strategies with Code Examples

All examples below belong inside a Service Worker file (`sw.js`) listening to the `fetch` event.

### 1. Cache First (Falling Back to Network)

Looks for a match in the cache first. If found, returns it immediately. If not found, fetches it from the network, caches it for future requests, and returns it.

```javascript
// sw.js
const CACHE_NAME = "static-assets-v1";

self.addEventListener("fetch", (event) => {
  // Apply Cache-First to images, fonts, and static bundles
  if (event.request.destination === "style" || event.request.destination === "image") {
    event.respondWith(
      caches.match(event.request).then((cachedResponse) => {
        if (cachedResponse) {
          return cachedResponse; // Return cached asset immediately
        }

        // Fetch from network if missing in cache
        return fetch(event.request).then((networkResponse) => {
          // Open cache and save the new asset
          return caches.open(CACHE_NAME).then((cache) => {
            cache.put(event.request, networkResponse.clone());
            return networkResponse;
          });
        });
      })
    );
  }
});

```

---

### 2. Network First (Falling Back to Cache)

Attempts to fetch the freshest version over the network. If the request fails (e.g., user is offline or connection is poor), it falls back to serving the cached version.

```javascript
// sw.js
const DYNAMIC_CACHE = "dynamic-data-v1";

self.addEventListener("fetch", (event) => {
  // Apply Network-First to API data or main page documents
  if (event.request.mode === "navigate" || event.request.url.includes("/api/")) {
    event.respondWith(
      fetch(event.request)
        .then((networkResponse) => {
          // Update cache with the latest response from network
          return caches.open(DYNAMIC_CACHE).then((cache) => {
            cache.put(event.request, networkResponse.clone());
            return networkResponse;
          });
        })
        .catch(() => {
          // Offline fallback: serve cached version if network fails
          return caches.match(event.request);
        })
    );
  }
});

```

### 3. Stale-While-Revalidate (Fastest + Auto-Updating)

Instantly serves the cached version to keep the UI feeling instant, while asynchronously sending a network request in the background to update the cache for the *next* page load.

```javascript
// sw.js
const SWR_CACHE = "swr-cache-v1";

self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.open(SWR_CACHE).then((cache) => {
      return cache.match(event.request).then((cachedResponse) => {
        // Trigger background revalidation request
        const fetchPromise = fetch(event.request).then((networkResponse) => {
          // Update cache in the background
          cache.put(event.request, networkResponse.clone());
          return networkResponse;
        });

        // Return cached version immediately if available, else wait for network
        return cachedResponse || fetchPromise;
      });
    })
  );
});

```

### 4. Network Only

Bypasses the Service Worker cache completely and sends the request directly to the network. If offline, the request fails.

```javascript
// sw.js
self.addEventListener("fetch", (event) => {

  if (event.request.method === "POST" || event.request.url.includes("/api/checkout")) {
    event.respondWith(fetch(event.request));
  }
});

```

### 5. Cache Only

Serves requests strictly from the cache. If the asset does not exist in the cache, the request fails. Useful for static offline fallbacks pre-cached during Service Worker installation.

```javascript
// sw.js

  event.waitUntil(
    caches.open("offline-v1").then((cache) => {
      // Pre-cache offline page during installation

    })

});

self.addEventListener("fetch", (event) => {
  // Serve offline page if user is completely disconnected
  if (event.request.mode === "navigate") {
    event.respondWith(
      fetch(event.request).catch(() => caches.match("/offline.html"))
    );
  }
});
```


Explain Service Worker cache versioning and update activation lifecycle with code examples

When deploying updates to a Progressive Web App (PWA), managing **cache versioning** and the **Service Worker lifecycle** is critical.

Without proper version management, users can stay trapped on stale, cached JavaScript/CSS assets indefinitely, or experience runtime crashes caused by mismatched dependencies between old and new releases.

---

## 1. The Service Worker Lifecycle Phases

Every Service Worker transitions through three distinct states:

```text
 ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
 │  Installing  │ ──► │   Waiting    │ ──► │  Activated   │
 │ (Pre-caches) │     │ (Skip-Waiting│     │(Cleans old   │
 └──────────────┘     │   required)  │     │  caches)     │
                      └──────────────┘     └──────────────┘

```

1. **Install (`install` event):** The browser detects a byte-for-byte change in `sw.js`. It downloads the new file and triggers the `install` event to pre-cache new static assets under a **new versioned cache name**.
2. **Waiting / Installed:** The newly installed Service Worker enters a **waiting state**. By default, it will not activate as long as there are active browser tabs using the previous version.
3. **Activate (`activate` event):** Once all old tabs are closed (or skipped programmatically via `skipWaiting()`), the new Service Worker activates and cleans up **legacy cache versions**.

---

## 2. Complete Production Implementation (`sw.js`)

This implementation demonstrates cache versioning, immediate activation (`skipWaiting`), and automatic cleanup of obsolete caches (`caches.delete`).

```javascript
// Change version string whenever deploying asset changes
const CACHE_VERSION = "v2";
const STATIC_CACHE = `static-assets-${CACHE_VERSION}`;
const DYNAMIC_CACHE = `dynamic-data-${CACHE_VERSION}`;

// Core App Shell Assets
const PRECACHE_ASSETS = [
  "/",
  "/index.html",
  "/styles.css",
  "/app.js",
  "/offline.html"
];

// ====================================================
// 1. INSTALL EVENT: Pre-cache new version assets
// ====================================================
self.addEventListener("install", (event) => {
  console.log(`[Service Worker ${CACHE_VERSION}] Installing...`);

  event.waitUntil(
    caches.open(STATIC_CACHE).then((cache) => {
      console.log(`[Service Worker ${CACHE_VERSION}] Pre-caching app shell...`);
      return cache.addAll(PRECACHE_ASSETS);
    })
  );

  // Force the waiting Service Worker to become the active Service Worker immediately
  self.skipWaiting();
});

// ====================================================
// 2. ACTIVATE EVENT: Delete legacy caches
// ====================================================
self.addEventListener("activate", (event) => {
  console.log(`[Service Worker ${CACHE_VERSION}] Activating...`);

  event.waitUntil(
    caches.keys().then((cacheNames) => {
      return Promise.all(
        cacheNames.map((cacheName) => {
          // Delete any cache bucket that doesn't match current version keys
          if (cacheName !== STATIC_CACHE && cacheName !== DYNAMIC_CACHE) {
            console.log(`[Service Worker ${CACHE_VERSION}] Deleting obsolete cache: ${cacheName}`);
            return caches.delete(cacheName);
          }
        })
      );
    }).then(() => {
      // Take control of all active clients/tabs immediately
      return self.clients.claim();
    })
  );
});

// ====================================================
// 3. FETCH EVENT: Serve active version assets
// ====================================================
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cachedResponse) => {
      if (cachedResponse) {
        return cachedResponse;
      }
      return fetch(event.request).then((networkResponse) => {
        return caches.open(DYNAMIC_CACHE).then((cache) => {
          cache.put(event.request, networkResponse.clone());
          return networkResponse;
        });
      });
    }).catch(() => caches.match("/offline.html"))
  );
});

```

## 3. Client-Side Lifecycle Management (`app.js`)

To notify users when a new update is ready—and allow them to refresh to load the latest release—listen to lifecycle state transitions on the main thread:

```javascript
// app.js (Main Thread)
if ("serviceWorker" in navigator) {
  window.addEventListener("load", async () => {
    try {
      const registration = await navigator.serviceWorker.register("/sw.js");

      // 1. Check if an update is already waiting
      if (registration.waiting) {
        promptUserForUpdate(registration.waiting);
      }

      // 2. Listen for new updates detected in the background
      registration.addEventListener("updatefound", () => {
        const newWorker = registration.installing;

        newWorker.addEventListener("statechange", () => {
          if (newWorker.state === "installed" && navigator.serviceWorker.controller) {
            // New version installed, waiting for user activation
            promptUserForUpdate(newWorker);
          }
        });
      });

    } catch (error) {
      console.error("Service Worker registration failed:", error);
    }
  });

  // Reload page automatically when the new Service Worker takes control
  let refreshing = false;
  navigator.serviceWorker.addEventListener("controllerchange", () => {
    if (!refreshing) {
      refreshing = true;
      window.location.reload();
    }
  });
}

function promptUserForUpdate(worker) {
  // Show UI notification banner to the user
  const userConfirmed = confirm("A new version of the app is available! Reload now?");

    // Post message to Service Worker triggering skipWaiting()
    worker.postMessage({ action: "skipWaiting" });
  }
}
```

## 4. Key Directives Explained

### `self.skipWaiting()`

* **Default behavior:** When a new `sw.js` finishes installing, it stays in the `waiting` state until **every open tab** using the older worker is closed by the user.
* **With `skipWaiting()`:** The newly installed Service Worker bypasses the waiting state and moves directly into the `activate` phase.

### `self.clients.claim()`

* **Default behavior:** An activated Service Worker does not control existing open tabs until those tabs are reloaded.
* **With `clients.claim()`:** The newly activated Service Worker takes immediate control over all open tabs without requiring a manual page refresh.

| **Activate** | `activate`         | Compares cache keys and deletes obsolete `v1` caches.    | `self.clients.claim()`     |
| **Update**   | `controllerchange` | Main thread detects controller swap and reloads page UI. | `window.location.reload()` |

Explain Background Sync API in Service Workers with code examples

The **Background Sync API** is a Web API that allows web applications to defer server requests to a background Service Worker until a user has a stable internet connection.

If a user performs an action while offline (e.g., sending a message, posting a comment, or submitting a form), standard `fetch()` calls fail immediately. Background Sync queues these requests in persistent storage (like `IndexedDB`) and registers a **sync event**. The browser then executes the request automatically in the background as soon as connectivity is restored—even if the user has closed the tab or navigated away.

---

## How Background Sync Works

```text
┌─────────────────┐       1. Offline Form Submit       ┌──────────────────┐
│ Main Thread Page│ ─────────────────────────────────► │ IndexedDB Queue  │
└────────┬────────┘                                    └────────┬─────────┘
         │                                                      │
         │ 2. Register Sync ('sync-messages')                   │
         ▼                                                      │
┌─────────────────┐       3. Connection Restored        ┌───────┴──────────┐
│ Service Worker  │ ◄────────────────────────────────── │  Sync Event      │
└────────┬────────┘                                     └───────┬──────────┘
         │                                                      │
         │ 4. Read Queue & Send Fetch                           │
         ▼                                                      │
┌─────────────────┐ ◄───────────────────────────────────────────┘
│ Server / API    │
└─────────────────┘

```

---

## 1. Step 1: Registering a Sync Task on the Main Thread (`app.js`)

When a user submits a form or performs an offline action:

1. Save the payload to **IndexedDB** so it survives browser restarts.
2. Register a sync task tag (e.g., `'sync-pending-messages'`) using `navigator.serviceWorker.ready`.

```javascript
// app.js (Main Thread)
import { saveToIndexedDB } from './db-utils.js'; // Helper function to save to IndexedDB

async function handleSendMessage(messageData) {
  try {
    // Attempt standard network request first
    const response = await fetch('/api/messages', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(messageData)
    });

    if (response.ok) {
      console.log('Message sent successfully online!');
      return;
    }
  } catch (error) {
    console.warn('Network offline or failed. Registering Background Sync...');
  }

  // Fallback: If offline or request failed
  if ('serviceWorker' in navigator && 'SyncManager' in window) {
    // 1. Save data to IndexedDB
    await saveToIndexedDB('pending_messages', messageData);

    // 2. Register sync tag with the Service Worker
    const registration = await navigator.serviceWorker.ready;
    await registration.sync.register('sync-pending-messages');

    console.log('Background Sync registered! Will send when online.');
  } else {
    console.error('Background Sync not supported in this browser.');
  }
}

```

---

## 2. Step 2: Listening for the Sync Event in the Service Worker (`sw.js`)

In the Service Worker, listen for the `'sync'` event. Check the event tag, retrieve queued items from IndexedDB, and send them to the server.

```javascript
// sw.js (Service Worker)
import { getFromIndexedDB, deleteFromIndexedDB } from './db-utils.js';

self.addEventListener('sync', (event) => {
  // Check for the specific sync tag
  if (event.tag === 'sync-pending-messages') {
    console.log('[Service Worker] Sync event triggered for: sync-pending-messages');

    // waitUntil keeps the Service Worker alive until the promise resolves
    event.waitUntil(processPendingMessages());
  }
});

async function processPendingMessages() {
  // 1. Read all pending items from IndexedDB
  const pendingMessages = await getFromIndexedDB('pending_messages');

  for (const message of pendingMessages) {
    try {
      // 2. Attempt to POST data to the server
      const response = await fetch('/api/messages', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(message)
      });

      if (response.ok) {
        console.log(`[Service Worker] Successfully synced message #${message.id}`);
        // 3. Remove successfully sent item from IndexedDB
        await deleteFromIndexedDB('pending_messages', message.id);
      } else {
        throw new Error(`Server status HTTP ${response.status}`);
      }
    } catch (error) {
      console.error(`[Service Worker] Sync failed for message #${message.id}:`, error.message);
      
      // Re-throwing the error causes the browser to retry the sync event later with exponential backoff
      throw error;
    }
  }
}

```

---

## 3. Retries and Exponential Backoff

If `event.waitUntil()` receives a rejected Promise (for example, if the server returns a 503 error or the connection drops mid-sync):

* The browser automatically re-schedules the `sync` event.
* Retries occur using a browser-managed **exponential backoff** strategy.
* The Service Worker will retry periodically until the operation succeeds or max retries are reached.

| **Safari (iOS / macOS)**  | ❌ Not Supported     | Safari does not support the One-Shot Background Sync API (uses Background Fetch API instead). |

### Graceful Fallback Strategy

Because Safari lacks support for Background Sync, always implement a fallback checking `navigator.onLine` or listening to the `'online'` window event:

```javascript
// Fallback for browsers lacking SyncManager support
if (!('SyncManager' in window)) {
  window.addEventListener('online', () => {
    console.log('Online event detected. Triggering manual queue processing...');
    processPendingMessagesManually();
  });
}

```

## 2. Workbox Precaching (`workbox-precaching`)

**Precaching** downloads and caches a predefined set of files when the Service Worker installs.

Workbox tracks file changes using **hashes**. If a file's hash changes in a new build, Workbox downloads *only* the updated asset, updates the cache, and cleans up obsolete versions automatically during activation.

### A. Precache Manifest Injection

Instead of manually typing file paths, build tools (like `workbox-cli`, `workbox-webpack-plugin`, or `vite-plugin-pwa`) generate a **precache manifest array** at build time and inject it into your Service Worker script:

```javascript
// sw.js
import { precacheAndRoute } from 'workbox-precaching';

// self.__WB_MANIFEST is replaced at build time with an array of objects:
// [{ url: '/index.html', revision: 'a1b2c3' }, { url: '/styles.css', revision: 'd4e5f6' }]
precacheAndRoute(self.__WB_MANIFEST || []);

```

### B. Manual Precaching Example (Without Build Tools)

If you are not using a build tool, pass an explicit manifest array containing version/revision strings:

```javascript
// sw.js
import { precacheAndRoute } from 'workbox-precaching';

precacheAndRoute([
  { url: '/index.html', revision: 'v1.0.0' },
  { url: '/styles.css', revision: 'v1.0.0' },
  { url: '/app.js', revision: 'v1.0.1' },
  { url: '/offline.html', revision: 'v1.0.0' },
]);

```

## 3. Workbox Runtime Routing (`workbox-routing` & `workbox-strategies`)

**Runtime Routing** intercepts outgoing network requests based on matching rules (URL patterns, request destinations) and applies a specific **caching strategy**.

Workbox provides 5 built-in strategies:

1. `CacheFirst`
2. `NetworkFirst`
3. `StaleWhileRevalidate`
4. `NetworkOnly`
5. `CacheOnly`

## 4. Complete Complete Example (`sw.js`)

Below is a complete `sw.js` script demonstrating precaching alongside all major runtime routing strategies, plugins (for cache expiration and status code validation), and offline fallbacks.

```javascript
// sw.js
import { precacheAndRoute } from 'workbox-precaching';
import { registerRoute, setDefaultHandler } from 'workbox-routing';
import { 
  CacheFirst, 
  NetworkFirst, 
  StaleWhileRevalidate, 
  NetworkOnly 
} from 'workbox-strategies';
import { ExpirationPlugin } from 'workbox-expiration';
import { CacheableResponsePlugin } from 'workbox-cacheable-response';

// ====================================================
// 1. PRECACHING (App Shell)
// ====================================================
// Precaches static assets generated at build time
precacheAndRoute(self.__WB_MANIFEST || []);


// ====================================================
// 2. RUNTIME ROUTING STRATEGIES
// ====================================================

// A. Cache First: Images (Max 50 items, expires in 30 days)
registerRoute(
  ({ request }) => request.destination === 'image',
  new CacheFirst({
    cacheName: 'images-cache',
    plugins: [
      new CacheableResponsePlugin({
        statuses: [0, 200], // Cache valid responses and CORS opaque responses
      }),
      new ExpirationPlugin({
        maxEntries: 50,
        maxAgeSeconds: 30 * 24 * 60 * 60, // 30 Days
        purgeOnQuotaError: true, // Automatically purge if storage limit reached
      }),
    ],
  })
);

// B. Stale-While-Revalidate: CSS & JS files
registerRoute(
  ({ request }) => request.destination === 'script' || request.destination === 'style',
  new StaleWhileRevalidate({
    cacheName: 'static-resources',
  })
);

// C. Network First: Dynamic API JSON requests (Timeout after 3s)
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/v1/'),
  new NetworkFirst({
    cacheName: 'api-cache',
    networkTimeoutSeconds: 3, // Fall back to cache if network takes > 3s
    plugins: [
      new CacheableResponsePlugin({
        statuses: [200],
      }),
    ],
  })
);

// D. Network Only: Payment / Checkout endpoints
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/checkout/'),
  new NetworkOnly()
);


// ====================================================
// 3. OFFLINE FALLBACK FOR NAVIGATION
// ====================================================
// If an HTML page request fails (offline), serve precached /offline.html
const navigationHandler = new NetworkFirst({
  cacheName: 'pages-cache',
});

registerRoute(
  ({ request }) => request.mode === 'navigate',
  async (options) => {
    try {
      return await navigationHandler.handle(options);
    } catch (error) {
      // Return precached offline fallback page if network and cache fail
      return caches.match('/offline.html');
    }
  }
);

```

## 5. Workbox Plugins Explained

Plugins extend Workbox strategies to automate cache management:

* **`ExpirationPlugin`**: Automatically bounds cache size by limiting maximum entries (`maxEntries`) or deleting items older than a set duration (`maxAgeSeconds`).
* **`CacheableResponsePlugin`**: Restricts caching to responses matching specific HTTP status codes (e.g., `200 OK`) to prevent caching server errors (`500`) or redirect loops.
* **`BackgroundSyncPlugin`**: Integrated into strategies (like `NetworkOnly`) to automatically queue failed network requests in `IndexedDB` and replay them when connectivity returns.

## Summary Matrix

| Workbox Strategy           | Underlying Mechanism                                                | Typical Target                                          |
| -------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------- |
| **`precacheAndRoute()`**   | Hash-validated cache installation and cleanup.                      | App shell, `index.html`, core build bundles.            |
| **`CacheFirst`**           | Serves cached asset immediately; fetches network on miss.           | Images, static fonts, media files.                      |
| **`NetworkFirst`**         | Fetches network first; falls back to cache on failure or timeout.   | HTML documents, user dashboards, API endpoints.         |
| **`StaleWhileRevalidate`** | Serves cached asset immediately while updating cache in background. | Non-critical styles, JavaScript bundles, user profiles. |

Explain Workbox BackgroundSync module with code examples

The **Workbox BackgroundSync module** (`workbox-background-sync`) automates the process of queuing failed network requests (such as POST, PUT, or DELETE API calls made while offline) in `IndexedDB` and replaying them automatically when network connectivity is restored.

Instead of writing manual `IndexedDB` read/write transactions or native `sync` event listeners, Workbox handles queue persistence, retries, exponential backoff, and sync registration declaratively.

---

## 1. How It Works

```text
┌─────────────────┐       1. POST/PUT Request (Offline)    ┌──────────────────┐
│ Web Application │ ─────────────────────────────────────► │ Service Worker / │
└─────────────────┘                                        │ Workbox Strategy │
                                                           └────────┬─────────┘
                                                                    │
                                   2. Rejects / Network Fails       │
                                ◄───────────────────────────────────┘
                                │
                                ▼ 3. Saves Request Payload
┌─────────────────┐       ┌────────────────────────┐
│ Browser Sync    │ ◄──── │ IndexedDB Queue        │
│ Manager         │       │ ('workbox-background-  │
└────────┬────────┘       │   sync')               │
         │                └────────────────────────┘
         │ 4. Connection Restored / Replays Requests
         ▼
┌─────────────────┐
│ Remote Backend  │
│ API             │
└─────────────────┘

```

---

## 2. Approach 1: Using `BackgroundSyncPlugin` with Workbox Strategies

The easiest way to use the module is as a **plugin** inside a Workbox strategy (like `NetworkOnly` or `NetworkFirst`).

Whenever a request matching the route fails due to a network error, `BackgroundSyncPlugin` intercepts the failed request, saves it to an `IndexedDB` queue, and registers a Background Sync tag with the browser.

```javascript
// sw.js (Service Worker)
import { registerRoute } from 'workbox-routing';
import { NetworkOnly } from 'workbox-strategies';
import { BackgroundSyncPlugin } from 'workbox-background-sync';

// 1. Create the BackgroundSyncPlugin instance
const bgSyncPlugin = new BackgroundSyncPlugin('api-mutation-queue', {
  maxRetentionTime: 24 * 60, // Retention period in minutes (24 hours max)
  
  // Optional lifecycle callback triggered when queued requests finish replaying
  onSync: async ({ queue }) => {
    try {
      await queue.replayRequests();
      console.log('[Workbox Sync] All queued requests replayed successfully!');
    } catch (error) {
      console.error('[Workbox Sync] Replay failed, will retry later:', error);
    }
  }
});

// 2. Register a route for offline mutations (e.g. submitting comments or posts)
registerRoute(
  ({ url }) => url.pathname.startsWith('/api/comments'),
  new NetworkOnly({
    plugins: [bgSyncPlugin], // Attach plugin to handle network failures
  }),
  'POST' // Match POST requests
);

```

## 3. Approach 2: Standalone Custom Queue Management

Explain Web Push API and Notification API in Service Workers with code examples

The **Web Push API** and **Notification API** work together to allow web applications to deliver real-time messages to users—even when the website or web browser tab is completely closed.

## 1. Step 1: Requesting Permission & Subscribing (`app.js`)

Before receiving push notifications, you must request permission from the user and generate a **PushSubscription** object containing a unique endpoint URL and encryption keys.

```javascript
// app.js (Main Thread)
const VAPID_PUBLIC_KEY = 'YOUR_VAPID_PUBLIC_KEY_HERE'; // Generated on your server

async function subscribeToWebPush() {
  if (!('serviceWorker' in navigator) || !('PushManager' in window)) {
    console.warn('Push Messaging is not supported in this browser.');
    return;
  }

  try {
    // 1. Request Notification Permission
    const permission = await Notification.requestPermission();
    if (permission !== 'granted') {
      throw new Error('Notification permission was denied by the user.');
    }

    // 2. Wait for Service Worker registration
    const registration = await navigator.serviceWorker.ready;

    // 3. Subscribe to the Push Service using VAPID key
    const subscription = await registration.pushManager.subscribe({
      userVisibleOnly: true, // Guarantees every push shows a visible notification
      applicationServerKey: urlBase64ToUint8Array(VAPID_PUBLIC_KEY)
    });

    console.log('User Push Subscription:', JSON.stringify(subscription));

    // 4. Send subscription keys to your backend server to save in DB
    await fetch('/api/save-subscription', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(subscription)
    });

    console.log('Push Subscription saved to server successfully!');

  } catch (error) {
    console.error('Failed to subscribe user to push notifications:', error);
  }
}

// Utility function: Convert VAPID base64 string to Uint8Array
function urlBase64ToUint8Array(base64String) {
  const padding = '='.repeat((4 - (base64String.length % 4)) % 4);
  const base64 = (base64String + padding).replace(/-/g, '+').replace(/_/g, '/');
  const rawData = window.atob(base64);
  const outputArray = new Uint8Array(rawData.length);
  for (let i = 0; i < rawData.length; ++i) {
    outputArray[i] = rawData.charCodeAt(i);
  }
  return outputArray;
}

```

## 2. Step 2: Handling Push & Clicks in Service Worker (`sw.js`)

In the Service Worker, listen for the **`push`** event to extract payload data and invoke `registration.showNotification()`. Listen for the **`notificationclick`** event to open or focus tabs when the user clicks the notification banner.

```javascript
// sw.js (Service Worker)

// A. Listen for incoming Push Events from Push Service
self.addEventListener('push', (event) => {
  let data = { title: 'New Notification', body: 'You have a new update!', url: '/' };

  if (event.data) {
    try {
      data = event.data.json(); // Parse JSON payload sent from server
    } catch (e) {
      data.body = event.data.text();
    }
  }

  const options = {
    body: data.body,
    icon: '/images/notification-icon.png',
    badge: '/images/badge-icon.png',
    vibrate: [100, 50, 100],
    data: {
      url: data.url || '/' // Attach target URL to notification metadata
    },
    actions: [
      { action: 'open', title: 'View Details' },
      { action: 'dismiss', title: 'Dismiss' }
    ]
  };

  // Keep Service Worker active until notification is shown
  event.waitUntil(
    self.registration.showNotification(data.title, options)
  );
});

// B. Listen for User Clicks on the Notification
self.addEventListener('notificationclick', (event) => {
  event.notification.close(); // Close the notification banner

  const targetUrl = event.notification.data.url;

  if (event.action === 'dismiss') {
    return; // User clicked "Dismiss" action button
  }

  // Focus an existing tab if open, otherwise open a new browser tab
  event.waitUntil(
    clients.matchAll({ type: 'window', includeUncontrolled: true }).then((clientList) => {
      for (const client of clientList) {
        if (client.url === targetUrl && 'focus' in client) {
          return client.focus();
        }
      }
      if (clients.openWindow) {
        return clients.openWindow(targetUrl);
      }
    })
  );
});

```

## 4. Key Rules & Constraints

1. **HTTPS Required:** Web Push requires an HTTPS origin (or `localhost` during development).
2. **`userVisibleOnly: true` Required:** Browsers require every push event to display a visible OS notification via `showNotification()`. Silent background pushes without user notifications are restricted to prevent tracking abuses.
3. **VAPID Keys:** Voluntary Application Server Identification (VAPID) authenticates your backend server with the browser vendor's Push Service without requiring proprietary API accounts.

Explain IndexedDB API with code examples and promises wrappers

**IndexedDB** is a low-level, transactional database API built directly into modern web browsers. Unlike `localStorage` (which is synchronous, limited to ~5MB, and stores only plain strings), IndexedDB is **asynchronous**, supports **large storage capacities** (hundreds of megabytes or gigabytes), and lets you store complex structured JavaScript objects, Files, and Blobs indexed with high-performance keys.

---

## 1. Core Concepts

* **Database (`IDBDatabase`):** The top-level container holding your application data. A single origin can have multiple databases.
* **Object Store (`IDBObjectStore`):** The equivalent of a table in relational databases or a collection in MongoDB. It holds records structured as key-value pairs.
* **Key Path & Auto Increment:** A key path defines which property on your objects serves as the primary key (e.g., `keyPath: "id"`).
* **Index (`IDBIndex`):** A secondary lookup mechanism allowing you to search object stores by properties other than the primary key (e.g., finding a user by their `email`).
* **Transaction (`IDBTransaction`):** All database operations (reads and writes) must happen inside a transaction. If any step fails, the entire transaction rolls back automatically.

---

## 2. Raw Native IndexedDB API Example

The raw IndexedDB API uses a legacy, request-based event model (`onsuccess`, `onerror`, `onupgradeneeded`).

```javascript
// Open or create a database named 'ShopDB' at version 1
const request = indexedDB.open('ShopDB', 1);

// Triggered ONLY when opening a database for the first time or bumping the version number
request.onupgradeneeded = (event) => {
  const db = event.target.result;

  // Create an Object Store named 'products' with 'id' as the primary key
  if (!db.objectStoreNames.contains('products')) {
    const store = db.createObjectStore('products', { keyPath: 'id', autoIncrement: true });
    
    // Create a secondary index to search products by category
    store.createIndex('by_category', 'category', { unique: false });
  }
};

request.onsuccess = (event) => {
  const db = event.target.result;
  console.log('Database opened successfully!');

  // Perform a Read/Write Transaction
  const transaction = db.transaction(['products'], 'readwrite');
  const store = transaction.objectStore('products');

  // Add a new product
  const addRequest = store.add({
    name: 'Wireless Mouse',
    category: 'Electronics',
    price: 29.99
  });

  addRequest.onsuccess = () => {
    console.log('Product added with generated ID:', addRequest.result);
  };

  transaction.oncomplete = () => {
    console.log('Transaction committed successfully.');
  };

  transaction.onerror = (event) => {
    console.error('Transaction failed:', event.target.error);
  };
};

request.onerror = (event) => {
  console.error('Failed to open database:', event.target.error);
};
```

## 3. Creating a Custom Promise Wrapper

Because native IndexedDB relies on nested request callbacks, wrapping operations in native Promises allows you to use clean `async/await` syntax.

```javascript
// db-wrapper.js

class SimpleDB {
  constructor(dbName, version) {
    this.dbName = dbName;
    this.version = version;
    this.db = null;
  }

  // Open database connection
  open(upgradeCallback) {
    return new Promise((resolve, reject) => {
      const request = indexedDB.open(this.dbName, this.version);

      request.onupgradeneeded = (e) => upgradeCallback(e.target.result);
      request.onsuccess = (e) => {
        this.db = e.target.result;
        resolve(this.db);
      };
      request.onerror = (e) => reject(e.target.error);
    });
  }

  // Generic write (add or update)
  put(storeName, item) {
    return new Promise((resolve, reject) => {
      const tx = this.db.transaction(storeName, 'readwrite');
      const store = tx.objectStore(storeName);
      const req = store.put(item);

      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });
  }

  // Generic get by key
  get(storeName, key) {
    return new Promise((resolve, reject) => {
      const tx = this.db.transaction(storeName, 'readonly');
      const store = tx.objectStore(storeName);
      const req = store.get(key);

      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });
  }

  // Get all items in an object store
  getAll(storeName) {
    return new Promise((resolve, reject) => {
      const tx = this.db.transaction(storeName, 'readonly');
      const store = tx.objectStore(storeName);
      const req = store.getAll();

      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });
  }

  // Query by secondary index
  getAllFromIndex(storeName, indexName, query) {
    return new Promise((resolve, reject) => {
      const tx = this.db.transaction(storeName, 'readonly');
      const store = tx.objectStore(storeName);
      const index = store.index(indexName);
      const req = index.getAll(query);

      req.onsuccess = () => resolve(req.result);
      req.onerror = () => reject(req.error);
    });
  }
}

// ====================================================
// Usage with async/await
// ====================================================
async function runDemo() {

  // Initialize DB
  await myDB.open((db) => {
    if (!db.objectStoreNames.contains('items')) {
      const store = db.createObjectStore('items', { keyPath: 'sku' });
      store.createIndex('by_type', 'type');
    }
  });

  // Write record
  await myDB.put('items', { sku: 'SKU-100', name: 'Mechanical Keyboard', type: 'Hardware', price: 89.99 });
  await myDB.put('items', { sku: 'SKU-200', name: 'USB-C Cable', type: 'Hardware', price: 12.99 });

  // Read record
  const item = await myDB.get('items', 'SKU-100');
  console.log('Fetched single item:', item);

  // Query index
  const hardwareItems = await myDB.getAllFromIndex('items', 'by_type', 'Hardware');
  console.log('All hardware items:', hardwareItems);
}

runDemo();
```

## 2. Step 1: The SharedWorker Script (`db-worker.js`)

The SharedWorker opens a **single** persistent connection to IndexedDB, listens for incoming messages from connected tabs, executes database operations safely, and broadcasts mutations back to all open tabs.

```javascript
// Track all active tab ports for broadcasting
const connectedPorts = new Set();
let db = null;

// Initialize IndexedDB connection inside the SharedWorker
function initDB() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open("AppSharedDB", 1);

    request.onupgradeneeded = (event) => {
      const db = event.target.result;
      if (!db.objectStoreNames.contains("users")) {
        db.createObjectStore("users", { keyPath: "id" });
      }

    request.onsuccess = (event) => {
      db = event.target.result;
      console.log("[SharedWorker] IndexedDB connected successfully.");
      resolve(db);
    };

    request.onerror = (event) => {
      console.error("[SharedWorker] IndexedDB error:", event.target.error);
      reject(event.target.error);

// Handle tab connections
self.onconnect = (event) => {
  const port = event.ports[0];
  connectedPorts.add(port);
  port.start();

  port.onmessage = async (event) => {
    const { id, action, payload } = event.data;

    // Ensure DB is initialized before processing requests
    await dbPromise;

    try {
      let result;

      switch (action) {
        case "GET_ALL_USERS":
          result = await getAllUsers();
          port.postMessage({ id, success: true, result });
          break;

        case "ADD_USER":
          result = await addUser(payload);
          port.postMessage({ id, success: true, result });

          // Broadcast change to ALL other open tabs
          broadcastEvent("USER_ADDED", result, port);
          break;

        default:
          port.postMessage({ id, success: false, error: "Unknown action" });
      }
    } catch (error) {
      port.postMessage({ id, success: false, error: error.message });
    }
  };

  // Clean up disconnected ports
  port.onmessageerror = () => connectedPorts.delete(port);
};
```

## 3. Step 2: The Main Thread Client (`db-client.js`)

Tabs interact with the SharedWorker using a Promise-based RPC (Remote Procedure Call) wrapper. Each request attaches a unique request ID so responses can be matched cleanly.

```javascript
// db-client.js
class SharedDBClient {
  constructor() {
    this.worker = new SharedWorker("db-worker.js");
    this.port = this.worker.port;
    this.pendingRequests = new Map();
    this.requestId = 0;

    this.init();
  }

  init() {
    this.port.start();

    // Listen for responses and broadcast events from SharedWorker
    this.port.onmessage = (event) => {
      const { id, success, result, error, isBroadcast, type, payload } = event.data;

      // Handle real-time broadcast updates from other tabs
      if (isBroadcast) {
        console.log(`[Tab UI Sync] Received broadcast event "${type}":`, payload);
        this.onBroadcastReceived(type, payload);
        return;
      }

      // Resolve pending RPC request Promise
      if (this.pendingRequests.has(id)) {
        const { resolve, reject } = this.pendingRequests.get(id);
        this.pendingRequests.delete(id);

        if (success) {
          resolve(result);
        } else {
          reject(new Error(error));
        }
      }
    };
  }

  // Generic request dispatcher returning a Promise
  sendRequest(action, payload = null) {
    return new Promise((resolve, reject) => {
      const id = ++this.requestId;
      this.pendingRequests.set(id, { resolve, reject });

      this.port.postMessage({ id, action, payload });
    });
  }

  // API Methods
  getAllUsers() {
    return this.sendRequest("GET_ALL_USERS");
  }

  addUser(user) {
    return this.sendRequest("ADD_USER", user);
  }

  // Hook for UI updates when another tab modifies the DB
  onBroadcastReceived(type, payload) {
    if (type === "USER_ADDED") {
      const userList = document.querySelector("#user-list");
      if (userList) {
        const li = document.createElement("li");
        li.textContent = `${payload.name} (ID: ${payload.id})`;
        userList.appendChild(li);
      }
    }
  }
}

// ====================================================

// ====================================================

// Add user on button click

});
```

## 2. Step 2: Main Thread Tab Client (`hub-client.js`)

Each open tab connects to `shared-hub.js`. It exposes a Promise-based request-response pattern for querying IndexedDB or sending socket messages, and registers a listener for live broadcast updates pushed from the SharedWorker.

```javascript
// hub-client.js
class SharedHubClient {
  constructor() {
    this.worker = new SharedWorker("shared-hub.js");
    this.port = this.worker.port;
    this.pendingRequests = new Map();
    this.requestId = 0;
    this.listeners = new Map();

    this.init();
  }

  init() {
    this.port.start();

    this.port.onmessage = (event) => {
      const data = event.data;

      // Check if message is a broadcast from the worker
      if (data.type) {
        this.emit(data.type, data.payload || data.status);
        return;
      }

      // Handle RPC Request/Response promises
      const { id, success, result, error } = data;
      if (this.pendingRequests.has(id)) {
        const { resolve, reject } = this.pendingRequests.get(id);
        this.pendingRequests.delete(id);

        if (success) {
          resolve(result);
        } else {
          reject(new Error(error));
        }
      }
    };
  }

  // Event Emitter for broadcasts
  on(event, callback) {
    if (!this.listeners.has(event)) {
      this.listeners.set(event, []);
    }
    this.listeners.get(event).push(callback);
  }

  emit(event, payload) {
    if (this.listeners.has(event)) {
      this.listeners.get(event).forEach((cb) => cb(payload));
    }
  }

  // Dispatch message to SharedWorker
  sendRequest(action, payload = null) {
    return new Promise((resolve, reject) => {
      const id = ++this.requestId;
      this.pendingRequests.set(id, { resolve, reject });
      this.port.postMessage({ id, action, payload });
    });
  }

  // API Methods
  getHistory() {
    return this.sendRequest("GET_HISTORY");
  }

  sendMessageOverSocket(text) {
    return this.sendRequest("SEND_WEBSOCKET_MESSAGE", { text });
  }
}
```

```html
    // 2. Listen for real-time incoming messages pushed to all open tabs
    hub.on("NEW_MESSAGE", (msg) => {
      appendMessageToUI(msg);
    });

    // 3. Load persisted history from IndexedDB on page load
    window.addEventListener("DOMContentLoaded", async () => {
      try {
        const history = await hub.getHistory();
        history.forEach(appendMessageToUI);
      } catch (err) {
        console.error("Failed to load history:", err);
      }
    });

    // 4. Send message over WebSocket via SharedWorker
    sendBtn.addEventListener("click", async () => {
      const text = inputEl.value.trim();
      if (!text) return;

      try {
        await hub.sendMessageOverSocket(text);
        inputEl.value = "";
      } catch (err) {
        alert("Failed to send: " + err.message);
      }
    });

    function appendMessageToUI(msg) {
      const li = document.createElement("li");
      li.textContent = `[${new Date(msg.timestamp).toLocaleTimeString()}] ${msg.text}`;
      listEl.appendChild(li);
    }
  </script>
</body>
```

| ------------------------ | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |

Explain how to build an offline-first sync engine using idb and Service Workers with code examples

An **offline-first sync engine** allows users to read, update, create, and delete data without an active network connection. All data mutations commit instantly to local storage using the **`idb` library** (IndexedDB wrapper) so the UI updates without delay. When network connectivity is restored, a **Service Worker** syncs pending local changes to the remote server in the background.

## 2. Step 1: Database Setup (`db.js`)

Define two primary object stores:

1. **Entity Store (`posts`):** Stores local application records (cached from server or created offline).
2. **Outbox Store (`sync-outbox`):** Tracks pending mutations (POST, PUT, DELETE) queued while offline.

```javascript
// db.js
import { openDB } from 'idb';

const DB_NAME = 'OfflineSyncApp';
const DB_VERSION = 1;

export async function initDB() {
  return openDB(DB_NAME, DB_VERSION, {
    upgrade(db) {
      // 1. Primary Data Store
      if (!db.objectStoreNames.contains('posts')) {
        db.createObjectStore('posts', { keyPath: 'id' });
      }

      // 2. Outbox Store for offline mutations
      if (!db.objectStoreNames.contains('sync-outbox')) {
        const outbox = db.createObjectStore('sync-outbox', {
          keyPath: 'id',
          autoIncrement: true,
        });
        outbox.createIndex('by-timestamp', 'timestamp');
      }
    },
  });
}

```

## 3. Step 2: Optimistic Local Writes & Queueing (`sync-manager.js`)

When a user creates or updates a record:

1. Generate a temporary client-side ID (e.g., `temp-1723000000000`).
2. Write the record directly to the `posts` store so the UI updates **instantly**.
3. Queue a mutation record into `sync-outbox`.
4. Register a Service Worker **Background Sync** event (`'sync-posts'`).

```javascript
// sync-manager.js
import { initDB } from './db.js';

export async function savePostOptimistically(postData) {
  const db = await initDB();

  // Create temporary record for immediate local rendering
  const tempId = postData.id || `temp-${Date.now()}`;
  const postRecord = { ...postData, id: tempId, syncStatus: 'pending' };

  // Use a single transaction to update both stores atomically
  const tx = db.transaction(['posts', 'sync-outbox'], 'readwrite');
  
  // 1. Save to local data store
  await tx.objectStore('posts').put(postRecord);

  // 2. Save mutation payload to outbox queue
  await tx.objectStore('sync-outbox').put({
    tempId,
    endpoint: '/api/posts',
    method: postData.id && !postData.id.startsWith('temp') ? 'PUT' : 'POST',
    body: postData,
    timestamp: Date.now(),
  });

  await tx.done;

  // 3. Register Background Sync with Service Worker
  if ('serviceWorker' in navigator && 'SyncManager' in window) {
    const registration = await navigator.serviceWorker.ready;
    await registration.sync.register('sync-posts');
  } else {
    // Fallback: If Background Sync isn't supported, trigger manual sync online
    window.dispatchEvent(new CustomEvent('manual-sync-trigger'));
  }

  return postRecord;
}

```

## 4. Step 3: Background Sync Processing (`sw.js`)

In the Service Worker:

1. Listen for the **`sync`** event matching the tag `'sync-posts'`.
2. Retrieve pending mutations from `sync-outbox` ordered by timestamp.
3. Post mutations to the server API.
4. Replace temporary client IDs with official server IDs and clear processed outbox items.

```javascript
// sw.js (Service Worker)
import { openDB } from 'idb';

const DB_NAME = 'OfflineSyncApp';
const DB_VERSION = 1;

self.addEventListener('sync', (event) => {
  if (event.tag === 'sync-posts') {
    event.waitUntil(processOutboxQueue());
  }
});

async function processOutboxQueue() {
  const db = await openDB(DB_NAME, DB_VERSION);
  const tx = db.transaction('sync-outbox', 'readonly');
  const mutations = await tx.objectStore('sync-outbox').getAll();

  for (const mutation of mutations) {
    try {
      console.log(`[SW Sync] Processing mutation ID ${mutation.id}...`);

      const response = await fetch(mutation.endpoint, {
        method: mutation.method,
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(mutation.body),
      });

      if (response.ok) {
        const serverData = await response.json();

        // Atomic update: swap temp ID for real server ID & remove outbox entry
        const updateTx = db.transaction(['posts', 'sync-outbox'], 'readwrite');
        
        // Remove temporary record if server generated a new ID
        if (mutation.tempId !== serverData.id) {
          await updateTx.objectStore('posts').delete(mutation.tempId);
        }

        // Save server-confirmed record
        await updateTx.objectStore('posts').put({ ...serverData, syncStatus: 'synced' });

        // Delete processed outbox item
        await updateTx.objectStore('sync-outbox').delete(mutation.id);

        await updateTx.done;
        
        // Notify open tabs about sync completion
        notifyTabs({ type: 'SYNC_COMPLETE', id: serverData.id });
      } else if (response.status >= 400 && response.status < 500) {
        // Unrecoverable client error (e.g. 400 Bad Request): discard outbox item
        await db.delete('sync-outbox', mutation.id);
      }
    } catch (error) {
      console.error(`[SW Sync] Network error during sync. Will retry later:`, error);
      // Re-throw error so the browser reschedules retry with exponential backoff
      throw error;
    }
  }
}

function notifyTabs(message) {
  self.clients.matchAll({ type: 'window' }).then((clients) => {
    clients.forEach((client) => client.postMessage(message));
  });
}

```

## 5. Step 4: Connecting the Main UI (`app.js`)

Render content directly from IndexedDB on page load. Listen for Service Worker messages and window connection events to refresh the UI automatically.

```javascript
// app.js
import { initDB } from './db.js';
import { savePostOptimistically } from './sync-manager.js';

// 1. Initial Page Load: Render directly from local IndexedDB
async function renderPosts() {
  const db = await initDB();
  const posts = await db.getAll('posts');

  const listEl = document.getElementById('posts-list');
  listEl.innerHTML = posts
    .map(
      (p) => `
    <li>
      <strong>${p.title}</strong> 
      ${p.syncStatus === 'pending' ? '<span class="badge">⏳ Pending Sync</span>' : ''}
    </li>`
    )
    .join('');
}

// 2. Handle Form Submission
document.getElementById('post-form').addEventListener('submit', async (e) => {
  e.preventDefault();
  const titleInput = document.getElementById('post-title');

  // Perform instant optimistic save
  await savePostOptimistically({ title: titleInput.value });
  titleInput.value = '';

  // Re-render immediately from local store
  await renderPosts();
});

// 3. Listen for sync completion messages from Service Worker
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.addEventListener('message', (event) => {
    if (event.data.type === 'SYNC_COMPLETE') {
      console.log('Sync confirmed by server! Re-rendering UI...');
      renderPosts();
    }
  });
}

// Initial render
renderPosts();
```

## Key Design Considerations

| Challenge               | Strategy                          | Solution                                                                                                          |
| ----------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Instant UI Updates**  | **Optimistic UI**                 | Write immediately to IndexedDB with a temporary client key before network requests resolve.                       |
| **Unreliable Networks** | **Outbox Queue Pattern**          | Decouple UI saves from API calls by storing mutation payloads in a `sync-outbox` queue.                           |
| **Conflict Resolution** | **Server Wins / Last Write Wins** | Overwrite local temporary records with server-validated payloads once the network sync completes.                 |
| **Browser Support**     | **Sync Fallback**                 | Listen for `window.addEventListener('online')` on browsers that lack native `SyncManager` support (e.g., Safari). |
