Explain Web Workers for parallel multi-threaded JavaScript with code examples

JavaScript is single-threaded by default: UI rendering, user events, and JavaScript execution all run on the **Main Thread**. If you execute intensive calculations (e.g., image manipulation, large data sorting, or cryptography) directly on the main thread, the UI freezes, causing dropped frames and unresponsiveness.

**Web Workers** allow you to spin up true multi-threaded background processes that run independently of the main UI thread.

---

## 1. How Web Workers Communicate

Main threads and Web Workers execute in separate global contexts and communicate using **message passing**:

* **`postMessage(data)`**: Sends data across the thread boundary.
* **`onmessage = (event) => {}`**: Receives data sent from the other thread.

> **Note:** Web Workers do **not** have access to the `window`, `document`, or DOM objects. They operate in a `WorkerGlobalScope` (`self`) with access to `fetch`, `setTimeout`, `IndexedDB`, and WebAssembly.

---

## 2. Basic Example: Offloading Heavy Work

### File 1: The Worker Script (`worker.js`)

```javascript
// worker.js - Runs in a separate background thread
self.onmessage = function (event) {
  const { number } = event.data;
  console.log(`[Worker] Received number: ${number}`);

  // Perform intensive CPU task (e.g. Fibonacci calculation)
  const result = fibonacci(number);

  // Send result back to main thread
  self.postMessage({ number, result });
};

function fibonacci(num) {
  if (num <= 1) return num;
  return fibonacci(num - 1) + fibonacci(num - 2);
}

```

### File 2: The Main Application Script (`main.js`)

```javascript
// main.js - Controls UI and worker thread
const worker = new Worker("worker.js");

// 1. Listen for messages returned from the worker
worker.onmessage = function (event) {
  const { number, result } = event.data;
  console.log(`[Main] Result received: Fibonacci(${number}) = ${result}`);
  
  // Clean up worker if no longer needed
  worker.terminate();
};

// 2. Handle errors
worker.onerror = function (error) {
  console.error("[Main] Worker Error:", error.message);
};

// 3. Trigger worker task without blocking UI interactions
console.log("[Main] Offloading heavy calculation to Web Worker...");
worker.postMessage({ number: 42 });

console.log("[Main] Main thread remains completely responsive!");

```

## 3. High-Performance Zero-Copy Data Transfer (`Transferable Objects`)

By default, `postMessage()` duplicates data using the **Structured Clone Algorithm**, which creates a deep copy in memory. For huge datasets (like 100MB image pixel buffers or array buffers), copying creates a noticeable performance delay.

To eliminate copy overhead, pass **Transferable Objects** (like `ArrayBuffer`). This transfers ownership of the memory instantly ($O(1)$ time complexity) to the recipient thread, rendering it unaccessible to the sender.

```javascript
// main.js
const worker = new Worker("image-processor.js");

// Create a 50MB binary buffer
const buffer = new ArrayBuffer(50 * 1024 * 1024);
console.log("Original Buffer size before transfer:", buffer.byteLength); // 52428800

// Pass 'buffer' as the SECOND parameter in postMessage to transfer ownership
worker.postMessage({ imageBuffer: buffer }, [buffer]);

// Buffer is now detached and cleared on the main thread!
console.log("Original Buffer size after transfer:", buffer.byteLength); // 0

```

```javascript
// image-processor.js (Worker)
self.onmessage = function (event) {
  const { imageBuffer } = event.data;
  console.log("[Worker] Received zero-copy buffer:", imageBuffer.byteLength); // 52428800

  // Mutate buffer directly in worker thread...

  // Transfer back to main thread when finished
  self.postMessage({ processedBuffer: imageBuffer }, [imageBuffer]);
};

```

## 4. Creating Inline Web Workers (Without External Files)

If you are using a bundler setup or want self-contained component files, you can create a Web Worker dynamically using `Blob` and `URL.createObjectURL()`:

```javascript
function createInlineWorker(workerFunction) {
  const code = `(${workerFunction.toString()})();`;
  const blob = new Blob([code], { type: "application/javascript" });
  return new Worker(URL.createObjectURL(blob));
}

// Inline Worker Code
const myWorker = createInlineWorker(() => {
  self.onmessage = (event) => {
    const data = event.data;
    // Process data...
    self.postMessage(`Processed ${data}`);
  };
});

myWorker.onmessage = (e) => console.log("Inline Worker result:", e.data);
myWorker.postMessage("Hello Inline World");

```

Compare Web Workers vs Service Workers vs Shared Workers in JavaScript with code examples

While all three Worker types execute JavaScript in background threads off the main UI thread, they are built for entirely different architectural purposes:

* **Dedicated Web Workers:** Created by a single script instance to offload heavy CPU operations from the UI thread.
* **Service Workers:** Act as programmable network proxies between the browser, web app, and network to enable offline access, caching, and background sync.
* **Shared Workers:** Shared across multiple browser windows, tabs, or iframes from the same origin to coordinate state or manage single shared network connections.

---

## 1. Feature Comparison

| Feature                  | Dedicated Web Worker                 | Service Worker                                             | Shared Worker                                              |
| ------------------------ | ------------------------------------ | ---------------------------------------------------------- | ---------------------------------------------------------- |
| **Primary Scope**        | CPU-intensive background computation | Network proxy, offline caching, push notifications         | Cross-tab communication & state synchronization            |
| **Lifetime**             | Tied to the tab/page that spawned it | Event-driven (starts/stops on demand, lives independently) | Alive as long as at least one tab/window holds a reference |
| **Connected Clients**    | Single tab / script                  | All tabs/pages under its registered scope                  | Multiple tabs, windows, or iframes from the same origin    |
| **DOM Access**           | ❌ No                                 | ❌ No                                                       | ❌ No                                                       |
| **Network Interception** | ❌ No                                 | ✅ Yes (`fetch` event listener)                             | ❌ No                                                       |
| **Communication**        | `postMessage`                        | `postMessage` or `BroadcastChannel`                        | `MessagePort` (`port.postMessage`)                         |

## 2. Dedicated Web Worker Example

Dedicated workers are spawned by a single script to perform heavy CPU operations (such as processing large data, parsing CSVs, or crunching numbers) without freezing the UI.

### `dedicated-worker.js`

```javascript
// Dedicated Worker Scope
self.onmessage = (event) => {
  const { number } = event.data;
  const result = heavyCalculation(number);
  
  // Return result to the single parent tab
  self.postMessage(result);
};

function heavyCalculation(num) {
  let count = 0;
  for (let i = 0; i < num * 1000000; i++) count += i;
  return count;
}

```

### `main.js` (Tab A)

```javascript
const worker = new Worker('dedicated-worker.js');

worker.postMessage({ number: 50 });

worker.onmessage = (event) => {
  console.log('Result from Dedicated Worker:', event.data);
  worker.terminate(); // Cleanup worker when done
};

```

## 3. Service Worker Example

Service Workers act as a network proxy sitting between your application and the network. They intercept HTTP requests to deliver offline caching, background data syncing, and push notifications.

### `sw.js`

```javascript
const CACHE_NAME = 'v1-static-cache';
const ASSETS_TO_CACHE = ['/', '/styles.css', '/app.js'];

// 1. Install Event: Cache static assets
self.addEventListener('install', (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(ASSETS_TO_CACHE))
  );
});

// 2. Fetch Event: Intercept network requests (Cache-first strategy)
self.addEventListener('fetch', (event) => {
  event.respondWith(
    caches.match(event.request).then((cachedResponse) => {
      // Return cached asset if found, otherwise hit the network
      return cachedResponse || fetch(event.request);
    })
  );
});

```

### `main.js`

```javascript
// Register Service Worker in the browser
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js')
    .then((registration) => {
      console.log('Service Worker registered under scope:', registration.scope);
    })
    .catch((error) => {
      console.error('Service Worker registration failed:', error);
    });
}

```

## 4. Shared Worker Example

Shared Workers allow multiple open tabs, windows, or iframes from the same domain to communicate through a single background worker process. This is ideal for managing a single WebSocket connection across tabs or syncing UI state across multiple windows.

### `shared-worker.js`

```javascript
const connections = new Set();

self.onconnect = (event) => {
  const port = event.ports[0]; // Acquire MessagePort for the connecting tab
  connections.add(port);

  port.onmessage = (e) => {
    console.log('[Shared Worker] Received message:', e.data);

    // Broadcast incoming message to ALL connected tabs
    connections.forEach((conn) => {
      conn.postMessage(`Tab Broadcast: ${e.data}`);
    });
  };

  port.start(); // Required when using onmessage event listener
};

```

### `main.js` (Loaded across Tab A and Tab B)

```javascript
const sharedWorker = new SharedWorker('shared-worker.js');

// Must interact via the .port property
sharedWorker.port.onmessage = (event) => {
  console.log('Received from Shared Worker:', event.data);
};

sharedWorker.port.start();

// Send message from any open tab
sharedWorker.port.postMessage('Hello from Tab ' + Math.random().toFixed(2));

```

## When to Use Which?

* **Use Dedicated Web Workers when:** You need to run complex CPU tasks (data parsing, image filtering, sorting large datasets) on a single page without blocking the main UI thread.
* **Use Service Workers when:** You want to build a Progressive Web App (PWA) with offline capabilities, custom caching strategies, background sync, or push notifications.
* **Use Shared Workers when:** You have multi-tab web applications that need to share state in real-time or share a single active connection (e.g., WebSocket) across multiple open tabs.
