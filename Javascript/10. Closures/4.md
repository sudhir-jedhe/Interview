Explain JavaScript Closures with visual memory diagrams and real-world practical use cases.

A **closure** is created whenever a function is created in JavaScript. It allows an inner function to **retain access to variables from its outer (enclosing) function’s scope**, even after the outer function has finished executing and returned.

To put it simply: **A function "remembers" the environment in which it was born.**

---

## How Closures Work in Memory

Under normal circumstances, when a function finishes executing, its **Execution Context** is popped off the Call Stack and its local variables are garbage collected.

However, when an inner function references variables from its outer function, JavaScript creates a **hidden `[[Scope]]` property** attached to that inner function. This keeps the outer variables alive in heap memory in a special variable bundle called a **Closure**.

---

### Step-by-Step Memory Tracing

Let's trace what happens in memory with this code:

```javascript
function createCounter() {
  let count = 0; // Outer variable

  return function increment() {
    count++; // Inner function accesses 'count'
    return count;
  };
}

const counter = createCounter();
console.log(counter()); // 1
console.log(counter()); // 2

```

1. **createCounter() Executed:** Call Stack: [ GEC, FEC: createCounter() ].
`createCounter()` is called. A local variable `count = 0` is created inside its execution context.

2. **Inner Function Returned:** Call Stack: [ GEC ].
`createCounter()` returns the `increment` function reference to `counter`. `createCounter`'s execution context is **popped off** the stack.

3. **:** Heap Memory: Closure (createCounter) -.
{ count: 0 }" title="Closure Formed in Heap">
Normally, `count` would be destroyed. But because `increment` references `count`, JavaScript preserves `count` inside a **Closure object** in heap memory attached to `counter`.

4. **counter() Invoked:** Call Stack: [ GEC, FEC: counter() ].
When `counter()` is executed, it looks for `count` in its local scope. Not finding it, it looks up its `[[Scope]]` link directly into the **Closure memory**, incrementing `count` from 0 to 1, then 1 to 2.

## 3 Real-World Practical Use Cases

### 1. Data Privacy & Encapsulation (Private Variables)

JavaScript didn't historically have private class fields (`#`). Closures were—and still are—the standard pattern to create genuinely private variables that cannot be accessed or mutated from the outside world.

```javascript
function createBankAccount(initialBalance) {
  let balance = initialBalance; // Private variable

  return {
    deposit(amount) {
      if (amount > 0) balance += amount;
      return `Deposited: $${amount}. New balance: $${balance}`;
    },
    withdraw(amount) {
      if (amount <= balance) {
        balance -= amount;
        return `Withdrew: $${amount}. Remaining: $${balance}`;
      }
      return 'Insufficient funds';
    },
    getBalance() {
      return balance; // Read-only access
    }
  };
}

const myAccount = createBankAccount(100);

console.log(myAccount.deposit(50));  // "Deposited: $50. New balance: $150"
console.log(myAccount.getBalance()); // 150
console.log(myAccount.balance);    // undefined (Cannot be accessed directly!)

```

---

### 2. Function Currying & Partial Application

Currying is a functional programming technique where a function with multiple parameters is transformed into a sequence of functions, each taking a single parameter.

```javascript
// Base discount applicator using closure
function applyDiscount(discountRate) {
  return function (price) {
    return price - (price * discountRate);
  };
}

// Preset specialized functions
const tenPercentOff = applyDiscount(0.10);
const twentyPercentOff = applyDiscount(0.20);

console.log(tenPercentOff(100));    // 90
console.log(twentyPercentOff(100)); // 80

```

---

### 3. State Preservation in Async Callbacks & Event Listeners

Closures allow asynchronous callbacks (like `setTimeout`, `fetch`, or event handlers) to maintain access to state from when they were created.

```javascript
function attachButtonListeners() {
  const buttonNames = ['Save', 'Edit', 'Delete'];

  for (let i = 0; i < buttonNames.length; i++) {
    // Each iteration creates a new block-scoped 'i' and button context
    const buttonName = buttonNames[i];
    
    // The click handler callback forms a closure over 'buttonName'
    setTimeout(() => {
      console.log(`Action registered for button: ${buttonName}`);
    }, (i + 1) * 1000);
  }
}

attachButtonListeners();
// After 1 sec: Action registered for button: Save
// After 2 sec: Action registered for button: Edit
// After 3 sec: Action registered for button: Delete

```

## Memory Leak Pitfall: Retaining Unnecessary Variables

Because closures keep variables in memory, holding onto unused references can lead to memory leaks if not managed carefully.

```javascript
function outer() {
  const massiveData = new Array(1000000).fill('Data'); // Huge memory footprint
  
  return function inner() {
    // Even if inner doesn't use 'massiveData', some engines may retain references 
    // if other inner closures in the same parent scope access it!
    console.log('Inner called');
  };
}

```

> **Rule of Thumb:** Nullify references (`counter = null`) when a closure is no longer needed to allow the garbage collector to free up heap memory.

### Question 1: The Infamous `var` in a `for` Loop

**Question:** What will be logged to the console, and how do you fix it?

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(function () {
    console.log(i);
  }, 1000);
}

```

**Answer:**

```javascript
3
3
3

```

**Explanation:**
`var` is **function-scoped**, not block-scoped. All 3 iterations share the *exact same variable `i*` in memory. By the time the `setTimeout` callbacks execute 1 second later, the loop has already completed and `i` has become `3`. All three closures point to that same `i`.

**Two Ways to Fix It:**

1. **Use `let` (ES6 Block Scope):**

```javascript
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 1000);
} // Logs: 0, 1, 2

```

`let` creates a new binding/variable for `i` in each loop iteration.
2. **Use an IIFE (Immediately Invoked Function Expression) to force closure scope:**

```javascript
for (var i = 0; i < 3; i++) {
  (function (index) {
    setTimeout(() => console.log(index), 1000);
  })(i);
} // Logs: 0, 1, 2

```

### Question 2: Independent Closure Instances

**Question:** What will be logged?

```javascript
function makeCounter() {
  let count = 0;
  return function () {
    return ++count;
  };
}

const counter1 = makeCounter();
const counter2 = makeCounter();

console.log(counter1());
console.log(counter1());
console.log(counter2());

```

**Answer:**

```javascript
1
2
1

```

**Explanation:**
Every invocation of `makeCounter()` creates a **brand-new Execution Context** with its own distinct `count` variable in heap memory. `counter1` and `counter2` maintain references to two completely separate closure environments.

### Question 3: Shared Closure Scope Across Multiple Inner Functions

**Question:** What will be logged?

```javascript
function setupHandlers() {
  let value = 10;

  return {
    getValue: () => value,
    setValue: (val) => { value = val; },
    increment: () => { value++; }
  };
}

const handler = setupHandlers();

handler.increment();
handler.setValue(100);
handler.increment();

console.log(handler.getValue());

```

**Answer:**

```javascript
101

```

**Explanation:**
All three inner functions (`getValue`, `setValue`, `increment`) were created within the same call to `setupHandlers()`. They **share the exact same closure scope** and reference the single `value` variable in memory.

### Question 4: Function Arguments vs. Outer Closure Variables

**Question:** What will be logged?

```javascript
let x = 10;

function outer(x) {
  return function inner(y) {
    console.log(x + y);
  };
}

const fn = outer(20);
x = 30;
fn(5);

```

**Answer:**

```javascript
25

```

**Explanation:**

1. When `outer(20)` is called, the parameter `x` shadows/overrides the global `x = 10`. So `x` inside `outer`'s lexical environment is `20`.
2. Changing global `x = 30` afterwards has no effect on `outer`'s local parameter `x`.
3. When `fn(5)` is called, `inner` adds its argument `y` (5) to the closed-over variable `x` (20), giving `25`.

### Question 5: Implementing a One-Time Executable Function (`once`)

**Question:** How would you write a `once()` higher-order function that ensures a given function can only be invoked once, regardless of how many times it is called?

**Answer:**

```javascript
function once(fn) {
  let called = false;
  let result;

  return function (...args) {
    if (!called) {
      called = true;
      result = fn.apply(this, args);
    }
    return result;
  };
}

// Example usage:
const initializeApp = once((status) => {
  console.log(`App initialized with status: ${status}`);
  return 'SUCCESS';
});

console.log(initializeApp('ACTIVE')); // Logs: "App initialized with status: ACTIVE", Returns: "SUCCESS"
console.log(initializeApp('PENDING')); // Returns: "SUCCESS" (Callback is NOT executed again)

```

**Explanation:**
The returned function uses closures to keep track of the `called` flag and the cached `result` across multiple calls without polluting the global namespace.

### Question 6: Memoization (Caching Expensive Function Results)

**Question:** Write a generic `memoize` function using closures to cache computation results.

**Answer:**

```javascript
function memoize(fn) {
  const cache = {}; // Closure variable storing previous calculations

  return function (...args) {
    const key = JSON.stringify(args);
    
    if (key in cache) {
      console.log('Fetching from cache for args:', args);
      return cache[key];
    }

    console.log('Calculating result for args:', args);
    const result = fn(...args);
    cache[key] = result;
    return result;
  };
}

const add = (a, b) => a + b;
const memoizedAdd = memoize(add);

console.log(memoizedAdd(5, 10)); // Calculating... -> 15
console.log(memoizedAdd(5, 10)); // Fetching from cache... -> 15

```
