While all Node.js package managers strive for reproducible builds across environments, **npm**, **Yarn** (Berry/v2+), and **pnpm** implement fundamentally different lockfile formats, dependency resolution algorithms, and `node_modules` file system structures.

---

## 1. Structural Comparison: `node_modules` Strategy

The way a package manager writes files to disk directly influences its lockfile design and resolution logic:

```text
 npm & Yarn (Flat / Hoisted):
 node_modules/
 ├── react/
 ├── lodash/            <-- Accessible to code even if not in package.json (Phantom Dependency)
 └── express/

 pnpm (Content-Addressable / Hard-Linked):
 .pnpm/                 <-- Store directory containing exact version subdirectories
   ├── react@18.3.1/
   └── lodash@4.17.21/
 node_modules/
 ├── react -> .pnpm/react@18.3.1/node_modules/react    <-- Symlink
 └── .pnpm/             <-- Strict isolation (No Phantom Dependencies)

```

| Metric                    | npm (`package-lock.json`)                  | Yarn v2+ (`yarn.lock`)              | pnpm (`pnpm-lock.yaml`)                       |
| ------------------------- | ------------------------------------------ | ----------------------------------- | --------------------------------------------- |
| **Directory Strategy**    | Hoisted / Flat                             | Hoisted or Plug'n'Play (PnP)        | Isolated / Symlinked                          |
| **Lockfile Syntax**       | JSON                                       | YAML / Custom JS-like format        | YAML                                          |
| **Phantom Dependencies**  | **Possible** (hoisted packages accessible) | **Possible** (in node-modules mode) | **Prevented** (strict symlink boundaries)     |
| **Disk Space Efficiency** | Duplicates across projects                 | Duplicates across projects          | **Global Store** (hard links save disk space) |

## 2. Lockfile Syntax & Data Models

### A. npm: `package-lock.json` (Nested Tree Model)

npm stores the dependency graph as a **nested physical tree representation**. It mirrors how `node_modules` is laid out on disk after hoisting.

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "lockfileVersion": 3,
  "packages": {
    "": {
      "dependencies": { "express": "^4.19.2" }
    },
    "node_modules/express": {
      "version": "4.19.2",
      "resolved": "https://registry.npmjs.org/express/-/express-4.19.2.tgz",
      "integrity": "sha512-5T6wfdUVyMbGmyUXzA3WAmjuUXLKS23JdE1q16d5wPnaOw42V6295q08LhXCISbEaqSo4Lre2cCmU5Re9VhhQ==",
      "dependencies": {
        "qs": "6.11.0"
      }
    }
  }
}

```

* **Characteristics:** Highly verbose, uses JSON path keys (`node_modules/express`), explicitly models exact disk path locations.

---

### B. Yarn: `yarn.lock` (Range Mapping Model)

Yarn maps **requested semver ranges** directly to their **resolved exact version and tarball location**.

```yaml
# THIS IS AN AUTOGENERATED FILE. DO NOT EDIT DIRECTLY.
# yarn lockfile v6

"express@npm:^4.19.2":
  version: 4.19.2
  resolution: "express@npm:4.19.2"
  dependencies:
    qs: "npm:6.11.0"
  checksum: 10/a52b86...

"qs@npm:6.11.0":
  version: 6.11.0
  resolution: "qs@npm:6.11.0"
  checksum: 10/c88d22...

```

* **Characteristics:** Maps semver queries (e.g., `"express@^4.19.2"`) to resolved packages. Avoids duplicating package metadata if multiple packages request the same range.

---

### C. pnpm: `pnpm-lock.yaml` (Content-Addressable Graph Model)

pnpm separates **importers** (workspace projects/root) from **packages** (the global content-addressable store mapping).

```yaml
lockfileVersion: '9.0'

settings:
  autoInstallPeers: true

importers:
  .:
    dependencies:
      express:
        specifier: ^4.19.2
        version: 4.19.2

packages:
  express@4.19.2:
    resolution: {integrity: sha512-5T6wfdUVyMbGmy...}
    dependencies:
      qs: 6.11.0

  qs@6.11.0:
    resolution: {integrity: sha512-cOA...}

```

* **Characteristics:** Strict separation between user-declared imports and underlying dependency graphs. Highly optimized for monorepos (`importers` block).

## 3. Resolution Algorithms: How They Determine What to Install

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 1. NPM RESOLUTION ALGORITHM (Maximal Hoisting)                         │
 │ • Maximize hoisting to root node_modules/ to flatten the tree.         │
 │ • If version conflicts occur, nest sub-dependencies inside parent.     │
 └────────────────────────────────────────────────────────────────────────┘

 ┌────────────────────────────────────────────────────────────────────────┐
 │ 2. YARN BERRY RESOLUTION (Plug'n'Play / Deferred Determinism)         │
 │ • Maps ranges to exact hashes.                                         │
 │ • In PnP mode, generates .pnp.cjs mapping file; skips node_modules.    │
 └────────────────────────────────────────────────────────────────────────┘

 ┌────────────────────────────────────────────────────────────────────────┐
 │ 3. PNPM RESOLUTION ALGORITHM (Strict Graph Symlinking)                 │
 │ • Resolves packages into global ~/.pnpm-store via content-hash.        │
 │ • Builds virtual store in .pnpm/ and symlinks explicit imports only.   │
 └────────────────────────────────────────────────────────────────────────┘

```

### 1. npm (Maximal Hoisting Algorithm)

* **Goal:** Create the flattest possible `node_modules` tree to prevent deeply nested directory structures (historical Windows path length limit).
* **Trade-off:** High chance of **phantom dependencies** (accessing packages in code that were hoisted from indirect dependencies without declaring them in `package.json`).

### 2. Yarn (Deterministic Resolution / PnP)

* **Goal:** Eliminate `node_modules` file creation entirely via **Plug'n'Play (PnP)**.
* **Mechanism:** Generates a `.pnp.cjs` map that intercepts Node's `require()` / `import` resolutions at runtime, loading packages directly from zipped caches in `O(1)` time.

### 3. pnpm (Symlinked Content-Addressable Resolution)

* **Goal:** Maximum disk efficiency + strict dependency isolation.
* **Mechanism:**

1. Computes content hashes and downloads tarballs to a centralized global store (`~/.local/share/pnpm/store`).
2. Hard-links files from the global store into the project's `node_modules/.pnpm` directory.
3. Symlinks *only* explicitly declared `package.json` dependencies into the root `node_modules/`, rendering phantom dependencies impossible.

## Summary Comparison Matrix

| Feature                 | npm                    | Yarn v2+ (Berry)             | pnpm                            |
| ----------------------- | ---------------------- | ---------------------------- | ------------------------------- |
| **Lockfile Name**       | `package-lock.json`    | `yarn.lock`                  | `pnpm-lock.yaml`                |
| **Format**              | JSON                   | Custom YAML-like             | Clean YAML                      |
| **Default Node Layout** | Hoisted `node_modules` | PnP or Hoisted               | Symlinked `.pnpm`               |
| **Monorepo Support**    | Native Workspaces      | Native Workspaces            | **Best-in-Class** Workspaces    |
| **Install Speed**       | Baseline               | Fast (Zero-install with PnP) | **Fastest** (hard link reuse)   |
| **Strictness**          | Permissive             | Configurable                 | **Strict** (No phantom imports) |
