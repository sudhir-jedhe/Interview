# Foundations: Why Image Optimisation Matters & How Browsers Load Images

As a **Senior React/Frontend Engineer**, understanding image optimisation is essential because images are often the **largest contributor to page weight** and directly impact load times, Core Web Vitals, SEO, and user conversion.

---

## Why Image Optimisation Matters

### Without Optimisation

```text
HTML     = 50 KB
CSS      = 100 KB
JS       = 300 KB
Images   = 5 MB
-----------------
Total    = ~5.45 MB

```

The browser spends the vast majority of its time downloading uncompressed, oversized media.

**Problems:**

* ❌ Slow initial page load and high Time to Interactive (TTI)
* ❌ Excessive mobile data and bandwidth usage
* ❌ Poor Core Web Vitals (specifically LCP and CLS)
* ❌ Lower SEO rankings due to poor performance signals

---

## How Browsers Load Images

When the browser receives an HTML document, it executes the following timeline:

```text
1. Download HTML
       ↓
2. Parse HTML
       ↓
3. Build DOM
       ↓
4. Discover Image URL (Preload scanner or main parser)
       ↓
5. Request & Download Image File
       ↓
6. Decode Image (Decompress raw pixels into GPU memory)
       ↓
7. Layout & Paint Image

```

> **Key Takeaway:** Images require both **network transfer time** and **CPU/GPU decoding time** before they can be rendered onto the screen.

---

## Critical Rendering Path & Core Web Vitals

Images directly influence all three Core Web Vitals:

| Metric                                | Impact              | Cause / Mitigation                                                                                        |
| ------------------------------------- | ------------------- | --------------------------------------------------------------------------------------------------------- |
| **LCP** *(Largest Contentful Paint)*  | **Direct Impact**   | The hero image is frequently the largest element above the fold. Heavy images delay LCP.                  |
| **CLS** *(Cumulative Layout Shift)*   | **Direct Impact**   | Images without explicit `width` and `height` cause content below to jump when the image finishes loading. |
| **INP** *(Interaction to Next Paint)* | **Indirect Impact** | Large main-thread CPU spikes caused by image decoding can delay event handling.                           |

## Choose the Right Format

| Format   | Best For                               | Pros                                                                   | Cons                                                         |
| -------- | -------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| **JPEG** | Photos, complex scenes, product photos | Broad compatibility, small file size                                   | Lossy, no alpha channel (transparency)                       |
| **PNG**  | Logos, crisp line art, UI icons        | Lossless, supports full transparency                                   | Very large file sizes for photographic content               |
| **WebP** | Modern web photos, UI assets           | **~25–35% smaller** than JPEG/PNG, supports transparency and animation | Broad support across all modern browsers                     |
| **AVIF** | Modern web media (next-gen)            | **~50% smaller** than JPEG, superior compression algorithms            | Slower encoding time; requires fallbacks for legacy browsers |

## Responsive Images

### The Anti-Pattern

Serving a 4000px high-resolution desktop image to a mobile viewport that only requires a 400px rendering box.

### The Solution: `srcset` & `sizes`

Allow the browser to choose the optimal file based on screen resolution and layout width:

```html
<img
  src="product-800.jpg"
  srcset="
    product-400.jpg 400w,
    product-800.jpg 800w,
    product-1200.jpg 1200w
  "
  sizes="(max-width: 600px) 100vw, (max-width: 1200px) 50vw, 33vw"
  alt="Wireless Noise-Canceling Headphones"
  width="800"
  height="600"
  loading="lazy"
  decoding="async"
/>

```

## Lazy Loading

### Problem

A web page contains 50 product images, but the user only views the top 3 on initial load. The browser downloads all 50 upfront, blocking critical JS and CSS resources.

### Solution

Use browser-native lazy loading to delay off-screen image requests until the user scrolls nearby:

```html
<img src="footer-banner.jpg" alt="Special Offer" loading="lazy" />

```

> ⚠️ **Critical Rule for Engineers:** **NEVER lazy-load your Hero / Above-the-Fold / LCP image!** Doing so delays resource discovery and artificially hurts your LCP metric. Always keep LCP images set to `loading="eager"` (or omit the attribute) and consider using `<link rel="preload">`.

## Specify Dimensions (Preventing CLS)

### Bad (Causes Layout Shifts)

```html
<!-- Browser does not know aspect ratio until download finishes -->
<img src="hero.jpg" alt="Hero Banner" />

```

### Good (Reserves Layout Space)

```html
<!-- Browser calculates aspect-ratio instantly using height and width attributes -->
<img src="hero.jpg" alt="Hero Banner" width="1200" height="600" />

```

### Modern CSS Aspect Ratio

```css
img {
  width: 100%;
  height: auto;
  aspect-ratio: 16 / 9;
}

```

## Standard React Implementation

Here is a resilient React component utilizing the `<picture>` tag for modern format fallbacks (`AVIF` → `WebP` → `JPEG`):

```jsx
import React from 'react';

export function ProductCard({ imageAlt, srcMap, width, height, isHero = false }) {
  return (
    <picture>
      {/* 1. Try modern AVIF format */}
      <source srcset={srcMap.avif} type="image/avif" />
      
      {/* 2. Fallback to WebP */}
      <source srcset={srcMap.webp} type="image/webp" />
      
      {/* 3. Legacy fallback (JPEG/PNG) */}
      <img
        src={srcMap.fallback}
        alt={imageAlt}
        width={width}
        height={height}
        loading={isHero ? 'eager' : 'lazy'}
        fetchpriority={isHero ? 'high' : 'auto'}
        decoding="async"
        style={{ width: '100%', height: 'auto', objectFit: 'cover' }}
      />
    </picture>
  );
}

```

## Next.js Optimised Approach (`next/image`)

Next.js provides an automated, production-ready image optimization component out of the box:

```jsx
import Image from 'next/image';

export function ProductBanner() {
  return (
    <div style={{ position: 'relative', width: '100%', height: '400px' }}>
      <Image
        src="/product-hero.jpg"
        alt="Featured Product"
        fill
        priority // Preloads image & removes lazy loading for LCP hero
        sizes="(max-width: 768px) 100vw, (max-width: 1200px) 50vw, 33vw"
        style={{ objectFit: 'cover' }}
        quality={80}
      />
    </div>
  );
}

```

**Automated Benefits of `next/image`:**

* ✅ **Automatic Format Conversion:** Serves WebP/AVIF depending on incoming browser request headers.
* ✅ **On-Demand Resizing:** Generates multiple `srcset` sizes on the fly via server/edge runtime.
* ✅ **CLS Prevention:** Enforces width/height or `fill` layouts automatically.
* ✅ **Native Lazy Loading:** Default `loading="lazy"` on all non-priority images.

## DevTools Audit Checklist

### 1. Network Tab

* Filter by **Img**.
* Verify `Type` column shows `webp` or `avif`.
* Check `Size` vs `Resource` size to ensure server-side compression is enabled (Gzip/Brotli or image compression).
* Check `Priority` column (LCP image should be `High`, off-screen images should be `Low`).

### 2. Lighthouse Audit Metrics

* **Serve images in next-gen formats:** Alerts if JPEGs/PNGs could be converted to WebP/AVIF.
* **Properly size images:** Alerts if rendered size is significantly smaller than intrinsic image dimensions.
* **Defer offscreen images:** Alerts if below-the-fold images lack `loading="lazy"`.
* **Image elements have explicit width and height:** Prevents CLS penalties.
