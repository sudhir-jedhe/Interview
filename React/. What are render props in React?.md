# React Render Props Pattern: The Complete Guide

A **Render Prop** is a design pattern in React where a component receives a **function as a prop** and calls that function to determine what UI to render dynamically.

Instead of hardcoding a child component's UI or behavior inside a parent component, the parent component encapsulates the stateful logic and delegates its rendering responsibility to the consumer function.

---

## 1. What Are Render Props and What Are They For?

### Definition

A render prop is a technique for sharing stateful code or UI behaviors between components using a prop whose value is a function. The component calls that function with its internal state or data, and the function returns a React element.

> **Note:** The prop doesn't have to be named `render`. Any prop name works, and passing a function directly as `children` (known as **Function as Child Components / FACC**) is extremely common.

### Purpose

* **Logic Reuse:** Encapsulates stateful logic (mouse tracking, form state, data fetching) in one place.
* **Separation of Concerns:** Separates **data management** from **UI rendering**.
* **Flexibility & Composition:** Allows consumers to render completely different UIs using the exact same underlying logic without changing the parent component.

---

## 2. Code Examples

### Example 1: Named `render` Prop (`MouseTracker`)

```jsx
import React, { useState } from 'react';

// 1. Logic Component (tracks mouse coordinates)
function MouseTracker({ render }) {
  const [position, setPosition] = useState({ x: 0, y: 0 });

  const handleMouseMove = (event) => {
    setPosition({ x: event.clientX, y: event.clientY });
  };

  return (
    <div style={{ height: '100vh' }} onMouseMove={handleMouseMove}>
      {/* Delegates rendering to the function passed via the 'render' prop */}
      {render(position)}
    </div>
  );
}

// 2. Usage
export default function App() {
  return (
    <MouseTracker
      render={({ x, y }) => (
        <h1>The current mouse position is ({x}, {y})</h1>
      )}
    />
  );
}

```

---

### Example 2: `children` as a Function Variant (FACC)

Passing the function directly between the component tags makes the syntax read more naturally:

```jsx
import React, { useState, useEffect } from 'react';

// Component that handles data fetching logic
function DataFetcher({ url, children }) {
  const [data, setData] = useState(null);

  useEffect(() => {
    fetch(url)
      .then((response) => response.json())
      .then((result) => setData(result));
  }, [url]);

  // Invokes 'children' as a function, passing data to it
  return children(data);
}

// Usage (Function passed as children)
function UserProfile() {
  return (
    <DataFetcher url="/api/user">
      {(data) => (
        <div>{data ? <h3>Welcome, {data.name}!</h3> : <p>Loading...</p>}</div>
      )}
    </DataFetcher>
  );
}

```

## 3. Render Props vs. Custom Hooks (Modern Era)

| Metric               | Render Props Pattern                                                                               | Custom Hooks (React 16.8+)                            |
| -------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| **Logic Sharing**    | Encapsulates state within a wrapper component.                                                     | Extracts state into a plain JavaScript function.      |
| **DevTools Tree**    | Increases JSX nesting ("Wrapper Hell").                                                            | Zero extra component wrappers or DOM nodes.           |
| **Primary Use Case** | Headless UI libraries & components owning layout/DOM structure (e.g., Virtualized Lists, Dialogs). | Pure stateful logic, side effects, and data fetching. |

### Are Render Props Still Used Today?

In modern React, **Custom Hooks** have largely replaced render props for pure logic sharing. However, render props remain the gold standard in **Headless UI Component Libraries** (like Radix UI, Downshift, or TanStack Virtual/Table) where a component needs to expose layout structures or accessibility props while letting the developer control the exact styling and UI elements.

---

## 4. Key Advantages & Performance Caveats

### Advantages

1. **High Reusability:** Logic is completely decoupled from presentation.
2. **Avoids HOC Pitfalls:** Unlike Higher-Order Components (HOCs), render props do not cause prop-name collisions or opaque wrapper chains.

### Performance Caveat (Inline Functions)

Defining an inline function inside JSX creates a new function reference on **every single render** of the parent component:

```jsx
// A new anonymous function is created on every render:
<MouseTracker render={({ x, y }) => <Display x={x} y={y} />} />

```

* **Impact:** This new function reference breaks optimizations like `React.memo` on the target component because the prop will fail referential equality checks (`oldProp !== newProp`).
* **Workarounds:**

1. Wrap the inline render function in `useCallback`.
2. Hoist static render functions outside the component scope.
3. Replace pure logic render props with **Custom Hooks**, which sidestep this issue completely.

Before React 16.8 introduced Hooks, **Higher-Order Components (HOCs)** and **Render Props** were the two primary patterns used to reuse stateful logic across components. Both solved the problem of duplicating code, but they approached it from opposite directions.

## 1. Code Comparison

Let's look at how both patterns solve the exact same requirement: **tracking window scroll position and making it available to a UI component**.

### Option A: Higher-Order Component (HOC) Pattern

An HOC is a **pure function that accepts a component and returns a new enhanced component**.

```jsx
import React, { useState, useEffect } from 'react';

// 1. The HOC (Factory Function)
function withScrollPosition(WrappedComponent) {
  return function WithScrollPosition(props) {
    const [scrollY, setScrollY] = useState(0);

    useEffect(() => {
      const handleScroll = () => setScrollY(window.scrollY);
      window.addEventListener('scroll', handleScroll);
      return () => window.removeEventListener('scroll', handleScroll);
    }, []);

    // Passes injected scroll state down as a prop, forwarding existing props
    return <WrappedComponent scrollY={scrollY} {...props} />;
  };
}

// 2. Base UI Component
function Header({ scrollY, title }) {
  return (
    <header className={scrollY > 100 ? 'compact' : 'expanded'}>
      <h1>{title}</h1>
      <p>Scrolled: {scrollY}px</p>
    </header>
  );
}

// 3. Export the Wrapped Component
export default withScrollPosition(Header);

```

---

### Option B: Render Props Pattern

A Render Prop component **delegates its rendering responsibility to a function prop**.

```jsx
import React, { useState, useEffect } from 'react';

// 1. The Logic Component
function ScrollTracker({ children }) {
  const [scrollY, setScrollY] = useState(0);

  useEffect(() => {
    const handleScroll = () => setScrollY(window.scrollY);
    window.addEventListener('scroll', handleScroll);
    return () => window.removeEventListener('scroll', handleScroll);
  }, []);

  // Executes children as a function, passing internal state
  return children(scrollY);
}

// 2. Usage in UI
export default function App() {
  return (
    <ScrollTracker>
      {(scrollY) => (
        <header className={scrollY > 100 ? 'compact' : 'expanded'}>
          <h1>My Dashboard</h1>
          <p>Scrolled: {scrollY}px</p>
        </header>
      )}
    </ScrollTracker>
  );
}

```

## 2. Trade-offs & Differences

| Feature / Issue              | Higher-Order Components (HOCs)                                                                                          | Render Props Pattern                                                                                      |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **How logic is passed**      | Injected invisibly via `props`                                                                                          | Passed explicitly via function parameters                                                                 |
| **Prop Naming Collisions**   | ❌ **High Risk:** If two HOCs inject a prop named `scrollY`, the outer HOC silently overrides the inner one.             | ✅ **No Risk:** The consumer explicitly names variables in the function parameter list `(scrollY) => ...`. |
| **React DevTools Tree**      | ❌ **Wrapper Hell / Nesting:** Creates multiple layers of anonymous wrapper components (`WithScroll(WithAuth(Header))`). | ⚠️ **JSX Nesting:** Adds JSX wrapper tags, but fewer hidden component abstractions in DevTools.            |
| **Static Composition**       | Composed **outside** the component rendering pipeline at module load time.                                              | Composed **dynamically** inside the JSX rendering flow.                                                   |
| **Type Safety (TypeScript)** | ❌ Difficult to type accurately due to dynamic prop injection and wrapping.                                              | ✅ Straightforward to type (standard function argument types).                                             |

## 3. When Was Each Used?

### The HOC Era (React 15 & Early 16)

HOCs were the standard approach promoted by major React libraries in the early days:

* **Redux:** `connect(mapStateToProps)(MyComponent)`
* **React Router v4:** `withRouter(MyComponent)`
* **Relay / Apollo:** `graphql(query)(MyComponent)`

**Why HOCs lost popularity:** The "black box" nature of injected props caused severe debugging friction in large applications. Tracking where a prop originated in a component wrapped in 4 different HOCs was tedious.

### The Render Props Era (React 16.0 – 16.7)

Render props surged in popularity as a direct alternative to HOCs because they made data flow **explicit and traceable**.

* **Formik:** `<Formik>{(props) => <form ... />}</Formik>`
* **React Router v5:** `<Route render="{(props)"> <MyComponent {...props}/>} />`
* **Downshift:** Autocomplete and dropdown UI primitives.

---

## 4. Modern Perspective: The Custom Hook Era (React 16.8+)

Today, both patterns have been largely superseded by **Custom Hooks**, which extract stateful logic into plain functions without adding any UI or component wrapper overhead:

```jsx
// Modern Hook Approach
function useScrollPosition() {
  const [scrollY, setScrollY] = useState(0);

  useEffect(() => {
    const handleScroll = () => setScrollY(window.scrollY);
    window.addEventListener('scroll', handleScroll);
    return () => window.removeEventListener('scroll', handleScroll);
  }, []);

  return scrollY;
}

// Clean usage in component:
function Header({ title }) {
  const scrollY = useScrollPosition(); // Pure, zero nesting!

  return (
    <header className={scrollY > 100 ? 'compact' : 'expanded'}>
      <h1>{title}</h1>
    </header>
  );
}

```

### Is either pattern still relevant today?

* **HOCs:** Rarely used in new code bases. Occasionally seen in top-level page wrappers (e.g., `withAuthGuard(DashboardPage)`).
* **Render Props:** Still actively used in **Headless UI Component Libraries** (such as *TanStack Virtual*, *Radix UI*, or *React Aria*) where a component owns DOM event listeners or layout calculations but gives the developer total rendering freedom.

Converting legacy **Render Prop components** or **Higher-Order Components (HOCs)** into modern **Custom Hooks** eliminates component wrapping overhead, avoids prop-name collisions, and makes stateful logic easier to read and test.

Here is a step-by-step migration guide showing how to refactor both patterns.

---

## 1. Converting a Render Prop Component to a Custom Hook

### Before: Render Prop Component (`DataFetcher`)

In the Render Prop approach, the logic is tied to JSX rendering via a function child:

```jsx
// ❌ Legacy Render Prop Component
import { useState, useEffect } from 'react';

function DataFetcher({ url, children }) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch(url)
      .then((res) => res.json())
      .then((result) => {
        setData(result);
        setLoading(false);
      })
      .catch((err) => {
        setError(err);
        setLoading(false);
      });
  }, [url]);

  // Calls children as a function
  return children({ data, loading, error });
}

// Usage in UI (Requires extra JSX nesting):
function UserProfile({ userId }) {
  return (
    <DataFetcher url={`/api/users/${userId}`}>
      {({ data, loading, error }) => {
        if (loading) return <p>Loading...</p>;
        if (error) return <p>Error loading user!</p>;
        return <h1>{data.name}</h1>;
      }}
    </DataFetcher>
  );
}

```

---

### Refactoring Step: Extract Logic into a Custom Hook

To create a Custom Hook:

1. Strip away all **JSX and children invocation**.
2. Rename the function so it starts with `use` (e.g., `useFetch`).
3. Return the state data directly (as an object or array) instead of calling `children(...)`.

```jsx
// ✅ Step 1: Create the Custom Hook
import { useState, useEffect } from 'react';

export function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch(url)
      .then((res) => res.json())
      .then((result) => {
        setData(result);
        setLoading(false);
      })
      .catch((err) => {
        setError(err);
        setLoading(false);
      });
  }, [url]);

  // Return raw state instead of rendering JSX
  return { data, loading, error };
}

```

---

### After: Clean Usage with Custom Hook

Now consume the hook directly inside any functional component—zero extra component nodes or wrapper tags in the React DevTools tree:

```jsx
// ✅ Step 2: Consume in Component
function UserProfile({ userId }) {
  const { data, loading, error } = useFetch(`/api/users/${userId}`);

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error loading user!</p>;

  return <h1>{data.name}</h1>;
}

```

## 2. Converting a Higher-Order Component (HOC) to a Custom Hook

### Before: Higher-Order Component (`withWindowSize`)

In an HOC, state is injected into a wrapped component via props:

```jsx
// ❌ Legacy HOC Pattern
import { useState, useEffect } from 'react';

function withWindowSize(WrappedComponent) {
  return function WithWindowSize(props) {
    const [size, setSize] = useState({
      width: window.innerWidth,
      height: window.innerHeight,
    });

    useEffect(() => {
      const handleResize = () => {
        setSize({ width: window.innerWidth, height: window.innerHeight });
      };

      window.addEventListener('resize', handleResize);
      return () => window.removeEventListener('resize', handleResize);
    }, []);

    // Injects 'windowSize' as a prop
    return <WrappedComponent windowSize={size} {...props} />;
  };
}

// Usage in UI (Component must be wrapped on export):
function Dashboard({ windowSize, title }) {
  return (
    <div>
      <h1>{title}</h1>
      <p>Screen Width: {windowSize.width}px</p>
    </div>
  );
}

export default withWindowSize(Dashboard);

```

---

### Refactoring Step: Convert HOC to Custom Hook

1. Remove the outer higher-order wrapper function (`WrappedComponent`).
2. Rename the function to start with `use` (e.g., `useWindowSize`).
3. Return the state directly instead of passing it as a prop.

```jsx
// ✅ Step 1: Create the Custom Hook
import { useState, useEffect } from 'react';

export function useWindowSize() {
  const [size, setSize] = useState({
    width: window.innerWidth,
    height: window.innerHeight,
  });

  useEffect(() => {
    const handleResize = () => {
      setSize({ width: window.innerWidth, height: window.innerHeight });
    };

    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, []);

  return size;
}

```

---

### After: Clean Usage with Custom Hook

```jsx
// ✅ Step 2: Call inside the component directly
export default function Dashboard({ title }) {
  const windowSize = useWindowSize();

  return (
    <div>
      <h1>{title}</h1>
      <p>Screen Width: {windowSize.width}px</p>
    </div>
  );
}

```

## 3. Backward Compatibility Pattern (Adapters)

If you have legacy codebases where hundreds of components still consume a Render Prop or HOC, you don't need to break existing code during refactoring!

**Best Practice:** Re-write the underlying logic as a **Custom Hook first**, then implement the Render Prop or HOC as a lightweight wrapper around that hook:

```jsx
// 1. Core Logic (Custom Hook)
export function useFetch(url) {
  /* ... state & effect logic ... */
}

// 2. Backward Compatibility Adapter for Legacy Render Prop consumers
export function DataFetcher({ url, children }) {
  const state = useFetch(url);
  return children(state);
}

// 3. Backward Compatibility Adapter for Legacy HOC consumers
export function withFetch(url) {
  return function (WrappedComponent) {
    return function WithFetch(props) {
      const state = useFetch(url);
      return <WrappedComponent fetchState={state} {...props} />;
    };
  };
}

```

This strategy gives you the best of both worlds: modern components can consume `useFetch()` directly, while existing components continue working uninterrupted.

While **Custom Hooks** have largely replaced Render Props for pure state and logic sharing, modern **Headless UI libraries** (such as *Radix UI*, *TanStack Table/Virtual*, *Downshift*, and *React Aria*) heavily combine **Render Props** and **Compound Components** to achieve total visual flexibility without sacrificing complex accessibility (a11y) and keyboard navigation behaviors.

Here is a detailed look at how these two patterns work together in production today.

---

## 1. The Core Philosophy: What is "Headless UI"?

A **Headless UI Component** handles all the hard, invisible engineering work:

* ARIA roles and state management (`aria-expanded`, `aria-selected`, `aria-controls`).
* Complex keyboard interaction (Arrow keys, Escape, Home/End focus trapping).
* State management (open/closed, active item tracking, selections).

It leaves **100% of the styling, HTML structure, and rendering** to you. To do this seamlessly, it relies on two patterns working in tandem:

1. **Compound Components:** Provides a clean, declarative JSX API for structuring sub-parts (`Dropdown.Trigger`, `Dropdown.List`, `Dropdown.Item`).
2. **Render Props:** Exposes internal states (`isOpen`, `isSelected`, `isHighlighted`) down to the UI elements so you can conditionally style them.

---

## 2. Real-World Architecture: A Headless Select/Dropdown

Here is a complete, working example of how a modern headless UI library constructs an accessible Dropdown component using Compound Components and Render Props.

### The Headless Component Implementation

```jsx
import React, { createContext, useContext, useState } from 'react';

// 1. Create Context for state sharing across Compound Components
const SelectContext = createContext(null);

function useSelectContext() {
  const context = useContext(SelectContext);
  if (!context) throw new Error('Select sub-components must be rendered within <Select>');
  return context;
}

// 2. Root Component (Container)
export function Select({ children, defaultValue = null }) {
  const [isOpen, setIsOpen] = useState(false);
  const [selectedValue, setSelectedValue] = useState(defaultValue);

  const toggle = () => setIsOpen((prev) => !prev);
  const close = () => setIsOpen(false);

  return (
    <SelectContext.Provider value={{ isOpen, toggle, close, selectedValue, setSelectedValue }}>
      <div className="headless-select-container">{children}</div>
    </SelectContext.Provider>
  );
}

// 3. Trigger Sub-Component (Uses Render Prop)
Select.Trigger = function SelectTrigger({ children }) {
  const { isOpen, toggle, selectedValue } = useSelectContext();

  // If children is a function, execute it as a Render Prop!
  const renderedContent = typeof children === 'function' 
    ? children({ isOpen, selectedValue }) 
    : children;

  return (
    <button
      type="button"
      aria-expanded={isOpen}
      onClick={toggle}
      className="select-trigger"
    >
      {renderedContent}
    </button>
  );
};

// 4. Menu List Sub-Component
Select.List = function SelectList({ children }) {
  const { isOpen } = useSelectContext();
  if (!isOpen) return null;

  return <ul className="select-dropdown-menu" role="listbox">{children}</ul>;
};

// 5. Option Item Sub-Component (Uses Render Prop)
Select.Item = function SelectItem({ value, children }) {
  const { selectedValue, setSelectedValue, close } = useSelectContext();
  const isSelected = selectedValue === value;

  const handleSelect = () => {
    setSelectedValue(value);
    close();
  };

  const renderedContent = typeof children === 'function'
    ? children({ isSelected })
    : children;

  return (
    <li
      role="option"
      aria-selected={isSelected}
      onClick={handleSelect}
      className="select-item"
    >
      {renderedContent}
    </li>
  );
};

```

### How You Consume It in Your Application

Because of the Render Props and Compound Component pattern, consumer code looks clean, declarative, and allows custom Tailwind classes or CSS conditional styling based on internal state:

```jsx
export default function App() {
  return (
    <Select defaultValue="dark">
      {/* Trigger button uses a Render Prop to render an icon based on isOpen */}
      <Select.Trigger>
        {({ isOpen, selectedValue }) => (
          <div className="flex items-center justify-between p-2 border rounded">
            <span>Theme: {selectedValue}</span>
            <span className={`transform transition ${isOpen ? 'rotate-180' : ''}`}>▼</span>
          </div>
        )}
      </Select.Trigger>

      {/* Menu items use Render Props to apply selected/active styles */}
      <Select.List>
        <Select.Item value="light">
          {({ isSelected }) => (
            <div className={`p-2 ${isSelected ? 'bg-blue-500 text-white' : 'bg-white'}`}>
              ☀️ Light Mode {isSelected && '✓'}
            </div>
          )}
        </Select.Item>

        <Select.Item value="dark">
          {({ isSelected }) => (
            <div className={`p-2 ${isSelected ? 'bg-blue-500 text-white' : 'bg-white'}`}>
              🌙 Dark Mode {isSelected && '✓'}
            </div>
          )}
        </Select.Item>
      </Select.List>
    </Select>
  );
}

```

## 3. Why This Hybrid Approach Outperforms Pure Hooks

You might wonder: *If Custom Hooks exist, why don't headless libraries use ONLY hooks?*

Consider TanStack Table (`useReactTable`) vs Radix UI (`<Dialog.Root>`):

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│                             HEADLESS PATTERNS                               │
├──────────────────────────────────────────┬──────────────────────────────────┤
│           Custom Hooks Only              │  Compound Components + Render    │
│       (e.g., TanStack Table)             │      Props (e.g., Radix UI)       │
├──────────────────────────────────────────┼──────────────────────────────────┤
│ * Best when you need full control over   │ * Best when the component owns   │
│   DOM creation and element placement.    │   specific DOM hierarchy/portal  │
│ * You wire up all aria-attributes,       │   relationships (e.g. Modals).   │
│   event listeners, and refs manually.    │ * Accessibility attributes &     │
│ * High flexibility, but requires writing │   DOM focus management are       │
│   more boilerplate DOM code.             │   handled automatically.         │
└──────────────────────────────────────────┴──────────────────────────────────┘

```

### 1. Automatic DOM Injection & Portals

Components like Modals or Tooltips need to render into `document.body` via a React Portal. A custom hook cannot automatically wrap elements in a portal or attach event listeners to parent containers without extra ref wiring. A Compound Component can.

### 2. Zero-Boilerplate ARIA Binding

With custom hooks, you must manually spread props (`<button {...getTriggerProps()}>`).
With Headless Compound Components, the ARIA wiring happens **inside** `Select.Trigger`, keeping the user's JSX code clean while exposing state via Render Props.
