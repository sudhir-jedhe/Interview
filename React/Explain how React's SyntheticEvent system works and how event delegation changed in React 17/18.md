React’s event handling system abstracts native browser events into a unified, cross-browser wrapper called **`SyntheticEvent`**.

To deliver high performance and low memory overhead, React does not attach event listeners directly to individual DOM elements (like `<button>` or `<input>`). Instead, it uses **Event Delegation**, listening at a higher level in the DOM tree and routing events internally.

---

# Architecture of React Event Delegation

```text
  REACT 16 (Legacy Event Delegation)             REACT 17 / 18 (Modern Event Delegation)
  
      document (Global Level)                        #root / Container Node (Isolated Root)
  ┌─────────────────────────────┐                ┌─────────────────────────────┐
  │  document.addEventListener  │                │  rootNode.addEventListener  │
  └──────────────┬──────────────┘                └──────────────┬──────────────┘
                 │                                              │
                 ▼                                              ▼
    [ Entire Document / Page ]                     [ React Application Tree ]
    • Global event pollution                       • Micro-frontend friendly
    • Breaks nested React roots                    • Safe e.stopPropagation()

```

---

## 1. What is a `SyntheticEvent`?

A `SyntheticEvent` is a cross-browser wrapper around the browser's native `Event` object (`e.nativeEvent`).

### Key Characteristics

* **Cross-Browser Consistency:** Normalizes differences across browser event implementations (e.g., standardizing `e.preventDefault()`, `e.stopPropagation()`, and mouse/keyboard property names).
* **Native Event Access:** The underlying browser event is always accessible via `e.nativeEvent`.
* **Pooling Removed in React 17+:** In React 15/16, React used **Event Pooling** (reusing `SyntheticEvent` objects to reduce garbage collection). Accessing `e.target` asynchronously inside a `setTimeout` required calling `e.persist()`. **React 17 completely removed event pooling**, meaning `SyntheticEvent` properties remain accessible asynchronously without calling `e.persist()`.

---

## 2. How React Event Delegation Works Under the Hood

When you write JSX like `<button onClick={handleClick}>`, React does **not** call `element.addEventListener('click', handleClick)`.

Instead, the event delegation lifecycle executes in 4 distinct phases:

1. **Root Event Registration:** During initial mounting (`ReactDOM.createRoot`), React attaches a single top-level event listener for every known event type (`click`, `keydown`, `change`, etc.) to the root container node.
2. **Native Capture/Bubble Phase:** When a user clicks a button, the browser fires a native DOM event that bubbles up to the root container.
3. **Dispatch & Fiber Tree Lookup:** When the event hits the root container listener, React intercepts `e.nativeEvent` and inspects the target DOM node to find its corresponding **Fiber Node**.
4. **Synthetic Propagation Simulation:** React traverses up the Fiber tree from the target node, collecting all matching JSX event handlers (`onClickCapture`, `onClick`). It constructs a SyntheticEvent and invokes those handlers sequentially, simulating capture and bubble phases entirely within JavaScript.

---

## 3. The Architecture Shift: Event Delegation in React 17/18

In **React 16 and earlier**, React attached all delegated event listeners to the global **`document`** object. In **React 17 and 18**, React changed event delegation to attach listeners to the **root DOM container node** (e.g., `<div id="root">`) where `ReactDOM.createRoot()` is mounted.

```javascript
// React 16 (Targeted document)
document.addEventListener('click', reactEventHandler);

// React 17/18 (Targeted root container)
const rootNode = document.getElementById('root');
rootNode.addEventListener('click', reactEventHandler);

```

---

### Why This Change Was Critical

#### A. Safe Multi-Version / Micro-Frontend Architecture

When embedding multiple React applications (or different React versions) on a single web page:

* **React 16 Problem:** Both React apps attached listeners to `document`. Calling `e.stopPropagation()` inside a nested React app failed to stop events from reaching the outer React app because both listened at the same level (`document`).
* **React 17/18 Solution:** Event listeners are isolated inside their respective root container nodes (`#root-app-1` vs `#root-app-2`). Events do not bleed across boundaries.

#### B. Interoperability with Non-React / Legacy Code

If a legacy non-React script listens to events on `document` or parent DOM wrappers:

* In React 16, stopping propagation inside React (`e.stopPropagation()`) would still allow the native event to bubble up to `document` before React could catch it.
* In React 17/18, calling `e.stopPropagation()` inside a React event handler stops the native event from bubbling past the `#root` container, matching standard DOM behavior.

#### C. Smooth Upgrade Paths

Attaching event listeners to root containers enables teams to safely run two different major versions of React (e.g., React 17 and React 18) side-by-side inside the same page during incremental migration projects.

## Technical Comparison Matrix

| Event System Metric               | React 16 (Legacy)                      | React 17 / 18 (Modern)                          |
| --------------------------------- | -------------------------------------- | ----------------------------------------------- |
| **Delegation Attachment Target**  | `document` (Global Document Object)    | **`rootNode`** (e.g., `<div id="root">`)        |
| **Event Pooling (`e.persist()`)** | Enabled (Event objects were reused)    | **Disabled** (Event objects are persistent)     |
| **Nested React Trees Support**    | ❌ Broken (`e.stopPropagation()` leaks) | ✅ **Isolated & Safe**                           |
| **`onScroll` Event Behavior**     | Delegated to `document`                | Bound directly to target element (non-bubbling) |
| **`onFocus` / `onBlur` Mapping**  | Uses `focusin` / `focusout` internally | Aligned closer to native DOM standards          |
