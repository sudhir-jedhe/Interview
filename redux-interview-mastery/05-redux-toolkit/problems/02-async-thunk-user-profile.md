# Problem 2: Async Thunk for Fetching a User Profile

## Task

Implement a `userSlice` that fetches a user profile by id from `/api/users/:id`, correctly modeling the pending/fulfilled/rejected lifecycle in `extraReducers`, with:

- A `status` field: `'idle' | 'loading' | 'succeeded' | 'failed'`.
- An `error` field holding a UI-friendly message on failure.
- Protection against a stale response overwriting a newer one if the user id changes quickly (e.g., navigating between two user profile pages before the first request finishes).

## Reference solution

```javascript
import { createSlice, createAsyncThunk } from '@reduxjs/toolkit';

export const fetchUserProfile = createAsyncThunk(
  'user/fetchProfile',
  async (userId, { rejectWithValue, signal }) => {
    try {
      const response = await fetch(`/api/users/${userId}`, { signal });
      if (!response.ok) {
        const body = await response.json().catch(() => ({}));
        return rejectWithValue({
          status: response.status,
          message: body.message ?? 'Failed to load user profile',
        });
      }
      return await response.json();
    } catch (err) {
      if (err.name === 'AbortError') {
        // request was cancelled (e.g. component unmounted) — let RTK's
        // built-in `condition`/abort handling mark this rejected without
        // treating it as a "real" user-facing error
        throw err;
      }
      return rejectWithValue({ status: 0, message: 'Network error' });
    }
  }
);

const userSlice = createSlice({
  name: 'user',
  initialState: {
    profile: null,
    status: 'idle',
    error: null,
    currentRequestId: undefined, // tracks which in-flight request is the "latest"
  },
  reducers: {
    profileCleared(state) {
      state.profile = null;
      state.status = 'idle';
      state.error = null;
      state.currentRequestId = undefined;
    },
  },
  extraReducers: (builder) => {
    builder
      .addCase(fetchUserProfile.pending, (state, action) => {
        state.status = 'loading';
        state.error = null;
        state.currentRequestId = action.meta.requestId; // remember which request this is
      })
      .addCase(fetchUserProfile.fulfilled, (state, action) => {
        // ignore this response if a newer request has since started
        if (state.currentRequestId !== action.meta.requestId) return;
        state.status = 'succeeded';
        state.profile = action.payload;
        state.currentRequestId = undefined;
      })
      .addCase(fetchUserProfile.rejected, (state, action) => {
        if (state.currentRequestId !== action.meta.requestId) return;
        if (action.meta.aborted) {
          state.status = 'idle'; // cancelled, not a real failure
          return;
        }
        state.status = 'failed';
        state.error = action.payload?.message ?? action.error.message;
        state.currentRequestId = undefined;
      });
  },
});

export const { profileCleared } = userSlice.actions;
export default userSlice.reducer;
```

## Why the `requestId` guard matters

Every dispatch of `fetchUserProfile(id)` gets a unique `action.meta.requestId`, generated by RTK, shared across that specific call's `pending`/`fulfilled`/`rejected` actions. If a user navigates from profile A to profile B before A's request resolves, two overlapping requests are in flight. Without the guard, whichever response arrives *last* wins — which could be the stale request for profile A landing after profile B's request already succeeded, silently showing the wrong profile. Storing `currentRequestId` on `pending` and checking it in `fulfilled`/`rejected` ensures only the most recently dispatched request's result is ever applied to state, discarding results from requests that are no longer the "current" one.
