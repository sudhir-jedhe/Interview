# Interview Q&A: Reducer Composition and Architecture

**Q: `combineReducers` gives each slice reducer only its own slice of state. How, then, can one slice react to an action that "belongs" to another slice — e.g., resetting the cart when the user logs out?**
A: The state tree is partitioned by `combineReducers`, but the *action* namespace is global — every reducer function, regardless of which slice it owns, receives every dispatched action and independently decides whether to respond to it. So `cartReducer`'s `switch` (or `createSlice`'s `extraReducers`) can have a `case 'auth/loggedOut':` even though `'auth/loggedOut'` is an action type "owned" by a different slice's action creators. This is the sanctioned mechanism for cross-slice reactions, not a workaround.

**Q: When using `createSlice`'s `extraReducers`, should you match on a raw string (`'auth/loggedOut'`) or the imported action creator (`authSlice.actions.loggedOut`)? Why does it matter?**
A: Always prefer the action creator. Matching on a raw string works today but silently decouples the match from its actual source of truth — if the other slice's `name` is ever renamed (changing the generated action type), the string-based match stops working with no error, while `builder.addCase(authSlice.actions.loggedOut, ...)` stays correct automatically because it always reflects whatever type that action creator currently produces (and gives you type-checking in TypeScript).

**Q: Why split reducers by state-tree domain rather than by UI feature? A "checkout" feature touches cart, user, and payment — wouldn't a `checkoutReducer` be more cohesive from a feature perspective?**
A: The state tree's shape should reflect the *data's* natural domain boundaries, not any one feature's usage of that data — cart data is used by checkout, but also by the product page, the header badge, and order history; user data is used by checkout, but also by the profile page and the header. A `checkoutReducer` that reaches across cart/user/payment would create competing ownership: is cart quantity logic defined in `cartReducer` or in `checkoutReducer`? Keeping one reducer per state domain (`cart`, `user`, `payment`), each independently testable and owned, avoids that ambiguity — features are free to read/dispatch across multiple slices without those slices needing to know about each other.

**Q: What's the practical cost of a single, un-split, 800-line switch-statement reducer, beyond "it's harder to read"?**
A: Concretely: merge conflicts multiply, because Git can't reconcile two engineers' independent case additions to the same function body even when their changes are logically unrelated; unit testing becomes harder, because testing one domain's logic requires importing and understanding the whole file; and onboarding is slower, because a new engineer working on, say, notifications has to read through cart and user logic to find the relevant cases. Splitting by domain via `combineReducers` fixes all three by construction, at essentially zero runtime cost.
