# Interview Q&A: Reducer Purity and Mutation

**Q: What specifically breaks — mechanically, not just "it's bad practice" — if a reducer mutates state instead of returning a new object?**
A: Two concrete things: (1) `useSelector`/`connect`'s re-render decision is based on reference equality (`===`) between the previous and new selected value; a mutation leaves the reference unchanged, so subscribed components don't re-render even though the data changed — a silent, stale-UI bug with no error or warning. (2) Redux DevTools' time-travel/"jump to action" feature keeps a snapshot of state at each point in the action history; if a reducer mutates a shared object, snapshots that reference that same object retroactively "change" too, corrupting the history DevTools relies on to let you step backward and forward accurately.

**Q: How does `createSlice` let you write `state.items.push(x)` safely, when the exact same line in a hand-written reducer would be a real bug?**
A: `createSlice` wraps every reducer function with Immer's `produce`. Inside the function, `state` isn't the real state object — it's a Proxy (a "draft") that records every operation performed on it. When the function returns, Immer uses the recorded operations to construct a genuinely new, immutable object, leaving the real underlying state untouched. The syntax looks like mutation for developer convenience; the actual object graph handed to `getState()` afterward is always a new one where anything changed, and structurally shares (reuses by reference) any part of the tree that wasn't touched.

**Q: Can a `createSlice` reducer both mutate the draft *and* return a new value in the same function?**
A: No — Immer throws an error if you do both in one reducer, because it's ambiguous which strategy should determine the final state. You must pick one: either mutate the `state` parameter with no return statement, or leave `state` untouched and `return` an entirely new value. See `output-based/04-createSlice-forgetting-to-return-or-mutate.md` for the exact error and why it happens.

**Q: A reducer does `return { ...state }` with no other change, in its `default` case, instead of `return state`. Does that matter?**
A: Yes, and it's a subtle but real bug. `{ ...state }` creates a brand-new object reference even though nothing logically changed. Every component whose `useSelector` reads (directly or via a selector deriving from) that top-level state object would see "a new reference" on every single dispatch — including dispatches for completely unrelated action types — and re-render unnecessarily. The `default` case must return the exact same reference (`return state;`), not a shallow copy of it, specifically to preserve the "nothing changed" signal that reference equality is used to detect.
