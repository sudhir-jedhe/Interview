# The Standard Async Flow: Pending → Fulfilled / Rejected

Almost every async operation in a Redux app follows the same three-beat pattern, regardless of whether it's written by hand with `redux-thunk` or generated by `createAsyncThunk`: dispatch a "this started" action, do the async work, then dispatch either a "this succeeded" or "this failed" action depending on the outcome.

```javascript
// Hand-written version, no RTK — the pattern RTK's createAsyncThunk automates
function fetchOrders() {
  return async (dispatch, getState) => {
    dispatch({ type: 'orders/fetchPending' });
    try {
      const res = await fetch('/api/orders');
      if (!res.ok) throw new Error(`Request failed with status ${res.status}`);
      const data = await res.json();
      dispatch({ type: 'orders/fetchFulfilled', payload: data });
    } catch (err) {
      dispatch({ type: 'orders/fetchRejected', payload: err.message });
    }
  };
}
```

Why exactly this three-way split, and not just "dispatch the result when it arrives"? Because the UI needs to represent **three distinct states**, not two:

1. **Nothing has happened yet / idle** — often the implicit initial state before any dispatch.
2. **In flight** — the request has started but hasn't resolved. The UI shows a spinner, disables a submit button, etc. This is why `pending` is dispatched *synchronously*, the instant the thunk starts, not after any `await` — the UI needs to know "loading" immediately, not after the network round-trip that loading state is meant to cover.
3. **Settled — success or failure** — two genuinely different outcomes that the UI must render differently: a success shows data, a failure shows an error message (and often a retry action).

A common mistake is treating this as a two-state boolean (`isLoading: true/false`) with a separate, uncoordinated `error` field defaulting to `null`. That under-models the state space: it becomes possible (through incomplete/buggy dispatch sequences) to end up with `isLoading: false, error: null, data: null` — which looks like "idle" but might actually mean "silently failed with an error a previous action neglected to set," or `isLoading: true` while stale `error` from a previous failed attempt is still sitting there, incorrectly rendered alongside the spinner. Modeling status as a single enum (`'idle' | 'loading' | 'succeeded' | 'failed'`) makes illegal combinations unrepresentable — the UI's `switch (status)` can only ever be in one of exactly four states.

```javascript
const initialState = {
  data: null,
  status: 'idle', // 'idle' | 'loading' | 'succeeded' | 'failed'
  error: null,
};

function ordersReducer(state = initialState, action) {
  switch (action.type) {
    case 'orders/fetchPending':
      return { ...state, status: 'loading', error: null };
    case 'orders/fetchFulfilled':
      return { ...state, status: 'succeeded', data: action.payload };
    case 'orders/fetchRejected':
      return { ...state, status: 'failed', error: action.payload };
    default:
      return state;
  }
}
```

This exact shape — `status` enum + `data` + `error`, driven by a pending/fulfilled/rejected action triplet — is precisely what `createAsyncThunk` standardizes and generates for you, which is why understanding this pattern by hand first makes RTK's automation click immediately rather than feeling like magic.
