# Interview Q&A: Parameterized Selectors and the Shared-Instance Pitfall

**Q1: Walk through exactly why a single memoized selector taking an id parameter breaks when reused across multiple component instances.**

A: `createSelector`'s default cache holds exactly one entry — the most recent set of input values and their corresponding result. If one shared, module-level selector instance is called by multiple component instances, each with a *different* id (e.g., five `<Row rowId={id}>` components all calling the same `selectRowById`), then in any sequence of calls where consecutive calls have different ids, each call's inputs differ from the immediately preceding call's — so every call is a cache miss. The single cache slot gets evicted and overwritten by whichever component called last, meaning no component instance ever reliably gets a cache hit, and the result function ends up running on effectively every render for every instance — memoization provides no benefit at all, despite `createSelector` being used correctly in isolation.

**Q2: What's the standard fix, and how do you make sure each component gets its own selector instance?**

A: Use a selector **factory** — a function that, when called, returns a brand-new `createSelector(...)` instance with its own independent cache — and call that factory once per component instance, typically via `useMemo(makeSelector, [])` so the same instance (and its cache) persists across that component's own re-renders but is never shared with a different component instance. `const selectRowById = useMemo(makeSelectRowById, [])` inside the component, then `useSelector((state) => selectRowById(state, rowId))`.

**Q3: If you used `useMemo(makeSelector, [rowId])` instead of `useMemo(makeSelector, [])`, would that still work?**

A: It would still be correct, but it defeats part of the purpose — using `[rowId]` as the dependency array would create a *new* selector instance (and reset its cache) every time `rowId` changes, which for a component whose `rowId` prop is genuinely stable for its whole lifetime (the common case — a given row's id doesn't change) makes no practical difference. But it also means if `rowId` *did* change on an existing instance (e.g., a virtualized list reusing component instances for different rows as you scroll), you'd get a "fresh" selector with an empty cache exactly when the id changes — which is actually the same cache-miss outcome as not memoizing before you even reused it. `[]` (create once, for the component instance's whole lifetime) is generally the right choice specifically because keeping one stable cache slot per rendered row is the entire point.

**Q4: Is there an alternative to the factory pattern for parameterized selectors, and when would you use it instead?**

A: `createSelector` accepts a `memoizeOptions` configuration (or you can use `createSelectorCreator` with `lruMemoize`) to use a cache larger than size 1 — e.g., `{ memoizeOptions: { maxSize: 10 } }` remembers the last 10 distinct sets of inputs rather than just 1. This works well when you know the parameter takes a small, bounded set of distinct values (e.g., a fixed set of 5 dashboard tabs) shared across the whole app, since one selector instance with a larger cache can then serve all callers without thrashing. It's a worse fit than the factory pattern when the number of distinct parameter values is large or unbounded (e.g., arbitrary row ids in a big list), where a per-component-instance cache of size 1 (via the factory) is both simpler and more directly matched to the actual usage pattern.
