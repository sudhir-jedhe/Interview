# Interview Q&A: Performance and Re-renders

**Q: A component re-renders far more often than expected. What's your debugging process, specifically for Redux-connected components?**
A: First, use React DevTools' Profiler to confirm which component(s) are re-rendering and roughly how often, correlated against user actions. For each suspect component, inspect every `useSelector` call: does any of them construct a new object/array/function on each invocation (`.map`, `.filter`, object/array literals, inline arrow functions passed as the selector itself creating closures)? If so, that's almost always the cause, given `useSelector`'s default reference-equality comparison. The fix is one of: select a narrower/primitive value, add `shallowEqual`, or introduce a memoized `reselect` selector — chosen based on whether the component actually needs the derived array/object (memoize) or just a summary of it (select something narrower, sidestepping the issue).

**Q: When would you reach for `reselect`'s `createSelector` instead of just passing `shallowEqual` to `useSelector`?**
A: `shallowEqual` avoids the *re-render* but not the *recomputation* — the selector function itself still runs on every dispatch, doing the `.filter`/`.map`/whatever work again, even if the result ends up discarded because it's shallowly equal to before. For a cheap derivation, that's fine. For an expensive one (large-list sorting, grouping, multi-step aggregation), `createSelector` avoids the recomputation itself by memoizing based on its declared input selectors, only re-running the "combiner" function when at least one input's reference actually changed. Use `shallowEqual` for cheap-to-recompute derivations where only rendering cost matters; use `reselect` when computation cost matters too.

**Q: Does splitting one `useSelector` call into several always improve performance?**
A: Not automatically, and not always meaningfully — the improvement specifically comes from avoiding a *newly constructed object/array* being compared by reference, not from the raw number of `useSelector` calls. Splitting `useSelector((s) => ({a: s.a, b: s.b}))` into two calls selecting `s.a` and `s.b` separately helps because it removes the object-construction problem. Splitting `useSelector((s) => s.user)` (already a stable reference from the store) into finer pieces doesn't meaningfully help unless `state.user` itself changes more often than the specific sub-fields the component actually renders — it's about avoiding unnecessary re-renders relative to what the component actually displays, not about hook count for its own sake.

**Q: Is it possible to over-optimize `useSelector` usage? What's the cost of doing so?**
A: Yes — every `useSelector` call sets up its own subscription and comparison logic, so splitting every conceivable field into its own call adds real (if usually small) overhead and more code to read/maintain, for state that may change rarely enough that the "waste" from a broader selector was never actually visible to users. The right approach is profiling-driven: apply narrow selectors, `shallowEqual`, or `reselect` where profiling (or a code-review red flag like a persistent, high-traffic component doing unmemoized array/object derivation) shows a real problem, not as a blanket rule applied to every `useSelector` in the codebase.
