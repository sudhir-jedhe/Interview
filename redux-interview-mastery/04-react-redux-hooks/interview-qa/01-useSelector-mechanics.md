# Interview Q&A: `useSelector` Mechanics

**Q: Walk through exactly what happens internally when a component using `useSelector` re-renders after a dispatch.**
A: `react-redux` maintains an internal subscription (built on the store's `subscribe`) per connected component. After a dispatch, that subscription callback fires, causing `useSelector` to re-run the selector function against the new state. The new result is compared to the previous render's result — by strict reference equality (`===`) by default, or via a custom comparator if one was passed as `useSelector`'s second argument. If the comparison says "different," `useSelector` triggers a re-render of the component (via React's internal state-update mechanism); if "same," it skips it, and the component's previous render output stands.

**Q: Why does `useSelector` default to reference equality instead of deep equality?**
A: Performance — deep equality requires traversing the entire object/array structure on every comparison, which is expensive for large or deeply nested state, and worse, doesn't have an obvious "when to stop" boundary for very large state trees. Reference equality is O(1) and fast regardless of state size, at the cost of requiring the selector author to be deliberate about returning stable references (primitives, or memoized objects/arrays) when they want to avoid unnecessary re-renders.

**Q: A selector returns `state.cart.items` directly, with no transformation. Does it have the referential-equality problem?**
A: No — `state.cart.items` is a reference to whatever array object is currently living in the store's state; it isn't a *new* array being constructed by the selector. As long as the reducer only replaces that array reference when its contents genuinely change (correct immutable-update practice, per `02-actions-reducers`), `useSelector` will correctly see "unchanged" when nothing changed, and "changed" when the reducer legitimately produced a new array. The problem specifically arises when the *selector itself* derives a new object/array (`.map`, `.filter`, a spread, an object literal) on every call, independent of whether the source data changed.

**Q: Can `useSelector`'s selector function have side effects, like logging or dispatching another action?**
A: It shouldn't — the selector may run multiple times per render for reasons outside your control (React's Strict Mode intentionally double-invokes selectors in development to help surface exactly this kind of bug, and `react-redux` itself may re-run selectors defensively in certain edge cases). A selector should be a pure, synchronous function of `state` — the same discipline reducers are held to, and for a similar reason: predictability. Side effects belong in `useEffect`, event handlers, or middleware, not inside a selector function.
