# Interview Q&A: Principles and Philosophy

**Q: State the three principles of Redux, and for each one, name a concrete bug that results from violating it.**
A: (1) Single source of truth — violating it means multiple stores or state scattered outside the tree, causing components to read stale or inconsistent copies of "the same" data. (2) State is read-only — violating it (mutating state outside a reducer) means changes bypass the action/reducer pipeline entirely, so DevTools never sees them, middleware never runs, and time-travel is impossible for that change. (3) Changes via pure functions — violating it (side effects or non-determinism inside a reducer) breaks time-travel/replay, because replaying the same actions no longer reproduces the same state, and can cause different behavior between environments (e.g., server-rendering vs client hydration mismatches if a reducer calls `Date.now()`).

**Q: Why is "state is read-only" enforced by convention rather than by the language? Nothing stops me from writing `state.count = 5` inside a reducer.**
A: Correct — plain Redux (`createStore`) doesn't freeze state or throw on mutation; the guarantee is a contract, not a runtime enforcement. In development, tools like `redux-immutable-state-invariant` (bundled into Redux Toolkit's default middleware) detect mutations by deep-comparing state before/after each dispatch and throwing a descriptive error, specifically because the raw library can't catch it for you. Redux Toolkit's `createSlice` goes further and makes mutation *safe* by running reducers through Immer, which intercepts assignment-style code and produces real immutable updates — but that's a deliberate ergonomic layer on top of the same underlying principle, not a relaxation of it.

**Q: What's the difference between the store's `subscribe` mechanism and React re-rendering? Why doesn't every `dispatch` cause every connected component to re-render?**
A: `store.subscribe(listener)` is a raw, low-level hook that fires the listener after *every* dispatch, with no concept of what changed. `react-redux`'s `useSelector` builds on top of `subscribe`: internally it subscribes once, and on every notification it re-runs your selector function against the new state and compares the result to the previous render's result (by reference, by default). Only if that comparison fails does it force a re-render of that specific component. This means the "is this relevant to me" filtering happens per-component, in `react-redux`, not in the store itself.

**Q: Someone says "Redux makes React apps faster." Is that true?**
A: Not inherently, and it's a common misstatement. Redux (and `react-redux`) doesn't make rendering faster by default — done carelessly (e.g., selecting a large object and causing broad re-renders), it can make things slower than well-organized local state. What Redux and `useSelector` provide is a *mechanism* for fine-grained, subscription-based updates (a component only re-renders when the specific slice of state it selects changes, rather than re-rendering because a distant ancestor's state changed and the whole subtree re-rendered), which *can* be used to build more efficient update patterns than prop-drilling through many components — but that requires writing narrow, well-designed selectors, not just adopting Redux.
