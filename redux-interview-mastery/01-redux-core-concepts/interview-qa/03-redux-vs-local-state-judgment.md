# Interview Q&A: Redux vs Local State Judgment

**Q: A candidate says "I always put all my state in Redux, it's simpler than deciding case by case." How do you respond in an interview setting?**
A: Push back constructively: ask them to justify putting, say, a text input's live value or a dropdown's open state in Redux. The honest cost is real — every keystroke now dispatches an action, runs through the reducer and any middleware, and triggers `useSelector` comparisons in every subscribed component, for state that's read and written by exactly one component. "Always Redux" isn't simpler, it's just uniform; it trades a small amount of per-feature decision-making for a large amount of unnecessary indirection and boilerplate on state that never needed to leave the component. The interview signal you want is someone who can articulate *why* a given piece of state belongs where it belongs, not a blanket rule.

**Q: Give an example of state that starts local but should be "lifted" to Redux as the app grows — and explain what specifically changes that justifies the move.**
A: A "recently viewed products" list. Early on, it might live in the product detail page's local state, updated whenever that page mounts. As the app grows, the requirement expands: show recently viewed items in the header's quick-access menu, in a "continue browsing" section on the homepage, and persist them to `localStorage` across sessions. What changed is that the state is now read by multiple, distant components (no longer just the page that wrote it) and needs a single, shared update path (adding an item must behave identically regardless of which product page triggered it) — exactly the two signals in `04-when-to-use-redux.md` for centralizing state.

**Q: Is React Context a substitute for Redux? When would you pick one over the other?**
A: Context solves *prop drilling for reads* — it doesn't provide dispatch semantics, middleware, or partial/selector-based re-render optimization out of the box. For infrequently-changing, broadly-read values (theme, current locale, feature flags), Context is often sufficient and lighter-weight than pulling in Redux. For state with frequent updates, non-trivial update logic shared across many call sites, or a need for time-travel/logging/middleware, Redux remains a better fit — because with Context alone, *every* consumer of that context re-renders on any change to the provided value, unless you manually split contexts or memoize heavily, which starts to reinvent what `useSelector`'s reference-equality check already gives you for free.

**Q: What's a concrete tell, during code review, that a piece of state was put in Redux unnecessarily?**
A: It has exactly one reader and one writer, both within the same component or a direct parent/child pair, and nothing else in the codebase imports its selector or dispatches its actions. If `git grep` for a given action type or selector only turns up matches inside one feature folder, and specifically inside one component's file plus its immediate children, that's local state wearing a Redux costume — a strong candidate for reverting to `useState`/`useReducer`.
