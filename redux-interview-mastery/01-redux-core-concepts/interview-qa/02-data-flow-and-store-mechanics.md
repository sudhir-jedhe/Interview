# Interview Q&A: Data Flow and Store Mechanics

**Q: Walk me through, step by step, what happens between a user clicking a button and the screen updating, in a Redux + React app.**
A: (1) The `onClick` handler calls `dispatch(actionCreator(...))`, producing a plain action object. (2) `dispatch` runs the action through any middleware chain (e.g., thunk, logger), then invokes the root reducer with `(currentState, action)`. (3) The root reducer (usually built via `combineReducers`/`configureStore`) delegates to each slice reducer; each one either returns a new value for its slice or the same reference if the action doesn't concern it. (4) The store replaces its internal state reference with the newly assembled object and calls every registered `subscribe` listener. (5) `react-redux`'s internal subscription (set up per-component by `useSelector`) re-runs each component's selector against the new state; components whose selected value changed are scheduled for re-render by React; React re-renders those components (and their children, unless memoized) with the new props/selected values, producing the updated screen.

**Q: Can two different components dispatch two different actions that both update the same slice, and if so, what determines the final state?**
A: Yes — any number of components can dispatch actions targeting the same slice; there's no ownership restriction. The final state is simply the result of running the reducer over the two actions in the order they were actually dispatched (dispatch is synchronous per call, so there's no race condition from two dispatches interleaving mid-reducer). If component A dispatches `cart/itemAdded` and then component B dispatches `cart/itemRemoved`, the slice reducer runs once for each, in that order, and the final state reflects both updates applied sequentially.

**Q: What does `getState()` return immediately after the store is created, before any action has been explicitly dispatched by app code?**
A: The default state produced by running every reducer with `state = undefined` against Redux's internal bootstrap action. Since each reducer doesn't recognize that internal action type, it falls into `default: return state`, and because `state`'s parameter has a default value (`state = initialState`), that default is what actually gets returned. So `getState()` reflects each reducer's declared default, assembled by `combineReducers` into the full tree — not an empty object.

**Q: Is `replaceReducer` something you'd use often in a typical app?**
A: Rarely in a small-to-medium app — most apps set up their root reducer once at startup and never touch it again. It matters in two specific situations: code-splitting, where a lazily-loaded feature module registers its own slice reducer only once that feature's bundle has loaded (common in large apps using dynamic `import()` for route-based code splitting), and hot module replacement during development, where a dev-server plugin calls `replaceReducer` to swap in an updated reducer function without losing the app's current runtime state, so you don't have to manually re-navigate to reproduce whatever state you were debugging.
