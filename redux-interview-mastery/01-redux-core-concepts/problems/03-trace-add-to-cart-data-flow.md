# Problem: Trace and Diagram the Full "Add to Cart" Data Flow

## Task

Given the component/reducer code below, trace — step by step, in order — everything that happens from the moment a user clicks "Add to cart" to the moment the screen visually reflects the update. Produce both a written trace and an ASCII diagram. This tests whether you actually understand the pipeline end to end, not just each piece in isolation.

## Given code

```jsx
// cartSlice.js
import { createSlice } from '@reduxjs/toolkit';

const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    itemAdded(state, action) {
      state.items.push(action.payload);
    },
  },
});
export const { itemAdded } = cartSlice.actions;
export default cartSlice.reducer;

// ProductCard.jsx
function ProductCard({ product }) {
  const dispatch = useDispatch();
  return (
    <button onClick={() => dispatch(itemAdded(product))}>
      Add to cart
    </button>
  );
}

// CartBadge.jsx
function CartBadge() {
  const count = useSelector((state) => state.cart.items.length);
  return <span>{count}</span>;
}
```

## Solution — written trace

1. User clicks the button in `ProductCard`. React's synthetic event system invokes the `onClick` handler.
2. The handler calls `dispatch(itemAdded(product))`. `itemAdded(product)` is an action creator generated by `createSlice`; it returns a plain action object: `{ type: 'cart/itemAdded', payload: product }`.
3. `dispatch` (obtained via `useDispatch`, which reads the store instance off React Context provided by `<Provider store={store}>`) calls the *real* Redux store's `dispatch` with that action.
4. The store runs the action through any configured middleware chain (in a default `configureStore` setup: `redux-thunk`, the immutability/serializability dev checks, etc. — none of which intercept a plain synchronous action like this one, so it passes through unchanged).
5. The store invokes the root reducer with `(currentState, action)`. The root reducer (assembled by `configureStore` from the `cart` slice, and any others) delegates the `cart` key to `cartSlice.reducer`.
6. `cartSlice.reducer` runs the `itemAdded` case. `state.items.push(action.payload)` looks like a mutation, but because `createSlice` wraps reducers in Immer, this is recorded and used to produce a *new* immutable `cart` state object (`{ items: [...oldItems, product] }`) rather than mutating the original.
7. `combineReducers` (internally, via `configureStore`) sees that the `cart` slice's returned value differs by reference from before, so it assembles a new root state object: `{ cart: <new cart state>, ...other unchanged slices> }`.
8. The store commits this new root state object as its current state, then calls every `subscribe` listener. `react-redux` registered one such listener when `<Provider>` mounted (plus per-`useSelector` bookkeeping).
9. For every component using `useSelector`, `react-redux` re-runs that component's selector function against the new state and compares the result to the value from the previous render (reference equality by default).
   - `CartBadge`'s selector, `(state) => state.cart.items.length`, returns a new number (`1` vs previous `0`) — numbers compare by value, so this "changed," and `CartBadge` is scheduled to re-render.
   - `ProductCard` doesn't use `useSelector` at all here, so it's unaffected by this dispatch (aside from React's normal render cycle if its own props/state changed, which they didn't).
10. React re-renders `CartBadge` with the new count, produces the new virtual DOM for that subtree, diffs it against the previous render, and commits the minimal DOM mutation — the badge now visually shows `1`.

## Solution — diagram

```
[User clicks "Add to cart"]
            |
            v
  onClick -> dispatch(itemAdded(product))
            |
            v
  action = { type: 'cart/itemAdded', payload: product }
            |
            v
  store.dispatch(action)  -- middleware chain (thunk, dev checks) --> passes through
            |
            v
  rootReducer(state, action)
     |
     +--> cartSlice.reducer(state.cart, action)  [Immer-wrapped]
     |         returns new cart state: { items: [...items, product] }
     |
     +--> other slice reducers: no matching case, return same reference
            |
            v
  new root state committed to the store
            |
            v
  store notifies subscribers (react-redux's internal listener)
            |
            v
  useSelector re-runs selectors in every connected component
     |
     +--> CartBadge's selector result changed (0 -> 1) => re-render scheduled
     +--> ProductCard's selector (none used) => unaffected
            |
            v
  React re-renders CartBadge, reconciles virtual DOM, commits DOM patch
            |
            v
  [Screen shows updated cart badge count]
```

## Interview follow-ups this problem invites

- "At which exact step would a `console.log` inside the reducer run relative to React re-rendering?" — inside step 6, strictly before the store commits state or notifies any subscriber; reducer execution always fully completes before any component re-renders as a result of it.
- "If `ProductCard` also used `useSelector` to read `state.cart.items.length`, would it re-render too?" — yes, for the same reason `CartBadge` does; any component subscribed to a piece of state that changed re-renders, regardless of which component dispatched the action that changed it.
