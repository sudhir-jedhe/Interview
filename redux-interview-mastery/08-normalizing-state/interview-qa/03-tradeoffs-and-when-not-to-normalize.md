# Interview Q&A: Trade-offs and When Not to Normalize

**Q: Give a concrete example of state that should NOT be normalized.**
A: A `ui` slice like `{ theme: 'dark', sidebarOpen: false, activeModal: null }`. There are no repeated entities here, nothing is referenced from multiple places, and nothing benefits from ID-based lookup — normalizing it would just add two useless fields (`byId`, `allIds`) around scalar UI flags. A good heuristic: normalize collections of *entities with identity* that can be referenced from more than one place or updated item-by-item; don't normalize configuration/flag-shaped state just because normalization is the "advanced" pattern.

**Q: A teammate says "we should normalize everything, it's just better practice." How do you respond in a design review?**
A: Push back constructively: normalization trades write-side simplicity for read-side indirection, and that trade is only worth it when the write-side complexity (deep nested updates, duplicate entities) is actually a problem you have. For a small, flat list of five dropdown options, adding a `byId`/`allIds` wrapper is pure ceremony with no benefit — you'd be optimizing for a re-render or update-complexity problem that doesn't exist at that scale. The right framing is "normalize where entities are relational and mutated independently," not "normalize as a blanket rule."

**Q: How would you decide whether to hand-roll normalization or reach for `normalizr` or `createEntityAdapter`?**
A: If you're consuming a small, shallow API shape once (one level of nesting, one relationship), hand-rolling it inline is fine and avoids a dependency. Reach for `normalizr` when the API shape is deep, has multiple cross-referencing entity types, or the same schema is reused across several endpoints — writing that traversal by hand repeatedly is where bugs creep in (forgetting to dedupe, mismatched ID fields). Reach for `createEntityAdapter` specifically for the Redux-side storage and CRUD reducers/selectors of a normalized collection — the two tools solve different halves of the problem (normalizr: API response → flat entities map; createEntityAdapter: flat entities map → Redux slice with adapter methods) and are commonly used together.

**Q: What's the single biggest risk normalization introduces that a nested shape doesn't have?**
A: Referential integrity becomes your problem. In a nested shape, deleting a post automatically takes its embedded comments with it — there's nothing else to clean up because there was never a separate copy. In a normalized shape, comments live independently of posts, so deleting a post leaves orphaned comment entities unless you explicitly cascade the delete. This is a real cost, not a minor footnote, and any team adopting normalization should decide up front how relationship cleanup is handled (dispatched cascade actions, `extraReducers` cross-slice listeners, or a normalized-cache library like RTK Query that tracks and invalidates related data for you).
