# Interview Q&A: `createEntityAdapter` and Selectors

**Q: What exactly does `createEntityAdapter` generate for you?**
A: Two things. First, a set of pre-built, Immer-aware reducer functions for common CRUD operations on a normalized collection — `addOne`/`addMany`, `setAll`, `setOne`, `updateOne`/`updateMany`, `upsertOne`/`upsertMany`, `removeOne`/`removeMany`. Second, via `getSelectors()`, a set of memoized selectors — `selectAll`, `selectById`, `selectIds`, `selectTotal` — that read from the `entities`/`ids` shape without every consumer needing to know the storage layout. It also provides `getInitialState()` to produce the correctly-shaped empty state, optionally merged with your own extra fields.

**Q: What's the difference between `updateOne` and `upsertOne`, and when does the difference actually bite you?**
A: `updateOne` takes `{ id, changes }` and merges `changes` into an *existing* entity; if the ID isn't present, it's a silent no-op — it does not insert. `upsertOne` takes a full entity object and either inserts it (if the ID is new) or replaces/merges it (if the ID exists). It bites you when ingesting data you're not sure is new or a refresh — e.g., a WebSocket message that might be a brand-new chat message or a redelivered one after reconnect. Using `updateOne` there would silently drop genuinely new entities because they don't exist yet to be "updated."

**Q: How does a `sortComparer` interact with `updateOne`, and what's a subtle consequence?**
A: If you configure a `sortComparer`, the adapter re-sorts the `ids` array after every mutating operation, including `updateOne` — not just on insert. So patching a field that participates in the comparator (e.g., `priority`) can silently reorder the collection as a side effect of what looks like an unrelated field edit. If you need list order to reflect something like insertion order regardless of later field edits, don't include the mutable field in the comparator, or don't use a `sortComparer` at all and sort explicitly in a selector when you need to.

**Q: Does using `createEntityAdapter` automatically solve referential integrity, e.g., cleaning up comments when their parent post is deleted?**
A: No. Each adapter/slice only manages its own entity type — deleting a post via `postsAdapter.removeOne` has zero effect on the `comments` slice, even if some comments reference that post's ID. Cascading deletes (or reference cleanup) is something you have to implement explicitly, typically by dispatching an additional action (or handling the post-removal action in the comments slice via `extraReducers`) that removes the affected comments. This is a real trade-off of normalization worth naming unprompted in an interview: you get cheap updates, but you take on the responsibility a database's foreign-key constraints would otherwise handle for you.
