# Interview Q&A: Choosing the Right Tool

**Q: A hiring manager asks: "Would you introduce Redux into a brand-new project today?" How do you answer without sounding either dogmatic or wishy-washy?**
A: "It depends on specific, checkable characteristics of the app and team — not a blanket yes or no." Then name the actual criteria: team size and need for enforced conventions, whether the state is mostly server-cache data (which shouldn't be hand-rolled Redux regardless of the client-state answer), complexity of async orchestration, and whether time-travel/action-log debugging is valuable for this domain. Giving the criteria, not just a verdict, is what signals real judgment rather than a memorized opinion.

**Q: What's the most common Redux misuse you'd flag in a code review, related to this topic?**
A: Storing server-fetched data (a list of users, a product catalog, an order history) in a hand-rolled slice with `status`/`data`/`error` fields and a `createAsyncThunk`, instead of using RTK Query or React Query. This is server-cache management being reimplemented, slice by slice, without the caching, deduplication, invalidation, and refetch-on-focus behavior a dedicated query library provides for free — and it's extremely common because it's the "obvious" way to fetch data if you already know Redux, even when it's not the best tool for that specific job.

**Q: If a team is already fully invested in Redux, and a new alternative library seems marginally better on paper, would you recommend switching?**
A: Usually no, and this is a legitimate, non-lazy answer: migration cost for an established codebase with many connected components is real and ongoing (bugs introduced during migration, retraining engineers, temporary dual-maintenance of two patterns), and it needs to be weighed against the actual, measured pain the current approach causes — not a hypothetical "cleaner in theory" argument. The bar for migrating an established, working system should be a specific, recurring problem the current architecture can't reasonably solve, not "the new thing has less boilerplate."

**Q: How would you explain the relationship between "Redux vs Zustand" and "Redux vs RTK Query" — are these the same kind of question?**
A: No, and conflating them is a common mistake. "Redux vs Zustand/Jotai/Context" is a question about *client state* management — how do you hold and update state that's genuinely local to the app. "Redux vs RTK Query/React Query" is a question about *server-cache* management — how do you fetch, cache, and keep fresh data that originates from a server. A well-architected app answers both questions somewhat independently: it might use RTK Query for all server data and Zustand (not Redux) for the remaining client state, or Redux for both halves via `createSlice` + `createApi` in the same store — the point is recognizing these as two separate decisions with two separate sets of criteria, not one monolithic "which state library" choice.
