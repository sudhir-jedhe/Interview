# Interview Q&A: Mutation and Serializability

**Q: "Just mutate the state, Immer will handle it" — is this always true?**
A: No, and this is a genuinely important qualification. It's true only inside reducers wrapped by Immer, which is what `createSlice` and `createReducer` do automatically for you. A plain reducer function passed directly to `createStore` or used inside `combineReducers` without RTK has no Immer wrapping — mutating state there is a real, unguarded mutation that returns the same reference, breaking `useSelector`'s change detection and corrupting DevTools' state history. Knowing which context you're in is the actual skill being tested.

**Q: Why does mutating a deeply nested object corrupt Redux DevTools' time-travel, not just the current render?**
A: DevTools typically holds *references* to previous state snapshots for performance, rather than deep-cloning the entire tree on every action. If a reducer mutates a nested object in place instead of replacing it with a new object, every snapshot — including ones from before the mutating action — that happens to reference that same nested object now reflects the mutated value, because there was only ever one copy of it. Jumping back to "before" in DevTools shows data that's actually "after," because the underlying object was never actually duplicated.

**Q: Why does RTK warn about storing a `Date` object in state, when `Date` objects can be serialized to JSON just fine?**
A: Two separate reasons. First, DevTools/persistence layers serialize with `JSON.stringify`, and a `Date` round-trips through that as a string, not back into a `Date` instance — so naive persistence/rehydration silently changes its type unless you add custom (de)serialization logic. Second, and more subtly: two different `Date` instances representing the exact same instant are never `===` equal, and a naive `Object.is`/reference-equality check (the same kind `useSelector` and `createSelector` rely on) will treat every re-render's freshly-constructed `Date`, even one representing an unchanged timestamp, as "changed." Storing the timestamp as a plain number (`Date.now()`) avoids both problems.

**Q: Is disabling RTK's `serializableCheck` middleware ever a reasonable choice?**
A: It's reasonable as a narrow, targeted exception — ignoring a specific, deliberately-chosen path via the `ignoredPaths`/`ignoredActions` options, with a comment explaining why that particular value is intentionally non-serializable and why that's safe in context. Disabling the check globally to silence warnings without addressing their cause is not reasonable — it removes a safety net for the entire app, not just the one value that prompted the change, and non-serializable values elsewhere will now go undetected until they cause a harder-to-diagnose bug (like a DevTools crash) instead of a clear dev-mode warning.
