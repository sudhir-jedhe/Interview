# Interview Q&A: Derived Data and Action Design

**Q: What's the test for whether a piece of data belongs in state versus being computed in a selector?**
A: Ask: "can this value be computed purely from other values already in state?" If yes, it almost always shouldn't be stored — store the inputs once, and derive the output via a (memoized, if the computation isn't trivial) selector every time it's needed. The main legitimate exceptions are values that are prohibitively expensive to recompute even with memoization, or values that need to persist independently of their original inputs (a historical snapshot, an audit log entry) — and those should be deliberate, documented exceptions, not the default choice.

**Q: What's the actual failure mode of storing derived data, beyond "it's not best practice"?**
A: Update drift. Every reducer case that touches the source data also has to remember to correctly update the derived field, and "remember to update N places whenever the source changes" is exactly the kind of manual bookkeeping that silently breaks the moment a new reducer case is added by someone who doesn't realize the derived field needs maintaining too — with no error, no warning, just a wrong number rendered somewhere. A memoized selector makes this class of bug structurally impossible, because there's no second copy of the fact to forget to update.

**Q: When is it acceptable to dispatch multiple actions for what feels like "one user action"?**
A: When the underlying fields are genuinely independent and being observed briefly out of sync wouldn't be incorrect or confusing — e.g., two unrelated form fields updating as the user types in each, dispatched separately, is fine. The line to watch for is when the fields conceptually represent *one event* and any code observing them independently mid-sequence would see a state that's genuinely invalid or nonsensical (a "shipping set but payment not yet set" checkout, a "half-created" entity). That's the signal to consolidate into a single, well-designed action carrying all the related data.

**Q: How would you refactor a component that currently dispatches 4 separate actions for one form submission?**
A: Design one action type that carries the full payload for the logical event (`checkoutSubmitted({ shippingAddress, billingAddress, paymentMethod })`), write one reducer case that atomically applies all the fields in that single case, and replace the 4 `dispatch()` calls at the submission call site with 1. The resulting DevTools action log then shows one entry per real user event, matching the mental model of what actually happened, and no other part of the app can observe an intermediate, half-submitted state — because that state transition never exists as a separate, dispatchable step.
