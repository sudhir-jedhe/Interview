# Interview Q&A: Server-Cache Data and Selector Memoization

**Q: What's the quickest heuristic for spotting "this slice shouldn't be hand-rolled Redux" in a code review?**
A: Ask whether, after mentally deleting the `status`/`error`/`loading` fields and the `pending`/`fulfilled`/`rejected` reducer cases, what's left is just "data = whatever the server returned," with zero client-only logic mixed in. If so, that slice's entire job is caching a server response — which is exactly the problem RTK Query (or React Query) already solves, with request deduplication, cache invalidation, and refetch-on-focus included, none of which the hand-rolled version has unless someone writes it by hand, per endpoint, correctly, every time.

**Q: A hand-rolled fetch slice "works fine" in current testing — why push back on it anyway?**
A: Because the missing behaviors (dedup, invalidation, refetch-on-focus) tend to surface as intermittent, hard-to-reproduce bugs rather than obvious failures — "the list doesn't show the item I just created until I refresh the page" or "two components fired duplicate requests and one overwrote the other's in-flight update." These bugs are easy to miss in a quick manual test and expensive to debug in production once real usage patterns (multiple tabs, slow networks, concurrent mutations) expose them. Flagging it in review is cheaper than debugging the eventual incident.

**Q: Why does an unmemoized `useSelector` callback cause a re-render even when the underlying data hasn't changed?**
A: Because `useSelector` decides whether to re-render by comparing the selector's *previous return value* to its *new return value* using `===` (reference equality) by default. If the selector's function body does `.filter()`, `.map()`, `.sort()`, or builds an object/array literal inline, it allocates a brand-new reference on every single call, regardless of whether the underlying source data actually changed — so the comparison always reads "changed," even when it isn't.

**Q: How does `createSelector` (from `reselect`, re-exported by RTK) actually prevent the unnecessary re-render?**
A: It memoizes based on its declared input selectors, not on the whole state tree. On each call, it first cheaply re-runs the input selectors and compares each one's result to the previous call's result by reference. Only if at least one input selector's result actually changed does it re-run the (potentially expensive) result function and produce a new output reference; otherwise it returns the exact same cached reference from last time. Because the output reference is stable across calls where the inputs didn't change, `useSelector`'s `===` check correctly reports "no change," and the component skips the re-render — turning an implicit, easy-to-miss allocation problem into an explicit, cache-backed one.
