# Interview Q&A: Spotting Anti-Patterns in Code Review

**Q: You're reviewing a PR with a new Redux slice. What are the first three things you check?**
A: (1) Is any `reducers` case reaching into nested data and mutating it directly outside of `createSlice`'s Immer wrapping — and if it *is* inside `createSlice`, is that mutation-looking code actually correct because Immer handles it? (2) Does the slice store any field whose value could instead be computed from other fields already in state — a `count`, `total`, `isValid`, or similar name is a strong signal to look closer. (3) Is this slice's entire purpose "cache a server response" with no client-only logic — if so, question whether it should be an RTK Query endpoint instead.

**Q: How would you explain to a junior engineer why their reducer "works" in manual testing but is still wrong?**
A: Manual testing usually only checks "does the UI show the right thing right now," which a mutating reducer can pass, because the mutated object *does* contain the right data — the bug isn't in the data, it's in whether other code (React's re-render detection, DevTools' history, a memoized selector elsewhere) can correctly detect that a change happened at all. Demonstrate concretely: add a `console.log(previousState === nextState)` around the dispatch, or check DevTools' time-travel on a nested field — either will reveal the reference-equality problem that "does the screen look right" testing can't catch.

**Q: What's a fast way to demonstrate the derived-data anti-pattern's risk to a skeptical teammate who thinks "it's just one extra field, it's fine"?**
A: Show them the exact bug from `output-based/03-derived-total-drifts-out-of-sync.md`: write a reducer with a stored `totalPrice`, correctly update it in `itemAdded`, and *deliberately* forget to update it in `itemRemoved`. Run it, and show the resulting wrong total with no error, no warning — just a silently incorrect number. The visceral point is that this bug requires zero malice or carelessness beyond "one reducer case among several, written by someone who didn't think to check every other reducer case that touches the same derived field" — which is exactly how real teams, working on real codebases with many contributors over time, actually introduce this bug.

**Q: If you inherited a codebase with all seven anti-patterns from this topic present somewhere, how would you prioritize fixing them?**
A: Roughly by blast radius and detectability. Fix non-serializable state and direct mutation first — both can silently corrupt debugging tools and are usually quick, mechanical fixes once located (RTK's `serializableCheck` warnings often locate the former for you automatically). Then server-cache-in-hand-rolled-Redux and unmemoized selectors, since both tend to cause the most user-visible symptoms (stale data, laggy UI) and their fixes (RTK Query migration, wrapping in `createSelector`) are well-established, incremental, and don't require touching unrelated code. Derived-data and overly-nested-state fixes usually require more careful, slice-specific refactoring, so schedule those deliberately rather than rushing them. Fragmented-action-dispatch is typically the lowest urgency, since it's more of a design-quality issue than a correctness bug unless you can demonstrate a concrete intermediate-state problem like in `output-based/04`.
